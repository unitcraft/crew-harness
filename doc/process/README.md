# Как идёт работа над CrewHarness

Основа — методика [unitcraft/ai-dev-methodology](https://github.com/unitcraft/ai-dev-methodology): алгоритм исполнителя
(`task-algorithm.md`), цикл сессий (`task-sessions.md`), раннер (`task-runner.md`). Методику не копируем — ссылаемся;
здесь — только как она применена в этом проекте и где мы от неё отступаем
([ADR-0001](../decisions/0001-work-by-methodology.md)).

## Роли

| Роль методики | Кто у нас |
|---|---|
| Заказчик, владелец | владелец репозитория: ставит задачи, отвечает на вопросы, утверждает spec и plan, принимает результат |
| Оркестратор (раннер) | пока — агент-оркестратор, который ведёт цикл вручную; потом — сам CrewHarness (задача 001) |
| Исполнитель, проверяющий | сессии агента; каждая проверка — новая сессия, не видевшая рассуждений автора |

Утверждение («Статус: утверждено, дата, кто»), ответы на вопросы, решения по списку «требует утверждения», пуш и
переключение живой системы делает только владелец или по его прямому слову.

## Задача

Папка `doc/tasks/NNN-<slug>/` ([описание](../tasks/README.md)). Номера задач — свои, с 001; старые планы плагина
(001–015) — в [архиве](../plans/README.md). Код задачи — в отдельном рабочем дереве на ветке задачи; папка задачи
коммитится в `main` на воротах: утверждение spec, утверждение plan, сдача.

## Цикл и ворота

Как в `task-sessions.md`: С1 разбор → С2 проверка (до двух чистых заходов подряд, чистый — с тремя пробами, потолок
четыре захода) → ответы владельца → утверждение spec → С3 план → С4 проверка → решения владельца → утверждение plan →
С5 реализация → С6 проверка → решения по FAIL / NOT VERIFIED → С7 сдача → С8 проверка → коммит и пуш.

Ворота, которые здесь не останавливают работу (разрешено методикой): В2 (профиль запуска равен умолчанию), В3
(заход засчитывается как записан; владелец читает находки в `log.md` и вправе вернуть). Остальные — останавливают.

## Отступления от методики

| Что | Почему | Решение |
|---|---|---|
| Раннер вручную: оркестратор запускает сессии агентами и ведёт `log.md`, `progress.log`; `state.json` нет | раннера ещё нет — его и строим | до готовности сервиса (задача 001) |
| Раздел раннера «Сборка запроса и кеш» не исполняется: агенты на подписке (CLI) не дают управлять слоями кеша и усилием на запрос | подписка, а не API ([ADR-0004](../decisions/0004-agent-drivers-on-subscriptions.md)) | вопрос В-02 задачи 001 |
| Тяжёлые прогоны в сессиях — только по одному тесту или через очередь машины | общая нагруженная машина ([AGENTS.md](../../AGENTS.md), п. 10–11) | — |
| Коммит и пуш по завершении задачи — по правилам [AGENTS.md](../../AGENTS.md) (рабочее дерево, `--ff-only`, `-s`) | живая рабочая копия `main` | — |

## Решения

Реестр — [doc/decisions/](../decisions/README.md), формат MADR. Обязательно раньше кода при смене технологии,
контракта, формата данных на диске, топологии и при отступлении от правил.
