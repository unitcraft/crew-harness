## Роли (методика оставляет их назвать проекту)

| Роль методики | У нас |
|---|---|
| Заказчик, владелец, принимающий | владелец репозитория — один человек во всех трёх ролях |
| Оркестратор / раннер | агент-оркестратор ведёт цикл вручную, пока раннером не станет сам CrewHarness (задача 001) |
| Исполнитель, проверяющий | сессии агента; каждая проверка — новая сессия |

Без владельца не делается: утверждение spec и plan, ответы на вопросы, решения из «требует утверждения», решения по
FAIL / NOT VERIFIED, перезапуск и переключение живой системы.

## Отличия

| Методика | У нас | Почему |
|---|---|---|
| Папка задачи — рядом с папкой кода, вне репозитория | `doc/tasks/NNN-<slug>/` в репозитории; коммитится в `main` на воротах (утверждение spec, plan, сдача); код задачи — в отдельном рабочем дереве на ветке задачи, поэтому diff реализации папку задачи не видит | владелец, 2026-10-07: «как в nova docs/plans»; задачи видны в репозитории |
| Подготовка: копия `task-algorithm.md` в папке задачи, промпты называют его по имени | копий методики в задаче нет: версия методики закрепляется коммитом при старте задачи — строка `Методика: unitcraft/ai-dev-methodology @ <коммит>` в `log.md`; сессия получает в промпте ссылку на `task-algorithm.md` этого коммита и читает его оттуда | владелец, 2026-10-07: копия в каждой задаче — вторая правда и расходящиеся версии; закреплённый коммит сохраняет главное — задача проверяется по той версии, с которой начата |
| Слияние только squash, обновление ветки — ребейз | слияние в `main` — `git merge --ff-only` из рабочего дерева; подпись коммита — `-s` (Signed-off-by) | один исполнитель, линейная история; живая рабочая копия `main` ([AGENTS.md](../../AGENTS.md), п. 4–6) |
| Раннер — программа, `state.json` | цикл ведёт оркестратор вручную: сессии — отдельными агентами, `log.md` и `progress.log` ведутся, `state.json` нет | раннера ещё нет — его строим (задача 001) |
| Раннер собирает запрос сам: слои кеша, поддержание, усилие на фазу | не исполняется: агенты работают через CLI на подписке и этими рычагами не управляют | [ADR-0004](decisions/ADR-0004-agent-drivers-on-subscriptions.md); как быть в продукте — вопрос В-02 задачи 001 |
| Ворота В2 и В3 можно перевести в «показать и продолжить» | переведены: профиль по умолчанию не спрашиваем; заход засчитывается как записан, владелец читает находки в `log.md` и вправе вернуть | меньше остановок владельца |
| Проверки перепрогоняют доказательства | тяжёлые прогоны — по одному тесту или через очередь машины, весь набор — только когда машина свободна | общая нагруженная машина ([AGENTS.md](../../AGENTS.md), п. 9–10) |

## Дополнения

- **Каждый вопрос владельцу — с рекомендацией** (владелец, 2026-10-07): кроме полей вопроса по методике (шаг 7:
  адресат, варианты, срок, умолчание) — строка «Рекомендация: <вариант> — потому что <довод>». Без исключений, в том
  числе для вопросов про деньги и подписки: рекомендация не решение, решает владелец. Вопрос без рекомендации —
  существенная находка проверки.
- **Номера задач** — с 001. План задачи — `plan.md` в её папке, как в методике; в Канон он не переносится
  ([ADR-0007](decisions/ADR-0007-plan-in-task-epics.md)).
- **Эпик** — задача, которую не сделать одним циклом методики (владелец, 2026-10-07; в методике понятия нет):
  - у эпика обычная `spec.md`; его `plan.md` вместо шагов кода перечисляет дочерние задачи — порядок, зависимости и
    какие REQ и AC спецификации эпика закрывает каждая; каждое REQ и AC эпика закрыто хотя бы одной дочерней задачей;
  - эпик узнаётся по второй строке `plan.md`: `Тип: эпик`; имя папки не меняется;
  - дочерняя задача — обычная задача методики со своими `spec.md` и `plan.md`; в `task/message.md` — строка
    `Эпик: <ссылка на папку эпика>` и REQ эпика, которые она закрывает;
  - дочерняя задача выделяется, если ей нужна своя спецификация, своя приёмка или её можно выпустить отдельно; иначе
    это срез внутри плана обычной задачи (С5);
  - эпик принят, когда приняты все дочерние задачи и сверено покрытие его REQ и AC.
- **Трекер** не ведётся: статус задачи — в её папке. Если у задачи появится задача в трекере, ссылка на неё пишется в
  `task/message.md`; эпик соответствует эпику или родительской задаче трекера, дочерние задачи — подзадачам.
- **Публичность** — всё в репозитории, включая папки задач и их материалы, без приватных данных
  ([ADR-0006](decisions/ADR-0006-public-repository.md)).
- **Решения** — реестр [doc/decisions/](decisions/README.md) по правилам методики.
- **Отличие записывается сюда** тем же коммитом, что его вводит; отступление от правила методики — ещё и решением в
  `doc/canon/decisions/`.
