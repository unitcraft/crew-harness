## Роли (методика оставляет их назвать проекту)

| Роль методики | У нас |
|---|---|
| Заказчик, владелец, принимающий | владелец репозитория — один человек во всех трёх ролях |
| Оркестратор / раннер | агент-оркестратор ведёт цикл вручную, пока раннером не станет сам CrewHarness (задача 001) |
| Исполнитель, проверяющий | сессии агента; каждая проверка — новая сессия |

Закрытый список решений человека — по методике (раздел 4); исключение проекта — вопросы типов `requirements`, `plan`,
`implementation` вне ворот при настройке `answer_mode` (раздел «Режимы ответа на вопросы» ниже, [ADR-0010](decisions/ADR-0010-question-answering-modes.md)).

## Отличия

| Методика | У нас | Почему |
|---|---|---|
| Папка задачи — рядом с папкой кода, вне репозитория | `doc/tasks/NNN-<slug>/` в репозитории; коммитится в `main` на воротах (утверждение spec, plan, сдача); код задачи — в отдельном рабочем дереве на ветке задачи, поэтому diff реализации папку задачи не видит | владелец, 2026-10-07: «как в nova docs/plans»; задачи видны в репозитории |
| Подготовка: копия `task-algorithm.md` в папке задачи, промпты называют его по имени | копий методики в задаче нет: версия методики закрепляется коммитом при старте задачи — строка `Методика: unitcraft/ai-dev-methodology @ <коммит>` в `log.md`; сессия получает в промпте ссылку на `task-algorithm.md` этого коммита и читает его оттуда | владелец, 2026-10-07: копия в каждой задаче — вторая правда и расходящиеся версии; закреплённый коммит сохраняет главное — задача проверяется по той версии, с которой начата |
| Слияние только squash, обновление ветки — ребейз | слияние в `main` — `git merge --ff-only` из рабочего дерева; подпись коммита — `-s` (Signed-off-by) | один исполнитель, линейная история; живая рабочая копия `main` ([AGENTS.md](../../AGENTS.md), п. 4–6) |
| Раннер — программа, `state.json` | цикл ведёт оркестратор вручную: сессии — отдельными агентами, `log.md` и `progress.log` ведутся, `state.json` нет | раннера ещё нет — его строим (задача 001) |
| Раннер собирает запрос сам: слои кеша, поддержание, усилие на фазу | не исполняется: агенты работают через CLI на подписке и этими рычагами не управляют | [ADR-0004](decisions/ADR-0004-agent-drivers-on-subscriptions.md); как быть в продукте — вопрос В-02 задачи 001 |
| Ворота В2 и В3 можно перевести в «показать и продолжить» | переведены: профиль по умолчанию не спрашиваем; заход засчитывается как записан, владелец читает находки в `log.md` и вправе вернуть | меньше остановок владельца |
| Проверки перепрогоняют доказательства | тяжёлые прогоны — по одному тесту или через очередь машины, весь набор — только когда машина свободна | общая нагруженная машина ([AGENTS.md](../../AGENTS.md), п. 9–10) |

## Дополнения

- **Слова вместо кодов** — по методике ([`methodology.md`](https://github.com/unitcraft/ai-dev-methodology/blob/main/methodology.md), раздел 18, «Форма ответа владельцу»); механизм в плагине: тексты панели,
  писем и ответов инструментов строит `taskRef`, его проверяют тесты; про ответы агента механизма нет — судится приёмкой (владелец и Сессия С6).
- **Журналы сессии** (владелец, 2026-10-09): `progress.log` — ход (методика, «Строки `progress.log`»; время ставит `progress_line` плагина); `profile.log` —
  подсказка профиля по методике, формат без изменений, даты нет; `usage.log` — учёт сессии (время, модель, ступень, вариант, токены, стоимость, лимиты,
  вызовы инструментов, запуски тестов, итог, хеш последнего коммита): одна строка JSON на сессию с версией формата `v`, `at` и `started` — ISO 8601
  с местным поясом; пишет `usage_line` плагина (после задачи 014; до неё не ведётся).
- **Дата в каждой записи журналов** (владелец, 2026-10-09): новые записи несут дату и время местные для машины; прежние остаются допустимыми.
  `log.md`: `ГГГГ-ММ-ДД ЧЧ:ММ <вид>: <текст>`, вид — решение владельца, заседание, ворота, документ, пуск, слияние, находка; переходный срок: страж
  ([`check-task-docs.py`](../../scripts/guards/check-task-docs.py), правило `log-line`) проверяет только добавленные строки с датой не раньше 2026-10-10,
  в хуке `pre-commit`.
- **Задачи** — `doc/tasks/NNN-<slug>/`, номера с 001; статус — в папке задачи, трекер и список задач не ведутся (таблиц статусов и перечней задач в `.md`
  нет). План — `plan.md` в папке задачи, в Канон не переносится ([ADR-0007](decisions/ADR-0007-plan-in-task-epics.md)).
- **Эпик** (владелец, 2026-10-07): правила эпика — в методике ([`task-sessions.md`](https://github.com/unitcraft/ai-dev-methodology/blob/main/task-sessions.md), «Большая работа: эпик»).
  Здесь — проект: единственный эпик — [001-crew-service](../tasks/001-crew-service/); его разбиение на дочерние задачи записано в журнале
  эпика; имя папки эпика не меняется.
- **Публичность** — всё в репозитории, включая папки задач и их материалы, без приватных данных
  ([ADR-0006](decisions/ADR-0006-public-repository.md)).
- **Решения** — реестр [decisions/](decisions/README.md); отличие от методики записывается сюда тем же коммитом, что его вводит, и решением в
  `doc/canon/decisions/`.
- **Журнал хода `progress.log`** (владелец, 2026-10-08: «уже долго ничего нет, это плохо, надо чтобы процесс показывался»): формат и правила записи — в
  методике ([`task-runner.md`](https://github.com/unitcraft/ai-dev-methodology/blob/main/task-runner.md), «Строки `progress.log`»); панель окна читает журнал из всех рабочих деревьев репозитория. Проект добавляет:
  - дата в каждой новой строке (`[ГГГГ-ММ-ДД ЧЧ:ММ]`); прежние `[ЧЧ:ММ]` допустимы (владелец, 2026-10-09);
  - время берётся инструментом `progress_line` плагина в окнах OpenCode (команды часов там отклоняются), иначе `date "+%Y-%m-%d %H:%M"`;
  - строку `запуск` оркестратор пишет в журнал той копии, где сессия пишет свои строки (С5, С5д, С5п, С6, КОММИТ, ПУШ — в дерево задачи; если дерева ещё
    нет, запуск не пишется);
  - панель берёт для каждой сессии копию, где у неё больше строк (при равенстве — основная); «давно нет вестей» — при молчании неоконченной сессии дольше
    10 минут (константа панели); законченная показывается 15 минут, молчащая пропадает через 24 часа;
  - формат проверяет страж [`check-task-docs.py`](../../scripts/guards/check-task-docs.py): предел подписи — у добавленных строк в `pre-commit`, не в CI;
    страж проверяет форму, а не честность строки, «пишется по ходу» судится приёмкой (владелец и Сессия С6).
## Режимы ответа на вопросы

Настройка проекта `answer_mode` (и предел `answer_max`) в `.opencode/crew-harness.json` отдаёт часть вопросов сессий их
собственной рекомендации; ставит её только человек (правка файла и коммит). Решение — [ADR-0010](decisions/ADR-0010-question-answering-modes.md);
как это делает плагин — раздел «Answering session questions» в `opencode-plugin/README.md`. Пока цикл ведёт оркестратор вручную,
правила ниже читают он и сессии; панели и журнала плагина у ручного цикла нет.

**Типы вопросов и ворота методики.**

- ворота В4 (ответы на вопросы разбора) — тип `requirements`;
- ворота В6 (решения из «требует утверждения») — тип `plan`;
- ворота В7 (вопрос реализации) — по уровню ответа: реализация — `implementation`, план — `plan`, требования — `requirements`, неясно — владельцу;
- ворота, которых режим не закрывает, — тип `gate`: всегда владельцу при любых ключах.

**Форма вопроса.** Блок «В-NN …?» со строками `Тип: requirements|plan|implementation|gate`, `Рекомендация: <вариант> — потому что <довод>`
и `Автоответ: допустим`, знак «?» в конце строки с вопросом. `Рекомендация:` пишется одним абзацем без пустых строк (пустая строка
обрывает значение), вопрос заканчивают знаком «?» в конце строки, поля — отдельными строками ниже. Нет типа, рекомендации или строки `Автоответ: допустим`, тип `gate` или
любое сомнение — вопрос идёт владельцу.

**Запись в «Ответы».** Источник ответа по настройке — строкой: `Источник: рекомендация Сессии С1, режим recommendations, настройка проекта
(answer_mode, коммит <хеш>, <дата>), не слово владельца`. Общие правила (слово владельца старше, потолок заходов не сбрасывается) — в методике.
В `log.md` задачи: `ответ по настройке: <вопрос>, режим <режим>, потолок не сброшен, заход N`.

## Проект поверх методики: параметры

Правила, общие для любого проекта, — в методике ([`methodology.md`](https://github.com/unitcraft/ai-dev-methodology/blob/main/methodology.md), [`task-sessions.md`](https://github.com/unitcraft/ai-dev-methodology/blob/main/task-sessions.md),
[`task-runner.md`](https://github.com/unitcraft/ai-dev-methodology/blob/main/task-runner.md), [`task-algorithm.md`](https://github.com/unitcraft/ai-dev-methodology/blob/main/task-algorithm.md)); оригинал правится в его репозитории, здесь —
только то, что задаёт проект (владелец, 2026-10-10: «наша задача — уменьшить нашу часть канона … в каноне не нужно пересказывать
оригинальную методологию»).

- **Размер задачи** (методика: `task-sessions.md`, «Правила»): число записей `REQ` в `spec.md` — S до 10, M до 25, L до 50; больше 50 —
  на воротах В4 предложение разбить, решает владелец. Предел размера документов — S 30 КБ, M 80 КБ, L 150 КБ, только предупреждение и
  только для файлов, изменённых после 2026-10-10; следование — `spec-trace.md`. Пороги условные: после 10–20 задач с учётом
  (`usage.log`) проверяется, связан ли счёт `REQ` с затратами и возвратами; границы меняются только решением владельца. Страж —
  [задача 017](../tasks/017-doc-guard/); до неё судится приёмкой.
- **Риск** называет владелец при оценке перед Сессией С1 и на воротах В2 перед Сессией С5: безопасность, деньги, данные, внешние контракты.
- **Этапы и модель** (методика: `task-runner.md`, «Этапы и модель»): набор моделей — ключ `profile_sets` в `.opencode/crew-harness.json`
  (задачи 003, 015, 016): этапы `develop`, `develop_accept` (прежнее `accept` — псевдоним), `plan`, `plan_accept` задаются явно, `spec`,
  `spec_accept`, `delivery`, `delivery_accept` наследуют (сдача — на ступень ниже); ступени модели `heavy`, `medium`, `light` (в методике —
  класс A, B, C), `task` — по весу задачи; `tier_min` и `tier_max` срезают любую ступень. Правило «проверяющий на другой семье» в
  плагине — заметка в `/crew-sets show`: этап без клетки по-прежнему идёт по `spawn_models` (требование задачи 003).
- **Помощники** (методика: `methodology.md`, раздел 18): выключены. Первый кандидат классификатора — Jev (платный по API; экономит подписку,
  только когда заменяет вызов модели подписки; ключ сервис не хранит, ADR-0004).
- **Слияние** (методика: `methodology.md`, раздел 5, «Очередь слияния»): предпроверка без замка — [ADR-0009](decisions/ADR-0009-merge-precheck-without-lock.md).
- **Хранение** (файлы или база; где и когда данные попадают в базу, как синхронизируются) — вопрос продукта, эпик 001, а не методики.
