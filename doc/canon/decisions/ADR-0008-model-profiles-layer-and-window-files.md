# ADR-0008. Профили моделей: окно — файлом в рабочем дереве задачи, локальные правки — слоем в ящике плагина

## Контекст

Задача [003](../../tasks/003-model-profiles/): владелец переключает командами окна, на каких моделях идут разработка,
приёмка, планирование и приёмка плана, и вместе с моделью меняется окно контекста. Окно в OpenCode — не свойство этапа и
не сессии, а свойство модели в папке: каталог моделей отвечает на запрос по каталогу сессии и собирается из файлов
настроек от корня диска вниз; настройки конфига накладываются после плагинов, поэтому значение, поставленное плагином
в самом OpenCode, проигрывает файлу (проба задачи 003). Провайдер Claude Code читает те же файлы на каждый ход.
Значит окно можно сменить без перезапуска, только записав файл настроек в нужную папку. Владелец, 2026-10-08: файл окон
в корень проекта не писать, только в рабочее дерево задачи; сессии приёмки идут в основной папке и окон профиля не
получают, их окно — общие настройки владельца.

Отдельный вопрос — где живут правки, сделанные командами окна: «включить набор» и «поправить окно» должны
действовать сразу, а закоммиченный файл настроек проекта плагин читает только из ветки по умолчанию, и коммитит его
человек. Хранить правки негде, кроме ящика плагина. Новая запись плагина в рабочие деревья и новый вид состояния в
ящике — это то, что правило о публичном репозитории и граница «что плагин пишет» велят записывать решением.

## Варианты

Окно:

1. **Менять окно в самом OpenCode (`ctx.model.transform`).** + нет файлов. − конфиг накладывается после плагинов и
   побеждает (замер: плагин поставил 52500, каталог остался 66000); провайдер Claude Code читает файлы, а не каталог.
2. **Файл `.opencode/opencode.json` в корне проекта.** + один файл на проект. − корень может не быть репозиторием
   (нет общего каталога git для исключения), накрывает вложенный проект, рядом лежит рукописный файл владельца, который
   сильнее файла плагина на том же уровне; рабочие деревья лежат рядом с репозиторием и корня не видят.
3. **Файл `.opencode/opencode.json` с пометкой плагина в рабочем дереве каждой задачи.** + цепочка настроек идёт от
   корня диска к папке сессии, файл доходит ровно до сессии исполнителя; плагин сам создаёт эту папку и git для
   исключения есть; рукописное не затрагивается. − окна приёмки и основных папок профиль не меняет (там сессии идут
   в основной папке); файл надо вести по жизни задачи.

Локальные правки:

1. **Целая копия файла настроек в ящике.** + просто читать. − не отличает «моё» от «пришло коммитом»: после коммита
   файла копия молча спорит с ним.
2. **Слой записей поверх закоммиченного файла, у каждой записи — значение файла, на которое она легла.** + видно, что
   правил человек, что изменилось в файле с тех пор; `save` переносит свои записи и не затирает чужие. − больше кода
   (наложение, сверка, снятие).
3. **Правка рабочей копии файла проекта сразу.** + нет слоя. − не действует до коммита, а смена набора должна
   действовать сразу; агент и человек правят один файл вперемешку.

## Решение

Окно — вариант 3, правки — вариант 2.

- **Файл окон** — `.opencode/opencode.json` в рабочем дереве задачи (только там; корень проекта и основные папки не
  трогаются). В файле — только `limit` моделей включённого набора и ключ-пометка `_crew_harness`; файл без пометки
  плагин не перезаписывает и не удаляет. Строка `/.opencode/opencode.json` с комментарием добавляется в
  `info/exclude` общего каталога git. Список записанных файлов — реестр в ящике по проекту. Файл снимается, когда
  набора нет, когда задача принята или отменена, когда папка исчезла.
- **Слой и снимок** — в ящике плагина, папка `profiles/`, по проекту: `<проект>.layer.json` (записи слоя),
  `<проект>.snapshot.json` (последнее допустимое состояние трёх ключей и имени набора), `<проект>.windows.json`
  (реестр файлов окон). Закоммиченный файл проекта плагин меняет только командой `save` владельца и вызовом
  `crew_config set` интегратора, и только тремя ключами.
- **Три новых ключа настроек проекта:** `model_profiles` (справочник «семья → ступень → модель и окно»),
  `profile_sets` (наборы «этап → семья и ступень») и `profile_set` (имя набора по умолчанию; ставит человек).
  Формат — обычный JSON, читается без кода плагина.
- **Перечень того, что плагин пишет** (DNC-03 задачи): файл окон с пометкой в рабочем дереве задачи; строка в
  `info/exclude`; три ключа в рабочей копии `.opencode/crew-harness.json`; свои файлы в ящике. Больше ничего.

## Последствия

- \+ Смена набора и окна действует за секунды, без перезапуска сервиса и без коммита; рукописные настройки не
  переписываются.
- \+ Правки владельца отличимы от пришедшего коммитом; недопустимые данные не останавливают работающие вкладки
  (снимок).
- − Окно профиля действует только на сессии в рабочих деревьях задач; приёмка идёт в основной папке и берёт окно из
  общих настроек владельца — об этом говорят `use`, `check` и README.
- − Плагин читает цепочку настроек OpenCode сам (свой разбор), потому что общего кода с провайдером нет;
  при смене порядка чтения в новой версии OpenCode сообщения об окнах могут разойтись с действительностью — `check`
  печатает версию, проба задачи сверяет цепочку с каталогом моделей сервера.
- − Исключение через `info/exclude` общего каталога git затрагивает все рабочие деревья репозитория (файл с таким
  именем в них скрыт от git).
- − Два процесса, пишущих слой одновременно, дают «побеждает последняя запись»; команды редки, блокировок нет.

## Границы

Касается плагина `opencode-plugin/`. Сервис на Go, драйверы, пульт, код OpenCode и провайдера Claude Code не
затрагиваются. Пороги сжатия (`compaction.reserved`, `keep`, `auto`) не меняются, явный порог провайдера не
переписывается и не отменяется.

Когда пересмотреть: OpenCode начнёт принимать окно модели от плагина поверх конфига, либо сессии приёмки начнут идти
в рабочем дереве.
