# Спецификация ACP-клиента (черновик)

> Исследовательский материал, не Канон и не утверждённая спецификация задачи. Относится к будущему собственному
> бинарнику, запускающему CLI-агенты, а не к плагину CrewHarness. Получен от оркестратора 2026-10-12 по слову
> владельца: «передай файл сессии CrewHarness, пусть к себе проект заберет (подумает куда положить)».
> Переданный текст ниже сохранён без содержательных изменений; пример пути MCP-сервера приведён к `C:/work/...`.
> Утверждения о протоколе, командах запуска и условиях
> подписок при сохранении не перепроверялись; перед реализацией нужна проверка актуальных первоисточников.

Дата: 2026-10-12. Источник: страницы протокола на https://agentclientprotocol.com (список в конце) и официальный список
агентов. Всё, что взято не из спецификации, помечено «из памяти, проверить».

Цель: свой бинарник запускает готовые CLI-агенты разных семей моделей (Claude, Codex, Gemini, Kimi, OpenCode и др.) одним
клиентским кодом. Стандартные инструменты (чтение, правка, команды) реализует **сам агент**; свои инструменты подключаются
MCP-серверами.

## 1. Транспорт

- Агент запускается как **дочерний процесс** клиента. Клиент пишет в его stdin, читает его stdout.
- Одно JSON-RPC-сообщение (запрос, ответ или уведомление) на строку, без переводов строк внутри, UTF-8.
- В stdin/stdout — только сообщения протокола. Логи агента идут в **stderr**: сохранять в файл сессии.
- Завершение: закрыть stdin, затем убить процесс, если не вышел за разумный срок.
- Streamable HTTP в спецификации — черновик, не использовать. Свои транспорты допустимы, если сохранён формат JSON-RPC.

## 2. Жизненный цикл

```
запуск процесса
  → initialize                       (версия протокола, возможности)
  → authenticate                     (только если агент вернул authMethods и без входа не работает)
  → session/new | session/load | session/resume
  → [session/set_config_option]      (модель, режим, уровень рассуждений — по списку агента)
  → цикл:  session/prompt  ⇄  session/update … (+ входящие запросы агента)  →  stopReason
  → session/close (если поддержано)  → закрыть процесс
```

Версия протокола — целое число (сейчас `1`), растёт только при несовместимых изменениях. Если агент вернул версию, которой
клиент не знает, — закрыть соединение и сообщить пользователю.

## 3. Исходящие вызовы клиента

| Метод | Параметры | Результат |
|---|---|---|
| `initialize` | `protocolVersion`, `clientCapabilities` (`fs`, `terminal`), `clientInfo` (`name`, `title`, `version`) | `protocolVersion`, `agentCapabilities`, `agentInfo`, `authMethods` |
| `session/new` | `cwd` — абсолютный путь; `mcpServers` | `sessionId` (+ `configOptions`, режимы, если есть) |
| `session/prompt` | `sessionId`, `prompt` — массив блоков (текст, ссылки на ресурсы; картинки/аудио/встроенный контекст — только если агент объявил `promptCapabilities`) | `stopReason` после окончания хода |
| `session/cancel` | `sessionId` (уведомление) | — |
| `session/set_config_option` | `sessionId`, `configId`, `value` | полный список опций с текущими значениями |
| `session/load` | `sessionId`, `cwd`, `mcpServers` | пустой результат после воспроизведения истории потоком `session/update` |
| `session/resume` | то же | пустой результат, история не воспроизводится |
| `session/close` | `sessionId` | освобождает ресурсы |

Условия: `session/load` — только при `agentCapabilities.loadSession = true`; `resume` и `close` — только при
`agentCapabilities.sessionCapabilities.resume` / `.close`. Всё, чего агент не объявил, считается неподдерживаемым.

### Пример `initialize` и `session/new`

```json
{"jsonrpc":"2.0","id":0,"method":"initialize","params":{
  "protocolVersion":1,
  "clientCapabilities":{},
  "clientInfo":{"name":"my-client","title":"My Client","version":"0.1.0"}}}

{"jsonrpc":"2.0","id":1,"method":"session/new","params":{
  "cwd":"C:/work/project",
  "mcpServers":[{"name":"mytools","command":"C:/work/tools/my-mcp.exe","args":["--stdio"],"env":[]}]}}
```

### MCP-серверы в `session/new`

- **stdio** — обязателен у любого агента: `name`, `command`, `args`, `env` (список `{name, value}`).
- **http** — только при `mcpCapabilities.http`: `type:"http"`, `name`, `url`, `headers`.
- **sse** — устарел, не использовать.
- Контекст сессии (например номер задачи) передавать серверу через `env`.

## 4. Входящие запросы агента (клиент обязан ответить)

### 4.1. Разрешения: `session/request_permission`

Параметры: `sessionId`, `toolCall` (внутри `toolCallId`), `options` — список `{optionId, name, kind}`, где `kind` один из
`allow_once`, `allow_always`, `reject_once`, `reject_always`. Ответ:

```json
{"outcome":{"outcome":"selected","optionId":"opt-allow"}}
{"outcome":{"outcome":"cancelled"}}
```

`cancelled` обязателен при отмене хода. Клиент может отвечать автоматически по настройкам пользователя.

### 4.2. Файлы: `fs/read_text_file`, `fs/write_text_file`

Агент вправе вызывать их, **только если клиент объявил** `clientCapabilities.fs.readTextFile` / `writeTextFile`.
Чтение: `sessionId`, `path` (абсолютный), опционально `line` (с 1), `limit`; ответ `{content}`. Запись: `path`, `content`;
клиент **обязан создать файл**, если его нет; ответ `{}`.

### 4.3. Терминал: `terminal/*`

Только при `clientCapabilities.terminal = true`. `terminal/create` (`command`, `args`, `env`, `cwd`, `outputByteLimit`) →
`terminalId` сразу, без ожидания конца; `terminal/output` → `{output, truncated, exitStatus?}`; `terminal/wait_for_exit` →
`{exitCode, signal}`; `terminal/kill` — завершить, терминал остаётся действительным; `terminal/release` — убить и освободить.
Обрезать вывод при превышении лимита по границе символа, выставляя `truncated`.

### 4.4. Решение о возможностях клиента

**Минимальный клиент не объявляет `fs` и `terminal`.** Тогда агент делает файловые операции и команды **своими**
встроенными инструментами, а клиент только показывает ход и отвечает на запросы разрешений. Объявлять `fs` и `terminal`
стоит, если нужно, чтобы агент работал через ваши файлы и терминал (песочница, запись, учёт).

## 5. Уведомления `session/update`

Поле `update.sessionUpdate` определяет вид. Разбирать:

| Вид | Что в нём |
|---|---|
| `agent_message_chunk` | кусок ответа (необязательный `messageId` группирует куски) |
| `agent_thought_chunk` | кусок рассуждений |
| `user_message_chunk` | кусок сообщения пользователя (при воспроизведении истории) |
| `tool_call` | `toolCallId`, `title`, `kind` (`read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `switch_mode`, `other`), `status`, `content`, `locations`, `rawInput` |
| `tool_call_update` | `toolCallId` и только изменившиеся поля; статусы `pending`, `in_progress`, `completed`, `failed`; содержимое: текст, **diff** (`path`, `oldText`, `newText`), терминал (`terminalId`) |
| `plan` | записи плана: содержимое, приоритет, статус |
| `usage_update` | занято окна контекста и (необязательно) накопленная стоимость |
| `config_option_update`, `current_mode_update` | агент сам изменил настройки |
| `available_commands_update` | список команд агента (слэш-команды) |
| `session_info_update` | название и метаданные сессии |
| `notice`, `compaction_update`, `compaction_summary_chunk` | только при объявленных `session.notices` и `session.compaction` |

**Неизвестные виды и поля пропускать без ошибки.**

## 6. Ход и отмена

`session/prompt` отвечает один раз, когда ход закончен, с `stopReason`: `end_turn`, `max_tokens`, `max_turn_requests`,
`refusal`, `cancelled`.

Отмена: послать `session/cancel`; сразу пометить незавершённые вызовы инструментов отменёнными; на **все висящие**
`session/request_permission` ответить `cancelled`; продолжать принимать обновления до ответа на `session/prompt` (он придёт
со `stopReason: cancelled`).

## 7. Модель и параметры

Список настроек определяет **агент** (`configOptions` в ответе на создание сессии): у каждой опции свои допустимые значения.
Зарезервированные категории: `model`, `mode`, `thought_level`, `model_config` (например контекст или баланс скорость/качество);
категории — подсказка для интерфейса, не гарантия. Клиент строит выбор **по тому, что вернул агент**, и меняет вызовом
`session/set_config_option`. Переносимого набора параметров у разных семей нет: вести таблицу «агент → доступные опции».
Старый механизм режимов (`modes`) заменён опциями; агенты на переходе шлют оба.

## 8. Политика разрешений (решить до реализации)

- Что одобрять автоматически (например чтение внутри `cwd`), что спрашивать у человека (запись, команды), что всегда отклонять.
- Запоминать ли `allow_always` на стороне клиента.
- Журнал всех решений: время, сессия, инструмент, вариант.
- Отдельная политика для неинтерактивных запусков (нет человека): по умолчанию отказ.

## 9. Ошибки и устойчивость

- Процесс агента завершился или завис: таймаут без обновлений, перезапуск или завершение хода с ошибкой.
- Запросы клиента, кроме `session/prompt`, — с таймаутом; `session/prompt` долгий.
- При закрытии ответить на висящие запросы агента, затем закрыть процесс.
- Несовместимая версия протокола — закрыть соединение и сообщить.
- Размер вывода и число обновлений ограничить (потоки бывают очень большими).

## 10. Общая модель событий поверх ACP

Свести ход любого агента к одному набору: сообщение, рассуждение, вызов инструмента (начат, обновлён, завершён, с видом
и diff), запрос разрешения (и решение), план, расход, итог хода (`stopReason`). Особенности агентов хранить в «сыром» поле.

## 12. Подписка Claude (кратко)

По условиям Anthropic ([страница](https://code.claude.com/docs/en/legal-and-compliance)): пользователю разрешено входить в
**неизменённый** Claude Code своей подпиской; сторонним продуктам нельзя предлагать вход через Claude.ai, собирать, хранить
или пересылать токены, пропускать запросы через чужие учётные данные подписки. Мост ACP запускает Agent SDK под входом
пользователя и токенов не хранит, но явного разрешения для этого пути Anthropic не даёт: серая зона. Разделение подписки
на отдельный «Agent SDK credit» с 15 июня 2026 по сообщениям поставлено на паузу. Заложить переключение на API-ключ
настройкой. Перед продуктом для других проверить Commercial Terms.

## 13. План проверки

1. Поддельный агент (скрипт, отвечающий по протоколу): все исходящие методы, все виды `session/update`, запросы разрешений.
2. Два настоящих агента сразу: один родной (OpenCode или Gemini), один через мост (Claude).
3. Сценарии: отмена посреди вызова инструмента, отказ в разрешении, падение процесса, длинный вывод, повтор сессии
   (`load`/`resume`), смена модели, MCP-сервер со своим инструментом.
4. По результатам заполнить таблицу возможностей раздела 11.

## 14. Открытые вопросы

- С каких двух агентов начинать.
- Нужны ли `fs` и `terminal` (по умолчанию нет, см. 4.4).
- Политика разрешений для неинтерактивных запусков.
- Нужен ли запасной драйвер через командную строку агента (`claude -p` и аналоги) для случаев, где ACP не покрывает нужное
  (учёт расходов, продолжение сессии, особые возможности).
- Как хранить историю сессий: самим или полагаться на `load` агента.
