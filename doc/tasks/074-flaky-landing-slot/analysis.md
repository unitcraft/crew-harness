# Разбор 074: нестабильность ячейки AC-04 «cleanup_limit» теста crew-landing-slot

Задание — `task/message.md`. Источник: владелец, 2026-10-17 («по рекомендации», чат оркестратора).

## 1. Что проверяет ячейка и как краснеет

AC-04 проверяет шаги автоплана (`planSteps` в `index.ts`): готовая утверждённая задача-план ставит шаги задачами, пока лимиты
позволяют. Три сценария подряд на одной папке данных: `hold` (две принятые заполняют `inflight_limit 2`, шагов нет), `free` (принятые
не считаются, ставятся два шага, третий ждёт), `cleanup_limit` (две принятые ждут уборки при `cleanup_limit 2`, шагов нет). Между
сценариями вызывался `reset()` — стирание папки задач проекта, номера начинались заново.

Красная ячейка: `AC-04 cleanup_limit … :: spawned 3` (строка `cell("AC-04 cleanup_limit …")`, `n === 0`).

## 2. Частота до правки (чистый `main` e781d65, дерево задачи)

- Одиночные прогоны: 9 красных из 20 (45%), во всех одна и та же ячейка и то же «spawned 3».
- Прогон с отладочной печатью (временной, не сохранена): из 6 прогонов 3 красных, в каждом красном печать показала проход автоплана,
  который взял задачу-плана №3 прежнего сценария (`spawned` 2, `cleanup_limit` 5 из настроек прошлого сценария), хотя на диске уже
  лежала новая задача №3 (`spawned` 0, `cleanup_limit` 2).

## 3. Причина

Причина — в тесте; в коде плагина лимит `cleanup_limit` в автоплане соблюдён (проверено мутацией, раздел 5).

`planSteps` читает задачу-план и настройки (`loadConfig`), затем ждёт git (`await fileAtAsync(…)`, `index.ts`, строка с чтением плана
из целевой ветки), затем по этому снимку ставит шаги и пишет задачу-план обратно (`saveTask(pt)`). Ожидание git на Windows — десятки
миллисекунд при цикле прохода 200 мс, поэтому проход почти всегда «в полёте». Тест после `await wait(1_400)` синхронно делал
`reset()`, создавал принятые и новую задачу-план с тем же номером 3; проход, ждавший git в этот миг, возобновлялся со старым снимком:
старые лимиты (`inflight_limit 2`, `cleanup_limit 5`), старая запись `spawned` с двумя шагами. Новые принятые (2 штуки, не счёт
`inflight`) его не останавливали, он ставил третий шаг и записывал старую задачу №3 поверх новой. Отсюда `spawned 3` = два шага
прошлого сценария + один новый. Ожидание фиксированной паузой скрывало, что тест сам и стирал состояние под работающим фоновым
проходом.

В работе так не бывает: номера задач не переиспользуются, папку задач под проходом никто не стирает. Поэтому код не менялся.

## 4. Что сделано (`opencode-plugin/test/crew-landing-slot.test.mjs`)

1. Сценарий AC-04 получил свой проект (`scn-hold`, `scn-free`, `scn-cleanup_limit`), под идущим автопланом ничего не стирается;
   запоздавший проход прошлого сценария пишет только в папку своего проекта. Хелперы (`mk`, `reset`, `all`, `spawnedOf`) работают в
   проекте `PROJECT`, вне AC-04 он `proj`. После AC-04 папки сценариев убираются.
2. Пауза 1,4 с заменена ожиданием условия: проход прочёл план (`plan.total` равно 3) и поставил столько шагов, сколько позволяют
   лимиты (0, 2, 0); затем короткая выдержка 0,8 с показывает, что лишнего шага не появляется. Если проход план так и не прочёл
   (60 с), сценарий возвращает -1 и ячейка падает, а не проходит на «ничего не поставлено». Первый прогон с полной нагрузкой рядом
   показал, что одна пауза без условия не годится: «spawned 0» в 16 из 20 прогонов (8 прогонов параллельно и рядом полный набор по 4).
3. Ожидание «после cleanup» увеличено с 4 до 60 с (условие то же).

Проверка не ослаблена: ячейки и ожидаемые числа (0, 2, 0, ≥1) прежние.
