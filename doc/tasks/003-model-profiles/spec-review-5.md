Желание владельца (профили и наборы по трём семьям с окнами для четырёх этапов, разные модели для реализации и приёмки,

четырёх по тексту до сессий не доходят (находка 1). Остальное — поверхностные.

## Находки

1. **Окно профиля для этапов «приёмка» и «приёмка плана» по тексту не применяется нигде, а цель и ожидаемое состояние говорят,
   что окно задаётся для четырёх этапов; вопрос отложен в Д-23 с умолчанием «как есть».** критичность: существенная;
   уровень: требования.
   Что не так: файл окон пишется только в worktree задач (REQ-08, REQ-22, Д-11). Сессия приёмки создаётся в основной папке
   `t.directory` (код: `startReviewer`, `index.ts:563…566`, `location: { directory: t.directory }`), worktree создаётся
   только для сессии исполнителя (`startTask`, ветка `t.kind === "spawn"`, `index.ts:1034…1056`). Значит, у сессий приёмки и
   приёмки плана окно всегда берётся из рукописных и глобальных настроек (Д-23, REQ-22, REQ-10 «для основных папок»), а
   клетки набора «приёмка» и «приёмка плана» задают только модель. Именно эти два этапа — главный сценарий владельца
   (перекрёстная проверка: приёмка на Kimi или Codex, AC-03, AC-15, образцы `cross-kimi`, `cross-codex`); в основном проекте
   владельца настроен `reviewer: acceptor`, то есть приёмка всегда идёт новой сессией в основной папке, а не в worktree.
   Окно профиля `kimi`/`codex`, которое владелец правит командой (`/crew-profiles set kimi all … 150000`), на приёмщика
   этих семей не подействует; `use` скажет только общее «основные папки не меняются», не связав это с этапами. Противоречие
   внутри текста: goal — «с каким окном контекста идут четыре этапа»; msg M-11 — «значение приходится менять под семью и под
   этап»; REQ-08 — «Один набор значений определяет и сжатие OpenCode, и порог Claude Code»; AC-08 проверяет окна только для
   worktree, ни один AC не проверяет окно сессии приёмки и не признаёт его отсутствие; AC-19 не обязывает README сказать об
   этом. Д-23 передаёт решение плану, но план не вправе сужать цель; «без решения действует как есть» превращает
   нерешённый вопрос в молчаливое сужение желания владельца.
   Цитата: «Сессия приёмки создаётся в `t.directory` (основная папка), и её окно берётся из рукописных настроек; сможет ли
   приёмка идти в worktree задачи, решает план (Д-23)» (REQ-22); «Владелец командами в окне переключает, на каких моделях
   (семья и ступень) и с каким окном контекста идут четыре этапа работы» (goal).
   Место: goal, expected_state, REQ-08, REQ-10, REQ-22, Д-23, AC-08, AC-15, AC-19.
   Нужно: решить сейчас, а не в плане: либо (а) окно профиля применяется и к приёмке (приёмка идёт в worktree задачи — тогда
   проверить вливание из основной папки — или файл окон пишется ещё в папку, где создаётся сессия приёмки, но это снимает
   решение владельца «только worktree» и требует его слова), либо (б) честно сузить цель, ожидаемое состояние и REQ-08:
   «окно профиля действует на сессии исполнителя (разработка, планирование); у приёмки и приёмки плана профиль задаёт модель,
   окно — из рукописных настроек», с этой строкой в сообщении `use`, README (AC-19) и в таблице `/crew-sets show`, и AC на
   это. Рекомендация — (б) с явным вопросом владельцу (с рекомендацией, proc «Дополнения»), если ему нужны окна приёмки.

2. **Поверхностная: строка 3 таблицы REQ-33 говорит «файлы не меняются», REQ-09 — «файл равен окнам последнего допустимого
   состояния» и пишется при создании worktree.** критичность: поверхностная; уровень: требования.
   Причина, почему не меняет требования, число, сценарий или текст наружу: оба текста читаются согласованно, если «не
   меняются» — про существующие файлы (в строке 4 так и сказано); новая задача при недопустимых данных со снимком получает
   файл по снимку, а ровно как — деталь реализации, ни один AC не различает.
   Место: REQ-09, REQ-33 (строка 3), AC-37(б).

3. **Поверхностная: строка 4 таблицы («этап описан — отказ REQ-15») шире REQ-15, который отказывает, когда «профиль не
   находится».** критичность: поверхностная; уровень: требования.
   Причина: при недопустимости без снимка по причине «конфликт окон одной модели» профиль этапа находится; отказывать ли
   тогда — читается двояко, но состояние возможно только после потери снимка (перезапуск без ящика) и обе реализации
   безопасны (отказ не подменяет семью); AC-37(г) проверяет случай с повисшей ссылкой.
   Место: REQ-15, REQ-33 (строка 4), AC-37(г).

4. **Поверхностная: снимок REQ-33 назван «действующими данными проекта (файл со слоем)» — не сказано, что он охватывает только
   ключи профилей, наборов и имени.** критичность: поверхностная; уровень: требования.
   Причина: контекст (сессии идут «по снимку» набора) и REQ-11 («`spawn_models` продолжает действовать») не оставляют другого
   чтения; реализация, замораживающая весь файл, нарушила бы REQ-11, и это поймал бы самотест DNC-01.
   Место: REQ-33, REQ-31.

5. **Поверхностная: AC-39 велит для `crew_config set` с `profile_set` на несуществующий набор отказ «по проверке связей
   REQ-34», REQ-21 и AC-23 — отказ «имя меняет человек».** критичность: поверхностная; уровень: требования.

   `profile_set` работает при загрузке файла и `save`, где AC-37 её покрывает.
   Место: REQ-21, REQ-34, AC-23, AC-39.

6. **Поверхностная: настоящее перекрытие окна профиля рукописным — это отслеживаемый в репозитории `.opencode/opencode.jsonc`,
   попавший в worktree; AC-40 проверяет корень проекта и основную папку, где файла плагина нет и «перекрытия» нет.**
   критичность: поверхностная; уровень: требования.
   Причина: REQ-16 уже требует проверять папку worktree («проверяются папки worktree и основные папки»); AC-40 лишь

7. **Поверхностная: REQ-07 пишет «модель той же семьи», REQ-14 сравнивает с «провайдер/id профиля»; не сказано, какой профиль
   семьи — клетки приёмки или любой из трёх ступеней.** критичность: поверхностная; уровень: требования.
   Причина: для Kimi (одна модель на трёх ступенях) различия нет; для Codex вкладка на другой ступени (например `gpt-6-luna` при

   чтениях, а AC-04 проверяет вариант в строке модели.
   Место: REQ-07, REQ-14, AC-04.

8. **Поверхностная: формулировки.** критичность: поверхностная; уровень: требования.
