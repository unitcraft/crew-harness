# Задание: профили моделей и окон контекста по семьям и этапам работы

Заказчик и владелец: владелец репозитория `unitcraft/crew-harness` (он же отвечает на вопросы и принимает результат).
Репозиторий кода: `unitcraft/crew-harness` (https://github.com/unitcraft/crew-harness, ветка `main`). Дата задания: 2026-10-08.

Задача полная: разбор, план, реализация, сдача.

## Что есть сейчас

- Плагин OpenCode в `opencode-plugin/` ведёт задачи и письма между вкладками. Модель исполнителя задаётся ступенью задачи
  (`tier`: heavy, medium, light) и ключом проекта `spawn_models` («ступень → провайдер/модель»); какие вкладки считаются какой
  ступенью — ключ `tiers` (подстроки имён моделей). Оба ключа — в файле проекта `.opencode/crew-harness.json`; значения по
  умолчанию — в `opencode-plugin/config-schema.ts` (heavy — Opus, medium — Sonnet, light — Haiku, все через `claude-code`).
- Кто принимает сданную задачу, задаёт ключ `reviewer` (воркер, интегратор или отдельная роль приёмщика). **Модель приёмщика
  не задаётся**: он идёт на той модели, на какой открыта его вкладка. Для планирования и приёмки плана отдельных настроек нет.
- Окно контекста модели (`limit.context`) лежит не в плагине, а в настройках OpenCode: общих (`opencode.jsonc` пользователя)
  и проектных (`.opencode/opencode.jsonc` рядом с кодом). Сжатие начинается на `context` минус `compaction.reserved`.
  Для окон Claude Code провайдер `claude-code` берёт ту же границу для самого Claude Code.
- Три семьи моделей в работе: Claude Code (через провайдер `claude-code`), Kimi Code (`kimi-code-plan-global`), Codex (провайдер
  `openai`, вход через ChatGPT). Измерение расхода (2026-10-08): расход лимитов у Kimi определяет длина сессии — средний запрос
  несёт около 97 тысяч токенов истории, половина запросов — больше 100 тысяч и даёт 84% расхода; поэтому окно ставится ниже
  штатного, и значение приходится менять под семью и под этап работы.

## Что нужно

Устройство, предложенное владельцу и объяснённое ему так (уточнять разбором, не менять без его слова):

1. **Профили** — справочник: для каждой семьи (Claude Code, Kimi Code, Codex) и ступени (heavy, medium, light) записана модель
   (провайдер/модель) и окно контекста.
2. **Этапы работы** — четыре: разработка (исполнитель), приёмка, планирование, приёмка плана.
3. **Наборы** — именованные раскладки «этап → профиль и ступень» (например: обычный; перекрёстная проверка, где приёмка на
   другой семье; только Kimi — когда у другой семьи закончился лимит).
4. **Включённый набор** — одно имя в файле проекта; команда вроде `/crew-profile <имя>` меняет его и показывает, что включено
   (без аргумента — показывает). Остальное (модели, окна, этапы) подтягивается из справочника.
5. Без новых ключей поведение прежнее: ничего не ломается, `spawn_models` и `tiers` остаются работать как сейчас.
6. Профили — данные в файле проекта, не привязанные к устройству плагина: их должен суметь читать и будущий сервис задачи 001.

## Что надо выяснить в разборе (владелец этого не знает и я тоже)

- Как менять окно контекста при переключении набора: плагин может подставлять окно только окнам Claude Code; для Kimi и Codex
  окно — настройка OpenCode. Можно ли менять её без перезапуска сервиса; если нет — как это показать владельцу.
- Сможет ли приёмщик на другой семье моделей пользоваться теми же инструментами `crew_*`: окнам Claude Code они приходят через
  отдельный процесс, остальным — напрямую через OpenCode.
- Где проходит граница «этап»: как плагин узнаёт, что вкладка делает приёмку плана, а не приёмку задачи.
