### Формат данных (Д-01 окончательно)

- `model_profiles` — `{"<семья>": {"heavy": П, "medium": П, "light": П}}`, П = `{"model": "провайдер/модель", "context": N,
  "output": N[, "input": N]}`; пустая запись («заполнить», REQ-30) — `{"model": ""}` (поля окна необязательны). Семья —
  `[a-z0-9-]+`, не `all`, `context`, `output`, `input` (пункт 3 захода 7: запрет трёх слов безвреден и однозначен; проверяет
  `all`, остальные — в том же тесте).
- `profile_sets` — `{"<имя набора>": {"develop"|"accept"|"plan"|"plan_accept": {"family": "<семья>", "tier":
  "heavy"|"medium"|"light"|"task"}}}`; незнакомый ключ-этап читатель игнорирует (Д-10, DNC-09), незнакомый ключ внутри клетки
  — отказ. Клетка — объект, а не строка «семья/ступень»: так формат расширяется; в командах и показе — «семья/ступень».
- `profile_set` — строка, имя набора по умолчанию; ставит человек (REQ-21).
- Русские названия этапов принимаются только в командах: `разработка`→develop, `приёмка` и `приемка`→accept,
  `планирование`→plan, `приёмка-плана` и `приемка-плана`→plan_accept (через дефис: пробел в аргументе — разделитель). В файле
  и слое — только латиница.
- Запрещённые имена наборов, правило имён — REQ-03; константы лежат в `profiles.ts` (`RESERVED_WORDS`, `SET_NAME_RE`).

### Слой локальных правок (REQ-31, REQ-25, REQ-04)

Выбор: **плоская карта записей в ящике по проекту**, файл `profiles/<проект>.layer.json` в `BASE` (`paths.ts`), запись
атомарная (временный файл и переименование, как `writeSettings`). Ключи карты и значения:

```text
name                       {value: "<имя>", base: "<имя из файла или null>"}        включённое локально имя
profile:<семья>/<ступень>  {value: П | null, base: П | null}                       null у value — пометка об удалении
set:<имя>                  {mode: "new" | "deleted", base: <клетки файла> | null}    набор создан слоем / убран слоем
cell:<имя>/<этап>          {value: клетка | null, base: клетка | null}
```

- `base` — значение закоммиченного файла в момент правки; по нему `show`/`check` называют «в файле теперь иначе», а `save`
  отличает свои записи от чужих (REQ-29, REQ-31). Запись слоя главнее файла по ключу (AC-33).
- Действующие данные = `applyLayer(file, layer)`: запись справочника — слой или файл; набор `mode: "new"` — только клетки
  слоя (одноимённый набор файла игнорируется), `mode: "deleted"` — набора нет, иначе набор файла с наложенными клетками.
  «Файл» — то, что даёт `rawSettingsFor` (закоммиченный файл плюс опция `local`): для остального плагина источник тот же.
- Почему не иначе: целая копия файла в слое не различает «моё» и «пришло коммитом» (REQ-29, AC-35); опция плагина `local`
  читается при загрузке и лежит в рукописном файле владельца (DNC-03); отдельная база — лишняя зависимость. Карта читается
  из любого процесса (сервис, MCP-сервер вкладок claude-code) обычным чтением файла, без сервера.
- `reset` — снятие записей по префиксу ключа (форма → префикс: имя → `name`; набор → `set:<н>`+`cell:<н>/`; клетка →
  `cell:<н>/<этап>`; семья → `profile:<с>/`; запись → `profile:<с>/<ступень>`; `all` → всё). Запись слоя, равная файлу
  (после коммита), удаляется сверкой `pruneLayer` на проходе (AC-35, REQ-29).
- `save`: для каждой записи слоя читается рабочая копия файла; запись пропускается и перечисляется, если значение в файле
  (закоммиченном или рабочей копии) не равно `base` и не равно значению слоя; `save force` перезаписывает перечисленное;
  остальные ключи рабочей копии и записи, которых слой не касался, не трогаются; пишет `writeSettings` только три ключа,
  собранных из свежей рабочей копии. Плагин не коммитит (AC-29, AC-35). Проект старой формы опций (без папки настроек) —
  отказ `save` с причиной: писать некуда.
- Состояние слоя читается на каждом обращении (файл мал); тяжёлые пересчёты на проходе гейтятся подписью (`mtime`+размер
  слоя, хеш трёх ключей файла).

### Состояние набора, снимок, таблица REQ-33

`stateRow(name, effective, snapshot)` в `profiles.ts` — одна чистая функция, возвращающая строку 1…7 таблицы REQ-33 и
данные, по которым идут сессии (`active`: действующие данные, снимок или ничего). Допустимость = нет ошибок: форма значений
(REQ-13), повисшие ссылки **включённого** набора, ссылка включённого набора на пустую запись, конфликт окон одной модели
(REQ-24), `input` больше `context`. Повисшие ссылки других наборов — предупреждения. Снимок: файл
`profiles/<проект>.snapshot.json` (три ключа и имя), пишется проходом сервиса `profilesStep` (первый допустимый проход при
включённом наборе, в том числе сразу после `use`; обновляется на каждом допустимом; удаляется на строках 1 и 7). Читатели
(`crew_spawn` в любом процессе) снимок только читают. Причина единого места: исходы для сессий, файлов и сообщений обязаны
совпасть (REQ-33), поэтому ни один потребитель не пересчитывает таблицу сам.

### Выбор модели (REQ-06, REQ-07, REQ-15, REQ-17, REQ-32)

- `resolveStageProfile(state, stage, {inputTier?, taskTier?, autoPlan?})` → `{model, family, tier, set, viaSnapshot,
  window: boolean}` | `{refuse: текст}` | `undefined` (этап не описан или набора нет — вызывающий берёт `spawn_models`, код
  прежний слово в слово). Ступень: для develop/plan — `inputTier` (ключ присутствует во входе и значение `isTier`), иначе
  ступень клетки, `task` → `medium`; для шагов авто-плана — ступень клетки develop (`task` → `medium`); для accept/plan_accept
  — ступень клетки, `task` → ступень записи задачи; для `reassign` `inputTier` = ступень записи задачи (REQ-32).
- Вызов в `core.ts: crew_spawn` вместо строки `cfg.spawnModels[tier] ?? DEFAULT_SPAWN_MODELS[tier]`; схема `crew_spawn.tier`
  теряет `default: "medium"` (REQ-19), код по-прежнему берёт `medium`, когда ключа нет. Отказ — ответ инструмента до создания
  записи задачи (задача не создаётся, номер не тратится).
- **Ступень записи задачи при включённом наборе — ступень, на которой реально запущена сессия** (решение Сессии С3;
  см. «Требует утверждения» Р-03). Без набора запись прежняя (`input.tier` или `medium`). Причина: иначе `reassign` и приёмка
  по клетке `task` читали бы `medium` у задачи, запущенной на `heavy` по клетке, и модель молча менялась бы.
- Приёмщик: `assignReviewers` **после ветки `reviewer: integrator`** (она первая и от набора не зависит) и перед назначением вкладки или сессии вызывает `resolveStageProfile` (accept или plan_accept по `t.plan`) и
  записывает **выбранную модель в задачу до `startReviewer`** (`t.review_model`), `startReviewer` берёт её из записи: повтор
  оборванного запуска даёт ту же модель (по образцу `t.executor`). Отказ REQ-15: задача остаётся «сдана, приёмщика нет»,
  одно письмо интегратору с причиной (постоянный id письма), строка в `crew_doctor`; на проходе повторяется без новых писем.
- Открытая вкладка роли (REQ-07): если клетка этапа с явной ступенью — вкладка годится, только когда `familyOfModel(c.model)`
  равна семье клетки (любая из трёх ступеней семьи); `task`-клетка модель вкладки не проверяет; вкладка без известной
  модели при явной ступени не годится. `reviewer: integrator` — как сейчас; плагин `session.switchModel` не вызывает
  (DNC-09).
- Шаги авто-плана (`planSteps`): модель — `resolveStageProfile(develop, autoPlan)`; отказ — шаг в этот проход не ставится,
  автору плана одно письмо (постоянный id), строка в `crew_doctor`.
- След (REQ-17): `Task.profiles?: {at, role: "executor"|"reviewer", session, stage, set, family, tier, model, window:
  "profile"|"general"|"snapshot"}[]` (добавляется запись на каждый запуск сессии); `taskEvent` — одна строка истории; строка
  журнала плагина `profile edit: <проект> <команда> <что изменено> (<старое> -> <новое>)` на **каждую успешную правку**:
  `set`, `unset`, `new`, `rename`, `delete`, `use`, `reset` (все формы), `save` и `save force` обеих команд — пишет
  **единственный вызывающий** `commitEdit(project, правка)` в `profile-cmd.ts`: каждый глагол обеих команд (включая `use`, `reset`,
  `save`) вызывает его ровно один раз после успешного применения, а `saveLayer`, `resetLayer` и прочие функции слоя журнал не
  пишут (одна строка на правку, не две); отказанная правка в журнал не пишется (пишется причина
  отказа одной строкой `profile edit refused`).
- Семья вкладки (REQ-14): `familyOfModel(строка, data)` — строка приводится к `провайдер/id` (часть после `#` отбрасывается,
  регистр не различается), сравнивается целиком с моделями всех трёх ступеней всех семей; `tierOf` и ключ `tiers` не меняются.

### Файл окон (REQ-08, REQ-09, REQ-22)

- Путь: `<worktree>/.opencode/opencode.json`. Содержимое: `{"_crew_harness": "<пометка, одна строка>", "provider":
  {"<провайдер>": {"models": {"<id>": {"limit": {"context", "output"[, "input"]}}}}}}` — только `limit`, никаких `compaction`
  (DNC-02). Модели — все три ступени каждой семьи, названной в клетках набора; одинаковые модели с равным окном — одна
  запись. Пометка — ключ `_crew_harness`; файл без пометки плагин не перезаписывает и не удаляет (REQ-08, DNC-03).
- Исключение из git: строка `/.opencode/opencode.json` с комментарием-пометкой в `info/exclude` каталога
  `git rev-parse --git-common-dir` (путь разрешается от worktree), добавляется один раз.
- Реестр записанных файлов: `profiles/<проект>.windows.json` в ящике — `{<абсолютная папка worktree>: {hash, task, at}}`;
  по нему плагин находит, что снимать, когда набора нет (строки 1 и 7), и убирает записи исчезнувших папок.
- Кому нужен файл: задача `kind: "spawn"`, `worktree_ready`, статус из `OPEN_STATUSES` кроме `accepted`, папка существует.
  Принятая и отменённая задача файл теряет (`releaseTaskWindow` из веток `accept` и `cancel` в `core.ts` плюс сверка
  прохода). Атомарная запись, только если содержимое отличается (Д-08).
- Когда пишется: перед `session.create` в `startTask` (после `ensureWorktree`, до первого хода сессии — REQ-22); на проходе
  `profilesStep` при смене подписи данных (коммит, `use`, `reset`, правка командой, `save`, старт плагина). Недопустимое
  состояние без снимка: новые файлы не пишутся, существующие не трогаются (строка 4 REQ-33).
- Состояние, по которому пишется файл, берётся по проекту **задачи** (`t.project`), а не по вхождению папки в корень: вложенные
  и соседние проекты чужих файлов не получают (REQ-11, AC-24); реестр ведётся по проекту.
- Первый проход после старта плагина пересчитывает файлы безусловно (REQ-09 «при старте»), дальше — по подписи данных.
- Расхождение файла с набором и непомеченный `.opencode/opencode.json` в worktree находит `windowProblems(state, задачи)`;
  его строки входят в `profileProblems` (REQ-16).
- Почему не `ctx.model.transform` и не корень проекта: Ф-15, Ф-23, Ф-30, решение владельца (файл только в worktree).

### Чтение настроек OpenCode (REQ-10, REQ-16, REQ-23, REQ-29, AC-25, AC-40)

`profile-windows.ts: configChain(dir, env)` повторяет порядок OpenCode (глобальные `opencode.json(c)` из `XDG_CONFIG_HOME` или
домашнего каталога, затем для каждого уровня от корня диска вниз `opencode.json`, `opencode.jsonc`, `.opencode/opencode.json`,
`.opencode/opencode.jsonc`) — как `opencodeConfigFiles` провайдера, с собственным разбором JSONC. Дубль логики сознательный:
репозитории публичные и независимые, импорта между ними нет; риск расхождения при смене версии OpenCode — в рисках.
Функции: `chainWindow(dir, providerID, modelId)` (значение и файл каждого поля окна; файл плагина пропускается),
`predictWindow(dir, model, содержимое)` (что станет в папке после записи), `handWrittenOverrides(dir, model)` (рукописные файлы
**позже** файла плагина в цепочке — сильнее; и более слабые выше по пути с иным значением — справочная строка «будет
заменено файлом плагина», пункт 4 захода 7), `reservedOf(dir)` (`compaction.reserved` для порога в сообщениях; только
чтение, DNC-02), `explicitCompact(dir, modelId)` (опции провайдера в файлах цепочки,
`providers["claude-code"].settings.autoCompactWindow`, и проектный файл провайдера вверх от папки; число значит «для всех»;
ключ — точное имя, семейство по подстроке или `*`). Если окно модели нигде в файлах не записано, в сообщении «в файлах
настроек не задано» (пункт 5 захода 7).

### Команды (REQ-05, REQ-20, REQ-27…REQ-29; закрывает Н-04)

- Серверные слэш-команды `crew-sets` и `crew-profiles` через `ctx.command.transform` рядом с `crew-help`; ответ —
  `ctx.session.synthetic({sessionID, text, resume: false})` (без хода модели), запасной путь как у `crew-help`. Аргументы
  читаются из `prompt.text` — **факт** (заседание С4, заход 1, проба 1 на одноразовом сервере OpenCode 2.0.23: аргумент
  приходит в `prompt.text` целиком, без имени команды; при перезагрузке плагина реестр команд заменяется и приходит
  `command.updated`, перезапуск не нужен). Оговорка: «на экране окна не проверялось»; поэтому шаг 1 остаётся проверкой в живом
  окне перед закрытием задачи (ворота Г3, по слову владельца), а не пробой одноразового сервера. Проект сессии — по каталогу карточки вкладки, иначе по каталогу плагина. Если проба покажет, что аргумент не
  доходит, запасной путь — команды окна (`tui.ts`) с `dialog.prompt` и файлом запроса в ящике (по образцу `/plans`): это
  меняет шаги 10–11 и идёт через Сессию С3 правка.
- Грамматика: слова через пробел; глагол — первое слово; `crew-sets`: `show [<имя>] | use <имя> | reset [<имя> [<этап>] | all]
  | set <имя> <этап> <семья>/<ступень> | unset <имя> <этап> | new <имя> [from <имя>] | rename <а> <б> | delete <имя> | check |
  save [force]`; `crew-profiles`: `show [<семья>] | set <семья> <ступень|all> <модель> <context> output=<n> [input=<n>] | new
  <семья> [from <семья>] | rename <а> <б> | delete <семья> [<ступень>] | reset [<семья>[/<ступень>] | all] | check | save [force]`.
  Без аргументов — таблица. Неизвестный глагол или лишний аргумент — отказ с перечнем глаголов, данные не тронуты.

  стать недопустимым (REQ-28), остальные — не создавать повисшую ссылку (REQ-34); отказ называет место и значения.
  Пакетная форма `set <семья> all` проверяется одной проверкой на все три ступени.
- Сообщения владельцу — словами, без голых кодов требований (process.md); тест ищет в ответах шаблон `REQ-` и `AC-` — 0.
- REQ-20 (желательное): таблица-диалог в окне — шаг 14, после всего обязательного, с пробой: совпадение имён слэш-команд
  окна и сервера. Нет проверенного способа без ущерба — REQ-20 остаётся невыполненным с причиной (Р-04).

### Граничные случаи

Проект без папки настроек (старая форма): профили читаются из `legacyWalk`, слой работает, `save` отказывает. Два процесса
пишут слой одновременно — последняя запись побеждает (команды редки; блокировок плагин не вводит). Worktree с рукописным

`crew_task assign` (вкладка владельца, без worktree) окон профиля не получает, `use` говорит об этом (REQ-22).

### Риски

- **Аргумент серверной команды не дойдёт в живом окне (Н-04)** — на одноразовом сервере доходит (факт заседания С4); проверка в живом окне — ворота Г3; запасной путь описан выше (правка плана).
- **Новые команды не появятся в живом окне без перезапуска** — на одноразовом сервере перезапуск не нужен (заседание С4, проба 2: `command.updated`); в живом окне проверяется на воротах Г3; понадобится перезапуск сервиса — это ворота Г2 (AG п.12), не действие плана.
- **Расхождение с цепочкой настроек OpenCode** при смене версии — `check` печатает версию; проба шага 13 сверяет цепочку с
  каталогом моделей сервера на двух папках.
- **Нагрузка**: 38 прежних файлов плюс 7 новых — только по одному с паузой 5 с, `npm test` целиком не запускается
  (AG п.9, слово владельца); тест, подвесивший машину, — остановка и вопрос владельцу.
- **Кеш настроек 5 с** (`settings.ts`) и проход раз в секунду: тесты задают свои `XDG_DATA_HOME` и `XDG_CONFIG_HOME` (цепочка настроек не зависит от настоящих настроек машины, К-07), `CREW_HARNESS_SETTINGS_TTL_MS=1`,
  `CREW_HARNESS_POLL_MS=60`.
- **Размер**: `core.ts` (2282 строки) и `index.ts` (1416) растут минимально — вся логика в новых модулях, в старых файлах
  вызовы.
