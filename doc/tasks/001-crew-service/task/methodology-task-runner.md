# Раннер: автоматизация цикла сессий

Алгоритм программы, которая ведёт задачу по [task-sessions.md](task-sessions.md): запускает сессии агента, считает заходы, показывает прогресс по шагам, останавливается у ворот, где решает человек, и собирает запросы к модели так, чтобы кеш контекста переживал смену сессий. Правила цикла здесь не повторяются: что делает каждая сессия и когда повтор заканчивается, сказано в task-sessions.md; здесь только то, что нужно программе, чтобы это исполнить. Константы цикла — потолок заходов, число чистых заходов подряд, число проб — берутся из «Правил» task-sessions.md; в программе они названы ПОТОЛОК_ЗАХОДОВ, ЧИСТЫХ_ПОДРЯД, ПРОБ_В_ЧИСТОМ, и числа в этом файле — примеры при нынешних значениях.

## Словарь

| Термин | Что это | Пример |
|---|---|---|
| **Задача** | одно задание заказчика, одна папка задачи, одно рабочее дерево | — |
| **Фаза** | крупный отрезок цикла с одними воротами на выходе: РАЗБОР, ПЛАН, РЕАЛИЗАЦИЯ, СДАЧА, ОБРАТНАЯ_СВЯЗЬ | фаза ПЛАН заканчивается утверждением plan.md |
| **Сессия** | один промпт из task-sessions.md, выполненный агентом; виды — С1 … С9, их правки и продолжение; в логах у каждого вида код без пробелов | С6 — проверка реализации, С5п — правка реализации |
| **Диалог** | цепочка запросов к модели с общим префиксом и накопленной историей; сессия — либо новый диалог (разбор, план, реализация, проверки, сдача), либо ход живого диалога автора (правки, продолжение) | С5п — ход диалога С5 |
| **Этап проверки** (stage) | пара «проверка ↔ правка» одного артефакта: spec, plan, review, delivery; по нему считаются заходы, потолок и чистая серия; в «Правилах» task-sessions.md это слово «этап» | review-3.md — третий заход этапа review |
| **Заход** | порядковый номер файла проверки внутри этапа; при возврате в фазу не обнуляется (task-sessions.md, «N — номер захода») | review-3.md |
| **Шаг** | счётная единица работы внутри сессии; у каждого вида сессии своя единица | С5: шаг плана 7/12; С6: доказательство 2/17 |
| **Ворота** | точка, где программа останавливается и ждёт решения человека; идентификаторы В1 … В13 | В5 — утверждение spec.md |
| **Профиль запуска** | параметры одного запуска модели: класс модели, усилие, размышление, ожидаемый объём входа, срок жизни кеша | класс A, усилие 4 |
| **Класс модели** | A — самая способная, B — средняя, C — быстрая; какая модель поставщика стоит за классом, задаёт конфигурация программы | — |
| **Усилие** | ступень 1–5 от минимальной к предельной; какому уровню поставщика соответствует ступень, задаёт конфигурация программы: имена уровней у поставщиков свои и меняются | С3: усилие 5 |
| **Размышление** | вкл — модель рассуждает перед ответом и между вызовами инструментов; выкл — самый дешёвый режим рассуждений, который модель даёт отключить; если отключить нельзя, выкл значит минимальная ступень усилия. Какие сочетания усилия и размышления модель принимает, знает конфигурация программы | С7: выкл |

Слово «этап» ниже значит только этап проверки; для фазы, сессии и шага оно не используется.

Коды сессий: С1, С1п, С2, С3, С3п, С4, С5, С5д (продолжение), С5п, С6, С7, С7п, С8, С9, КОММИТ, ПУШ. Автор этапа: spec — С1, plan — С3, review — С5, delivery — С7; проверка: С2, С4, С6, С8; правка: С1п, С3п, С5п, С7п.

Строка прогресса для человека: `Фаза · код сессии · единица k/N · заход j/ПОТОЛОК`, где j = n − pass_origin + 1, n — номер файла проверки; у сессий без заходов часть «заход» не показывается. Пример: `РЕАЛИЗАЦИЯ · С6 · доказательство 2/17 · заход 2/4 (review-6.md)`.

## Единицы шага и откуда берётся N

| Код | Единица шага | Откуда программа берёт N до запуска |
|---|---|---|
| С1 | источник | число файлов в task/ без task/feedback-*/ плюс ссылки в task/message.md |
| С1п | существенная находка или ответ | K из первой строки файла с находками; число ответов в разделе «Ответы» spec.md |
| С2 | источник | число из строки `итого:` раздела «Опись источников» spec.md |
| С3 | требование | число REQ-xx в spec.md |
| С3п | существенная находка или решение | K из файла с находками; число `решено:` в plan.md |
| С4 | требование | число REQ-xx в spec.md |
| С5 | шаг плана | нумерованные строки раздела «План» plan.md |
| С5д | шаг плана | строки раздела «План» минус строки `шаг <n>: сделан` в result.md |
| С5п | существенная находка | K из review-N.md; из feedback-N.md — число замечаний с исходом «правлю» и уровнем «реализация» |
| С6 | доказательство | строки `[ ]`/`[x]` раздела «DoD» plan.md плюс строки раздела «Трассировка» result.md |
| С7 | файл | 2 или 3 по способу сдачи |
| С7п | существенная находка | K из delivery-review-N.md |
| С8 | сценарий | число AC-xx в spec.md |
| С9 | замечание | неизвестно до запуска: агент сообщает N первой строкой прогресса |
| КОММИТ, ПУШ | — | единиц нет: сессионная часть хвоста только «Сессия: <код>. Единиц нет: одна строка «<код> 0/0 старт», строку ПРОФИЛЬ не пиши» |

Если считать нечем, программа показывает `?/?` до первой строки агента. Если агент сообщил N, отличное от посчитанного, программа показывает N агента и один раз пишет расхождение в log.md: агент видит содержимое, программа только форму. k > N не ошибка: показывается как есть, шкала не выше 100 %.

## Машинные форматы

Программа читает только эти места; каждое из них требует либо промпт task-sessions.md, либо машинный хвост ниже. Всё остальное в файлах — для людей и агентов.

| Файл | Что читается | Формат |
|---|---|---|
| spec.md, plan.md | статус | первая строка начинается с `Статус: черновик` или `Статус: утверждено`; дата и кто — после запятой, программа их только показывает. Первая строка, не подходящая ни под одно, — ворота В13, а не статус «черновик»: молчаливый черновик запустит проверку заново поверх утверждённого документа |
| plan.md | базовая ревизия | вторая строка `База: ревизия <хеш>, <дата>` |
| spec.md | требования, сценарии, запреты | идентификаторы `REQ-NN`, `AC-NN`, `DNC-NN` в начале строки |
| spec.md | опись источников | раздел «Опись источников»; число из его последней строки `итого: <число>` |
| plan.md | шаги плана | нумерованные строки `1.` … `n.` раздела «План» |
| plan.md | ветка задачи | строка `Ветка: <имя>` в разделе «План» |
| plan.md | DoD | строки раздела «DoD», начинающиеся с `[ ]` или `[x]` |
| plan.md | решения | строки раздела «Требует утверждения»; пометка `решено:` |
| result.md | статус | первая строка `Статус: в работе` или `Статус: готово` |
| result.md | сделанные шаги | строки `шаг <n>: сделан` |
| result.md | статусы критериев | слова `PASS`, `FAIL`, `NOT VERIFIED`, `N/A` в строках раздела «Трассировка» |
| result.md | решения владельца | у каждой строки FAIL, NOT VERIFIED и Known limitations пометка `решение владельца: …, <дата>` |
| spec.md, plan.md, result.md | вид остановки | первое слово последнего абзаца: `ревизия`, `план`, `требования`, `вопрос`; читается только при статусе «черновик» или «в работе» |
| *-review-N.md | итог захода | первая строка `Заход N: существенных K, поверхностных M, проб P` |
| *-review-N.md | находки | пункт нумерованного списка `1.` … `n.`; внутри поля `критичность: существенная` / `критичность: поверхностная` и `уровень: реализация` / `план` / `требования` / `вне задачи` / `сдача`; пункт без поля критичности — существенная |
| review-N.md | отчёт по секретам | строка, начинающаяся с `Секреты в diff:` (пункт 5 С6) |
| feedback-N.md | замечания | первая строка `Раунд N: правлю K, доводом M, отвергаю R`; пункт нумерованного списка с полями `исход: правлю` / `отвечаю доводом` / `отвергаю` и `уровень: реализация` / `план` / `требования` |
| feedback-N.md | маршрут | последняя строка `Маршрут: С1 правка` / `Маршрут: С3 правка` / `Маршрут: С5 правка` / `Маршрут: С7` |
| progress.log | прогресс | строки `<код> <k>/<N> <подпись>`: код сессии без пробелов, первая пара чисел через `/`, остаток — подпись; время появления строки ставит программа при чтении |
| profile.log | подсказка профиля | строки `ПРОФИЛЬ от <код>: класс=<A|B|C> усилие=<1..5> размышление=<вкл|выкл> бюджет=<целое число токенов> причина=<текст>`; поля разбираются по отдельности, неразобранное поле — умолчание |
| state.json | состояние программы | см. ниже; агенты его не читают |

Оба лога лежат в папке задачи и только дописываются. Программа запоминает длину каждого перед запуском сессии и читает только строки, дописанные после отметки; при повторном запуске оборвавшейся сессии отметка ставится заново.

**Машинный хвост** — текст, который программа добавляет к промптам task-sessions.md; сами промпты не меняются, подстановки в них (`<репозиторий>`, `<источник правок>`, `<способ сдачи>`, `<ответ>`, `<ветка из plan.md>`, `<папка задачи>`) заполняет программа (см. `run`). Общая часть хвоста одинакова для всех сессий и живёт в системном промпте (слой 1 ниже), без подстановок. Сессионная часть подставляется в конец промпта сессии (слой 4): в ней код сессии, единица шага и требования формы, которых промпт не задаёт.

```text
Общая часть (в системном промпте):

Прогресс пиши в progress.log в папке задачи, по строке на каждую завершённую
единицу: «<код сессии> <k>/<N> <подпись>». Первая строка — «<код сессии> 0/<N> старт»,
где N — число единиц, которое ты видишь. Код сессии бери дословно из строки «Сессия:».
Закончив, допиши в profile.log в папке задачи одну строку с рекомендацией для
следующего запуска, какая бы сессия ни пошла по маршруту: «ПРОФИЛЬ от <код сессии>:
класс=<A|B|C> усилие=<1..5> размышление=<вкл|выкл> бюджет=<целое число токенов>
причина=<текст>». Класс A — самая способная модель, B — средняя, C — быстрая; усилие
1 — минимальное, 5 — предельное. Основание — то, что ты замерил: число источников
и их объём, число требований, шагов плана, размер diff, были ли в этой сессии ошибки
понимания. Если останавливаешься, не завершив, первым словом последнего абзаца
своего файла назови вид остановки: ревизия, план, требования или вопрос; в result.md
при этом верни первую строку «Статус: в работе».

Сессионная часть (в конце промпта сессии):

Сессия: <код>. Единица прогресса: <единица из таблицы>.
С1, С1п:            Опись источников — раздел «Опись источников», последняя строка раздела «итого: <число>».
С3, С3п:            Строки DoD — в разделе «DoD», каждая начинается с «[ ]». Шаги плана — раздел «План»,
                    нумерованный список 1., 2., …; имя ветки задачи — отдельной строкой «Ветка: <имя>»
                    в том же разделе. Список решений — раздел «Требует утверждения».
С5, С5д, С5п:       Таблицу трассировки помести в раздел «Трассировка».
С2, С4, С6, С8:     Находки — нумерованным списком, в каждой поля «критичность:» и «уровень:»
                    (у С8 уровень «сдача»). Итоговая строка — первой строкой файла.
С6:                 Строку по пункту 5 начни словами «Секреты в diff:».
С9:                 Замечания — нумерованным списком 1., 2., …, в каждом поля «исход: правлю /
                    отвечаю доводом / отвергаю» и «уровень: требования / план / реализация».
                    Первая строка файла: «Раунд N: правлю K, доводом M, отвергаю R». Последняя строка:
                    «Маршрут: С1 правка», «Маршрут: С3 правка», «Маршрут: С5 правка» или «Маршрут: С7».
КОММИТ, ПУШ:        только «Сессия: <код>. Единиц нет: одна строка «<код> 0/0 старт», строку ПРОФИЛЬ не пиши».
```

`state.json` — память программы между запусками, агенты его не видят. Пишется атомарно (временный файл, затем переименование) после каждого изменения и перед каждыми воротами.

```text
state
├── task_dir, repo_dir, delivery_mode        папка задачи, рабочее дерево, способ сдачи
├── phase                                     РАЗБОР | ПЛАН | РЕАЛИЗАЦИЯ | СДАЧА | ОБРАТНАЯ_СВЯЗЬ | ЗАВЕРШЕНО
├── step                                      ближайшее действие внутри фазы (сессия или ворота); фаза при входе продолжает с него
├── running                                   {сессия, источник, заход, время старта} — ставится до запроса, снимается после проверки форматов
├── next[phase]                               сессия, с которой фаза начинается при возврате, и её источник
├── pass[stage]                               номер следующего захода этапа; при загрузке — не меньше 1 + наибольший N файлов этапа на диске
├── pass_origin[stage]                        заход, от которого считается потолок; сбрасывается каждой правкой по решению владельца
├── clean_streak[stage]                       сколько чистых заходов подряд
├── unaccounted[stage]                        подряд незасчитанных чистых заходов без проб
├── out_of_scope[]                            находки уровня «вне задачи» из заходов С6, ждут решения у В8
├── feedback_round                            номер раунда обратной связи
├── approvals[file]                           {дата, кто, hash содержимого} — утверждения spec.md и plan.md
├── profile_by_phase, hint                    выбранные профили; подсказка агента для следующего запуска (одна, стирается после применения)
├── transcript[author]                        расшифровка живого диалога автора: файл, время старта последнего запроса, срок жизни, профиль
├── prefix[kind]                              kind ∈ {основной, сдача}: {fingerprint, tokens, last_request_started_at, ttl}
├── gates_mode[В*]                            какие ворота переведены в режим «показать и продолжить», решение владельца
└── usage[]                                   по каждому запросу: прочитано из кеша, записано в кеш, без кеша, цена
```

## Сборка запроса и кеш контекста

Кеш контекста у поставщика модели — кеш **префикса**: запрос сравнивается байт в байт от начала до точки отсечки, и любое изменение раньше точки обнуляет всё после неё. Порядок слоёв в запросе: инструменты → системный промпт → сообщения. Отсюда правило сборки: от самого стабильного к самому изменчивому, точки отсечки на границах стабильности.

```text
Слой 0  инструменты              один и тот же набор на все сессии задачи, отсортирован по имени
Слой 1  системный промпт         task-algorithm.md + «Правила» task-sessions.md + общая часть хвоста
                                 ─── отсечка 1: не меняется всю задачу
Слой 2  первое сообщение         материалы из task/ без подпапок task/feedback-*/, в порядке имён по кодам символов
                                 ─── отсечка 2: не меняется всю задачу
Слой 3  второе сообщение         spec.md, затем plan.md — после утверждения, байт в байт
                                 ─── отсечка 3 (только когда слой непуст): пишется заново при каждом утверждении
                                     и при каждом возврате в РАЗБОР или ПЛАН; слои 0–2 при этом читаются из кеша,
                                     заново пишутся только токены spec.md и plan.md — одна запись на фазу
Слой 4  дальше                   промпт сессии с сессионной частью хвоста, изменчивые файлы: result.md,
                                 review-N.md, feedback-N.md, task/feedback-N/ (только у С9), ход диалога
                                 ─── отсечка 4: автоматическая, на последнем блоке, двигается с диалогом
```

У сессий сдачи (С7, С7п, С8, КОММИТ, ПУШ) свой короткий префикс `prefix[сдача]`: слои 0–1 те же, вместо слоёв 2–3 одно сообщение с spec.md, plan.md, result.md и последним review-N.md, без материалов task/; отсечки после слоя 1 и после этого сообщения. Он пересобирается при каждом входе в фазу СДАЧА и после повтора С7. Сессии сдачи не читают кеш старших сессий и не пишут в него; поэтому у них может быть свой класс модели.

Правила, без которых раскладка не работает:

- **В слоях 0–3 нет времени, номеров заходов, кодов сессий и случайных значений.** Всё изменчивое — в слое 4. Один лишний байт в слое 1, например дата в системном промпте, обнуляет кеш всей задачи на каждом запросе.
- **Материалы в слое 2 — только форматы, которые поставщик принимает блоком документа или изображения** (текст, PDF, изображения). Остальное (видео, архивы, выгрузки, код) перечисляется в слое 2 строкой «файл <имя>, <размер> — читай инструментом», сам файл агент читает с диска. Обратная связь в префикс не входит: task/feedback-N/ приходит после сдачи и меняла бы слой 2 каждый раунд.
- **Одна модель на всю задачу.** Кеш привязан к модели: смена класса между сессиями обнуляет кеш целиком. Класс выбирается на задачу; исключение — сдача с её коротким префиксом.
- **Усилие и размышление одинаковы у всех сессий фазы**: автора, проверки и правки. Их смена обнуляет кеш сообщений (слои 2–4), у части моделей и слои 0–1, поэтому проверка с другим усилием, чем у автора, слои 2–3 из кеша не читает. Если поставщик даёт задавать усилие служебным сообщением внутри диалога без сброса кеша, оно идёт в слое 4, усилие уровня запроса фиксируется на всю задачу (ступень фазы РАЗБОР), и усилие можно менять на сессию; иначе только на границе фаз.
- **Правка и продолжение — ход того же диалога.** С1п, С3п, С5п, С5д добавляют ход в диалог автора, если он жив и профиль тот же: тогда читается весь накопленный префикс. Поставщик диалог не хранит: программа сама хранит расшифровку — все ходы байт в байт, включая вызовы инструментов, их результаты и блоки рассуждений, которые поставщик требует возвращать, — в служебной подпапке папки задачи, которую промпты не называют и проверяющие не читают; «продолжить» значит отправить расшифровку целиком плюс новый ход. Если поставщик хранит диалог сам, вместо расшифровки хранится его идентификатор с теми же полями времени. Диалог жив, если с начала его последнего запроса прошло меньше срока жизни отсечки 4 (или его держало поддержание) и профиль совпадает; иначе расшифровка удаляется и сессия идёт новым диалогом. Чтение из кеша стоит доли цены входа на каждом ходе, поэтому очень длинный диалог С5 продолжать дороже, чем начать новый поверх слоёв 0–3: программа сравнивает размер расшифровки с размером слоёв 0–3 и показывает выбор у В2, когда расшифровка больше примерно вдвое.
- **Проверка — новый диалог с тем же префиксом.** С2, С4, С6 обязаны не видеть рассуждений автора, но слои 0–3 у них байт в байт те же, поэтому дорогая часть читается из кеша; свежим остаётся только слой 4.
- **Срок жизни кеша продлевается каждым чтением** и считается от **начала** запроса, который пишет или читает кеш: ход дольше короткого срока (предельное усилие, длинный выход) обнуляет свой же префикс до следующего запроса даже при нулевой паузе; для таких фаз на отсечках 1–3 выбирается длинный срок. По умолчанию срок короткий (минуты); есть длинный (час) за двойную цену записи; записи с длинным сроком должны стоять раньше записей с коротким. Выбор по паузам между запросами с общим префиксом:

| Пауза между запросами | Что делает программа |
|---|---|
| пауза плюс длительность предыдущего запроса меньше короткого срока | ничего: каждый запрос продлевает кеш |
| между коротким и длинным сроком: человек читает находки, отвечает заказчику | либо длинный срок на отсечках 1–3, либо поддержание (ниже) |
| больше часа | при длинном сроке — поддержание, пока оно дешевле перезаписи; при коротком — следующий запрос пишет кеш заново, и это нормально |

- **Поддержание** — тот же запрос с нулевым выходом: он читает кеш и продлевает его за цену чтения. Требования: без потоковой передачи, без структурированного вывода, без принудительного вызова инструментов; та же модель, усилие, размышление и те же отсечки, что у настоящего запроса, иначе поддерживается чужая запись. Период — срок жизни самой короткой живой отсечки минус минута, отсчёт от старта предыдущего запроса. Потолок — пока суммарная цена поддержания меньше цены перезаписи: при чтении в десятую долю входа это около 45 минут для короткого срока и около 19 часов для длинного; числа — пример, программа считает по формуле `keep_alive`, цена каждого вызова пишется в usage и показывается у ворот.
- **Фан-аут не раньше первого ответа.** Если программа запускает несколько сессий параллельно, первая должна начать отвечать, прежде чем стартуют остальные: иначе все пишут кеш, никто не читает.
- **Проверка после каждого запроса.** Ожидаемое чтение — токены отправленного префикса (`prefix[kind].tokens`) по счётчику поставщика. Тревога «кеш не читается», если отпечаток того же префикса не изменился (модель, усилие, размышление, байты), от начала прошлого запроса этого префикса прошло меньше срока жизни, а прочитано из кеша меньше 90 % ожидаемого. Если при этом записано в кеш больше нуля — это перезапись, и в log.md идёт её причина: истёк срок, сменилась модель или усилие, обновлён слой 3; сравнение слоёв делается только при разных отпечатках. Молчаливая потеря кеша стоит дороже всего, потому что ничего не ломается.
- **Объём.** Предел входа профиля = окно контекста модели его класса − максимум выхода − запас на ход диалога (не меньше четверти окна). Для нового диалога считаются токены префикса и промпта, для продолжения — токены расшифровки плюс ход; счётчик поставщика, моделью выбранного профиля, перед каждым запуском и после каждой пересборки префикса. Расшифровка не помещается — диалог закрывается, сессия идёт новым диалогом, строка в log.md. Новый диалог не помещается — программа не режет молча, а останавливается у В1: решает человек (разбить задачу, поднять класс, убрать лишнее из task/). Столбец «Ожидаемый вход» в таблице профилей — для оценки цены, не предел.

## Профили запуска

Класс модели — на задачу, усилие и размышление — на фазу, ожидаемый вход — на сессию. Умолчания (одно значение в клетке; подсказка агента и человек могут поднять):

| Фаза | Сессии | Класс | Усилие | Размышление | Ожидаемый вход |
|---|---|---|---|---|---|
| РАЗБОР | С1, С1п, С2 | A | 4 | вкл | материалы + spec + 60 тыс. |
| ПЛАН | С3, С3п, С4 | A | 5 | вкл | spec + код по карте + 80 тыс. |
| РЕАЛИЗАЦИЯ | С5, С5д, С5п, С6 | A | 4; 5 на всю фазу, если затронуты безопасность, деньги или данные — решает человек у В2 перед С5, подсказку даёт ПРОФИЛЬ от С3 или С4 | вкл | план + код + result + diff + 200 тыс.; при длинном прогоне — лимит на выход, если поставщик его даёт |
| СДАЧА | С7, С7п, С8 | B | 2 | выкл, если модель позволяет | spec + plan + result + review + 20 тыс. |
| СДАЧА | КОММИТ, ПУШ | B | 1 | выкл, если модель позволяет | diff + 10 тыс. |
| ОБРАТНАЯ_СВЯЗЬ | С9 | A | 3 | вкл | материалы + spec + result + feedback + 40 тыс. |

**Подсказка агента.** После каждой сессии, кроме КОММИТ и ПУШ, агент пишет строку `ПРОФИЛЬ от <код>`. Она действует на один следующий запуск, какая бы сессия ни пошла по маршруту, и стирается после него; в log.md — «ПРОФИЛЬ от <код> применён к <код>». Порядок сравнения: класс C < B < A, усилие 1 < … < 5, размышление выкл < вкл, бюджет — по числу. Правила:

- совет выше по классу берётся только там, где умолчание допускает выбор (фаза СДАЧА); в остальных фазах класс задачи не меняется, совет пишется в log.md;
- совет выше по усилию берётся без вопроса, только если поставщик меняет его сообщением внутри диалога без сброса кеша; иначе это В2 с пометкой «смена перепишет кеш слоёв 2–4 и закроет диалог автора», а на границе фазы применяется сразу; совет включить размышление — только на границе фазы;
- для сессий «тот же диалог» (С1п, С3п, С5п, С5д) профиль диалога не меняется, совет только записывается;
- совет ниже показывается человеку всегда, даже когда В2 переведены в режим «не спрашивать при совпадении с умолчанием»;
- «выкл» при усилии, с которым модель не принимает выключение, программа понижает до допустимого и пишет это в log.md;
- совета нет или строка не разобрана — умолчание, в log.md строка «ПРОФИЛЬ не получен от <код>».

Выбранный профиль пишется в state.json и показывается у В2 вместе с ценой, которую программа оценивает по токенам слоёв.

## Протокол прогресса

1. До запуска программа считает N по таблице единиц и показывает `шаг 0/N`; если считать нечем — `?/?`.
2. Агент пишет строки в progress.log; программа следит за файлом от отметки, поставленной перед запуском, и обновляет `k/N`. N для показа — из последней строки агента, если он его назвал.
3. Если файл не растёт дольше порога (умолчание 10 минут) и запрос ещё не завершён, программа не вмешивается, а показывает «без прогресса <минут>»: длинный ход без строк — нормально для реализации и подозрительно для проверки, решает человек.
4. По завершении запроса программа сверяет артефакт с progress.log: число строк `шаг n: сделан` в result.md против строк прогресса С5, число находок против N у правки. Расхождение — строка в log.md, не остановка.
5. Прогресс задачи — фаз завершено из пяти; прогресс фазы — заход j/ПОТОЛОК текущего повтора и шаг k/N текущей сессии.

## Алгоритм

Псевдокод. Коды сессий — из словаря; `gate(В*)` — ворота, ждут человека; `run(...)` — один запуск агента; `loop_review(...)` — повтор «проверка → правка» по «Правилам» task-sessions.md. Все функции сохраняют state после каждого изменения. Внутри фазы каждое действие перед запуском пишет `state.step`, и при входе в фазу выполнение продолжается с него, а не с первой строки.

```text
алгоритм run_task(task_dir, repo_dir):
    state ← load_or_init(task_dir)
    prepare(state)                                   # раздел «Подготовка» task-sessions.md + блокировка (ниже)
    prefix[основной] ← build_prefix(state)
    если state.running: run(state.running.сессия, source=state.running.источник, pass=state.running.заход)   # оборванная сессия заново

    пока state.phase ≠ ЗАВЕРШЕНО:
        reconcile_approvals(state)                   # файл «утверждено» с чужим hash → invalidate, log
        выбор state.phase:                           # вход в фазу — со state.step

        РАЗБОР:
            если state.next[РАЗБОР]:
                (s, src) ← state.next[РАЗБОР]; state.next[РАЗБОР] ← ∅
                fixed ← run(s, source=src)
                если fixed = stopped(«вопрос»): answers ← gate(В4); write_answers(spec.md, answers); run(С1п, source=«Ответы»); owner_fix(spec); continue
            иначе если нет spec.md: run(С1)
            verdict ← loop_review(spec)
            выбор verdict:
                route(«требования»): run(С1п, source=verdict.source); continue        # остаёмся в РАЗБОР
                stopped(«вопрос»):   answers ← gate(В4); write_answers(spec.md, answers); run(С1п, source=«Ответы»); owner_fix(spec); continue
                clean:               пропуск
            answers ← gate(В4)                       # вопросы и сценарии заказчику; текст и источник каждого ответа
            если answers непусты:
                write_answers(spec.md, answers); run(С1п, source=«Ответы»); owner_fix(spec)
                если answers меняют цель, границы или сценарии: continue            # loop_review заново
            gate_approve(spec.md)                    # В5
            prefix[основной] ← build_prefix(state)   # слой 3 теперь содержит spec.md
            state.phase ← ПЛАН

        ПЛАН:
            если state.next[ПЛАН]:
                (s, src) ← state.next[ПЛАН]; state.next[ПЛАН] ← ∅
                fixed ← run(s, source=src)
                выбор fixed:
                    stopped(«требования»): to_requirements(source=«последний абзац plan.md»); continue
                    stopped(«вопрос»):     answer ← gate(В7); если answer.level = «реализация»: log(«умолчание подтверждено»)
                                           иначе: route_answer(answer); continue
            иначе если нет plan.md: run(С3)
            если stop_word(plan.md) = «требования»: to_requirements(source=«последний абзац plan.md»); continue
            verdict ← loop_review(plan)
            выбор verdict:
                route(«требования»): to_requirements(source=verdict.source); continue
                stopped(«вопрос»):   answer ← gate(В7)
                                     если answer.level = «реализация»: log(«умолчание подтверждено»)   # дальше В6
                                     иначе: route_answer(answer); continue
                clean:               пропуск
            decisions ← gate(В6)                     # раздел «Требует утверждения»
            write_decisions(plan.md, decisions)
            если decisions меняют шаги, карту или DoD: run(С3п, source=«решено»); owner_fix(plan); continue
            gate_approve(plan.md)                    # В5
            prefix[основной] ← build_prefix(state)   # слой 3: spec.md + plan.md
            state.phase ← РЕАЛИЗАЦИЯ

        РЕАЛИЗАЦИЯ:
            если state.next[РЕАЛИЗАЦИЯ]:
                (s, src) ← state.next[РЕАЛИЗАЦИЯ]; state.next[РЕАЛИЗАЦИЯ] ← ∅
                outcome ← run(s, source=src)         # С5п после находок или обратной связи, С5д после ответа
            иначе если нет result.md или status(result.md) = «в работе»:
                outcome ← run(С5)                    # старт или возобновление: С5 сам читает result.md
            иначе:
                outcome ← done                       # result.md готов: сразу проверка
            пока outcome ≠ done:
                выбор outcome:
                    stopped(«ревизия») | stopped(«план»): to_plan(source=«последний абзац result.md»); выйти во внешний цикл
                    stopped(«требования»): to_requirements(source=«последний абзац result.md»); выйти во внешний цикл
                    stopped(«вопрос»):
                        answer ← gate(В7)            # текст, источник, уровень ответа называет человек
                        если answer.level = «реализация»: log(«умолчание подтверждено»); outcome ← run(С5д, answer)
                        иначе: route_answer(answer); выйти во внешний цикл
            verdict ← loop_review(review)
            выбор verdict:
                route(«план»):       state.next[РЕАЛИЗАЦИЯ] ← (С5п, verdict.source); to_plan(source=verdict.source); continue
                route(«требования»): state.next[РЕАЛИЗАЦИЯ] ← (С5п, verdict.source); to_requirements(source=verdict.source); continue
                stopped(«вопрос»):   answer ← gate(В7)
                                     если answer.level = «реализация»: state.next[РЕАЛИЗАЦИЯ] ← (С5п, последний review-N.md + ответ как FACT)
                                     иначе: state.next[РЕАЛИЗАЦИЯ] ← (С5п, answer); route_answer(answer)
                                     continue
                clean:               пропуск
            decisions ← gate(В8, строки FAIL / NOT VERIFIED / Known limitations, state.out_of_scope)
            write_owner_marks(result.md, decisions); state.out_of_scope ← ∅; owner_fix(review)
            если среди decisions «закрыть руками»: gate(В8, «подтвердите, что закрыто»); state.clean_streak[review] ← 0; continue
            если среди decisions «урезать объём»: state.next[РЕАЛИЗАЦИЯ] ← (С5п, «решение владельца»); to_requirements(source=decisions); continue
            state.phase ← СДАЧА

        СДАЧА:
            если есть строка FAIL / NOT VERIFIED / Known limitations без «решение владельца:»: gate(В8); continue
            если state.feedback_round > 0 и есть delivery/customer.md и нет delivery/customer-<round>.md:
                rename(delivery/customer.md → delivery/customer-<round>.md)
            prefix[сдача] ← build_prefix_delivery(state)
            run(С7, delivery_mode=state.delivery_mode)
            verdict ← loop_review(delivery)
            выбор verdict:
                restart:             continue        # С7 заново после С5п по решению владельца
                route(«план»):       state.next[РЕАЛИЗАЦИЯ] ← (С5п, verdict.source); to_plan(source=verdict.source); continue
                route(«требования»): state.next[РЕАЛИЗАЦИЯ] ← (С5п, verdict.source); to_requirements(source=verdict.source); continue
                stopped(«вопрос»):   answer ← gate(В7)
                                     если answer.level = «реализация»: log(«умолчание подтверждено»); continue      # С7 заново
                                     иначе: state.next[РЕАЛИЗАЦИЯ] ← (С5п, answer); route_answer(answer); continue
                clean:               пропуск
            если в последнем review-N.md нет строки «Секреты в diff:»: gate(В12)
            если diff рабочего дерева с последним коммитом пуст:                  # сдача только текстов
                log(«сдача без изменений кода»); gate(В10г); state.phase ← ОБРАТНАЯ_СВЯЗЬ; continue
            gate(В10а)                               # коммит: показать commit.txt, ветку, состояние дерева
            run(КОММИТ)                              # промпт «Вы после С8» без пуша
            если сообщение последнего коммита ≠ commit.txt байт в байт: gate(В10б)
            gate(В10в)                               # пуш: показать сообщение из истории
            run(ПУШ)
            gate(В10г)                               # отправка customer.md заказчику — делает человек
            state.phase ← ОБРАТНАЯ_СВЯЗЬ

        ОБРАТНАЯ_СВЯЗЬ:
            fb ← gate(В11)
            если fb = завершить: state.phase ← ЗАВЕРШЕНО; continue
            state.feedback_round += 1; save(task/feedback-<round>/, fb)
            run(С9)
            owner_fix(все этапы)                     # потолок считается от этой правки
            выбор parse_route(feedback-<round>.md):
                «С1 правка»: state.next[РЕАЛИЗАЦИЯ] ← (С5п, feedback-<round>.md); to_requirements(source=feedback-<round>.md)
                «С3 правка»: state.next[РЕАЛИЗАЦИЯ] ← (С5п, feedback-<round>.md); to_plan(source=feedback-<round>.md)
                «С5 правка»: state.next[РЕАЛИЗАЦИЯ] ← (С5п, feedback-<round>.md); state.phase ← РЕАЛИЗАЦИЯ
                «С7»:        state.phase ← СДАЧА

    снять блокировку; show(«задача завершена»)


алгоритм to_requirements(source):
    invalidate(spec.md); invalidate(plan.md)         # план строится на требованиях и заново проходит С3п и С4
    state.next[РАЗБОР] ← (С1п, source)
    state.next[ПЛАН]   ← (С3п, source + «Изменения захода N» или «Ответы» в spec.md)   # и находки уровня «план» из того же файла
    state.phase ← РАЗБОР

алгоритм to_plan(source):
    invalidate(plan.md); state.next[ПЛАН] ← (С3п, source); state.phase ← ПЛАН

алгоритм route_answer(answer):                       # уровни «план» и «требования»; «реализация» разбирается в фазе
    «план»:       to_plan(source=answer)
    «требования»: to_requirements(source=answer)

алгоритм owner_fix(stage):                           # правка по решению владельца: «Потолок» task-sessions.md
    state.pass_origin[stage] ← state.pass[stage]


алгоритм loop_review(stage):
    пока state.clean_streak[stage] < ЧИСТЫХ_ПОДРЯД:
        n ← state.pass[stage]
        review ← run(checker(stage), pass=n)         # run не возвращает ошибок: В13 внутри
        summary ← parse_summary(review)
        если summary отсутствует: все находки существенные; log(«итоговой строки нет»)
        если summary.K = 0 и summary.P < ПРОБ_В_ЧИСТОМ:
            log(«заход n: чистый без проб, не засчитан»); state.pass[stage] += 1
            state.unaccounted[stage] += 1; если state.unaccounted[stage] ≥ 2: gate(В13, «проверка второй раз без проб»)
            continue                                 # проверка заново, правка не нужна
        state.unaccounted[stage] ← 0
        verdict ← gate(В3, review)                   # человек читает находки и пробы; может поднять критичность
                                                     # или не засчитать чистый заход, если пробы — не пробы;
                                                     # возвращает существенные находки с уровнями, без уровня «вне задачи»:
                                                     # те копятся в state.out_of_scope для В8
        state.pass[stage] += 1
        если verdict = не_засчитан: log(«заход n: пробы — не пробы, не засчитан»); continue
        если verdict.K = 0: state.clean_streak[stage] += 1; continue
        state.clean_streak[stage] ← 0
        если n − state.pass_origin[stage] + 1 ≥ ПОТОЛОК_ЗАХОДОВ:        # существенные остались после потолка
            choice ← gate(В9, все находки этапа)
            owner_fix(stage)
            выбор choice:
                «урезать объём»:      вернуть route(«требования», source=review)
                «спросить заказчика»: вернуть stopped(«вопрос»)
                «остановиться»:       только stage ∈ {review, delivery}:
                                      run(С5п, source=«решение владельца: не делаю, <дата>»)
                                      если stage = delivery: вернуть restart       # С7 заново
                                      вернуть clean
                «ещё заход»:          пропуск        # дальше правка по находкам этого захода
        levels ← уровни существенных находок из verdict
        если «требования» ∈ levels: вернуть route(«требования», source=review)
        если «план» ∈ levels и stage ∈ {review, delivery}: вернуть route(«план», source=review)
        fixed ← run(fixer(stage), source=review, pass=n)      # ход диалога автора, если жив
        выбор fixed:
            stopped(«вопрос»):  вернуть stopped(«вопрос»)
            stopped(«ревизия»): вернуть route(«план», source=артефакт автора)
            stopped(w):         вернуть route(w, source=артефакт автора)
    state.clean_streak[stage] ← 0                    # следующий цикл по этому этапу начнётся заново
    вернуть clean


алгоритм run(session, source?, pass?):
    state.step ← session; save(state)
    N ← count_units(session)
    profile ← choose_profile(session, defaults, state.hint); state.hint ← ∅
    gate(В2, profile, оценка цены)
    prompt ← PROMPTS[session] + TAIL_SESSION(session)
        # подстановки: <репозиторий> ← state.repo_dir; <папка задачи> ← state.task_dir; <источник правок> ← source;
        # <способ сдачи: …> ← state.delivery_mode; <ответ>, <кто ответил или какой документ> ← answer.text, answer.source;
        # <ветка из plan.md> ← строка «Ветка:» раздела «План» plan.md. Агент запускается из task_dir.
    kind ← сдача если session ∈ {С7, С7п, С8, КОММИТ, ПУШ} иначе основной
    если session ∈ {С1п, С3п, С5п, С5д} и dialog_alive(author(session), profile):
        conv ← continue(state.transcript[author(session)])
        если не помещается(conv + prompt, profile): закрыть диалог; conv ← new(prefix[kind]); log(«расшифровка не помещается»)
    иначе:
        conv ← new(prefix[kind])
    check_budget(conv + prompt, profile)             # В1 — только если не помещается новый диалог
    off_p ← размер(progress.log); off_h ← размер(profile.log)
    state.running ← {session, source, pass, now}; save(state)
    response ← call_model(conv, prompt, profile, stream=вкл)
        # перед каждым запросом (и каждым ходом с инструментами): state.prefix[kind].last_request_started_at ← время старта; save
        # временная ошибка (лимит частоты, перегрузка, сбой) → повтор до 3 раз с растущей паузой, тот же диалог
        # выход обрезан по лимиту → один ход «продолжи с места обрыва», затем ошибка
        # постоянная ошибка или отказ модели → gate(В13): «повторить» — заново этот же run; «остановить» — выход из программы
    параллельно: tail(progress.log, от off_p) → k/N
    record_usage(response.usage); check_cache(response, kind)      # правило «Проверка после каждого запроса»
    если session ∉ {КОММИТ, ПУШ}: state.hint ← parse(profile.log, от off_h) или ∅ с log(«ПРОФИЛЬ не получен от <код>»)
    если артефакта сессии нет: gate(В13, последнее сообщение агента)       # «повторить» / «остановить»
    verify_formats(артефакт)
        # нарушены → один ход «исправь форму файла: …» в том же диалоге; снова нарушены → gate(В13)
    если session — автор или правка:
        state.transcript[author(session)] ← {conv, started_at = state.prefix[kind].last_request_started_at, ttl, profile}
    state.running ← ∅; save(state)
    вернуть outcome(артефакт)
        # статус «готово» или файл без стоп-слова → done; стоп-слово в последнем абзаце → stopped(слово)


алгоритм gate(В*, …):
    state.step ← В*; save(state)
    пока ворота открыты:
        keep_alive(conv_next)                        # conv_next — расшифровка автора текущего этапа, если жива
                                                     # (её чтение продлевает и слои 0–3), иначе new(prefix текущей фазы)
    показать, ждать решения; при потолке поддержания расшифровка считается мёртвой и удаляется


алгоритм build_prefix(state):
    layer0 ← tools, отсортированные по имени
    layer1 ← read(task-algorithm.md) + rules(task-sessions.md) + TAIL_COMMON
    layer2 ← файлы task/ кроме task/feedback-*/, порядок по кодам символов имени;
             принимаемые форматы — блоками, остальные — строкой «файл <имя>, <размер> — читай инструментом»
    layer3 ← [spec.md если утверждён] + [plan.md если утверждён]
    отсечки: после layer1, после layer2, после layer3 (если непуст); четвёртая — автоматическая на хвосте
    срок жизни отсечек 1–3: длинный, если ожидаемая пауза у ворот или длительность хода больше короткого срока
    state.prefix[основной] ← {fingerprint = hash(класс, усилие, размышление, bytes(layer0..layer3)), tokens, ttl}
    вернуть (layer0, layer1, layer2, layer3)

алгоритм build_prefix_delivery(state):               # при каждом входе в СДАЧА и после restart
    слои 0–1 те же; одно сообщение: spec.md, plan.md, result.md, последний review-N.md
    отсечки после слоя 1 и после этого сообщения
    state.prefix[сдача] ← {fingerprint, tokens, ttl}


алгоритм keep_alive(conv):                           # пока открыты ворота
    период ← срок жизни самой короткой живой отсечки conv − минута
    потолок ← (цена записи − цена чтения) / цена чтения × период
    каждые период от старта предыдущего запроса, пока ожидание < потолок:
        call_model(conv, нулевой выход, без потока, без принудительного вызова инструментов,
                   без структурированного вывода; та же модель, усилие, размышление, отсечки)


алгоритм invalidate(file):
    первая строка file ← «Статус: черновик»; approvals[file] ← ∅
    закрыть диалоги, в слое 3 которых был file: plan.md — диалог С5; spec.md — диалоги С3 и С5
        # диалог автора файла (С1 для spec.md, С3 для plan.md) не закрывается: его слои 0–3 не изменились,
        # правка идёт его ходом, если он жив
    prefix[основной] ← build_prefix(state)


алгоритм gate_approve(file):                         # В5
    если status(file) = утверждено и (нет approvals[file] или approvals[file].hash ≠ hash(file)):
        показать первую строку, спросить «это ваше утверждение?»; нет → первая строка ← «Статус: черновик»; log
    ждать подтверждения человека в программе, что он поставил «Статус: утверждено, <дата>, <кто>»
    approvals[file] ← {дата, кто, hash(file)}

алгоритм reconcile_approvals(state):                 # при загрузке и перед каждым run
    для file ∈ {spec.md, plan.md}: если status = утверждено и hash(file) ≠ approvals[file].hash:
        invalidate(file); log(«правка после утверждения, статус снят»)   # правило task-sessions.md


алгоритм load_or_init(task_dir):
    state ← read(state.json) или пустое
    если state.running непусто: файл захода, начатый оборвавшейся сессией, переименовать в *.partial.md
    для каждого stage: pass[stage] ← max(state.pass[stage], 1 + наибольший N файлов этапа на диске);
                       pass_origin[stage] ← state.pass_origin[stage] или pass[stage]
    если state.step — ворота: показать их заново и сверить с файлами (статус «утверждено», «решено:», пометка владельца,
        коммит с текстом commit.txt в истории); решение уже в файле → просить подтвердить, а не повторять сессии
    вернуть state                                    # оборванную сессию перезапускает run_task по state.running


алгоритм prepare(state):                             # идемпотентен
    проверки раздела «Подготовка» task-sessions.md
    создать task_dir/runner.lock с идентификатором процесса; занят живым процессом → остановиться
    в служебной папке системы контроля версий рабочего дерева (не попадает в diff) — файл с путём папки задачи;
        принадлежит другой задаче → gate(«дерево занято другой задачей»)
    первый коммит, если кода нет, — только если истории ещё нет
```

## Ворота

Места, где программа ждёт человека; ворота в псевдокоде — только из этого списка. Содержание действий человека не повторяется: оно в абзацах «Вы после …» task-sessions.md.

| Ворота | Где | Что решает человек |
|---|---|---|
| В1 | перед запуском нового диалога | материалы не помещаются в предел входа |
| В2 | перед каждой сессией | профиль запуска и его цена; продолжать ли длинный диалог автора |
| В3 | после каждой проверки | читает все находки и пробы; может поднять критичность или не засчитать чистый заход, если пробы — не пробы; засчитывает заход |
| В4 | после С2 | «Вы после С2»: вопросы и сценарии заказчику; текст и источник каждого ответа |
| В5 | после В4 и В6 | ставит «Статус: утверждено» в spec.md, затем в plan.md |
| В6 | после С4 | «Вы после С4»: решения из раздела «Требует утверждения» |
| В7 | остановка «вопрос» | текст, источник и уровень ответа: реализация, план, требования |
| В8 | после С6 | «Вы после С6»: решение по каждой строке FAIL, NOT VERIFIED, Known limitations и по находкам «вне задачи»; подтверждение «закрыто руками» |
| В9 | потолок заходов | урезать объём, спросить заказчика, остановиться, ещё заход |
| В10а–г | сдача | коммит; сообщение коммита изменено; пуш после чтения сообщения из истории; отправка заказчику («Вы после С8») |
| В11 | после сдачи | обратная связь или завершение задачи |
| В12 | перед коммитом | в последнем review-N.md нет строки «Секреты в diff:» |
| В13 | любая сессия | сессия не завершилась, артефакта нет, форма не исправлена со второй попытки, первая строка статуса не разобрана, проверка второй раз подряд без проб: повторить или остановить программу |

Отключаемы только ворота, у которых есть действие по умолчанию, не требующее записи человека: В2 (профиль равен умолчанию), В3 (засчитать заход как написано — человек вправе отказаться от этого права на задачу), В4 и В6 при пустом списке. В5, В7, В8, В10 требуют записи человека в файл или действия вне программы: статус «утверждено», ответ, пометку владельца, пуш и отправку заказчику программа без человека не ставит и не делает. В1, В9, В11, В12, В13 — решения без умолчания. Решение об отключении пишется в state.json по идентификатору ворот.

## Что проверить в программе до первой задачи

- Два запроса подряд с одинаковыми слоями 0–3 показывают чтение из кеша, близкое к размеру этих слоёв; смена промпта сессии в слое 4 этого не меняет; проверка в новом диалоге читает слои 0–3.
- Поддержание не отклоняется поставщиком и после него чтение из кеша сохраняется; период считается от старта предыдущего запроса.
- Смена усилия между сессиями одной фазы ловится как перезапись с причиной в log.md; запрос сдачи сверяется с отпечатком префикса сдачи, а не основного.
- Строка `Заход N: …` разбирается на всех четырёх видах файлов проверки; файл без строки даёт «все находки существенные», а не «чистый заход»; чистый заход без проб не засчитывается и не запускает правку; второй подряд — В13.
- Счётчик единиц даёт верное N на образце spec.md, plan.md и feedback-N.md; progress.log с другим N и строки прошлых запусков не ломают отображение.
- Потолок срабатывает после ПОТОЛОК_ЗАХОДОВ заходов с существенными находками, считая от последней правки по решению владельца; «ещё заход» ведёт к правке, а не к повторной проверке того же артефакта.
- Маршрут «требования» переводит и spec.md, и plan.md в «черновик» и ставит С1п и С3п в очередь; возврат в РЕАЛИЗАЦИЯ после этого запускает С5п, а не С5; готовый result.md без очереди ведёт сразу к С6.
- Остановка С5 или С5п с каждым из четырёх слов ведёт в свой маршрут; остановка С5п видна, потому что статус result.md возвращён в «в работе»; ответ уровня «реализация» продолжает диалог С5.
- Файл со статусом «утверждено», изменённый после утверждения, переводится в «черновик» до запуска следующей сессии, и его диалоги в слое 3 закрываются.
- После обрыва процесса на любой сессии перезапуск повторяет ту же сессию тем же промптом, продолжает фазу со state.step и не перезаписывает существующие файлы заходов.
- КОММИТ не пушит; сообщение коммита сверяется с commit.txt до ворот пуша; сдача без изменений кода пропускает коммит и пуш.
- Повторная сдача не затирает customer-<round>.md прошлого раунда.
