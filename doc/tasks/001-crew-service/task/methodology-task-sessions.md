# Выполнение задания агентом: сессии, промпты, повторы

Схема для минимального случая: есть только ИИ-агент, задание заказчика и этот репозиторий; трекера и команды нет. Это урезанное применение методологии (README, раздел 3): человек совмещает роли владельца и оркестратора, агент в разных сессиях играет исполнителя и проверяющего. Работа внутри каждой сессии идёт по [task-algorithm.md](task-algorithm.md), правила повторов взяты из README, раздел 10, требования к текстам наружу — из раздела 12.

Планирование и реализация разделены точкой утверждения плана. Между ними может пройти любое время, и их могут выполнять разные агенты: всё состояние лежит в файлах, промпты не опираются на прошлые разговоры.

Как вести этот цикл программой — запускать сессии, считать заходы, показывать прогресс по шагам, собирать запросы под кеш контекста — описано в [task-runner.md](task-runner.md). Форматы строк, которые программа читает из файлов цикла, заданы там же: часть из них требуют промпты ниже, остальное программа дописывает к промпту машинным хвостом.

## Схема

```
Подготовка (вы)
   ↓
С1 Разбор ─────────────────→ spec.md (черновик)
   ↓
С2 Проверка разбора ───────→ spec-review-N.md
   ├─ есть существенные ──→ С1 правка ──→ С2 заново
   ↓ два захода подряд без существенных
Вы: вопросы заказчику, ответы, подтверждение сценариев
   ├─ ответ меняет цель, границы, сценарии ──→ С1 правка ──→ С2
   ↓
spec.md: «утверждено»                              ══ граница 1 ══
   ↓
С3 План ───────────────────→ plan.md (черновик, базовая ревизия)
   ↓
С4 Проверка плана ─────────→ plan-review-N.md
   ├─ есть существенные ──→ С3 правка ──→ С4 заново
   ├─ план требует менять требования ──→ С1 правка ──→ С2 ──→ граница 1 ──→ С3 правка
   ↓ два захода подряд без существенных
Вы: решения из списка «требует утверждения»
   ├─ решение меняет план ──→ С3 правка ──→ С4
   ↓
plan.md: «утверждено»                              ══ граница 2 ══
   ↓            любое время, любой агент
С5 Реализация ─────────────→ код + result.md (ведётся по ходу)
   ├─ остановка «ревизия» или «план» ──→ С3 правка ──→ С4 ──→ граница 2 ──→ С5
   ├─ остановка «вопрос» ──→ вы отвечаете ──→ маршрут по уровню ответа (ниже)
   ↓ result.md: «Статус: готово»
С6 Проверка реализации ────→ review-N.md
   ├─ уровень «реализация» ──→ С5 правка ──→ С6 заново
   ├─ уровень «план» ────────→ С3 правка ──→ С4 ──→ граница 2 ──→ С5 правка ──→ С6
   ├─ уровень «требования» ──→ С1 правка ──→ С2 ──→ граница 1 ──→ С3 правка ──→ …
   ↓ два захода подряд без существенных
Вы: решение по строкам FAIL, NOT VERIFIED, Known limitations
   ↓
С7 Сдача ──────────────────→ delivery/
   ↓
С8 Проверка сдачи ─────────→ delivery-review-N.md
   ├─ есть существенные ──→ С7 правка ──→ С8 заново
   ↓ два захода подряд без существенных
Вы: коммит и пуш, отправка заказчику
   ↓
Обратная связь ──→ С9 Разбор обратной связи ──→ feedback-N.md
   ├─ требования ──→ С1 правка ──→ С2 ──→ граница 1 ──→ С3 правка ──→ … ──→ С8
   ├─ план ────────→ С3 правка ──→ С4 ──→ граница 2 ──→ С5 правка ──→ … ──→ С8
   ├─ реализация ──→ С5 правка ──→ С6 ──→ С7 ──→ С8
   └─ только «отвечаю доводом» и «отвергаю» ──→ С7 ──→ С8
```

**Маршрут ответа по уровню**, кто бы ни ответил и когда бы ответ ни пришёл: ответ не меняет spec.md и plan.md → «С5 продолжение», подтверждение умолчания — строкой в log.md; ответ меняет план → С3 правка; ответ меняет требования, границы или сценарии → С1 правка. Сделанные срезы остаются в рабочем дереве, С5 после повторного утверждения возобновляется по result.md.

## Подготовка

1. Создайте папку задачи рядом с папкой кода и скопируйте в неё task-algorithm.md из этого репозитория: промпты называют файлы относительно папки задачи. Заведите пустой log.md.
2. Всё от заказчика положите в task/ как есть; текст сообщения и ссылки — файлом task/message.md.
3. Каждую сессию запускайте из папки задачи, промпт вставляйте целиком первым сообщением. `<репозиторий>` замените абсолютным путём к рабочему дереву кода на ветке задачи. Если агент не пишет за пределы папки запуска, запускайте его из папки кода и первой строкой промпта дайте «Папка задачи: <путь>»: имена файлов читаются относительно неё.
4. Одна задача — одна папка задачи и одно рабочее дерево без чужих незакоммиченных правок: две задачи в одном дереве смешают diff для С6 и коммит после С8.
5. Если кода ещё нет: создайте папку кода, инициализируйте в ней систему контроля версий и сделайте первый коммит до С1. Без него нет базовой ревизии для plan.md, сверки в С5 и diff для С6. Выбор стека агент делает в С1 по шагу 6 и выносит в С3 в список «требует утверждения»; создаваемые файлы в карте помечаются «новый».
6. Новая сессия — новый чат или новый запуск агента без истории предыдущих. Оборвавшуюся сессию запускайте заново тем же промптом: промпты читают состояние из файлов.

```text
task-algorithm.md
task/                  всё от заказчика как есть
task/feedback-N/       обратная связь после сдачи
spec.md                спецификация; статус в первой строке
spec-review-N.md
plan.md                план; статус и базовая ревизия в первых строках
plan-review-N.md
result.md              отчёт реализации, ведётся по ходу; статус в первой строке
review-N.md
delivery/              тексты наружу
delivery-review-N.md
feedback-N.md          разбор обратной связи
log.md                 ваш журнал: на каждый заход первая строка его файла проверки
                       и ваше решение (следующая сессия или остановка)
```

## Правила

- **Всё состояние в файлах.** Любую сессию можно начать заново любым агентом.
- **Статус в первой строке spec.md и plan.md:** «Статус: черновик» или «Статус: утверждено, дата, кто»; форма строки одна, её читает программа (task-runner.md). Утверждение ставите только вы. Любая правка после утверждения возвращает статус «черновик», и документ заново проходит проверку и утверждение.
- **Реализация начинается только с утверждённых spec.md и plan.md.** Если план реализуется не сразу, он сначала сверяется с кодом по базовой ревизии.
- **Проверка всегда в новой сессии**, не в той, что писала. Правку можно делать в любой сессии.
- **Существенная находка** меняет требования, границы, сценарий, план, доказательство, число или то, что уйдёт заказчику. Находка без названной критичности считается существенной. Поверхностной проверяющий называет находку только с записанной причиной, почему она не меняет ничего из этого списка; находка про число, доказательство, сценарий или текст наружу поверхностной быть не может. Засчитывая заход, вы читаете все находки, а не итог, и вправе поднять критичность.
- **Отклонённая исполнителем находка закрывается не им.** Следующий заход проверки сверяет обоснование с материалами и кодом: согласен — закрывает; не согласен — повторяет находку как существенную с доводом. Отклонённую дважды решаете вы.
- **Остановка** наступает после двух заходов проверки подряд без существенных находок.
- **Чистый заход засчитывается только с тремя пробами.** Проба это команда с дословным выводом либо перечень осмотренного с числом и с тем, что там точно есть и что нашлось (README, разделы 10 и 13). «Прочитал и сравнил» пробой не является: такой заход чистым не засчитывается и идёт заново.
- **Потолок четыре захода на этап**, считая от последней правки по вашему решению или по обратной связи. Если существенные находки остаются, вы решаете: урезать объём — правка spec.md, дальше по схеме; спросить заказчика — вопрос с умолчанием и сроком; остановиться — С5 правка с исходом «не делаю: решение владельца, дата», открытые находки уходят в Known limitations result.md, дальше С7.
- **N — номер захода.** Внутри этапа не обнуляется: после обратной связи следующий файл проверки получает номер за последним существующим, иначе прежний перезапишется. У feedback-N свой счётчик — номер раунда обратной связи. В промптах правки N файла с находками и N в «Изменения захода N» один и тот же.

## Промпты

**С1 Разбор**

```text
Прочитай task-algorithm.md целиком. Выполни шаги 1–7 по материалам в папке task
и по коду в <репозиторий>. Результат запиши в spec.md, первая строка «Статус: черновик»:
1. Опись источников: каждый файл, картинка, ссылка, страница, таймкод видео;
   статус: прочитан / прочитан частично (что не получено) / недоступен; итого число.
2. Таблица покрытия: каждое утверждение, пометка, требование из материалов →
   REQ или AC с номером, constraint, либо «не требование: причина» — только для контекста
   и справки; пожелание это REQ с пометкой «желательное». Ни один фрагмент не пропускать.
3. Спецификация шага 3; FACT / INFERENCE / UNKNOWN, у каждого источник.
4. Сценарии приёмки AC в форме «когда … тогда», у каждого вид доказательства.
5. Пакет вопросов шага 7 со всеми его полями, включая адресата и срок, после которого
   работа идёт по умолчанию.
6. Тип задания, слои и обязательные уровни проверки по шагу 5; команды сборки, тестов
   и запуска проекта.
Код не пиши, план не составляй, ничего не коммить. Закончив, остановись.
```

**С1 правка**

```text
Прочитай task-algorithm.md, материалы в папке task, spec.md и <источник правок>:
spec-review-N.md; plan-review-N.md, review-N.md или feedback-N.md (из них бери только
находки уровня «требования»); последний абзац plan.md или result.md; раздел «Ответы» в spec.md.
Исправь spec.md по каждой существенной находке и каждому ответу: UNKNOWN с ответом
переводи в FACT с источником. Первая строка «Статус: черновик». Допиши «Изменения захода N»:
что исправлено, что отклонено и почему. Код и план не трогай, ничего не коммить.
```

**С2 Проверка разбора**

```text
Ты не писал spec.md. Прочитай task-algorithm.md, все материалы в папке task,
spec.md и все предыдущие spec-review-*.md.
Найди, что spec.md пропустила или исказила: источник не в описи; фрагмент без строки
в таблице покрытия; строка «не требование», хотя фрагмент читается как требование,
ограничение или сценарий — перечитай каждую такую строку, запиши их число; требование
без источника; неверно понятый скриншот или видео; вопрос, закрытый догадкой; сценарий,
который нельзя проверить; граница «не делаем», противоречащая материалам.
Если это не первый заход: закрыты ли прошлые находки — по самому документу, а не по
разделу «Изменения»; по каждой отклонённой — согласен ли ты с обоснованием, несогласие
запиши как существенную находку; не сломали ли правки соседнее.
Каждая находка: что не так; цитата из материала; место в spec.md; критичность:
существенная или поверхностная, у поверхностной — почему она не меняет требования,
сценарий, число или текст наружу; без критичности находка считается существенной.
Если существенных нет, приложи три разные пробы: команда с дословным выводом или
перечень осмотренного с числом и с тем, что там точно есть и что нашлось.
Первая строка файла: «Заход N: существенных K, поверхностных M, проб P».
spec.md не правь. Запиши результат в spec-review-N.md.
```

**Вы после С2.** Прочитайте в spec.md цель, список «не делаем» и сценарии. На вопросы, ответ на которые знаете, ответьте сами. Остальные вопросы и сценарии отправьте заказчику одним письмом. Ответы впишите в раздел «Ответы» в spec.md с пометкой, кто ответил. После ответов запустите С1 правку: UNKNOWN переводятся в FACT. С2 заново — если ответ меняет цель, границы или сценарии. Когда всё сошлось, поставьте в первой строке «Статус: утверждено, дата, кто».

**С3 План**

```text
Прочитай task-algorithm.md и spec.md. Если статус spec.md не «утверждено»,
остановись и сообщи. Выполни шаги 8–11 по коду в <репозиторий> и запиши plan.md:
первая строка «Статус: черновик»; вторая «База: ревизия <хеш коммита>, дата».
1. Карта шага 8: каждый REQ → путь файла от корня репозитория и имя функции или класса
   (новый файл помечен «новый») → какое изменение одной фразой.
2. Решение шага 9: изменения контрактов, схемы данных, зависимостей, конфигурации;
   граничные случаи; риски. Решения из перечня шага 9 вынеси отдельным списком
   «требует утверждения».
3. DoD шага 10: каждая строка с видом доказательства — команда или имя теста и файл,
   который его даст; «тесты» или «проверка» без имени не допускаются. Обязательные
   уровни шага 5 из spec.md и каждый пункт do_not_change — отдельными строками.
4. План шага 11: шаги по порядку зависимостей, у каждого проверяемый результат;
   что подготовить в окружении, включая имя ветки задачи, зависимости, тестовые данные.
Если для плана нужно изменить требования, не меняй spec.md: запиши это последним
абзацем и остановись. Код не пиши, ничего не коммить.
```

**С3 правка**

```text
Прочитай task-algorithm.md, spec.md, plan.md, код в <репозиторий> и <источник правок>:
plan-review-N.md; review-N.md или feedback-N.md (из них бери только находки уровня «план»);
последний абзац result.md; список «требует утверждения» с решениями в plan.md;
раздел «Изменения захода N» или «Ответы» в spec.md, если правились требования.
Исправь plan.md по каждой существенной находке, каждому решению и каждому изменению spec.md.
Если код ушёл от базовой ревизии, обнови карту по текущему коду и вторую строку «База».
Первая строка «Статус: черновик». Допиши «Изменения захода N»: что исправлено,
что отклонено и почему. Код не пиши, spec.md не трогай.
```

**С4 Проверка плана**

```text
Ты не писал plan.md. Прочитай task-algorithm.md, spec.md, plan.md, код в <репозиторий>
и все предыдущие plan-review-*.md. Базовую ревизию из plan.md читай через историю
(показать файл на ревизии, diff с ревизией), ветку не переключай, изменения не прячь:
в рабочем дереве могут лежать незакоммиченные срезы реализации.
1. Каждый REQ, AC и пункт do_not_change из spec.md есть в карте и в DoD; в плане
   нет изменений сверх spec.md.
2. Указанные файлы и функции существуют и делают то, что план предполагает; проверь
   по коду, кто их вызывает. Файлы с пометкой «новый» не существуют. Строка карты
   без пути и имени функции или строка DoD без команды и имени теста — существенная находка.
3. Не пропущены соседние места: все пути с той же логикой, документация,
   конфигурация, миграции, тесты.
4. Каждая строка DoD проверяема указанным доказательством; обязательные уровни
   шага 5 присутствуют.
5. Решения, требующие утверждения, вынесены в список, а не спрятаны в плане.
6. Если не первый заход: закрыты ли прошлые находки — по самому документу; по каждой
   отклонённой — согласен ли ты с обоснованием, несогласие запиши как существенную находку.
Каждая находка: что не так; чем доказано (файл, строка, вывод команды); критичность
с причиной у поверхностной; уровень: план или требования.
Если существенных нет, приложи три разные пробы: команда с дословным выводом или
перечень осмотренного с числом и с тем, что там точно есть и что нашлось.
Первая строка файла: «Заход N: существенных K, поверхностных M, проб P».
plan.md не правь. Запиши результат в plan-review-N.md.
```

**Вы после С4.** Прочитайте список «требует утверждения» и шаги плана. Решения, которые не можете принять сами, отправьте заказчику. Каждое решение впишите в plan.md рядом с пунктом списка: «решено: вариант, дата, кто». Если решение меняет шаги, карту или DoD, запустите С3 правку, указав источником правок этот список, затем С4. Когда всё сошлось, поставьте в первой строке plan.md «Статус: утверждено, дата, кто». С этого момента реализацию можно начинать в любое время и любым агентом.

**С5 Реализация**

```text
Прочитай task-algorithm.md, spec.md, plan.md и result.md, если он есть. Если статус spec.md
или plan.md не «утверждено», остановись и сообщи.
Если result.md есть и в нём нет «Статус: готово», это возобновление: сверь рабочее дерево
с записанными шагами и продолжай с первого незавершённого, готовые срезы не переделывай.
Если plan.md правился после последней записи в result.md, сначала выполни его
«Изменения захода N».
Если result.md нет: создай его с первой строкой «Статус: в работе» и запиши ревизию
```
