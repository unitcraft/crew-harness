## Решения

### Раскладка и язык

- Язык: sh для запуска и хуков git, Python (стандартная библиотека, 3.9 и новее) для всего, что читает содержимое:
  донор A сам вынес разбор кракозябр из `grep` в Python, а шаблон донора A для управляющих байтов
  (A: guards/check-no-control-chars.sh, `grep -P` по диапазону с `\x00`) на GNU grep 3.0 из Git Bash не находит NUL и UTF-16
  (проба захода 23, 28). Байтовый разбор в Python не зависит ни от локали, ни от версии grep (REQ-37). Новых пакетов нет.
- Интерпретатор: sh-код берёт первый запускающийся из `python`, `python3`, `py -3` (как B: guards/run-all.sh: на машине
  `python3` — заглушка магазина, поэтому кандидат проверяется запуском `-c "pass"` и версией); нет рабочего — красный с
  подсказкой (REQ-03). Хук агента вызывается как `python` (REQ-16, Ф-16). Python не пишет байт-код: каждый вход ставит
  `sys.dont_write_bytecode = True`, запускающие скрипты — `PYTHONDONTWRITEBYTECODE=1` (иначе `__pycache__` ломает
  «`git status --porcelain` пуст» из AC-17, а `.gitignore` не меняется).
- Линтеров не вводим (новая зависимость без требования): уровень A — `bash -n` и `sh -n` (в CI ещё `dash -n`: на ubuntu `sh` это dash), `compile()` Python, разбор JSON; `node --check` — N/A (новых `.mjs` нет); YAML workflow
  проверяет первый прогон Actions.

### Общий договор стражей (REQ-35, REQ-36, REQ-37, REQ-24)

- Вызов: `<страж> [--root <папка>] [--index | --commit <хеш>] [--ci]`; у стража сообщения дополнительно `--message-file <путь> --mode editor|message` — так его зовёт хук `commit-msg` (через `lib/find-python.sh`, как остальные хуки), а `--commit <хеш>` — так его зовут `pre-push` и CI (см. «Страж сообщения»). Без `--root` корень — `git rev-parse --show-toplevel`
  (нет git — красный: предпосылка). Источник содержимого: по умолчанию рабочая копия и список `git ls-files` (ручной прогон, CI);
  `--index` — индекс в том виде, как его видит хук (`git ls-files -s -z` и `git cat-file --batch`; с `--only` git подставляет
  временный индекс через `GIT_INDEX_FILE`, прогоны его соблюдают — AC-30); `--commit <хеш>` — только файлы, изменённые этим
  коммитом (`git diff-tree -r --root -m`), содержимое из его дерева (для `pre-push`, REQ-18). Существование цели ссылки и
  чтение целей судятся по тому же источнику: файл вне индекса — нет файла (AC-30).
- Вердикт — последняя строка вывода, одна из четырёх форм: `ок: осмотрено <N> <мишень>` (код 0); `судить нечего: <причина>`
  (код 0); `пропущено: <причина>` (код 0 локально, красный в CI; закрытый список причин в шапке стража пуст); `FAIL: <страж>:
  <K> нарушений` (код 1), перед ней строки `FAIL <файл>:<строка>: <правило>: <описание>`. Стражи дерева на пустой мишени печатают
  `FAIL: мишень потеряна …` (код 1), а не «ок» (REQ-27). Общий `run-all.sh` печатает таблицу страж → вердикт и число вердиктов
  каждого вида; код возврата считается до печати.
- stdout и stderr переключаются на UTF-8 (`reconfigure`); никаких классов `grep` и локали; пути только относительные от корня.
- Шапка (docstring/комментарий): метки `Зачем:`, `Проверяет:`, `Не проверяет:`, `Правило:` (пункт `AGENTS.md` или ADR) — их
  читает `check-wiring.py` (REQ-36).
- Пометки с причиной: на строке — `guard-allow(<правило>): <причина>` в любом комментарии (правила: `md-link`, `md-anchor`,
  `control-char`, `mojibake`, `fffd`); для файла, где предмет проверки — сам байт, — строка `guard-fixture(<правило>): <причина>`
  (правила: `nul`, `utf16`, `bom`, `eol` и перечисленные выше). Пометка без причины — красный; принятая пометка печатает причину;
  исключать папку или маску нельзя. Образцы нарушений самотесты собирают при прогоне (К-06, Д-09): в файлах стражей литералов
  нет.

### Охват текста (REQ-05, REQ-09…REQ-12, Д-06)

Охват один для всех стражей приватности и текста (запись режима 120000 судится как текст по цели ссылки из блоба; таких записей сейчас 0): все пути из `git ls-files` (в `--index` — из индекса, в `--commit` — файлы
коммита), кроме записей режима 160000 (подмодуль; не осмотрено, учитывается в числе «осмотрено») и файлов с расширением из явного списка бинарных
(`lib/guardlib.py: BINARY_EXT`): png, jpg, jpeg, gif, webp, ico, bmp, pdf, zip, gz, tgz, 7z, woff, woff2, ttf, otf, eot, mp3,
mp4, mov, webm, wasm. Определению git «бинарный по содержимому» не доверяем: файл вне списка с байтом NUL или BOM UTF-16
красный (`nul`, `utf16`). `.log`, `.gitignore`, `.gitattributes`, файлы без расширения (хуки, лицензии) и с неизвестным
расширением судятся. Содержимое — байты; строки декодируются UTF-8 с заменой, нумерация по `\n`. Правило «управляющие байты» —
диапазоны 0x00–0x08, 0x0B, 0x0C, 0x0E–0x1F и 0x7F (в замере шага 2 на текущем дереве должны дать 0; иначе правило 0x7F
выносится в отчёт как отступление).

### Механизм хука агента (Д-11, REQ-16)

`scripts/agent-hooks/guard-git.py` — свой однопроходный разборщик команды на Python, без сторонних пакетов; обоснование:
`shlex` не знает heredoc, here-string PowerShell и `if ($?) { … }`, падает на несбалансированных кавычках; регулярки донора
(A: claude-hooks/guard-git.py) режут кавычки и heredoc предварительной заменой и судят строку целиком — отсюда ложные отказы на
`git config user.email || echo none`, на продолжении строки и на here-string с апострофом (таблица AC-10).

- Вход: JSON из stdin, `tool_input.command`, `tool_name` (`PowerShell` включает режим PowerShell: продолжение строки — обратный
  апостроф (он же экранирование внутри `"…"`; `''` внутри `'…'` — один апостроф), обратная косая — обычный символ; иначе режим bash: продолжение — обратная косая). Ошибка разбора входа или самого
  разборщика — код 0 (подсказка, а не барьер, Н-12).
- Разборщик: автомат с состояниями «вне кавычек», `'…'`, `"…"` (со вложенным `$(…)`, рекурсивно), heredoc (`<<`, `<<-`,
  ограничитель в кавычках или нет; тело пропускается до строки с ограничителем), here-string PowerShell (`@'…'@`, `@"…"@`, в том
  числе с апострофом внутри), продолжение строки. Разделители вызовов вне литералов: `&&`, `||`, `;`, `|`, `&`, неэкранированный
  перевод строки, `(`, `)`, отдельно стоящие `{` и `}` (цепочки PowerShell 5.1 `A; if ($?) { B }`). Каждый вызов — список токенов
  с признаком «был в кавычках» и признаком «содержит обратный апостроф вне кавычек».
- Вызов git — токен `git` (или `git.exe`) на месте команды (после присваиваний `NAME=значение`, `sudo`, `env`, `command`, `exec`,
  `time`, `&`). Подкоманда — первый токен без дефиса после глобальных ключей `-C <путь>`, `-c <ключ=значение>`, `--git-dir=…`,
  `--work-tree=…`, `--no-pager`, `-p` (их значения пропускаются, а не разбираются, Н-13). Правила применяются к токенам самого вызова:
  `add` с аргументом `-A`, `--all`, `-u`, `--update` или `.`; подкоманда `stash`; `push` с `--force`, `-f`, `--force-with-lease…`,
  `--force-if-includes`, `+ref`; `commit`/`push` с `--no-verify`, `commit` с отдельным `-n` (слитные группы не разбираются);
  `filter-branch`, `filter-repo`; `config` с ключом `user.name`/`user.email` и значением после него; `commit` без `--only`, `-o`,
  `--include`, `-i`, `--amend`, отдельного `--` и без пометки `# index-verified: <причина>` в сыром тексте; флаг `-F`/`-m`/`-s`/`-S`/`-u`
  после `--` у `commit`; обратный апостроф вне кавычек в вызове `printf` или `python* -c`. Два правила по сырой команде (запись в
  файл командами PowerShell с обратным апострофом или `@"`; `git commit … -m …` с ОБРАТНЫМ апострофом (символ «`»), не с обычным) — регулярки донора на сыром тексте. Обычный апостроф («Don't …», «it's») ничего не затрагивает.
- Подтверждение «не мешает»: вся таблица AC-10 (42 строки) — данные самотеста `selftest/test-guard-git.py`, плюс изолированная
  красная проба на каждое правило (с `--only -- <файл>`, чтобы отказ давало именно оно), плюс пробы-хулиганы: вложенный heredoc
  внутри `"$(…)"`, несбалансированная кавычка, пустая команда, битый JSON — код 0 без исключений; пробы по plan-review-1: `git commit -s
  -m "Don't …" --only -- <файл>` — проход, та же команда с обратным апострофом — отказ; команда с кириллицей; PowerShell
  `Write-Host "say `"git add -A`""` (обратный апостроф — экранирование внутри `"…"`) и `''` внутри `'…'` — проход. Вход читается как
  байты (`sys.stdin.buffer`, UTF-8): кириллица в команде не превращает разбор в молчаливый код 0.
- Запись в `.claude/settings.json` безопасна при отсутствии скрипта: код 2 для PreToolUse — отказ каждой команды, а `python` на
  несуществующем файле выходит именно с кодом 2. Поэтому команда — обёртка `sh`: `{"hooks":{"PreToolUse":[{"matcher":"Bash|PowerShell","hooks":[{"type":"command","command":"sh -c 'f=\"${CLAUDE_PROJECT_DIR:-$(git rev-parse --show-toplevel 2>/dev/null)}/scripts/agent-hooks/guard-git.py\"; [ -f \"$f\" ] || exit 0; exec python \"$f\"'"}]}]}}` (одна строка, без перевода внутри значения; разобрано `json.loads`). Пустая переменная — корень текущего дерева через git; подкаталог — тот же корень; другое
  дерево без скрипта или папка не под git — выход 0; код 2 самого стража проходит насквозь (`exec`); нет `python` — код 127, не отказ. Ключа
  `permissions` нет: плагин сверяет `crew_watch` только с `permissions.deny` из этого файла (`opencode-plugin/deny.ts`, `projectDeny`), с
  одним ключом `hooks` список запретов пуст и поведение `crew_watch` не меняется (DNC-01; проверка — прямой вызов `watchRefusal` на дереве с готовым файлом, см. шаг 8 и DoD; `node opencode-plugin/test/crew-deny.test.mjs` остаётся только как «итог как в базе»). `test-guard-git.py` запускает команду из записи через `sh` в пяти положениях: корень, подкаталог,
  без `CLAUDE_PROJECT_DIR`, дерево без скрипта (код 0), красная команда (код 2); `check-wiring.py` разбирает команду, находит путь скрипта,
  разрешает его от корня и требует существующий файл, слово `python` и запуск интерпретатора. Исполняет ли окно OpenCode хук и задаёт ли
  оно `CLAUDE_PROJECT_DIR` (U-07) — проба в шаге 8: запуск напрямую и, по слову владельца, в живом окне.
### Страж сообщения (REQ-13…REQ-15, REQ-38, REQ-37): режимы и вызов

Хук `commit-msg` получает один аргумент — путь к файлу сообщения; режим коммита из файла не следует (при `-m`, `-F` и в редакторе файл
устроен одинаково, строка с `#` остаётся в нём во всех трёх случаях, а git убирает её только в режиме редактора). Признак режима —
окружение хука: `GIT_EDITOR=:` при `-m`, `-F`, `--no-edit` (проверено пробой проверки плана и пробой автора плана: подпись `Signed-off-by` в файле уже есть, а шаблон с
комментариями в режиме редактора ещё не очищен; в режиме редактора `GIT_EDITOR` — команда редактора или не задан). Механизм:

- `scripts/githooks/commit-msg` — sh-обёртка, единственное место, где читается среда: `mode=message`, если `${GIT_EDITOR-}` равно `:`, иначе `mode=editor`;
  вызов стража через интерпретатор, найденный `lib/find-python.sh` (как у остальных хуков): `<python> scripts/guards/guard-commit-message.py --message-file "$1" --mode "$mode"`. `--ci` обёртка не передаёт, переменные окружения режим CI не задают.
  Сам страж среды не читает (REQ-37: режим — вход стража, заданный аргументом; самотест задаёт `--mode` в каждой пробе явно).
- Для `pre-push` и CI вызов другой: `guard-commit-message.py --commit <хеш>` (сообщение берётся как сохранено, `git show -s --format=%B`, режимов нет); CI добавляет `--ci`.
- Известный остаток (Р-07): `core.editor=:` без `-m` даёт `GIT_EDITOR=:` и режим `message` — строка `#` судится, хотя git её убрал бы; ошибка только в сторону строгости.
- Пробы (`test-guard-commit-message.py` — на уровне стража с явным `--mode`, `test-commit-msg.py` — через настоящий `git commit` с хуком в одноразовом репозитории): один и тот же
  файл с запрещённым именем в строке `#` — красный при `--mode message` (`-m`, `-F`) и не судится при `--mode editor` (редактор — скрипт, дописывающий строку); строка `>` — красная
  в обоих; режим с diff — `commit.verbose=true` и редактор: имя только в удалённой строке diff проходит, имя в самом сообщении красное (AC-32 (а)); `-F` без режима с diff и
  имя в хвосте за строкой-ножницами — красный (AC-32 (б)); `-F -v` со строкой-ножницами — судится строже (проба «строже», Р-07); кириллица в строке `#` при `-F` — красный, в
  редакторе — проходит; `--amend --no-edit` — режим `message`; `git commit --amend -m` без изменений индекса (AC-18); нет списка имён — красный.

Определение «то, что git сохранит» (REQ-14) реализует `lib/message.py: effective_message(raw, mode, settings)`:

- `editor`: убрать строки, начинающиеся с символа комментария (`core.commentChar`, `auto` и многосимвольные значения не
  поддерживаются — считается `#`); хвост за строкой-ножницами убрать, если сразу за ней стоит служебная строка git «Do not modify
  or remove the line above» (набранная руками строка-ножницы без неё остаётся в истории — судится, находка захода 28). Допущение: служебная строка git английская (git без переводов); при переведённом git обрезки не будет и возможен ложный красный, только в сторону строгости. Проба на английской строке — в `test-guard-commit-message.py`;
- `message` (`-m`, `-F`): сообщение как есть; хвост за строкой-ножницами убрать только при включённом `commit.verbose`
  (`git config --bool commit.verbose`). Флаг `-v` в командной строке при `-m`/`-F` хуку не виден: хвост судится строже, чем
  требует REQ-14 — известный остаток (заход 27, 28: механизм, не поведение), в самотесте записан как проба «строже»;
- `--commit <хеш>` (`pre-push`, CI): сообщение берётся как сохранено (`git show -s --format=%B`), чистить нечего.

Правила стража сообщения: R1 `Signed-off-by` совпадает с автором (имя и адрес; автор — `git var GIT_AUTHOR_IDENT` в хуке, `%an <%ae>` у
коммита); R2 нет `Co-Authored-By`; R3 имя автора не пусто; R4 только ASCII, кроме строк на `>`; R5 адрес автора равен значению
`git config crewharness.expectedEmail` (пишет установщик; нет значения — красный «запусти установщик», в том числе при
`GITHUB_ACTIONS=true`); в режиме `--ci` R5 печатает «судить нечего: CI, нет настройки установщика»; R6 приватность: все строки
сообщения (включая `#` при `-m`/`-F` и `>`) через `machine_paths` и `names` — вердикт даёт «сообщение коммита, строка» и номер образца;
R7 пустое сообщение — красный. `pre-push` зовёт тот же страж без `--ci` (R5 действует на коммиты диапазона: коммит с другим адресом
автора краснит пуш — чинится ребейзом ветки задачи, `main` это не касается); CI зовёт его с `--ci`.

### Остальные решения

- Хук `pre-commit` (REQ-24, REQ-33): sh; находит Python; пишет вывод в буфер `$(git rev-parse --git-dir)/guards-precommit-out.$$` (в связанном рабочем дереве `.git` — файл, поэтому путь не строится руками; запасной вариант — `mktemp`; буфер удаляется по `trap`); код возврата решает до печати,
  печатает подпроцесс с `2>/dev/null || true`, сам в stdout не пишет (AC-24: `git commit … | head -1`); запускает
  `run-all.sh --index` (все `check-*`, один за другим) и `guard-secrets.py --index`; пустой индекс — «судить нечего» стража индекса,
  стражи дерева судят индекс целиком. Если хук не уложится в порог REQ-34, запуск стражей сливается в один процесс Python
  (`run-all` вызывает `main()` модулей) — только по замеру.
- Хук `pre-push` (REQ-18): читает строки stdin; удаление удалённой ветки (локальный хеш нулевой) — «судить нечего»; диапазон

- Установщик (REQ-28): корень из `git rev-parse --show-toplevel`; проверяет, что три хука и Python на месте; `git config --local

  установщик и AGENTS.md говорят об этом прямо, а ветки обновляются ребейзом (О-01).

### Риски

- Хук агента ловит текст команды и обходится сокращением, псевдонимом, слитными флагами (Н-12); ложный отказ законной команды —
  дефект, пропуск — нет. Смягчение: таблица AC-10 как данные теста и пробы-хулиганы.
- Хуки не видны в дереве, созданном до слияния задачи (И-03); обновление ветки ребейзом решает. После публикации ветки ребейз требует
  силового пуша, он запрещён (AGENTS.md п.5): порядок — удалить удалённую ветку (`git push origin --delete`, проходит) и запушить заново,
  каждый пуш на воротах Г3; слияние `main` в ветку не годится (линейная история).
- Дерево задачи 001 красное для стражей на базе плана (Н-11): 2 битые ссылки (`spec-review-12.md:47`, `spec-review-13.md:41`) и 3 строки
  U+FFFD (`spec-review-3.md:221`, `spec-review-4.md:156,157`). Зелёные прогоны «на дереве» и CI недостижимы, пока класс не закрыт (Р-06).
- Пушу файла workflow нужна область токена `workflow` у менеджера учётных данных git (у `gh` она есть, у менеджера может не быть): отказ
  первого пуша шага 11 не дефект плана, владелец обновляет токен.
- Каждый запуск Python на нагруженной Windows даёт задержку: 7 стражей в `pre-commit` могут не уложиться в 10 с (REQ-34);
  замер в шаге 9, запасной ход — один процесс.
- `GNU grep` нигде не применяется к содержимому; `git` 2.56 на машине и новее на `ubuntu-latest` ведут себя одинаково в режимах
  сообщения (проверено пробами захода 28); версия git CI проверяется первым прогоном.
- Журнал публичного репозитория не вычистить: маскирование и «вердикт без значения» проверены самотестом и пробой AC-31 до того, как
  в секрет попадёт настоящий список; секрет заводят после зелёной пробы.
- Побочные файлы: `__pycache__` (см. выше), временные папки самотестов вне репозитория, остаток подмены в `prove-red.sh` исключён
  копированием (рабочее дерево не меняется).
