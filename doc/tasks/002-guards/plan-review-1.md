## Находки

1. Запись хука агента не страхует от «хук не нашёл свой скрипт»: python в таком случае выходит с кодом 2, а для хука
   PreToolUse код 2 — отказ каждой команды оболочки. План (раздел «Механизм хука агента») пишет в `.claude/settings.json`
   команду `python "${CLAUDE_PROJECT_DIR:-.}/scripts/agent-hooks/guard-git.py"` и сам признаёт, что окно OpenCode может не
   задавать `CLAUDE_PROJECT_DIR` (U-07); тогда путь идёт от текущей папки, а агент, чья папка — подкаталог (например
   `opencode-plugin/`) или другое дерево, получает код 2 на каждый `git status`, `ls` и любую иную команду. «Ошибка разбора —
   код 0» относится только к внутренностям стража, а не к запуску. Проверка в шаге 8 — запуск хука напрямую из корня, этот
   случай она не ловит. Доказано: проба 3 (`python <несуществующий файл>` даёт код 2, вывод в разделе проб). Это ровно
   то, чего боится Р-05 (хук начинает действовать на работающих агентов), но вред здесь не подсказка, а потеря
   всех команд. Нужно: команда-обёртка, которая при отсутствии скрипта выходит с 0 (и не глотает код 2 самого стража),
   проба «скрипта нет / переменной нет / папка — подкаталог» в `test-guard-git.py` и в `check-wiring.py` (проверка, что
   путь из записи разрешается в существующий файл из корня).
   - критичность: существенная — сломает работающее (команды чужих окон после слияния, Г5)
   - уровень: план

   рабочем дереве (а AGENTS п.3 требует именно его для каждой задачи) `.git` — файл, а не папка. Доказано: проба 4
   (в связанном дереве запись в `.git/…` не удалась, `git rev-parse --git-dir` указывает в общий `.git/worktrees/…`).
   После шага Г2 хук общий для всех деревьев (`core.hooksPath` лежит в общей конфигурации, проба 4), то есть
   реализация буквально по плану отказывает или падает на каждом коммите в рабочем дереве задачи. Самотесты плана ходят в
   «одноразовые репозитории» (обычные `git init`), связанного дерева в них нет, поэтому дефект пройдёт все `test-*.py`.
   Нужно: буфер через `git rev-parse --git-dir` (или `mktemp`), и проба в `test-pre-commit.py`, `test-commit-msg.py`,
   `test-pre-push.py`: `git worktree add` во временном репозитории и коммит/пуш из него.
   - критичность: существенная — сломает работающее (все коммиты в деревьях после Г2) и AC-24/AC-30 не будут

6. Правило хука агента по сырой команде описано двусмысленно, и буквальное чтение даёт массовые ложные отказы. План
   (раздел «Механизм хука агента») перечисляет «`git commit … -m … ` + апостроф»; спецификация (REQ-16, строка AC-10 про
   `git commit -m`) говорит об ОБРАТНОМ апострофе (символ «`»), а про обычный апостроф сказано, что он «не затрагивается
   вовсе». Сообщения коммитов здесь на английском и часто содержат обычный апостроф («Don't …», «it's»); исполнитель, прочитавший
   план строго, поставит регулярку донора на апостроф и откажет законным коммитам. Решение владельца «ложные отказы
   законных команд существенны». Таблица AC-10 строки `git commit -m … '` с обычным апострофом не содержит (строка про
   апостроф — для `printf`), так что тест бы не поймал. Нужно: в плане написать «обратный апостроф (`)» и добавить в
   данные теста две строки: `git commit -s -m "Don't …" --only -- <файл>` — проход и ту же команду с обратным апострофом —
   отказ.
   - критичность: существенная — ложный отказ законной команды (утверждённое решение: существенно)
   - уровень: план

   код 0, то есть хук молча не сработает. Нужно читать `sys.stdin.buffer` и декодировать UTF-8.
   - критичность: поверхностная — отказ в пользу прохода (подсказка, не барьер, Н-12), законные команды не страдают;
     требование REQ-37 для хука агента не названо в AC; но пробу с кириллицей в `test-guard-git.py` стоит добавить
   - уровень: план

## Пробы

- Проба 1. Версии на машине: `git version 2.56.0.windows.1`, `Python 3.14.4` (требования плана: git не старее 2.40, Python
  3.9+, ubuntu-latest в CI): план исполним.
- Проба 2. Одноразовый репозиторий во временной папке, хуки `commit-msg` и `pre-commit`, печатающие среду: при `-m` и `-F`
  `GIT_EDITOR=:` и в файле сообщения стоит подпись `Signed-off-by` и строка с `#` при `-F` (остаётся в файле); при
  редакторе `GIT_EDITOR=<путь редактора>`, в файле только то, что оставил редактор, до очистки; при `--amend --no-edit`
  `GIT_EDITOR=:`; при `--only -- a` в `pre-commit` `GIT_INDEX_FILE=next-index-N.lock`, `git ls-files` видит `a b`;
  при `-v` с редактором в файле шаблон `# Please enter the commit message…` до очистки. Итог: признак режима плана верен.
- Проба 3. Запуск `python` с несуществующим файлом (как хук при неверной папке): `can't open file … No such file or
  directory`, `exit=2`. Подтверждает находку 1.
- Проба 4. Репозиторий `w` с `scripts/githooks/pre-commit` и связанное дерево `w-wt` (`git worktree add`): в обычном
  дереве запись `.git/буфер` — `ok`, в связанном — `FAILED`; `git rev-parse --git-dir` в связанном дереве оканчивается на
  `w-wt` (путь внутри общего `.git/worktrees`); `git config --get core.hooksPath` в обоих деревьях даёт `scripts/githooks`
  (конфигурация общая). Подтверждает находку 2.
- Проба 5. Сканер по всем отслеживаемым файлам, кроме расширений из списка плана, плюс `plan.md` (читает файлы, ничего не
  пишет): файлов 156; управляющих байтов 0, BOM 0, U+FFFD в 2 файлах (`spec-review-3.md`, `spec-review-4.md` задачи 001, строки 221,
  156, 157), смешанных концов строк 0 (4 файла целиком с CRLF в рабочей копии — `LICENSE-APACHE`, `LICENSE-MIT`,
  `spec-review-24.md`, `spec-review-25.md` — в индексе LF, `git ls-files --eol`: `i/lf w/crlf`), путей от буквы диска
  и домашних каталогов вне `C:/work/` 0; все записи режима 100644 (155). Подтверждает находку 4 и п. 12.
- Проба 6. Покрытие машинно: REQ, не названных в DoD, — 0 из 38; AC — 0 из 32; DNC — 0 из 6; REQ без строки карты — 0;
  AC без строки покрытия — 0; строк DoD 42, шагов 14.
- Проба 7. Донорские файлы, на которые ссылается план (15 меток: A — 7 файлов guards, хук агента, dco-workflow; B —
  5 файлов guards и установщик, папка хуков): существуют все 15 из 15.
- Проба 8. `gh` только чтением: `gh auth status` (вход есть, область токена включает `repo` и `workflow`), `gh api
  repos/unitcraft/crew-harness` (`private: false`, права администратора `true`), `…/branches/main/protection` —
  404 «Branch not protected» (защиты нет, как предполагает план), `…/actions/permissions` — `enabled: true`,
  `gh secret list` — пусто (секрета нет). Менеджер учётных данных git — отдельный (`credential.helper=manager`).
- Проба 9. Команды DoD уровня A в одноразовом репозитории: `git ls-files -z -- 'scripts/*.sh' 'scripts/githooks/*' | xargs -0
  -n1 bash -n` — `exit=0` и ловит вложенные файлы; `… 'scripts/*.py' | xargs -0 -n1 python -B -c "…compile…"` — на файле с
  синтаксической ошибкой `exit=123` (xargs; код не 1, а 123, DoD пишет «код 0» для зелёного — верно), на пустой выборке
  тоже 123 (команда без файлов красная, как нужно).
- Проба 10. Чтение `opencode-plugin/deny.ts`: `projectDeny` находит `.claude/settings.json` вверх от папки вкладки до корня
  git и берёт `permissions.deny`; при файле без этого ключа `rules=[]`, `watchRefusal` возвращает `undefined`. Утверждение
  плана о неизменности `crew_watch` верно.
- Проба 11. `git diff --stat d963ecc 583764e`: вне `doc/tasks` и `opencode-plugin` один файл — `doc/canon/process.md` (+15);
  `.gitattributes`, `AGENTS.md`, `README.md`, `doc/tasks/README.md`, `doc/canon/decisions` без изменений; в
  `opencode-plugin/` 8 файлов (4 `.ts`, 4 теста); изменённых (M) файлов `doc/tasks/*/task/` — 0. Шапка плана точна;
  подтверждает, что `<база>` AC-26 нельзя брать `d963ecc`, и что чужие правки плагина на `main` идут.
- Проба 12. Поиск в plan.md имён и путей: образцы-подстроки (буква диска с путём, `Sources`, имена обоих проектов-доноров и
  приватного репозитория A, названия из кода доноров) — 0 совпадений, кроме слова «sources» в имени коммита плана (не
  путь). Те же образцы после записи искались в plan-review-1.md, progress.log, profile.log и log.md.

Проверка своих файлов поиском (те же образцы): plan-review-1.md, progress.log, profile.log, log.md — 0 совпадений каждый.
