## Находки

1. Границы Н-12 и Н-13 говорят, что хук агента не разбирает слитные флаги, а требование REQ-16 и сценарий AC-10 требуют
   отказа на слитных `-sn`. Что не так: Н-12 (строки 240–241): хук «не видит псевдонимы, сокращения флагов, слитные
   флаги, смену каталога, настройку через `-c` и окружение …»; Н-13 (строка 250) относит «слитные флаги» к убранному
   разбору команд git. REQ-16 (334–336) требует отказа на «короткий `-n` у `git commit`», а AC-10 (строка 763) — отказа
   на `git commit -sn …`; в «Изменениях захода 15» (1250–1251) это сказано прямо: «пробы `-n` и `-sn` (отказ)». `-sn` —
   это слитные короткие флаги `-s` и `-n`: чтобы увидеть `-n` внутри `-sn`, хук обязан разбирать слитные флаги, то
   есть делать то, что Н-12 и Н-13 объявляют вне объёма (решение В9). Донор A такого правила не имеет: проба 2 — на
   `git commit -sn -F m.txt --only -- a.txt` код 0 (и на `git commit -n …`, и на `--no-verify`: этих правил у донора
   нет, заход 13, находка 3). Значит `-sn` — не «простое правило донора A», а новое поведение, которое границы запрещают
   подразумевать. Сессия С3 не может выполнить оба текста; Сессия С6 вправе записать FAIL по любому из них.
   - Цитата: «не видит псевдонимы, сокращения флагов, слитные флаги, смену каталога» (Н-12); «`git commit -n …`;
     `git commit -sn …`» → «отказ» (AC-10).
   - Место в spec.md: Н-12 (240–247), Н-13 (248–252), REQ-16 (334–336), AC-10 (763), «Изменения захода 15» (1250–1251).
   - Что сделать: либо убрать `git commit -sn …` из AC-10 и пометку из «Изменений» (отказ на отдельный `-n` остаётся;
     обход слитным флагом — обход подсказки, по решению В9 не существенен); либо дописать в Н-12 и Н-13 «кроме `-n` в
     слитных коротких флагах `git commit` (AC-10)». Рекомендация (Сессия С2): первое — слитный `-sn` обходит хук, а
     не вызывает ложный отказ, и разбор слитных флагов — тот самый разбор, который владелец убрал.
   - критичность: существенная. Граница «не делаем» и сценарий приёмки противоречат друг другу; любая правка меняет
     границу или сценарий.
   - уровень: требования

2. REQ-16 называет перевод строки разделителем вызовов git, не отделяя от него продолжение строки; законная
   многострочная команда по тексту получает отказ. Что не так: REQ-16 (строка 324): «команды в цепочке (`&&`, `||`, `;`,
   `|`, перевод строки) судятся каждая сама по себе». В оболочке перевод строки после обратной косой черты (bash) или
   обратного апострофа (PowerShell) — не разделитель, а продолжение той же команды. Исключения в тексте нет. Команда
   ```text
   git commit -s -F <файл> \
     --only -- <файлы>
   ```
   (длинный перечень файлов на второй строке) по буквальному чтению распадается на два «вызова», и первый — `git commit
   -s -F <файл> \` без перечня файлов — получает отказ правила О-07 («коммит без перечня файлов»). Это та же ошибка,
   что закрывали заходы 17–18 (правило судит не тот отрезок команды), но в другом месте: границы вызова. В таблице
   AC-10 ни одной многострочной команды, кроме heredoc, нет, так что самотест хука её не поймает (класс не покрыт
   ни одной строкой; проход цепочек с `&&` и `;` строки 772–775 проверяют другое).
   - Доказательство (проба 3): токенизатор Python `shlex` на команде с `\` и переводом строки возвращает отдельный
     токен `'\n'` — реализация «режем по переводу строки», как читается REQ-16, отрежет `--only -- <файлы>` от
     `git commit`. Хук донора A пропускает эту команду (код 0) лишь потому, что его правило ищет `--only` по всей
     строке, а не по вызову. В PowerShell продолжение — обратный апостроф, и донор отклоняет (код 2) и
     `git commit -s -m "Fix cell"` + апостроф + перевод строки + `--only -- a.txt`, и `Set-Content …` с продолжением:
     законное продолжение попадает под правила «обратный апостроф» из последних пунктов REQ-16, написанные для
     подстановки команд внутри двойных кавычек bash. Репозиторий уже трактует перевод строки как разделитель
     (README плагина, строка 118, список разделителей запретов проекта), так что буквальное чтение вероятно.
   - Место в spec.md: REQ-16 (324; 343–349), AC-10 (757–793).
   - Что сделать: в REQ-16 одной фразой — перевод строки после обратной косой черты (bash) или обратного апострофа
     (PowerShell) продолжение, а не разделитель; в AC-10 две зелёные пробы (bash: `git commit -s -F <файл> \` +
     перевод строки + `--only -- <файл>`; PowerShell 5.1: то же с обратным апострофом); для PowerShell решить, считается
     ли апостроф продолжения «обратным апострофом в команде» для сырых правил REQ-16 (рекомендация Сессии С2: не
     считается; иначе назвать цену в Н-12).
   - критичность: существенная. Ложный отказ законной команды (решение владельца на воротах В9: существенно); меняет
     требование REQ-16 (граница вызова) и сценарий AC-10 (новые пробы).
   - уровень: требования
