## Находки

1. Запрет смены `core.hooksPath` (REQ-16) по-прежнему узнаёт не все написания того же свойства: `git --config-env=…`
   и запись `include.path` (или `includeIf.*.path`) в конфигурацию репозитория снимают красный хук `pre-commit`
   (проба 3). Тот же класс, что находка 1 захода 7: правило судит перечень форм, а не свойство «команда меняет
   действующее значение `core.hooksPath` или ключа ожидаемого адреса».
   - Материал: meth §20 «Четыре пробы каждого стража»: «то же свойство другим синтаксисом — красный»; meth §19:
     находка стража исправляется переписыванием текста, а не обходом; spec-review-7, находка 1.
   - Место в spec.md: REQ-16 — «запись или снятие `core.hooksPath` и ключа ожидаемого адреса», «настройка через `-c`
     судится как запись», запрет «запись `git config user.*`»; AC-10 — пробы только `git config core.hooksPath`,
     `--unset`, `git -c`, регистр ключа, `GIT_CONFIG_*`; Н-12 перечисляет непокрытое (псевдонимы, скрипт, другой
     интерпретатор), а эти две формы — нет. Строк с `--config-env`, `include.path` в spec.md — 0 (проба 1).
   - Факт (проба 3, git 2.56): `git --config-env=core.hooksPath=HP commit` при `HP=<пустой каталог>` — код 0, хук не
     запущен; `git config include.path <файл>` — ключ не `core.hooksPath` и не `user.*`, хук агента по REQ-16 его
     пропускает, — после него `git commit` — код 0; после снятия `include.path` хук снова красный (код 1). Тем же
     `--config-env=user.email=…` подменяется адрес автора мимо запрета записи `git config user.*`.
   - Следствие: агент, получивший отказ на `--no-verify` и `-c core.hooksPath`, проходит красный страж приватности
     третьим написанием; самотест по AC-10 зелёный на хуке, который это пропускает.
   - Что сделать: в REQ-16 к правилу свойства добавить: `--config-env` судится как `-c`; запись `include.*` и
     `includeIf.*` в конфигурацию git — отказ (подключает чужой файл настроек, где может стоять любой ключ); в AC-10 —
     по пробе на обе формы. Класс закрыть одним местом: в REQ-16 одна фраза, что хук разбирает все способы, которыми
     git задаёт настройку на один вызов (`-c`, `--config-env`, `GIT_CONFIG_*`) и на постоянную (`git config` любой
     области и `include`), а не перечень ключей.
   - критичность: существенная
   - уровень: требования

2. О-01 внесён как «`git rebase`, когда текущая ветка — `main`», но не сказано, чья ветка текущая: каталога сессии
   агента или репозитория, на который указывает команда. Из рабочего дерева задачи `git -C <рабочая копия main> rebase
   <ветка>` переписывает `main` (проба 4), хотя в каталоге сессии текущая ветка — ветка задачи.
   - Материал: log.md, ответ В-01: «rebase на ветке задачи разрешён, на main запрещён»; AG п.3: изменения — в отдельном
     рабочем дереве на своей ветке, `main` — живая рабочая копия (К-04); meth §20 «то же свойство другим синтаксисом».
   - Место в spec.md: REQ-16 — «`git rebase`, когда текущая ветка — `main`; на ветке задачи `rebase` разрешён (О-01)»;
     О-01; AC-10 — только «`git rebase main` на ветке `main`» (отказ) и «`git rebase main` на ветке задачи» (проход);
     правило донора «меняющая команда git без `-C`» убрано целиком (Д-05), так что `-C` больше ничем не судится; Н-12
     этот путь не называет. Строк с `-C ` в spec.md — 0 (проба 1).
   - Факт (проба 4): в одноразовом репозитории с рабочим деревом ветки задачи `git -C <дерево main> rebase task` из
     дерева задачи — код 0, `main` переписан (3 коммита, в середине — коммит задачи); `git rebase task main` из дерева
     задачи при `main`, занятой другим рабочим деревом, git сам отклоняет (код 128), но если `main` нигде не занята —
     переключает и переписывает её.

     переписанная живая `main` подгружается сервисом (К-04) и затем не пушится (`pre-push`) — расхождение с GitHub
     чинится руками; самотест по AC-10 зелёный.
   - Что сделать: в REQ-16 задать свойство: rebase запрещён, если ветка, которую он переписывает, — `main`; ветка
     определяется как у git — аргумент `<ветка>` у `git rebase <база> <ветка>`, иначе текущая ветка репозитория,
     заданного `-C`, `--git-dir`, `--work-tree`, `GIT_DIR`/`GIT_WORK_TREE` или ведущим `cd <путь> &&`; не удалось
     определить — отказ. В AC-10 — пробы `git -C <дерево main> rebase …` и `git rebase <база> main` с ветки задачи
     (отказ) и `git -C <дерево задачи> rebase main` (проход). Класс тот же, что в находке 1, — можно закрыть той же
     фразой REQ-16 о разборе команды «как git».
   - критичность: существенная
   - уровень: требования
