## Масштаб находок о хуке агента

По Н-12 хук агента — первый барьер, а не полный. Поэтому новый способ обойти его считается существенным, только
если агент, который не собирается нарушать правило, может прийти к нему случайно: штатной формой команды в своей
оболочке, привычным приёмом или из-за отказа самого хука. Экзотический обход, который надо выбрать намеренно (псевдоним
в `-c`, правка файла настроек git инструментом записи файлов, запуск git из другой программы), записывается
поверхностным с пометкой «Н-12»: он не меняет требований, а дополняет перечень того, что хук не закрывает. Находка 3
ниже — не про хук агента: это путь без единого хука git в штатной работе, Н-12 к ней не относится.

## Находки

1. Хук агента описан только для bash: REQ-16 не говорит, для каких инструментов агента он ставится (у донора A — для
   двух, `Bash|PowerShell`), а смена каталога перед rebase перечислена одной формой bash — «ведущий `cd <путь> &&`».
   На этой машине оболочка агента — Windows PowerShell 5.1, где `&&` — синтаксическая ошибка (проба 4). Агент без
   умысла пишет `cd <дерево main>; git rebase <ветка>` или `Set-Location <путь>; …`. По тексту REQ-16 хук такую смену
   каталога не разбирает и берёт ветку каталога сессии, то есть ветку задачи, — rebase `main` проходит. Если С3
   поставит хук только на инструмент `Bash`, а это не запрещено ни REQ-16, ни AC-10, то через инструмент PowerShell в
   Claude Code проходят вообще все правила REQ-16: `--no-verify`, `git add -A`, силовой пуш.
   - Материал: log.md, ответ В-01: «rebase на ветке задачи разрешён, на main запрещён»; meth §20 «то же свойство
     другим синтаксисом — красный»; хук агента донора A (`guard-git.py`, шапка): «PreToolUse-хук Claude Code (Bash +
     PowerShell)», подключение `matcher = "Bash|PowerShell"`; spec-review-8, находка 2 (тот же класс).
   - Место в spec.md: REQ-16, строки 307–308 («для команд оболочки», инструменты не названы) и 312–315 (смена каталога —
     только `cd <путь> &&`); AC-10 — все пробы в синтаксисе bash, из PowerShell — только `Set-Content` с обратным
     апострофом; Н-12 не говорит о PowerShell. Строк с `Set-Location`, `matcher`, `Bash|PowerShell` в spec.md — 0
     (проба 1).
   - Почему существенная по шкале Н-12: обходом здесь служит штатная форма команды в основной оболочке агента на этой
     машине, умысла не нужно.
   - Что сделать: в REQ-16 назвать инструменты, на которые ставится хук (`Bash` и `PowerShell`; плагин OpenCode отдаёт
     команды как `Bash`, S27). Смену каталога судить как свойство: любая более ранняя часть той же команды, которая
     меняет каталог (`cd`, `Set-Location`, `Push-Location`, `pushd`) или ветку, при любом разделителе (`&&`, `;`,
     `||`, перевод строки) или в подоболочке; не удалось определить — отказ. В AC-10 добавить пробы
     `cd <дерево main>; git rebase <ветка>` и `Set-Location <дерево main>; git rebase <ветка>` (отказ), а также
     `git commit --no-verify` через инструмент PowerShell (отказ).
   - критичность: существенная
   - уровень: требования

3. В штатной работе коммиты создаются вообще без хуков git, и до публикации их не проверяет ничто. `git cherry-pick` и
   `git rebase --continue` после разрешения конфликта создают коммит без `pre-commit` и без `commit-msg`. Новые строки,
   которые агент написал при разрешении конфликта, в историю попали непроверенными (проба 3). Rebase ветки задачи
   владелец разрешил именно для обновления от `main` (О-01). `pre-push` по REQ-18 проверяет только fast-forward и
   удаление, стражи приватности он не запускает. CI срабатывает уже после пуша, а историю без силового пуша не
   вычистить: это сказано в самом REQ-16.
   - Материал: msg п.1 и «Что есть сейчас»: «История уже переписывалась один раз из-за попавших в неё приватных
     данных»; ADR-0006; sur G-25: у донора B `pre-push` зовёт тот же полный набор стражей, что `pre-commit`; log.md,
     ответ В-01.
   - Место в spec.md: REQ-16, строки 327–328 («Хук git — единственный барьер стражей приватности до публикации»);
     REQ-18 (`pre-push` — только fast-forward и удаление); REQ-24 (стражи дерева — из `pre-commit` и CI, не из
     `pre-push`); expected_state: «Красный страж останавливает коммит, слияние или пуш»; AC-12 — проб приватности
     в `pre-push` нет. Строк с `rebase --continue` в spec.md — 0 (проба 1).
   - Это не обход хука агента: команды разрешены, умысла нет. Шкала Н-12 к находке не относится.
   - Что сделать: в REQ-18 или REQ-24 добавить, что `pre-push` прогоняет стражи приватности (страж индекса в режиме
     diff или дерева и страж запрещённых имён) и страж сообщения по коммитам пуша в том же диапазоне, что у REQ-19.
     Красный — пуш отклонён. В AC-12 добавить пробу: коммит после `git cherry-pick` или после `git rebase --continue` с
     выдуманным путём машины в строке разрешения конфликта — `pre-push` отказывает и называет коммит и файл. Исправить
     фразу REQ-16 о «единственном барьере».
   - критичность: существенная
   - уровень: требования

   - критичность: поверхностная
   - уровень: требования
