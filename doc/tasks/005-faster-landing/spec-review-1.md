## Находки

1. Срок git не снимает осиротевшие процессы на https и на недоступном адресе; сценарий AC-11 этого не ловит.

   Что не так: REQ-09 полагается на «внешний срок 20 с и собственный срок git (`http.lowSpeedTime`)», а Т-2 заключает, что при этом «процессов не осталось». Проба этого захода показала, что это верно только для обычного http. Адрес в https (у проекта интегратора `origin` именно такой) и недоступный адрес (пакеты не доходят) `lowSpeedTime` не останавливает: после убийства `git.exe` внешним сроком остаются `git.exe` и `git-remote-https.exe`.

   Цитата: «с `-c http.lowSpeedLimit=1000 -c http.lowSpeedTime=3` git завершился сам за 3,2 с (код 128, «Operation too slow»), процессов не осталось» (Т-2); AC-11: «сервер, принимающий соединение и молчащий … после срока не остаётся процессов `git` с этим адресом».

   Место: REQ-09, Т-2 (абзац «Сбои сети»), AC-11, Н-02.

   Замер (проба 1): молчащий порт по `http://` — код 128 за 3,3 с, процессов нет; тот же порт по `https://` — внешний срок 12 с убил процесс, остались 2 процесса git до закрытия порта; недоступный адрес по `https://` — после срока 8 с остались 2 процесса и были на месте через 14 с (убраны по номеру). Ключа срока соединения у git нет: проба с `http.connectTimeout=3` не завершилась за 7 с (проба 6). Убийство дерева процессов по номеру собственного запуска (`taskkill /T /F /PID`) оставило ноль процессов.

   Следствие: реализация, сделанная по тексту (`lowSpeedTime` плюс `execFile timeout`), на реальном https-источнике оставит на каждом сбое сети по два чужих для плагина процесса git, а тест AC-11 на обычном http будет зелёным. Требование «без осиротевших процессов» по тексту не выполняется, а сценарий его не проверяет.

   Что нужно в тексте: REQ-09 должно требовать снятия дерева процессов запуска по сроку (не только `timeout` у `execFile`), AC-11 должен включать молчащий сервер по `https://` и недоступный адрес с проверкой списка процессов после срока.

   критичность: существенная

   уровень: требования
