# Разбор 101: отмена и предел времени crew_watch убивают всё дерево команды

Задание — `task/message.md`. Источник: слова владельца в чате оркестратора, 2026-10-19: «по рекомендации» на предложение завести задачу по дефекту, найденному задачей 100 (раздел 4 её `analysis.md`); до этого: «как исключить такие тормоза без моего участия». Код — `opencode-plugin/watch.ts`, тест — `opencode-plugin/test/crew-watch-tree.test.mjs`, описание — раздел «Cancel closes the whole tree» в `opencode-plugin/README.md`.

## 1. Что сделано

- `watch.ts`: каждый процесс команды watch получает в окружении метку `CREW_WATCH_ID=<id наблюдения>` (в обоих режимах запуска: со скрытой консолью из задачи 100 и прежнем). Метку нельзя перебить полем `env` наблюдения.
- `watchTreePids(id)` и `killWatchTree(w, log)`: один проход Git Bash читает `/proc/<pid>/environ` всех процессов msys (около 0,4 с, в основном старт Git Bash), отбирает процессы с меткой этого наблюдения и добавляет их потомков по `PPID`. Все найденные Windows-pid (плюс pid самого наблюдения, если жив: запись, начатая прежним кодом без метки) закрываются одним `taskkill /T /F`; закрытие идёт до трёх кругов с повторным обходом. Не-Windows: те же pid, `SIGKILL`.
- Где вызывается: `dropWatch` (отмена, закрытая задача, перенос) теперь всегда, а не только пока жив pid наблюдения; `pollWatches` при коде 124 (предел времени) и при «оборвано». При обычном выходе команды ничего не убивается.
- Свойства watch сохранены: `.exit` атомарно, запись отменённого `status: done`, `cancelled`, `code: null`, код 124 и письмо о пределе времени, переживание службы, консоль из задачи 100.
- Тест `crew-watch-tree` (в цепочке `npm test`, строка в `test/README.md`), абзац в README плагина.

## 2. Красная проба до кода

Тест запускает через watch команду с деревом: `sleep`, `bash -c 'timeout .. sleep ..'` и нативную программу Windows (`cmd /c ping`); у каждого процесса уникальное девятизначное число в командной строке; поиск по числу и только среди процессов sleep, timeout, bash, cmd, ping. На коде до исправления `cancelWatch` оставил живыми все 8 процессов дерева: красный на первом шаге. Это шире, чем писала задача 100: не только `timeout.exe` и `sleep.exe`, но и нативные потомки и промежуточные `bash`. После исправления зелёные шаги: отмена, предел времени, «оборвано», `dropWatch` при уже мёртвом bash наблюдения; соседний процесс без метки остаётся живым после каждого шага. С выключенной чисткой в `pollWatches` шаг предела времени красный. Те же шаги зелёные с `CREW_HARNESS_WATCH_NO_CONSOLE=1`.

## 3. Две находки под нагрузкой

- Git Bash обхода иногда падает на старте: вывод пуст, код 1, как у дерева без процессов; без защиты дерево оставалось живым в 2–3 запусках из 8. Теперь последняя строка вывода обхода — маркер конца; без него обход повторяется до 6 раз.
- Шестизначное число в командной строке изредка совпадало с числами в командных строках чужих программ; очистка теста при отладке могла закрыть чужие процессы (в одном сбойном прогоне в «найденных» были процессы Electron-приложений, браузеров, Docker). Число стало девятизначным, находка и очистка берут только процессы sleep, timeout, bash, cmd, ping. Инцидент отладки: что именно закрылось, неизвестно (владельцу сообщено оркестратором); в коммит попала исправленная версия.

## 4. Выбор способа

Группа процессов msys отвергнута (`timeout` ставит себя в свою группу, нативные программы сигналом msys не закрываются); обход по `PPID` теряет усыновлённых потомков, взят как дополнение; job-объект недоступен из Node без FFI; одного `taskkill /T` по pid мало (это и есть дефект). Выбрана метка в окружении плюс обход `/proc/*/environ` плюс потомки по `PPID` плюс один `taskkill`. Метка — переменная окружения, не аргумент: невидима команде пользователя и наследуется всем, что запущено командой.

Ограничения: нативная программа с очищенным окружением, чей msys-родитель уже мёртв, в `/proc` не видна (на практике закрывается через `/T` по живому родителю); окно между обходом и `taskkill` допускает повторное использование pid, риск принят как пренебрежимый.

## 6. Расхождения с заданием и открытое

- Процессы, оставленные командой в фоне при нормальном выходе, не закрываются. → не нужно, потому что так было раньше, и команда может сознательно оставлять фоновую службу.
- Наблюдения, запущенные до перезапуска службы, меткой не обладают; для них закрывается дерево по живому pid наблюдения, как раньше. → не нужно, потому что после перезапуска старые наблюдения доживают сами.
- Тест предела времени пишет запись `.req.json` напрямую с лимитом 24 с: инструмент даёт минимум минуту. → не нужно, потому что проверяется тот же код `pollWatches`.
- Описание инструмента `crew_watch` и русская справка `crew_help` про отмену дерева не менялись (справка заморожена golden-файлом). → не нужно, потому что поведение «отмена останавливает команду» из них и так следовало.
- Служба не перезапускалась; в живой системе заработает после «обновляй» и перезапуска по слову владельца (AGENTS.md, п. 12). → не нужно, потому что это порядок владельца.
