# Задание: учёт затрат сессии — операция `usage_line` и файл `usage.log`

Заказчик и владелец: владелец репозитория `unitcraft/crew-harness` (он же отвечает на вопросы и принимает результат).
Репозиторий кода: `unitcraft/crew-harness` (`opencode-plugin/`, Канон, правила журналов). Операция записи прогресса `progress_line` первоначально
появилась в плагине `opencode-windows-env` (https://github.com/unitcraft/opencode-windows-env) и по решению владельца 2026-10-09 переносится в
crew-harness вместе с новой `usage_line`: журналы задачи — территория CrewHarness; в `opencode-windows-env` остаются запрет часов и штамп. Дата задания: 2026-10-09.
Источник: вопросы владельца 2026-10-09 («что ещё писать в журнал: затраченное время, израсходованные лимиты, название модели?»),
[раздел «Три журнала сессии» Канона](../../../canon/process.md).

Задача полная: разбор, план, реализация, сдача.

## Чего хочет владелец (его слова, 2026-10-09)

- «что еще туда можно писать? например, затраченное время, израсходованные лимиты, название модели, что-то еще?»
- «не будет ли потом проблем с разбором этого файла, чтобы, например, записать данные в БД?» — учёт должен быть машинным
  (фиксированные поля, версия формата), а не свободным текстом.
- Решение 2026-10-09 («по рекомендации»): `progress.log` остаётся узким (время метки), `profile.log` остаётся подсказкой профиля
  раннеру по методике (формат не расширяется), фактический учёт идёт в отдельный файл `usage.log`.

## Что есть сейчас

- `progress.log` — ход (`<код> k/N [ЧЧ:ММ] <что сделано>`); время ставит операция `progress_line` плагина `opencode-windows-env`.
- `profile.log` — строки `ПРОФИЛЬ от <код>: класс=… усилие=… размышление=… бюджет=… причина=…` (вход раннеру).
- Затраты сессии нигде не записываются: токены и стоимость видны только в окне и в карточке сессии OpenCode; лимиты подписки
  Claude Code измеряет проект `claude-limits`.

## Что нужно

Операция `usage_line` (инструмент плагина crew-harness, как `progress_line`: узкая, без оболочки, только дозапись в файл `usage.log` внутри
папки проекта, файл должен существовать или создаётся только рядом с `progress.log` задачи — решает разбор), которая сама
добавляет одну строку JSON на сессию с полем версии формата `v` и полями: код сессии; начало, конец, длительность; модель,
ступень, вариант (усилие); токены сессии (ввод, вывод, чтение и запись кэша) и стоимость; остаток лимитов подписки, где он
известен (Claude Code — из `claude-limits`); число вызовов инструментов и запусков тестов; наибольшая задержка службы за сессию;
итог (первая строка отчёта или `review-N.md`); хеш последнего коммита. Данные берутся у плагина (карточка сессии OpenCode,
журнал службы, git), агент передаёт только код сессии и итог. Правило «три журнала» записано в Каноне; формат `usage.log`
описывается в Каноне этой задачей.

## Что надо выяснить в разборе

- Откуда плагин берёт токены, стоимость, модель и вариант сессии (что отдаёт `ctx.session.get`/карточка), как считает время
  сессии (первая строка `progress.log`) и число вызовов инструментов; для сессий на провайдере Claude Code (внешний процесс).
- Как получать лимиты подписки (интерфейс `claude-limits`) и что делать, когда данных нет (поле пустое, не выдумывать).
- Где хранится `usage.log` (рядом с `progress.log` задачи), как защитить его от записи вне папки задачи и от переписывания истории.
- Как раннер и будущая БД читают файл (схема, версии, миграции формата).
