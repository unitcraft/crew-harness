# Задание: шаги прохода плагина не блокируют цикл службы — асинхронный git и предел времени шага

Заказчик и владелец: владелец репозитория `unitcraft/crew-harness` (он же отвечает на вопросы и принимает результат).
Репозиторий кода: `unitcraft/crew-harness` (https://github.com/unitcraft/crew-harness, ветка `main`). Дата задания: 2026-10-12.
Источник: наблюдение 2026-10-12: «мне кажется opencode service постоянно перезагружается». За девять минут (18:29–18:39) служба OpenCode стартовала семь раз: окна писали «Event stream stalled», затем несколько окон одновременно запускали `serve --service` (ошибка «порт уже занят»). Журнал плагина пишет задержку цикла службы 6–20 с постоянно и 37–40 с в 15:24–15:40 (UTC); когда задержка пришлась на проход плагина, шаг назван: почти всегда `leftWatch`, реже `assignReviewers`, `syncTitles` (например «задержка 36 878 мс, шаг leftWatch, проход идёт 37 с»).

Задача полная: разбор, план, реализация, сдача.

## Чего хочет владелец (его слова, 2026-10-12)

- «мне кажется opencode service постоянно перезагружается» и «согласен» с предложением: асинхронный git в шагах прохода, предел времени шага, журнал медленных шагов, тест.

## Что есть сейчас

- Плагин работает внутри процесса службы OpenCode; его проход (`pass`, шаги `leftWatch`, `assignReviewers`, `syncTitles` и другие в `index.ts`) вызывает `git` синхронно (`execFileSync` в `review.ts`, `leftoversOf` и родственные функции), пока git ждёт диск и процессор. На нагруженной машине один вызов занимает секунды, цикл событий службы стоит, окна считают службу мёртвой и запускают новую.
- 2026-10-07 шаг `leftWatch` уже облегчали (меньше задач за проход, `ls-remote` реже), но блокирующие вызовы остались, а нагрузка и число задач выросли.
- Время шагов прохода пишется в журнал только при задержке цикла (строка «loop lag»), общей картины нет.

## Что нужно

- **Асинхронный git:** вызовы `git` в шагах прохода (`leftoversOf` и функции, которыми пользуются `leftWatch`, `assignReviewers`, `syncTitles`) заменить на асинхронный запуск процесса (`execFile`/`spawn` без блокировки), предельное время одного вызова 5–10 с (останавливает процесс), число одновременных вызовов git в плагине не больше двух (очередь).
- **Предел времени шага:** если шаг идёт дольше заданного (рабочее значение 5 с, константа), он прерывается на границе вызова и продолжается на следующем проходе; в журнал одна строка: какой шаг, сколько, что осталось.
- **Журнал медленных шагов:** шаг, занявший больше 1 с, пишется одной строкой (имя, миллисекунды), без повторов на каждом проходе.
- Тест: шаг, ждущий зависший `git` (имитация: команда, спящая дольше предела), не блокирует цикл (параллельный таймер срабатывает вовремя) и прерывается по пределу; медленный шаг попадает в журнал один раз.
- Тесты по одному, с паузой 15 с ([AGENTS.md](../../../../AGENTS.md), п. 9: машина нагружена, тяжёлые прогоны не параллелить); красная проверка до правки.

## Что надо выяснить в разборе

- Какие функции в `review.ts`, `core.ts`, `index.ts` вызывают git синхронно из шагов прохода и из обработчиков, которые работают в цикле службы (`execFileSync`, `spawnSync`); какие из них можно оставить синхронными (короткие, локальные), а какие обязаны стать асинхронными.
- Нет ли других долгих синхронных мест (чтение базы OpenCode размером в несколько ГБ, обход папок): измерить, кто ещё блокирует цикл более секунды.
- Как сохранить порядок и атомарность шага при прерывании по пределу.
