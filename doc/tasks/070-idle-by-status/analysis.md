# Разбор 070: простой по статусу «в работе» без живой сессии

Задание — `task/message.md`. Основа — правило простоя задачи 063 ([разбор](../063-idle-between-sessions/analysis.md)).

## 1. Разбор

Случай (2026-10-17 ~01:25): владелец спросил по окну Новы «никто не работает?». Интегратор стоял молча при пяти открытых задачах,
значок `◷` не появился. Правило 063 считало «идущими» все задачи в статусах `starting`, `running`, `rework` — по статусу
«исполнитель работает», не глядя на сессию. По делу стояли #96 (заказ без исполнителя), #92 (исполнитель молчит часами), #94 и #91
(разбор ниже).

### Как отличены три случая

Вкладка-автор уже в состоянии `tasks` (все законные ожидания исключены порядком `statusOf`, разбор 063), открыта в окне, порог
включён. Новое — решение о каждой задаче автора в статусе `starting`, `running`, `rework` (функция `standing`, `idle-tab.ts`):

| Случай | Признак в данных | Причина (текст для владельца) |
|---|---|---|
| Нет сессии | не заказ; `executor` пуст, либо `executor` записан, а сводки сессии нет и визитка её не будит (`mayWakeCard`); задача не менялась дольше порога | `#96 без исполнителя` / `#96 сессии исполнителя нет` |
| Сессия молчит | сводка исполнителя есть, её состояние не из законных (`working`, `watch`, `owner`, `reply`, `question`), т. е. `task`, `tasks` или `idle`; молчание — от самого позднего из: конец последнего хода, непрочитанное письмо в ящике сессии, последнее изменение задачи — длится дольше порога | `#92 исполнитель молчит с 10:24` |
| Заказ другому интегратору | `kind: order`, `child` не записан; интегратор проекта-адресата (`order_to`) не ведёт ход сейчас; задача не менялась дольше порога | `#96 заказ не взят: nova-bignum.integrator вне окна` или `в окне, но не взял` |

Законное ожидание исполнителя причины не даёт: ход идёт (`working`), открыт `crew_watch` (`watch`), вопрос владельцу (`owner`), свой
вопрос с `expect_reply` (`reply`). Вопрос исполнителя автору (`question`) или «застряла» перед автором остаётся прежней причиной 063
«сессия ждёт указаний».

**«Поставлена, исполнитель ещё не запущен» против «заказ ждёт интегратора другого проекта».** Первое — задача `spawn`/`assign` с
записанным заранее id исполнителя и визиткой: пока не вышел порог, она «идёт»; вышел порог, а сессии нет — «нет сессии». Заказ —
`kind: order`, id исполнителя нет по построению, адресат — не наш проект, письмо `order-<проект>-<n>` лежит в ящике интегратора
адресата; его «берут» постановкой задачи с `parent` (в заказе появляется `child`). Поэтому до порога заказ задачей без исполнителя не
называется, а после порога называется отдельной причиной «не взят». Взятый заказ и заказ, чей адресат ведёт ход, — «идёт».

**#96 по записи** (только чтение): `kind: order`, `order_to: nova-bignum`, роль интегратор, статус `running` с 19:56, `child` нет,
исполнителя нет; в ящике интегратора `nova-bignum` три непрочитанных письма, сводки такого интегратора нет. Владелец выбрал исполнение
из проекта Нова (02:39), заказ отменён, работа продолжена задачей #99.

### Порог и ключ

Один ключ — `idle_tab_minutes` (20, 0 — выключено): условие «стоит» то же, что у 063, и владельцу достаточно одной настройки. Молчание
исполнителя считается от конца его хода, а не от письма автору: исполнитель, получивший письмо и ответивший пустым ходом, молчит
дальше. Сессия с долгим инструментом — `working`, а не «молчит».

### Стоит даже при идущей соседней задаче

«Между сессиями» (063) оправдывала идущая соседняя задача: вкладка может ждать её итога. Мёртвую задачу (нет исполнителя, молчит)
соседняя работа не оживляет: иначе #94 (исполнитель под `crew_watch`) скрыл бы #92 и #96.

### Ложные срабатывания

Не простой: исполнитель работает; исполнитель под `crew_watch`; открыт вопрос владельцу или свой вопрос с `expect_reply`; письмо
исполнителю в доставке (молчание считается от письма); задача или сессия только что появились и задача менялась недавно (порог от
`updated`); заказ взят (`child`) или адресат заказа ведёт ход; номер, занятый агентом вне OpenCode (`kind: external`). Правила 063
без изменений; без данных о сессиях (`idleBlockers` с тремя аргументами) прежнее поведение.

### Пробел: «принята, приёмщик ждёт cleanup»

На #91 Новы: задача `accepted` с 15:52, приёмщик под `crew_watch` «ждать отдельный cleanup plan #91» (предел 720 мин). Плагин шлёт
напоминания об уборке автору и приёмщику каждые `accepted_reminder_min` (30), но не больше `ACCEPTED_REMINDERS_MAX` (5): в ящике автора
все пять писем, шестого нет. После пятого плагин молчит (остаётся строка «не убрана N ч» в `/crew`), а для правила 063 `accepted` —
«идёт». **Пробел есть:** девять часов вкладка стояла законно по статусу. Закрыть его — решение о норме (после предела напоминаний
принятая задача с неработающим приёмщиком — тоже стоящая?), оно затрагивает 063 и напоминания; вынесено владельцу с рекомендацией «да»:
`doc/open-questions.md`, #5. Код 070 это не меняет.

### #94 — законно по правилу

Исполнитель под `crew_watch` «check #94 release gate / owner GO» (предел 61 мин) — открытое наблюдение, законное ожидание. Плагин не
отличит честное наблюдение CI от ожидания слова владельца по тексту заметки без ложных срабатываний. Наблюдение ограничено пределом;
кончилось — исполнитель молчит и после порога попадает под «молчит».
