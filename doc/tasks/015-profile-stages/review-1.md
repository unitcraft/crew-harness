## Существенные

1. Шаг авто-плана без набора идёт на `medium`, границы не применяются. `index.ts:959-962`: при `stepChoice === undefined` модель `cfg.spawnModels.medium`, ступень записи `"medium"` — без `clampTier`. При `tier_max: light` или `tier_min: heavy` шаги плана запускаются на sonnet. Доказано чтением кода: на этом пути нет вызова `clampTier`, нет `cfg.tierBounds`. Критичность: существенная (путь выбора модели из списка задания, срез «на всех путях»). Уровень: реализация.

2. Приёмщик без клетки (набор не включён или у набора нет клетки `develop_accept`/`plan_accept`) берёт `cfg.spawnModels[t.tier]` по записанной ступени задачи, без среза. `index.ts:586`. Запись `t.tier` срезана только при `crew_spawn`; у задач, поставленных `assign` (`core.ts:1845`, `1865`, ступень `"medium"`), шагов плана (п. 1) и созданных до смены границ срез не применяется. При `tier_max: light` приёмщик такой задачи уходит на sonnet. Доказано чтением: `index.ts:586` не вызывает `clampTier`, `cfg.tierBounds` в файле не упоминается. Критичность: существенная (приёмщик — отдельный путь из списка). Уровень: реализация.

3. Срез на пути без набора нигде не записан. `core.ts:1726` режет ступень молча; `stampProfile` (и строка журнала `tier clamp`, `core.ts:1359`) вызывается только при `chosen`. Требование 016 и README (`README.md:508-509`: «A clamp is written to the log of the plugin and to the task event») нарушены именно для основного случая — проект без наборов, который для этого и вводился. Доказано чтением `core.ts:1726-1749`, `1773`. Критичность: существенная (прямое требование «срез записывается в журнал»). Уровень: реализация.

4. `/crew-sets show` врёт про этап с клеткой `task`, унаследованной «ступенью ниже» (`delivery`, `delivery_accept` от клетки `task`). `profile-cmd.ts:381` строит таблицу «ступень задачи → модель» без `lowerTier`, а `resolveStageProfile` (`profiles.ts:368`) применяет `eff.lower`. Проба 1: набор `develop: claude/task`, `tier_max: medium`; show пишет у сдачи «medium → claude-code/sonnet», а `resolveStageProfile(..., "delivery", {taskTier:"medium"})` даёт `light`, `claude-code/haiku`; для `heavy` show «срез», а в коде `lowerTier(heavy)=medium` и среза нет. Требование 015: эффективная модель каждого этапа видна в show — для этих клеток показана не та. Критичность: существенная. Уровень: реализация.

5. Справка опросника врёт про приёмку. `config-schema.ts:47`, поле `why` ключа `profile_sets`: «приёмка без клетки берёт другую семью справочника, если она есть». Принятое решение: этап проверки без клетки идёт по `spawn_models`; правило семьи — только заметка в show (`profiles.ts:294-297` и README это говорят верно). Фраза попадает в `crew_config guide` и вводит владельца и агентов в заблуждение. Критичность: существенная (ложное утверждение о поведении, противоречит Канону и README). Уровень: реализация.

6. `crew_help` не описывает ни `tier_min`/`tier_max`, ни восемь этапов, хотя задание 016 прямо требует справки `crew_help`. В `core.ts` изменены только примеры глаголов (`1051-1052`); текст `crew_spawn` (`1148-1152`) по-прежнему говорит «tier на входе выбирает ступень внутри семьи набора» без упоминания границ, а описание `/crew-sets` (`1118-1121`) — «модель исполнителя, приёмщика, плана». Доказано чтением. Критичность: существенная (явный пункт «Что нужно» задания 016). Уровень: реализация.

## Поверхностные

7. `crew_config set` принимает `tier_min` выше `tier_max` (в одном вызове и по двум). `invalid()` проверяет значение по одному ключу, связи между границами нет (`core.ts:2251-2256`; для профилей связи есть через `linkErrorsOfWrite`). Ошибка потом видна в `crew_doctor` и show, границы выключаются. Поверхностная: ошибка настройки есть и обнаруживается, спека не требует отказа на записи. Уровень: реализация.

8. Срез ведёт к отказу, если у семьи нет профиля на срезанной ступени (проба 1: kimi только `heavy`, `tier_max: medium` — «приёмка: kimi/heavy → нет профиля»; в бою это отказ «профиля kimi/medium нет в справочнике», задача «сдана без приёмщика»). Текст отказа (`profiles.ts` в `resolveStageProfile`) не называет срез причиной. Поверхностная: пример README даёт всем семьям три ступени, отказ диагностируется; но в плане/требованиях не решено, что делать при дыре в справочнике (искать ближайшую ступень или отказывать). Уровень: требования/план.

9. Окна и строки приёмки не учитывают срез. `reviewerModels` (`profile-cmd.ts:449-460`) и строки окон в show для клетки `task` печатают окна всех трёх ступеней, включая срезанные; `st.endsWith("_accept")` теперь втягивает явные `spec_accept`/`delivery_accept` в подпись «Приёмка и приёмка плана», хотя плагин их не запускает. Поверхностная: только справочный текст. Уровень: реализация.

10. `crew_task reassign` без набора оставляет `t.model` записи (`core.ts:2190-2205`): новые границы при передаче не применяются. Поверхностная: «без набора — модель записи, как прежде» — прежнее и документированное поведение; но в списке путей среза reassign назван. Уровень: реализация (или требования: решить, применять ли срез при передаче).

11. Входная `tier` у `crew_send` (`core.ts:1587`) границами не режется, а `config-schema.ts:49` пишет «любая ступень любого этапа и входа tier»; README уточняет «`tier` of `crew_spawn`». Поверхностная: письмо выбирает вкладку, не модель; нужно привести формулировку схемы к README. Уровень: реализация.

12. В собственном `.opencode/crew-harness.json` репозитория все семь наборов по-прежнему с этапом `accept` (строки 68-176). Читается верно (проба 3), миграции нет — ожидаемо для «переходного срока», но срок и момент переписывания файла нигде не названы. Поверхностная: совместимость работает. Уровень: план.

- Таблица и наследование (`INHERIT`, `AUTHOR_OF`, `effectiveCell`): совпадают с Каноном; `spec`←`plan`, `spec_accept`←`plan_accept`, `delivery`/`delivery_accept` на ступень ниже; пустая основа даёт `undefined` (spawn_models), приёмка без клетки не наследует.

- Границы: min выше max или неверное значение — границы не применяются, текст в `problemsOf`/doctor; порядок «ступень ниже, затем срез» корректен; в подпись состояния (`stateSignature`) границы не входят, но уведомление доходит по 30-секундному циклу (`index.ts:757`).
