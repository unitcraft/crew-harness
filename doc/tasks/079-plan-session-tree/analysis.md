  дерева у задачи тогда не было, сессии работали там, куда их перевёл интегратор. Интегратор подготовил дерево вручную и записал его

- Сессия С3п-2 (запуск №29): в истории записи — «место задачи достроено по настройкам: worktree <папка деревьев>/crew-harness-061-…, ветка
  task/061-…», затем «не запущена: … git worktree add <тот же путь> task/061-…». В журнале плагина таких строк 23, с 18:01:55 до 18:30:27 UTC
  (запуск откладывается и повторяется раз в `START_RETRY_MS`, 2 минуты; автору уходит одно письмо на причину).
- Сейчас в записи путь `worktree` — дерево, подготовленное вручную (его вписал интегратор после последнего отказа). С таким путём плагин
  запускает сессию как обычно. Ручная правка обходила дефект, но не чинила его: любая запись без пути (или с путём, которого нет) приводила к
  тому же отказу.

## 2. Где плагин решает, какое у сессии дерево

- `core.ts`, `taskPlace`: путь дерева и ветка задачи по настройкам (`worktrees`, `worktree_name`, `branch_name`); при постановке пишутся в запись
  той же записью. Нет `worktrees` в настройках — путь не пишется, остаётся только ветка.
- `core.ts`, `spawnInFolder` → `startSession`: запись сессии: `place` task (дерево задачи, своего поля пути у сессии нет) или `own` (поля
  `worktree`, `branch` по шаблону; в `side` пишутся и они).
- `core.ts`, `crew_task track`: пишет только в `side` (список для уборки); `worktree` и `branch` записи задачи, `worktree` сессии не меняет,
  существование дерева и совпадение ветки не проверяет.
- `index.ts`, `startTask`: нет пути в записи, а в настройках `worktrees` есть — путь достраивается по шаблону; `ensureWorktree` для дерева
  задачи; для сессии `own` — ещё раз для `ses.worktree`; потом `writeLaunch` пишет строки запуска в дерево задачи и дерево сессии, `session.create`
  открывает сессию в `dir`.
- `review.ts`, `ensureWorktree`: папка по пути есть и на ней нужная ветка — готово; папки нет — `git worktree add <путь> <ветка>` (или `-b` от базы).

## 3. Где рождается второе дерево и почему

Источник — `ensureWorktree` (`review.ts`): он знает один путь из записи или настроек. Если папки по нему нет, он всегда делает `git worktree add` и
не спрашивает, стоит ли ветка уже в другом дереве. В 061 путь из настроек свободен, а ветка `task/061-…` выбрана в дереве, подготовленном вручную:
git отказывает, и запуск стоит. Если бы git не отказал (ветка не выбрана нигде), плагин создал бы второе дерево по второму пути — тоже неверно,
когда у записи есть другое. Запись `track` на это не влияла: она лежит в `side`, и `startTask` её не читает.

Вторая причина — путь, который помнит git, а папки нет (дерево удалили руками, `git worktree prune` не делали): `git worktree add` без `--force`
тоже отказывает. Сообщение плагина при этом было первой строкой «Command failed: git …» без причины от git.

Воспроизведено на одноразовом репозитории (`test/crew-session-tree.test.mjs`): задача с папкой поставлена при настройках без `worktrees` (запись
без пути), дерево сделано вручную на ветке задачи и записано `track`, настройки получили `worktrees`, затем `crew_spawn {task, session: "С3п",
place: "task"}` → на старом коде «записана, но не запущена: worktree … не создан», сессия не открыта, строки запуска не записаны.

## 4. Что сделано

`review.ts`, `ensureWorktree(repoDir, worktree, branch, base, rules)`:
1. Папки по пути нет → читается `git worktree list --porcelain`. Ветка уже выбрана в живом дереве:
   - это основная копия проекта → отказ «ветка … выбрана в основной копии проекта <путь>»;
   - дерево записано за другой открытой задачей проекта (её `worktree`, `worktree` её сессии или дерево из её `side`) → отказ «ветка … занята
     деревом <путь>: оно записано за задачей …»;
   - иначе дерево берётся как есть: возвращается его путь, второго `worktree add` нет.
2. Ветку помнит дерево с исчезнувшей папкой или путь записан в git без папки → `git worktree add --force` (ветка и коммиты целы).
3. Ошибка git называет причину («fatal: …»), а не первую строку «Command failed».

`index.ts`, `startTask`: если вернулось другое дерево, запись выравнивается по нему (`t.worktree` у дерева задачи, `ses.worktree` у сессии `own`),
в историю идёт событие; для сессии `own` дерево ещё и записывается в `side` для уборки. Дальше всё идёт через `t.worktree` (`writeLaunch`,
`nextLaunch`, `taskLog`, `session.create`).

Дерево вне папки деревьев проекта принимается, если оно подготовлено вручную и стоит на ветке задачи; прежнее правило «путь вне папки» действует на
путь из записи или настроек до `ensureWorktree` и не менялось. Не менялись: обычный запуск, `track`, уборка, `ownership`.

## 6. Не сделано

- `crew_task track` не выравнивает запись задачи по дереву, которое записал → не нужно, потому что единственное место, где путь дерева нужен записи, — запуск сессии, а там выравнивание теперь есть.
- Живая запись 061: путь дерева уже исправлен вручную интегратором → не нужно, потому что запись живая, по заданию правится только интегратором, а плагин с правкой работает и до исправления.
- Дерево на ветке, записанное за закрытой (принятой) задачей, считается свободным → не нужно, потому что закрытая задача свой путь уже убрала, а запись может ссылаться на давно удалённую папку.
- Ветка занята деревом вне репозитория проекта (другой клон) → не нужно, потому что `git worktree list` показывает только деревья этого репозитория, чужой клон не делит с ним `refs/heads`.
