1: # Выполнение задания агентом: сессии, промпты, повторы
2: 
3: Схема для минимального случая: есть только ИИ-агент, задание заказчика и этот репозиторий; трекера и команды нет. Это урезанное применение методологии ([methodology.md](methodology.md), раздел 3): человек совмещает роли владельца и оркестратора, агент в разных сессиях играет исполнителя и проверяющего. Работа внутри каждой сессии идёт по [task-algorithm.md](task-algorithm.md), правила повторов взяты из [methodology.md](methodology.md), раздел 10, требования к текстам наружу — из раздела 12.
4: 
5: Планирование и реализация разделены точкой утверждения плана. Между ними может пройти любое время, и их могут выполнять разные агенты: всё состояние лежит в файлах, промпты не опираются на прошлые разговоры.
6: 
7: Как вести этот цикл программой — запускать сессии, считать заходы, показывать прогресс по шагам, собирать запросы под кеш контекста — описано в [task-runner.md](task-runner.md). Форматы строк, которые программа читает из файлов цикла, заданы там же: часть из них требуют промпты ниже, остальное программа дописывает к промпту машинным хвостом.
8: 
9: ## Схема
10: 
11: ```
12: Подготовка (вы)
13:    ↓
14: С1 Разбор ─────────────────→ spec.md (черновик)
15:    ↓
16: С2 Проверка разбора ───────→ spec-review-N.md
17:    ├─ есть существенные ──→ С1 правка ──→ С2 заново
18:    ↓ два захода подряд без существенных
19: Вы: вопросы заказчику, ответы, подтверждение сценариев
20:    ├─ ответ меняет цель, границы, сценарии ──→ С1 правка ──→ С2
21:    ↓
22: spec.md: «утверждено»                              ══ граница 1 ══
23:    ↓
24: С3 План ───────────────────→ plan.md (черновик, базовая ревизия)
25:    ↓
26: С4 Проверка плана ─────────→ plan-review-N.md
27:    ├─ есть существенные ──→ С3 правка ──→ С4 заново
28:    ├─ план требует менять требования ──→ С1 правка ──→ С2 ──→ граница 1 ──→ С3 правка
29:    ↓ два захода подряд без существенных
30: Вы: решения из списка «требует утверждения»
31:    ├─ решение меняет план ──→ С3 правка ──→ С4
32:    ↓
33: plan.md: «утверждено»                              ══ граница 2 ══
34:    ↓            любое время, любой агент
35: С5 Реализация ─────────────→ код + result.md (ведётся по ходу)
36:    ├─ остановка «ревизия» или «план» ──→ С3 правка ──→ С4 ──→ граница 2 ──→ С5
37:    ├─ остановка «вопрос» ──→ вы отвечаете ──→ маршрут по уровню ответа (ниже)
38:    ↓ result.md: «Статус: готово»
39: С6 Проверка реализации ────→ review-N.md
40:    ├─ уровень «реализация» ──→ С5 правка ──→ С6 заново
41:    ├─ уровень «план» ────────→ С3 правка ──→ С4 ──→ граница 2 ──→ С5 правка ──→ С6
42:    ├─ уровень «требования» ──→ С1 правка ──→ С2 ──→ граница 1 ──→ С3 правка ──→ …
43:    ↓ два захода подряд без существенных
44: Вы: решение по строкам FAIL, NOT VERIFIED, Known limitations
45:    ↓
46: С7 Сдача ──────────────────→ delivery/
47:    ↓
48: С8 Проверка сдачи ─────────→ delivery-review-N.md
49:    ├─ есть существенные ──→ С7 правка ──→ С8 заново
50:    ↓ два захода подряд без существенных
51: Вы: коммит и пуш, отправка заказчику
52:    ↓
53: Обратная связь ──→ С9 Разбор обратной связи ──→ feedback-N.md
54:    ├─ требования ──→ С1 правка ──→ С2 ──→ граница 1 ──→ С3 правка ──→ … ──→ С8
55:    ├─ план ────────→ С3 правка ──→ С4 ──→ граница 2 ──→ С5 правка ──→ … ──→ С8
56:    ├─ реализация ──→ С5 правка ──→ С6 ──→ С7 ──→ С8
57:    └─ только «отвечаю доводом» и «отвергаю» ──→ С7 ──→ С8
58: ```
59: 
60: **Маршрут ответа по уровню**, кто бы ни ответил и когда бы ответ ни пришёл: ответ не меняет spec.md и plan.md → «С5 продолжение», подтверждение умолчания — строкой в log.md; ответ меняет план → С3 правка; ответ меняет требования, границы или сценарии → С1 правка. Сделанные срезы остаются в рабочем дереве, С5 после повторного утверждения возобновляется по result.md.
61: 
62: ## Подготовка
63: 
64: 1. Создайте папку задачи рядом с папкой кода и скопируйте в неё task-algorithm.md из этого репозитория: промпты называют файлы относительно папки задачи. Заведите пустой log.md.
65: 2. Всё от заказчика положите в task/ как есть; текст сообщения и ссылки — файлом task/message.md.
66: 3. Каждую сессию запускайте из папки задачи, промпт вставляйте целиком первым сообщением и дописывайте к нему машинный хвост из task-runner.md («Машинный хвост»): общую часть и сессионную часть этой сессии, со строкой «Сессия: <код>» и единицей прогресса: без неё агент журнал хода не ведёт. Если цель уточнена после прежнего запуска, уточнение идёт в то же первое сообщение перед прежней постановкой с пометкой «действует уточнение», датой и источником (слово владельца); прежнюю постановку не удаляют. `<репозиторий>` замените абсолютным путём к рабочему дереву кода на ветке задачи. Если агент не пишет за пределы папки запуска, запускайте его из папки кода и первой строкой промпта дайте «Папка задачи: <путь>»: имена файлов читаются относительно неё.
67: 4. Одна задача — одна папка задачи и одно рабочее дерево без чужих незакоммиченных правок: две задачи в одном дереве смешают diff для С6 и коммит после С8.
68: 5. Если кода ещё нет: создайте папку кода, инициализируйте в ней систему контроля версий и сделайте первый коммит до С1. Без него нет базовой ревизии для plan.md, сверки в С5 и diff для С6. Выбор стека агент делает в С1 по шагу 6 и выносит в С3 в список «требует утверждения»; создаваемые файлы в карте помечаются «новый».
69: 6. Новая сессия — новый чат или новый запуск агента без истории предыдущих. Оборвавшуюся сессию запускайте заново тем же промптом, закрыв прежнее окно агента и убедившись, что не осталось ни его процесса, ни запущенных им команд: промпты читают состояние из файлов. Каждый запуск, в том числе повтор, до старта агента отмечайте в log.md строкой `запуск №<n> <код> [время]` с порядковым номером и тем же номером дописывайте в progress.log `<код> 0/0 [время] запуск №<n>`: сессия, которую вы не запускали, — существенная находка (task-runner.md, «Строки progress.log»).
70: 7. Если задач несколько, порядок и пересечения запишите в task/message.md разделом «Связи» перед границами, по одной строке на пункт: «Зависит от» — какие задачи должны быть сделаны или влиты раньше; «Блокирует» — какие задачи ждут эту; «Пересекается (файлы)» — общие файлы и места кода, чтобы тот, кто сливается вторым, знал, где ждать конфликта; «Начинается после» — условие запуска сессий (слияние другой задачи, ответ заказчика). Нет связи — «—». Задачи называйте путями их папок. Раздел правите вы; С3 берёт из него пересечения и порядок слияния. Без раздела порядок слияния двух задач, правящих одни файлы, обнаруживается уже конфликтом при слиянии второй.
71: 
72: ```text
73: task-algorithm.md
74: task/                  всё от заказчика как есть
75: task/feedback-N/       обратная связь после сдачи
76: spec.md                спецификация; статус в первой строке
77: spec-trace.md          опись источников, таблица покрытия, история заходов, если вынесены из spec.md («Правила», размер документов)
78: spec-review-N.md
79: plan.md                план; статус и базовая ревизия в первых строках
80: plan-review-N.md
81: result.md              отчёт реализации, ведётся по ходу; статус в первой строке
82: current.md             где действуют результаты задачи, не код; остальное в папке — история (создаётся шагом плана)
83: review-N.md
84: delivery/              тексты наружу
85: delivery-review-N.md
86: feedback-N.md          разбор обратной связи
87: log.md                 ваш журнал: каждый запуск сессии, на каждый заход первая строка его файла
88:                        проверки и ваше решение (следующая сессия или остановка); агент сюда не пишет
89: ```

91: ## Правила
92: 
93: - **Всё состояние в файлах.** Любую сессию можно начать заново любым агентом.
94: - **Слово человека записывается с датой и источником** («владелец, ГГГГ-ММ-ДД»), по возможности цитатой, а не пересказом: через неделю иначе не отличить его решение от догадки исполнителя.
95: - **Статус в первой строке spec.md и plan.md:** «Статус: черновик» или «Статус: утверждено, дата, кто»; форма строки одна, её читает программа (task-runner.md). Утверждение ставите только вы. Любая правка после утверждения возвращает статус «черновик», и документ заново проходит проверку и утверждение.
96: - **Реализация начинается только с утверждённых spec.md и plan.md.** Если план реализуется не сразу, он сначала сверяется с кодом по базовой ревизии.
97: - **Проверка всегда в новой сессии**, не в той, что писала. Правку можно делать в любой сессии.
98: - **Существенная находка** меняет требования, границы, сценарий, план, доказательство, число или то, что уйдёт заказчику. Находка без названной критичности считается существенной. Поверхностной проверяющий называет находку только с записанной причиной, почему она не меняет ничего из этого списка; находка про число, доказательство, сценарий или текст наружу поверхностной быть не может. Засчитывая заход, вы читаете все находки, а не итог, и вправе поднять критичность.
99: - **Отклонённая исполнителем находка закрывается не им.** Следующий заход проверки сверяет обоснование с материалами и кодом: согласен — закрывает; не согласен — повторяет находку как существенную с доводом. Отклонённую дважды решаете вы.
100: - **Остановка** наступает после двух заходов проверки подряд без существенных находок.
101: - **Чистый заход засчитывается только с тремя пробами.** Проба это команда с дословным выводом либо перечень осмотренного с числом и с тем, что там точно есть и что нашлось ([methodology.md](methodology.md), разделы 10 и 13). «Прочитал и сравнил» пробой не является: такой заход чистым не засчитывается и идёт заново.
102: - **Потолок четыре захода на цикл проверки**, считая от последней правки по вашему решению или по обратной связи. Если существенные находки остаются, вы решаете: урезать объём — правка spec.md, дальше по схеме; разбить — требования и открытые находки уходят в части задачи с явным покрытием (раздел «Большая работа: эпик»); спросить заказчика — вопрос с умолчанием и сроком; остановиться — С5 правка с исходом «не делаю: решение владельца, дата», открытые находки уходят в Known limitations result.md, дальше С7.
103: - **N — номер захода.** Внутри цикла проверки не обнуляется: после обратной связи следующий файл проверки получает номер за последним существующим, иначе прежний перезапишется. У feedback-N свой счётчик — номер раунда обратной связи. В промптах правки N файла с находками и N в «Изменения захода N» один и тот же.
104: - **Размер задачи оценивается до дорогой работы.** Перед С1 по входу: цель пишется одной фразой; число источников и просьб; число затронутых частей системы; риск. Внутри С1 опись источников и таблицу покрытия сессия пишет первыми и останавливается у ворот с числом строк покрытия (будущие REQ): объём уже известен, текст ещё не написан. Слишком большая задача делится сразу: опись и покрытие не пропадают, их строки уходят в спецификации частей. Классы размера и порог «слишком большая» — параметры проекта. Глубина проверки спецификации — по большему из объёма и риска: у малой задачи без риска достаточно одного чистого захода с тремя пробами, у остальных — два. Без ранней оценки подготовка слишком большой задачи тратится целиком, а потом документ всё равно режут.
105: - **Размер документов.** Проект задаёт предел размера spec.md, plan.md, result.md по классу задачи; выход за предел — предупреждение, на ближайших воротах вы выбираете: сократить, разбить или записать причину. Сокращение — только без потери требований, источников и решений. Сначала перенос: опись, таблица покрытия и история заходов уходят в spec-trace.md, нормативные абзацы остаются в spec.md дословно; это механическая правка, статус не слетает, если дословное совпадение подтверждено. Потом переписывание: пересказ заменяется адресом (ссылка на файл и якорь, идентификатор), слова меняются, поэтому статус «черновик» и проверка С2; числа REQ, AC, DNC, решений и вопросов до и после сверяются. Выжимка отдельным файлом не хранится: она не источник и не основание вердикта. Документ, который и после сжатия выше предела, делится, а не готовится заново: REQ и AC уходят в части дословно с теми же номерами. Причина: копия расходится с оригиналом при первой правке, а каждый заход проверки перечитывает документ целиком.
106: - **Тесты по сценариям до кода.** Для нового поведения проверки по сценариям приёмки пишутся до реализации и до неё падают по названной причине (команда и вывод — в result.md); где независимость стоит цены, их пишет отдельная сессия, не автор кода. Для рефакторинга проверки сохранения поведения остаются зелёными; для задач без исполняемого результата «не применимо» записывается словом с причиной. Исправление дефекта — по-прежнему красный прогон до правки. Без этого тесты автора зеленеют ровно на тех расхождениях, которые должны ловить.

108: ## Задача, сессия, подзадача
109: 
110: Задача — папка задачи («Подготовка») со своей spec.md, приёмкой и воротами. Сессия — один запуск агента по промпту цикла (С1–С9) внутри задачи. Подзадача — пункт plan.md, который выполняется внутри сессии и своих ворот не имеет. Как отличить: нужна своя spec.md и приёмка — это задача (в том числе дочерняя задача эпика); нужен отдельный запуск агента по промпту — сессия; остальное — подзадача.

123: 1. Опись источников: каждый файл, картинка, ссылка, страница, таймкод видео;
124:    статус: прочитан / прочитан частично (что не получено) / недоступен; итого число.

145: ```text
