## 1. На что из исходного вопроса README не ответил

Исходный запрос: «расскажи, как в этом проекте организована разработка, какая используется
методология, **это общеизвестная методология?** запиши так, чтобы применить к новому проекту».

**Раздела о соотношении с известными методологиями в README нет** — ни одно название не
встречается: ADR назван «документом архитектурного решения», Definition of Done не употреблён,
сценарии «Когда … тогда» не связаны с BDD, trunk-based и Conventional Commits отсутствуют,
спринты вынесены за рамки.

Ответ по источникам — процесс не является одной именованной методологией, это сборка:

| Слой | Из чего собрано (названо в каноне — Н, по существу — С) |
|---|---|
| Поставка | trunk-based development (Н), одна защищённая `main`, squash-слияние, rebase вместо merge, удаление ветки; Conventional Commits (Н), из типа и scope собираются changelog и версия |
| Знание | ADR в формате MADR-lite (Н); канон как единый источник истины, спор с ним только через ADR; docs-as-code (С): статьи и ADR в репозитории тем же MR |
| Архитектура | contract-first — OpenAPI/AsyncAPI до кода (С); паттерны микросервисов: база на сервис, API-шлюз, transactional outbox, идемпотентные потребители, DLQ, BFF (Н частично); C4 (Н) |
| Ритм | спринт две недели, декомпозиция внутри спринта, Definition of Done (Н) — Scrum по духу без остальных церемоний; Scrum и Kanban не названы |
| Приёмка | сценарии «когда — тогда» (BDD / Given-When-Then без Given, BDD не назван); CI quality gate с пронумерованными правилами по уровням и подавлениями со сроком (аналог гейта SonarQube); shift-left (С): локальный прогон до пуша |
| Ревью | четыре глаза (С): ни строки без второго человека; коллективное владение кодом (XP, С): владельцев модулей нет |
| ИИ-слой | ИИ-агент с командами и хуками: слэш-команды, скиллы, субагент чтения, послойный контекст (Н); ralph loop (Н); spec-first (С): постановка как артефакт до кода |

**Самодельное в каноне проекта:** формула изоляции, доведённая до «одна сессия»; шаг «разработчик
дописывает технические сценарии и ждёт утверждения»; детерминированный вердикт при ИИ-ревью как
источнике находок; «статья тем же MR»; «живой контур с названным адресом»; «подавление ≠ отклонение
от правила»; TODO с адресатом; скилл безопасности на любом диффе; правила «-AI» не блокируют.

**Наша надстройка самодельная целиком:** оркестратор/исполнитель, вратарь старта, четвёрка
открытого вопроса, перепроверка по вехам, артефакты вне диффа, классы дефектов, файл состояния,
признаки жизни, правила измерения, сводный обзор, проверка исходящего текста, аудит своих находок.
Ближайшие известные аналоги — Definition of Ready для вратаря, blameless-постмортем с корневой
причиной для классов дефектов, паттерн orchestrator–worker для ролей.

**Нигде в источниках не названы:** Scrum, Kanban, GitLab Flow, DDD, BDD, docs-as-code, AI-first,
spec-driven, shift-left, XP, SemVer, 12-factor. Команда проекта себя ни к одной школе не относит;
README может честно сказать «сборка из известных практик плюс самодельная надстройка».

**Второе, чего нет как рамки:** README не разделяет два слоя — **канон проекта** (что предписывает
заказчик: путь задачи, ветки, MR, CI, DoD, ADR, скиллы, роли) и **нашу надстройку** над ним
(задания сессиям, перепроверка, свод, файл состояния). Для переноса это разделение ключевое: первый
слой новый проект должен *завести* (раздел 17), второй — приносит с собой оркестратор. Сейчас
раздел 3 смешивает оба, а раздел 17 описывает заведение первого слоя одной-двумя строками на шаг.
README и не говорит, что оркестратор — сам ИИ-сессия, работающая без подтверждений действий, а
владелец — человек с выключателем режима.

## 2. Где README расходится с источниками

1. **Роли склеены (разд. 2, 3, 8).** «Приёмщик (руководитель/заказчик): очередь работ, приоритеты,
   ревью, приёмка и закрытие» — четыре роли канона в одной. По канону ревьюер — **любой второй
   разработчик** (владельцев модулей за людьми нет), принимает тестировщик по сценариям на dev после
   слияния, закрывает аналитик, согласовав с бизнесом; руководитель решает то, что не решается
   правилом. В цикле разд. 3 шага «ревью человеком» нет вовсе. Оговорка живого проекта, которой тоже
   нет: ревьюер в MR обычно не назначается (25 из 30 влитых без ревьюера), приёмщик находит MR сам и
   сливает, свои MR сливает без ревью — «MR с обязательным ревью» (разд. 1) на новом проекте прочтут
   как всеобщее. [onboarding 07:30-43; kanon-vyzhimka-zadachi 153-155, 184; журнал 1088, 1360;
   komanda 298, 380]
2. **«Оркестратор не делает замеров внутри репозиториев» (разд. 2, стр. 43, 57-60)** — источники
   требуют обратного: состав предмета замеряется **оркестратором до выдачи** прогоном по всем клонам,
   «в задании названо, чем замерено»; оркестратор делает fetch и считает отставание каждого клона,
   в своде — пробу ребейзом в отдельном дереве и гигиену клонов; факт добывается **до** выдачи вопроса
   владельцу. Неполноту замера источники лечат **названной областью**, а не запретом. README
   противоречит и себе: разд. 2 отдаёт оркестратору «git-состояние клонов», разд. 5 требует «измерено
   до выдачи». Исключение, которого тоже нет: когда у исполнителя нет среды или он отказал, замер и
   публикация делаются из окна оркестратора, но текст проверяет тот, кто его не писал.
   [zadanie-start 71-78, 100-104, 404-424; komanda 166-194; vopros-vladelcu 37-39;
   schyot-i-perechen 98-100; журнал 5406, 5743]
3. **Критерий остановки перепроверки (разд. 7) передан в отменённой редакции.** README: «последний
   заход не дал ни одной правки; пока заход даёт правку — не публикуется, даже мелкую». Источник: один
   чистый заход критерием **не является** — он идёт сразу после правок и проверяет ровно то, что
   только что переписано; останов — **два захода подряд без существенных находок**; у каждой находки
   три вида критичности (существенная — меняет объём, доказательство, число или то, что уйдёт наружу;
   поверхностная — формулировка, порядок абзацев **ниже отсечки**, уточнение ссылки; не по адресу —
   чужой дефект, issue); находка без названной критичности считается существенной; **правка только
   текста** (описание, комментарий, статус, номер) круга не требует и проверяется на следующей вехе,
   отдельный круг — только при правке кода или тестов; второй заход — узкий, по трём вопросам;
   **потолок четыре захода на веху**, пятый с одними поверхностными — стоп и вопрос владельцу
   (упёрлись в выбор, не в проверку); критерий не выполнен → следующий заход тем же ходом, **без
   вопроса владельцу**. Прежняя редакция «круг после любой правки» дала семь заходов без находок —
   README воспроизводит именно её. [pereproverka 61-65, 620, 653-689, 704-706; soobshchenie 129-147;
   журнал 114, 557, 1287]
4. **«Заводить ли задачу по находке — заводить, всегда» (разд. 11)** — источники ставят условия:
   находка **сначала обязана быть находкой** («наблюдение с неизмеренным корнем в issue не идёт»,
   находка по одному признаку — ошибка заведения: заявлена по скриншоту, отозвана после замера);
   перед заведением — проверка дубля по ключевым словам предмета и **проверка дома** (открытая задача
   или решение — комментарий туда, новый issue раздвоит предмет); вопрос с ответом в каноне —
   непрочитанный документ, а не находка; признак лишнего issue — нет затронутого репозитория и ничего
   не меняет (заведённая задача закрыта приёмщиком как лишняя); расхождение внутри своей постановки —
   строкой в описании, без issue; для документации — правило отбора «заставит потерять время или
   прийти к неверному выводу». [журнал 6271-6273, 4664, 1458-1474, 385, 687, 120, 2454; nahodki 59-70]
5. **Чьё слово на публикацию и что его заменило (разд. 2, 3, 6, 8).** README не называет, кто даёт
   слово исполнителю, и в разд. 3 «исполнитель публикует приёмочный комментарий» расходится с разд. 2
   «не публикует ничего без слова». Источники: с 08.09 слово даёт **оркестратор** после чистой
   перепроверки, владелец не спрашивается («спрашивать слово, не показав текст, — ритуал, а не
   защита»); защиту заменили три вещи — перепроверка **до**, доклад ссылками **после**, перечень
   публикуемого **поимённо** в тексте исполнителю, сверх него ничего не создаётся. Канон при этом
   **запрещает** коммит и пуш без явной просьбы человека («жёсткий запрет воркспейса, а не настройка
   вежливости»), и неинтерактивная сессия работает без подтверждений действий — README не называет ни
   отклонение от канона, ни его цену, ни компенсацию. За владельцем в источнике **закрытый список**:
   сообщение заказчику; действия в чужой очереди работ (закрыть чужую задачу, назначить, приоритет —
   «своё правим сами, чужое — просьба»); выбор за пределами задачи, включая отказ от требования канона
   и действия с побочным эффектом на чужое; плюс право остановить режим словом. Всё, чего в списке
   нет, делается без спроса. И с 16.09 issue-находка заводится без отдельного слова — README
   фиксирует состояние 27.08. Полный перечень запрета при этом не включает **слияние** — источник его
   называет. [avtorezhim 23-26, 77-109; журнал 6519-6520, 5739, 4757-4762, 6167, 6703;
   zadanie-finish 131; onboarding 06:67, 08:94]
6. **Признак жизни (разд. 14) — в трёх местах прежняя редакция.** «Пока исполнитель работает» —
   неверно: строка идёт до слова владельца «стоп», и когда сессии нет, и при ожидании чужого хода
   (там нужнее всего), и при ожидании слова владельца; куплено дважды (10 минут молчания; таймер на 20
   минут «нечего проверять»). «Таймер ставится в том же сообщении, где сказано «жду»» — первая
   редакция; действующая: таймер в **каждом** ответе, включая итог и ответ после публикации,
   **первым** вызовом инструмента, и условие «в момент отправки существует живой таймер, и это
   проверено поиском среди своих вызовов этого ответа, а не памятью». Нет **отметки времени `[ЧЧ:ММ]`
   в начале каждого сообщения**, взятой отдельным вызовом без арифметики — без неё «владелец не
   отличит сообщение от вчерашнего». «Вырос файл сессии» назван годным признаком живости — **не
   годен**: после ответа файл растёт от служебных записей (192 с разницы прочитаны как «работает»);
   годен только «новая содержательная запись». И «ни один признак не сдвинулся» README трактует как
   «проверяю зависание», источник — как **третье состояние «сессия закончила ход, ход за нами»** (три
   дешёвых признака: нет новых записей после последнего ответа; рабочее дерево пусто при обещанной
   работе; отчёт кончается планом, вопросом или «жду слова»), плюс четвёртое — «ждёт ответа внешней
   службы» (файл и CPU стоят, а соединения установлены). [priznaki-zhizni 26-70, 94-115, 131-178,
   203-238, 349-407; otchyot-sessii 22-56; avtorezhim 48-49]
7. **«Лог без итоговой строки» как признак дочернего процесса (разд. 14, 16)** — недиагностичен:
   единственный в источниках случай замершего лога имел причиной **подавленный вывод при штатном
   завершении** (двойной `-q`, код 0), диагноз «дочерний процесс» назван ложным; у обеих причин лог
   выглядит одинаково, различает один прогон в переднем плане с печатью кода возврата. Правило
   отвязанного запуска остаётся, признак — нет; README передаёт половину урока. [priznaki-zhizni
   298-326; klass-defekta 79-105; журнал 186]
8. **Класс 7 и веха 4 (разд. 7, 12).** README: корень — «проверка перед стартом смотрит трекер»,
   веха 4 — «чужие открытые MR, совпадение голов». Источник: смотрятся трекер и чужие **открытые**
   MR, а появление предмета в основной ветке по ходу — нет; веха 4 в README воспроизводит ровно ту
   проверку, недостаточность которой и есть корень. Починка: **любая проверка против удалённой
   основной ветки начинается с fetch, рядом с выводом — ревизия** (четыре прогона вердикта отвечали
   «предок: да» на данных полуторачасовой давности, **три MR-дубля ушли наружу**); при работе дольше
   получаса предмет сверяется с обновлённой основной веткой перед пушем (лог по затронутым
   репозиториям, поиск по ключевому файлу); старт работы объявляется приёмщику письменно, когда он сам
   берёт задачи из очереди. [klass-defekta 45, 57-74; журнал 337, 42]
9. **«Вопрос исполнителя проводится через канон» (разд. 14)** — правило распространяется на
   **любой** вопрос владельцу, включая собственные вопросы оркестратора; сужение до «вопросов сессии»
   названо дырой, купленной 09.09, README воспроизводит её дословно. Рядом: «два вопроса задавать
   нельзя» (разд. 11) — в источнике три, третий — «сливать ли самим: не сливать, слияние выполняет
   ревьюер». [vopros-vladelcu 3-5, 19-21, 167-169; komanda 746-749; pereproverka 207-208, 441-442]
10. **«Канон требует четыре раздела» (разд. 8, стр. 211-212; разд. 12 «раздел, обязательный по
    канону»)** — атрибуция неверна: четвёртый раздел «что осталось за границами» — **наше** требование
    сверх трёх машинных; канон требует ссылку на постановку плюс три раздела. Норма источника: своё
    требование ставится **следом** за машинными, а не вместо одного из них — подмена уронила три
    пайплайна разом. [zadanie-start 128-131; kanon-vyzhimka-priemka 78-81; pereproverka 370-383]
11. **Отсечка как свойство интерфейса («ревьюер не видит, пока не раскроет», разд. 8)** — половина
    причины. Проверка формы описания в CI получает текст, **обрезанный ровно на 2700 символов**:
    раздел за отсечкой для машины не существует. И зелёный пайплайн относится к тому описанию, на
    котором прогонялся — **правка описания его не перезапускает: правил после прогона — перезапусти**.
    [журнал 5280, 4807; pereproverka 379, 396-401]
12. **«По вехам, а не после каждого ответа» (разд. 7)** — короткая сверка после каждого ответа
    («сделала ли ровно то, что просили») остаётся; по вехам идёт **полная** команда перепроверки.
    Формулировка README читается как «после ответов не проверять вовсе». [журнал 4981]
13. **«Закрывает приёмщик» (разд. 3, 8)** — верно по последней поправке (22.09), но правило
    **менялось трижды за месяц**: 22.08 «issue сами не закрываем» → 06.09 руководитель поручил
    закрывать нам («закрывает тот, кто ставил») → 08.09 разрешил закрывать постановки самим → 22.09
    «оставь открытой, закрываю я по итогам приёмки». Переносимая норма — не «закрывает приёмщик», а
    «кто закрывает — договорённость с приёмщиком, записанная письменно и перечитываемая». Два законных
    исключения (письменное указание приёмщика закрыть; слово владельца с проверкой предмета фактом) и
    ловушка: **ключевое слово автозакрытия в описании MR закрывает задачу молча**, минуя ответ по
    сценариям — замечание приёмщика. Если приёмщик закрыл сам — приёмочный комментарий не публикуется
    (читался бы как спор), доказательство по сценариям хранится у себя для акта. [журнал 2807, 427,
    226, 5676, 6200-6201, 5476, 6384, 6543-6548, 5152-5156]
14. **«Решениям добавляется датированное уточнение» (разд. 17 п. 2)** — в каноне два механизма:
    датированная вставка лечит **дрейф** принятого решения; **замена** решения — новый ADR со ссылкой,
    старому статус superseded, принятые не переписываются. README называет один. Источник же
    распространяет норму датированной вставки с решений **на issue**: вставка первым блоком описания,

16. **«Перепроверка (независимая)», «вердикт делает автор, перепроверку — нет» (разд. 3)** —

4. ★★ **Fetch перед любой проверкой против основной ветки; предмет сверяется с ней перед пушем** —

### Разд. 1–2. Рамка и роли

- ★ **Роли команды проекта.** Аналитик — владелец постановки; разработчик — вторая половина
  постановки его; ревьюер — любой второй разработчик, смотрит замысел и границы модуля; тестировщик
  принимает задачу целиком (не дифф) по сценариям на dev после слияния, **непроверяемый сценарий —
  дефект постановки** и возвращается аналитику, закрытый тестом сценарий всё равно проходится руками,
  если его видит человек; руководитель решает то, что не решается правилом, ролей тимлида и
  архитектора нет; отсутствующая роль не выпадает из цепочки — шаг делается силами команды; адресат
  открытых вопросов — руководитель. [onboarding 07:9-59; витрина, разд. 1-5]
- **Читатель проекта** (руководство, бизнес, новый человек): что заказано — лента задач, что готово
  — «Сценарии приёмки», на какой стадии — по MR, а не по ленте; непонятная без кода цель написана
  неправильно. [витрина, разд. 6]
- ★ **Действие с побочным эффектом на чужое** (перезапуск общего движка, сброс данных стенда) —
  только по слову владельца, с ценой, названной **до** действия; перед разрушающим шагом — снимок
  данных и полное состояние снимаемого процесса. Куплено безвозвратно потерянными записями.
  [журнал 5667, 5776, 5829, 5839-5848]
- **Автоматический режим** как таковой: порядок входа (состояние работ целиком → **свежий свод
  обязателен до любого действия** → живые сессии → первое действие называется и делается, «жду
  указаний» запрещено); очередь — незакрытая задача с влитым MR идёт в финиш раньше, чем свободная в
  старт; режим **не останавливается сам** — ни время суток, ни длина смены, ни «работа выглядит
  законченной»; формулировки «беру, если не скажешь иначе», «продолжать ли» запрещены (выглядят
  вежливостью, работают как остановка; куплено дважды); «делал больше, чем просил» — нарушение; после
  стопа таймеры сняты и задачи не берутся. [avtorezhim 14-43, 106-121; журнал 5900, 6346]
- **Атрибуция указаний проверяется по источнику**: слова приёмщика были приписаны владельцу, довод
  исполнителя принят против письменного указания; разрешения берутся у владельца напрямую —
  пересказанное через другую сессию не действует; решение владельца передаётся в его границах.
  [журнал 5932-5941, 1718-1726]
- **У задачи один управляющий**: параллельное окно управления доставило слово раньше находок, и они
  не попали в опубликованное. [журнал 5741, 5827]
- **Числа из чужого окружения под свой вердикт не подставляются**: перезапуск чужого прогона своими
  руками даёт другие числа — та же подмена, что «менялась только база». [priznaki-zhizni 328-332]

### Разд. 3. Жизненный цикл

- ★ **Правило изоляции словами**: одна задача = одна ветка от свежего main = один MR = один
  squash-коммит = одна сессия из корня воркспейса, хвосты между задачами не таскать; три причины
  (контекст прошлой задачи тянет правки не по теме; раздутый дифф ломает ревью; squash перестаёт быть
  обратимым); «поплывшая» сессия лечится перезагрузкой контекста; слияние — за ревьюером, автор себя
  не апрувит и не сливает. [kanon-vyzhimka-zadachi 9-26; onboarding 08:7, 92; журнал 1583-1585]
- ★ **Порядок внутри задачи — восемь шагов, не переставляются**: разобрать постановку → ветка от
  свежего main → контекст модуля и канона → дополнить постановку и **ждать утверждения, кода до этого
  нет** → ADR раньше кода → изменение только в границах → артефакты и контракты как часть готовности →
  линтеры, тесты, живой контур → MR по чужому чеклисту. [kanon-vyzhimka-zadachi 28-46]
- ★ **Контракт первичен**: OpenAPI/AsyncAPI до реализации, по нему параллельно стартует фронт;
  «правок API без парного MR контракта не бывает»; слоистый порядок — скелет с зелёным пустым CI,
  модели и миграции с ручным ревью миграции, API, события через outbox. [kanon-vyzhimka-priemka 36-47]
- ★ **Definition of Done** — чем доказывается «сделано» и что едет тем же MR: чеклист отмечен честно
  и полностью; статья базы знаний для функционального изменения («описать потом» не бывает); тесты того
  уровня, где живёт поведение; артефакты модуля (контекст, README, паспорт, схемы, модель угроз при
  смене поверхности атаки); контракт обновлён либо явно не требуется; ADR либо «не требуется»;
  логирование критических действий; апрув второго разработчика; влит squash, ветка удалена, клоны
  приведены в порядок; задача переведена в статус со ссылкой на MR. «Частично выполненный список —
  задача в работе, а не на ревью». [kanon-vyzhimka-zadachi 157-195; onboarding 08:137-143]
- **Точки цикла как наблюдаемые состояния** с признаками и «что дальше»: не начата / в работе /
  готова к публикации / на ревью / **возвращена** / готова к сдаче / закрыта; петли «возвращена →
  доработка» в схеме разд. 3 нет; «на ревью без замечаний» — нормальное состояние, не задержка;
  состояние «работа закончена, лежит незакоммиченной, сессия ждёт слова» из трекера и клонов не
  видно — только из отчёта сессии. [komanda 507-536]
- **Две точки входа финиша**: «готова к публикации» (полное задание) и «готова к сдаче» (MR влиты:
  комментарий, уборка); между ними обычно дни; «возвращена» → задание на доработку, в котором каждое
  замечание получает исход из трёх (правлю / отвечаю доводом / отвергаю с обоснованием), названа
  голова, на которой сделано ревью, ответ ревьюеру — одним комментарием **после** пуша.
  [zadanie-finish 63-81; komanda 586-589, 644-661]
- **Условия финиша**: ни один сценарий без ответа (отложенных «посмотреть глазами» нет); **хвосты
  названы** — расхождение клона с удалённым, неудалённое рабочее дерево, неопубликованный пакет,
  несобранный лок; по влитым за окно MR — открытая задача либо ждёт финиша, либо ответа по сценариям,
  третьего не бывает. [zadanie-finish 85-88; komanda 668-674]
- **Живой контур — норма при наблюдаемом поведении**, до MR; в описании названо, что проверялось:
  адрес, действие, результат; данные для прогона заводятся **штатными операциями**, не правкой базы
  (иначе следы позже станут дефектом), после прогона следы убираются штатно или перечисляются в
  приёмочном комментарии; ручное изменение живого окружения записывается (было/стало/откат), возраст
  окружения называется. [kanon-vyzhimka-zadachi 43-45; журнал 94-102, 693, 1196]
- **Проверки локально теми же командами, что у приёмки**; **уборка — часть финиша** (комментарий →
  закрытие → уборка), нужна независимо от кода возврата проверки гигиены. [витрина; журнал 254, 877]

### Разд. 4. Вратарь старта

- ★ **Письменный порядок работ приёмщика старше порядка из постановок**: живёт в состоянии работ,
  приходит не запросом; сначала поручение, потом раздел «Решения». [журнал 5226, 5594; komanda 626-631]
- ★ **Список в файле состояния или инструкции — второй источник правды**: в инструкциях не бывает
  номеров задач, диапазонов, веток, логинов и имён; «наше» определяется запросом по трём измерениям
  (назначено на нас / заведено нами / ждёт нашего ревью) в обоих состояниях; роль — из ведомого файла,
  не из прав доступа. [komanda 61-75, 118-135; журнал 6186, 3391]
- ★ **Выборка по одному состоянию слепа**: «назначено сейчас» не показывает ушедшее (три задачи ушли,
  четверо суток не замечали); «открытые» не показывают влитое чужими руками и закрытое без слияния;
  сводка уведомлений — самый надёжный признак «на нас что-то повесили». [журнал 5117-5123; komanda 93-98]
- ★ **Состояние задачи — запросом к трекеру, клон показывает прошлое**; автосвязь «задача → MR»
  отдаёт чужие MR соседних постановок — предмет проверяется фактом в основной ветке; сигнал
  (уведомление, флаг «нельзя слить», скриншот) говорит куда посмотреть, вывод — по состоянию объекта.
  14 «ждущих закрытия» оказались несделанной работой. [журнал 5825, 6144; komanda 39, 88-90, 872-878]
- ★ **Предшественники читаются из раздела «Решения» постановки целиком**; ★ **пустое поле
  исполнителя само не блокирует**, если задача поручена письменно, но просьба назначить остаётся;
  ★ **свободный номер и версия учитывают собственные незалитые MR**, пересечение по файлам
  проверяется и между своими открытыми ветками; ★ **правка инструкций не действует на уже идущую
  сессию** — оснастка загружается при старте, клон оснастки подтягивается перед задачей.
  [zadanie-start 36-53; журнал 783, 1069, 424, 1374]
- **Комментарии**: накопительны и не отменяют друг друга («последний» — неверный критерий); читаются
  и в закрытых задачах (приёмочный ответ приходит последним); вложения — наравне с текстом, «вложений
  нет» говорится явно; признак недочитанного — пересказ вместо цитаты из второй половины; строка-след
  «прочитаны все N на этом заходе, новых решений нет» — и перед финишем, и на каждой вехе. Решение из
  комментария переносится в задание **дословно в части, меняющей код** (пересказ «взят профиль
  такой-то» теряет половину, ради которой комментарий писался; цена — зелёные тесты и потеря писем в
  проде). [chitat-kommentarii 6-40; komanda 87-101, 495; zadanie-finish 19-23]
- **Занятый клон не блокирует** — рабочее дерево штатный путь, в задании названо где; **брать ненаше
  нельзя даже при пустой очереди**, свою находку без исполнителя — тоже (назначение — решение
  приёмщика); в «шаг наш» входит **ответ ревьюеру**; проверка по каждой свободной задаче отдельно —
  общий вывод «мы заняты» и есть ошибка; родственные задачи берутся пачкой ради контекста, но каждая
  своей веткой, соседи по пачке замеряются заранее. [zadanie-start 45-46; komanda 608-636;
  blokiruet-li 6, 27-29; журнал 866, 2484]
- Признак ошибки — рекомендация или находка, собранная **по одному признаку**; выборка из двух — не
  замер (довод «вольёт в любой момент» держался на паре соседних MR; медиана по 30 за 7 суток — 337
  минут при разбросе до 4160). [журнал 4158; schyot-i-perechen 24]

### Разд. 5. Постановка

- ★ **Две половины постановки**: авторская (аналитик или руководитель, от лица пользователя) и
  техническая (исполнитель дописывает технические сценарии — отказ соседнего модуля, истечение сессии,
  повтор из офлайн-очереди, пустой и предельный объём, вторая тема, узкий экран — **комментарием в тот
  же issue до кода** и ждёт утверждения); «система работает корректно» сценарием не является; если
  сценариев нет (задача заведена как находка) — исполнитель формулирует их и показывает до кода.
  README не говорит, кто пишет, и не различает утверждение постановки и утверждение дополнения.
  [kanon-vyzhimka-zadachi 48-66; журнал 2048, 2526, 3241-3248]
- ★ **Утверждения постановки и задания исполнитель сверяет с кодом до начала работы** (два из четырёх
  расхождений меняли работу); первое поручение — проверить факты самого задания; исполнитель оспаривает
  задание фактом. [журнал 2843, 2870, 176, 798]
- ★ **Формулировки «решение за ревьюером / на усмотрение» в issue запрещены** — это вопрос без
  умолчания, оформленный как решённый; вопрос читается на блокирующесть («утверждает ДО правки» —
  блокер, «предложить, утверждает» — нет); **два класса вопросов**: у вопроса внутри задачи умолчание
  есть, у вопроса о публикации умолчания нет и быть не может («промолчал — публикую» отменяет
  запрет). [журнал 457, 2572-2577; vopros-vladelcu 74-89]
- **Постановка живёт задачей в трекере**, не файлом и не в переписке; отдельного «плана» как
  документа нет; чего в ней не бывает — сроков, оценок, приоритетов, статусов. [витрина, разд. 2;
  onboarding 07:71-73]
- **Каноническая форма**: семь разделов с «Готовностью постановки»; постановка маленькая, не
  заменяет контракт, ADR, статью и описание MR; нарезка по правилу «один ответ на вопрос “когда
  готово”»; одна постановка — одна задача, даже если MR три; обязательна при наблюдаемом поведении;
  состав предмета измеряется прогоном (README это имеет), а вложения и адреса (номера строк, версии)
  устаревают — искать по содержанию. [postanovki\README 26-70; kanon-vyzhimka-priemka 20-34;
  журнал 5350, 6247]
- **ADR как норма, а не формат**: раньше кода; обязателен при смене контракта, схемы данных,
  технологии, безопасности, топологии и при любом отклонении от соглашений; «ADR добавлен либо явно не
  требуется» в описании MR — молчание неотличимо от «забыл подумать»; спорить с каноном только через
  ADR; **подавление проверки ≠ отклонение от правила**; класс ошибки — «плюсы отвергнутого варианта
  прочитаны как решение» (формат перечисляет альтернативы с плюсами, глаз находит фразу и не смотрит
  раздел «Решение»). [onboarding 08:38-49, 72-74; klass-defekta 42]
- ★ **Свою постановку правим в описании** датированной вставкой первым блоком, не переписыванием и
  не комментарием (приёмка идёт по описанию, комментарии читают не все); копия до правки, перечитать
  после — правка через API затирает целиком; не заводить переписку там, где можно исправить запись.
  [журнал 4728-4737, 4752-4771; nahodki 110-133]
- **Умолчание не применяется**, если работа «по умолчанию» зафиксирует за адресата непринятое решение
  в документе, который читают другие модули; срок умолчания течёт **с публикации** вопроса —
  задержка публикации обесценивает умолчание; исполнитель, вставший на «после утверждения пишу код»
  при умолчании со сроком, — класс «ожидание, которого процесс не требует» (простои 40 минут и
  3 ч 17 мин). [журнал 6297, 406, 927, 1061]
- **«Не выдумывай», второй канал**: дожило до кода — TODO с формулировкой вопроса, кто и когда
  закрывает; адресат обязателен, в документах только роли; молчание — не разрешение; секреты только
  плейсхолдерами; чужой модуль не менять — остановиться и обсудить. [kanon-vyzhimka-zadachi 112-138]
- Оценки трудоёмкости с ИИ-исполнителем — **часы, не недели**; занижать нельзя. [журнал 6416]

### Разд. 6. Задание исполнителю

- ★ **Задание не поручает финиш**: строку «закончив, вызови финиш» вписывать нельзя — что работа
  кончена, решает оркестратор после перепроверки; иначе перепроверка обходится целиком.
  [zadanie-start 368-380; журнал 4805]
- ★ **Перед заданием на финиш читается отчёт исполнителя** — не поручать сделанное («у тебя это
  готово, беру как есть»); задание, поручающее сделанное, обесценивает остальные пункты (4 из 12).
  Читаем, чтобы не дублировать, а не чтобы поверить. [zadanie-finish 44-61; журнал 4602-4617]
- ★ **Каждый передаваемый блок подписан адресатом** строкой над блоком — типология из шести
  (исполнителю / себе / приёмщику / владельцу глазами / владельцу руками / никому — ждём, и названо
  кого); блок без адресата — лишний или ошибка ответа; сначала команды запуска, потом задание.
  [podpisi 1-36; журнал 4548-4571]
- ★ **Новый блок исполнителю не выдаётся, пока по файлу сессии не проверено, что предыдущий по тому
  же предмету доставлен**; не доставлен — **один объединённый блок** «вместо предыдущего», а не второй
  рядом (три случая за сутки, простой 3 ч 17 мин при готовом диффе). Класс «решение не доставлено» в
  README есть, правила — нет. [podpisi 38-64; журнал 530, 1026-1030]
- ★ **Исполнитель информационно изолирован**: оркестратор сообщает ему о своих публикациях (иначе
  готовится дубль); правило из оснастки оркестратора **излагается в задании целиком**, а не адресуется
  путём — исполнитель работает в другой среде, совпадение имён каталогов делает ошибку незаметной;
  ссылка на канон законна, он в клоне исполнителя. [rasshirenie-granic 23-28; журнал 5354, 6253]
- ★ **Решение исполнителю формулируется действием (глаголами: «поправь, закоммить, запушь»), не
  предметом** («правим оба текста»): узкое прочтение запрета публикации законно, и решение
  доставляется наполовину; признак — описание MR говорит новое, дифф старое; правка опубликованного —
  тоже публикация. [vopros-vladelcu 135-141; журнал 1230, 768]
- ★ **Механизм потери шагов**: длинная инструкция цикла загружена целиком в начале, вторая половина
  к финишу «ощущается прочитанной»; отсюда финиш — отдельная команда, вызываемая в момент финиша, и
  **вердикт перед каждым пушем как принудитель** — проверки без «острого момента» молча заменяются
  парой поисков по коду. README даёт правило (п. 8) без механизма. [zadanie-start 15;
  zadanie-finish 15-17; журнал 3984-4021; витрина]
- **Части задания, которых нет в перечне README** (в источнике 12, в README 10): **где работать**
  (клон или рабочее дерево); **форма отвязанного запуска прямо в задании**, а не знанием оркестратора
  (часть коротких прогонов успевает закрыться зелёным — это и маскирует дефект); **команды запуска
  рядом**; форма первого пуша с явной веткой; **форма доказательств по каждому сценарию отдельно**
  (так и делается в живых заданиях); строка «возник вопрос — сформулируй последним абзацем и работу на
  нём не продолжай» (инструмент вопроса в неинтерактивном режиме недоступен); требование назвать
  идентификатор сессии первой строкой отчёта. [zadanie-start 108-174; avtorezhim 28-31;
  otchyot-sessii 13]
- **Запрет включает слияние**; **вызов финиша — на каждый репозиторий задачи**; в отчёт идёт то, что
  запускалось — проверка, заменённая поиском по коду, называется поиском; неточность в отчёте
  обесценивает остальные строки. [zadanie-finish 91, 131, 160-162]
- **Задание передаётся файлом и сохраняется копией** — след того, что именно поручалось, и
  восстановление после обрыва; **сессия запускается из каталога оснастки**, иначе остаётся без команд;
  запуск подтверждается **замером** через несколько секунд (процесс с текстом задания в аргументах
  плюс растущий лог), не возвратом команды — идентификатор фоновой задачи выдаётся и упавшей;
  объявляя запуск, сразу дать владельцу готовую команду наблюдения. [zadanie-start 253-256, 290-295;
  priznaki-zhizni 256-259, 289-296; avtorezhim 33-39]
- **Команды для человека — готовыми, с подставленными значениями**, в порядке ввода; позиционные
  переменные в примерах команды съедаются подстановкой при загрузке — писать безоговорочные формы.
  [zadanie-start 174, 247-251; sokratit 72-76]
- **Собранное запросом передаётся сессии готовым**, чтобы не выяснять дважды; проверенное — отдельным
  перечнем «не проверяй заново». [pereproverka 71-72, 586-587]

### Разд. 7. Перепроверка

- ★ **Все находки захода — сразу, нумерованным списком, готовым текстом блока** (что не закрыто, чем
  доказано, варианты, требование отчитаться), не строкой доклада; названная, но не переданная находка
  не закрыта — живёт в переписке; капельная выдача дала 16 кругов; «правок нет» ≠ «писать нечего» —
  если работа стоит и двинет её сессия, блок идёт с этим одним действием. [pereproverka 566-592;
  журнал 4477-4479, 5137]
- ★ **Карта слабых мест обходится полностью на каждом заходе**; глубина — по признаку «менялось ли»
  (менялось — разбор заново, нет — дешёвая сверка и строка «без изменений с захода N»); группа,
  пропущенная молча, — непройденная; по каждой правке прошлого захода названо, какая группа могла
  пострадать, и она пройдена заново (сжали «как проверить» — пропал адрес стенда); перед заходом
  читается след предыдущего — что находили и на каком состоянии. [pereproverka 218-234, 469-475]
- ★ **Свой прогон затирает доказательства чужого**: артефакты чистятся при запуске — сохранять до
  прогона, доказательство брать из файла сессии; проверочный `git add` меняет индекс; после каждого
  действия в чужом дереве — что изменилось (класс «своё же действие как источник ошибки»).
  [pereproverka 350-352, 741-756; журнал 4817-4819]
- ★ **Возврат с ревью**: сверять голову, на которой сделано ревью, с текущей — ревью бывает верным
  по содержанию и устаревшим по основанию; ответ — факты без упрёка, починка и ответ одним сообщением.
  [журнал 3804-3807; витрина]
- ★ **Достаточность**: закрыты сценарии приёмки постановки — дальше не идём; после зелёного вердикта
  заход только при изменении диффа или ошибке в своих выводах; круг не начинается ради полноты канона.
  [pereproverka 158-174]
- ★ **Комментарии задачи читаются целиком на каждом заходе** с строкой-следом; **число сценариев
  берётся из постановки**, не из описания MR или отчёта (шесть заходов брали число из пересказа);
  закрытый сценарий именуется тестом или проверкой **в момент закрытия**, не на финише («пять из
  шести» без имён — проверить нечем). [pereproverka 74-75, 178-181; журнал 834; schyot-i-perechen 20]
- ★ **Чего в перепроверке быть не должно**: вывода по уведомлениям («нельзя слить», «сборка упала»
  отстают) и вида на экране как доказательства (дефект по скриншоту отозван после замера в консоли).
  [pereproverka 446-452]
- ★ **Проверка завершена только при нуле сообщений агентам**; чужие сообщения (руководителю,
  комментарий, issue) считаются тоже — каждое ждёт отработки и проверки результата; след пишется
  **до** итога; в докладе больше находок, чем в следе — заход не закончен; не пройдена — следа нет.
  [pereproverka 522-525, 691-730]
- ★ **Найденное «не по адресу» — чужой дефект**; **неприменимый пункт чеклиста — с пояснением, не
  молча**, применимость требования тестов доказывается составом диффа; **ничего не закрыто
  упрощением** (заглушки, «пока так») — урезание решение владельца словами; «проверить нечем» словом
  не принимается — что пробовали и почему не вышло; сделанное сверх границ называется явно; находка
  безопасности автором не снимается — решение ревьюера или ИБ. [pereproverka 182-208, 286-290;
  журнал 1198, 1331]
- ★ **К концу задачи все свои находки перепроверяются запросом**: актуальна / закрыта этим диффом
  (назвать в описании MR, закрывает человек) / факт устарел / ложная; обратная ошибка — счесть живую
  устаревшей — дороже. [pereproverka 413-436]
- **Пятая веха — после публикации**: сверить фактически опубликованное запросом (описание с сервера,
  пайплайн по sha, следы, номера); у вех есть столбец «признак наступления». [журнал 5105, 5270;
  pereproverka 50-59]
- **След перепроверки устаревает при изменении содержимого** (коммит с кодом, ответ на ревью,
  догоняющий ребейз), не при пуше как таковом; устаревший равен отсутствующему и опаснее его; статус
  перепроверки — наравне со стадией по каждой задаче в работе. [komanda 196-221; zadanie-finish 27-40]
- **Отчёт исполнителя читается с диска целиком**, не по снимку (снимок обрезан рамкой, «чего жду от
  владельца» за кадром): на чём остановился и чего ждёт, числа дословно, признания об ошибках,
  «готово, но не опубликовано»; заготовки, видимые в отчёте, ещё не в трекере. [pereproverka 105-114;
  otchyot-sessii 19-20]
- **До кода полная перепроверка не гоняется** — превращается в разбор постановки, счётчик заходов
  растёт, сдача не двигается; **ручная проверка снимается, когда её взяла машина**, а машинное не
  гоняется на каждом заходе — только на вехе 4; «ничего не нашла» — тоже результат, но сначала
  убедиться, что искал; лечение соразмерно проверенной гипотезе — «полный сброс» ради непроверенной
  причины отвергается. [pereproverka 13, 25-34, 332-339; журнал 5234, 533-545]
- **Публикация без слова проверяется запросом «кто автор и когда»**; ложное срабатывание своих же
  правил — совпадение по шаблону ещё не находка, предмет читается. [pereproverka 300-301, 325-326]

### Разд. 8. Публикация и описание MR

- ★★ **Секреты и реквизиты.** Секрет, попавший в историю, скомпрометирован навсегда — его меняют, а
  не удаляют коммит; хук перед записью печатает файл и строку, но не значение; реквизиты (пароли,
  коды второго фактора, значения `.env`) ищутся в **описании каждого MR задачи и во всех несистемных
  комментариях** тремя дешёвыми проверками разом — дословный поиск известных значений, шестизначные
  коды по границам слова, строки 28+ букв-цифр с отсевом UUID и SHA; заглушки `<пароль>`, `<код>`
  доказательности не вредят; утечку отозвать нельзя. Утечка 10.09 уехала в описание влитого MR.
  Сканер секретов конвейера issue не проверяет; ПДн и выгрузки из продуктивных баз в трекер не идут
  — issue видят все участники группы. [pereproverka 308-322; soobshchenie 53-63; витрина; журнал,
  СЕЙЧАС 10.09]
- ★★ **Карта «что уходит наружу» до первого пуша**: ссылка на постановку полным адресом выше отсечки
  (стояла на 2737-м; короткая из репозитория модуля указывает не туда); следы оснастки и абсолютные
  пути — по всем файлам диффа **и по заготовкам текстов, идущим мимо git-хука** (описание MR,
  комментарии, issue); имена сторонних проектов и организаций, ссылки на приватный каталог, трейлеры
  и имена моделей в сообщениях коммитов; человек наружу называется логином, если имя не записано
  (имя по инициалам — догадка). [zadanie-finish 107-111; pereproverka 303-307; журнал 3068-3084,
  4847-4849, 5396]
- ★★ **Проверка исходящего сообщения до отправки** — отдельная процедура для любого текста наружу
  (сообщение руководителю, комментарий, ответ ревьюеру, приёмочный комментарий, issue): сообщение
  необратимо в отличие от коммита и проверяется строже кода; факты — из запросов, не из памяти и не из
  отчёта сессии; прежде чем просить — проверить запросом, что у адресата есть предмет («он мог бы» ≠
  «он делает»); вопрос с ответом в каноне наружу не идёт; адресат задаёт форму (руководителю — суть и
  решение без пути; ревьюеру — исход по каждому замечанию, после пуша; в задачу — только по существу;
  сторонним службам и чужим командам сами не пишем — через руководителя); канал задаёт вид (мессенджер
  — абзац одной строкой, дефис вместо тире); **трекер перечитывается до письма и ещё раз в последнем
  круге перед отправкой** — руководитель отвечает между сборкой и отправкой; находка по тексту
  чинится **в источнике** (состояние работ, описание MR, приёмочный комментарий); чеклист: каждое
  утверждение доказано или помечено предположением, числа только из вывода («почти все» не пишем),
  номера и адреса полные, понятно тому, кто не сидел в задаче, обещаний не больше сделанного, тон без
  извинений и пересказа пути. [soobshchenie 9-147; журнал 3539-3540, 4365-4378; витрина]
- ★★ **Про оснастку, автоматизацию и ИИ на своей стороне в текстах наружу — ни слова.**
  [CLAUDE.md; soobshchenie 65-88; живое задание на финиш]
- ★★ **Расширение границ автором**: тот же файл или предмет, без которого правка противоречива, —
  в этом же MR с формулировкой «расширено автором, довод такой-то» в описании и комментарием в
  постановку; «решением руководителя от <дата>» — только при существующем комментарии, на который
  можно сослаться; приписанное авторство решения — класс «выдуманный факт», проверяется наравне с
  числами; граница держится на классе утверждения, а не на числе строк; «противоречивый документ
  хуже устаревшего». [rasshirenie-granic 1-21; журнал 6084, 6229, 6301-6303, 5641, 5965]
- ★★ **Ссылка или цитата ставится по прочитанному тексту, а не по смыслу документа**: фраза из
  отвергнутого варианта принята за решение; решение ссылалось на канон, который этого не говорит;
  документ, уходящий в канон навсегда, проверяется сплошной сверкой ссылок открытием источника; ложная
  ссылка на канон хуже отсутствия. [журнал 216, 579-585, 1364]
- ★★ **Правила машины про описание**: маркер чеклиста воспроизводит **полное** условие (слово
  «чеклист» плюс строка `- [ ]`, обе выше отсечки; проверяется форма, не выполнение) — четыре захода
  мерили позиции четырёх разделов и объявили чисто; своё требование — **после** машинных, не вместо;
  **зелёный относится к тому описанию, на котором прогонялся — правил после прогона, перезапусти**;
  класс «правило машины, которого нет в нашей проверке» (обратный README-строке «наше требование
  машина не проверяет»). [zadanie-start 138-156; pereproverka 370-401]
- ★ **Запас до отсечки** считается до **первого пункта** чеклиста, порог 150–200 символов (номера
  issue и MR и взаимные ссылки подставляются после публикации и съедают запас), три числа со знаком;
  запасов два — машинный (до конца искомой подстроки заголовка) и человеческий (до конца текста
  раздела); позиция считается от начала текста, а не суммой длин разделов; раздел «на границе»
  (заголовок виден, текст обрезан) хуже раздела целиком ниже; сокращать **выше** раздела, а не
  дописывать ниже, и после сжатия проверить, что факты уцелели (сжатие выбросило нужную подстроку
  целиком). Куплено дважды за вечер, запас в один символ. [журнал 5645, 5398, 6158, 32, 134, 367, 430]
- ★ **Что обязано выжить в обрезанном виде**: ссылка на постановку — в первом абзаце (именно она
  уходила за обрезку); первым предложением каждого раздела — главное; самое спорное место работы
  (оговорки, отступления) — в видимой части, не только обязательные разделы. [журнал 850, 999, 913]
- ★ **Жёсткий порядок публикации**: issue по находкам → их номера в описания с перемером позиций →
  коммит → вердикт → пуш → MR; иначе описания уезжают без ссылок и правится опубликованное. У каждого
  MR своё полное описание — джоба проверяет описание именно этого MR, даже у парных; наличие разделов
  проверяется перечнем заголовков, а не поиском строки; пункты чеклиста, зависящие от пайплайна,
  отмечаются после зелёного отдельным действием, и оно не забывается. [журнал 514, 990, 1158, 907,
  1008, 184, 771]
- ★ **Порядок слияния парных MR называется ревьюеру в описании с обоснованием** (документ и контракт
  первыми, код после — иначе ссылка ведёт в main, где файла нет); при пересечении с чужим свежим MR —
  просить слить наш, старший, первым: конфликт достаётся автору свежего. MR простоял из-за документа,
  лежавшего готовым. [журнал 160, 170, 979, 1216]
- ★ **Любое утверждение о состоянии в тексте наружу датируется** («замер на …»); слова «сегодня,
  сейчас, идёт, влито» без даты не употребляются; в момент публикации сверяются состояние и sha;
  недоказуемое (о времени, о чужом) в тексты не идёт — за ночь устарели все три утверждения
  приёмочного комментария. Числа приёмочного комментария перемеряются **в слитом main**, не на голове
  ветки: «приёмка отвечает о состоянии main». [журнал 810, 306, 828, 1014, 36, 106]
- **Приёмочный комментарий публикуется вместе с MR, до слияния** — ревьюер читает, зная, чем закрыт
  каждый сценарий; своя запись правится, а не дублируется новой; попутно изменённое по построению
  (скачок версии, правило по аналогии, расширение границ) называется в описании отдельной строкой —
  иначе ревьюер видит необъяснённое; в текстах наружу не приписывать ревьюеру решений, которых он не
  принимал — решение оркестратора помечается «не согласовано»; внутренние ориентиры («снято с
  исполнителя решением от …»), суммы и позиции договора в тексты заказчику не выносятся; тексты
  формулируются от результата, видимого заказчику («администратор видит журнал», не «добавлена
  таблица»), отчёт заполняется строкой на задачу сразу после слияния. [журнал 968-972, 853, 291-294,
  505, 2941-2944]
- ★ **Уборка — после слияния и после ответа по каждому сценарию**, конкретными действиями:
  синхронизация, удаление рабочего дерева, уход с ветки, которой нет на удалённом; после squash git
  слитыми ветки не считает — призраки копятся сами; убранное раньше времени восстанавливают; гигиена
  всего рабочего места — отдельная регулярная проверка одним вызовом со значащим кодом возврата,
  безопасная по построению. [zadanie-finish 122-130; komanda 186-194; журнал 4202-4213]
- ★ **Чеклист копируется в описание целиком** и отмечается честно; неприменимый пункт — с
  пояснением; если находка закрывается нашим MR, это сказано в описании строкой с причиной и
  директивой закрытия — иначе связь невидима. [kanon-vyzhimka-zadachi 157-174; nahodki 98, 198-199]
- **Содержание разделов описания**: «что сделано и зачем» — замысел, не пересказ диффа; «как
  проверить» — адрес, операция, ожидаемое; «влияние на контракты» — меняется ли OpenAPI/AsyncAPI,
  ломающее ли, кого затрагивает; блок находок, разросшийся до абзацев, — признак чужого в MR.
  [kanon-vyzhimka-zadachi 140-151; zadanie-finish 148-150]
- **Форма доклада о публикации**: перечень «что и по какому адресу», полная ссылка по строке на
  объект (MR, каждое issue, комментарий, коммит), состояние пайплайна, без пересказа содержимого;
  **публикация подтверждается чтением опубликованного** — вернулся идентификатор, автор наш, длина
  тела равна отправленному; идентификатора нет — публикации не было при любом коде возврата.
  [avtorezhim 178-185; schyot-i-perechen 120-128]
- **Недоступность среды не откладывает публикацию**: сценарий живого стенда называется незакрытым с
  причиной либо закрывается замером по объявленному состоянию с оговоркой, чего замер не доказывает;
  ложное зелёное не ставится; «урезание объёма» — это когда работа не сделана **и об этом молчат**:
  сценарий, названный незакрытым с причиной, плюс заведённая постановка — штатная форма ответа.
  [журнал 6166, 6184, 6283-6285; vopros-vladelcu 147-165]
- **Опубликованное с неверным телом удаляется и публикуется заново**, не правится на месте.
  [журнал 6146, 5432]
- **Ребейз — когда**: по чужим открытым MR в общем репозитории (есть — перед сдачей, иначе дважды;
  нет — сразу), один раз непосредственно перед пушем; стабильность main не выводится из «открытых MR
  ноль» — чужой MR живёт меньше интервала проверок; пересечение по файлам конфликт не предсказывает —
  надёжна только проба ребейзом в отдельном дереве с откатом; незапушенная ветка конфликтует так же;
  версия общего пакета — кто вливается первым, берёт номер, второй сдвигает свой везде; зелёный
  пайплайн датирован; неразрешённое обсуждение блокирует слияние при зелёном. [zadanie-finish 98;
  komanda 161-194, 498-500; журнал 1345, 916]
- **Ветки и коммиты как норма**: одна защищённая main без прямого push; ветка с префиксом из закрытого
  списка и слагом; только squash; обновление rebase, не merge (merge-коммит — блокирующая находка);
  Conventional Commits — тип и scope по-английски, тело по-русски; после слияния ветка удаляется;
  подпись коммитов. [kanon-vyzhimka-priemka 50-76; onboarding 08:98-109, 162-175]
- **Трекер**: задача переводится в статус со ссылкой на MR, статус актуален до конца, не до мержа;
  часы; issue заводится без исполнителя, приоритета и вехи — очередь принадлежит приёмщику; метки
  проверяются перечнем. [onboarding 07:61-101; журнал 597, 946]
- **Производное от документов заказчика с грифом не выкладывается на внешние сервисы.**
  [журнал 3927-3935]

### Разд. 9. Правила измерения

- ★ **Отрицательный контроль обязателен**: проверка обязана краснеть на неисправленном коде или при
  снятой правке; сценарий, проходящий на неисправленном коде, не доказывает ничего — доказывается
  исправление, а не дефект (дифф на незакоммиченной ветке был пуст и «доказывал ноль»); совпадение
  признака с гипотезой — не проверка гипотезы, проверка — прогон, отличающийся ровно одним условием;
  прежде чем принять чужое объяснение своего наблюдения, сверить с собственными данными.
  [журнал 5386-5390, 5576, 5875-5879, 6042-6043; klass-defekta 95-105]
- ★ **Вывод не делается по обрезанному тексту**: применялись `cut`, `head`, срез, `maxlen`, один
  блок вывода, один раздел документа — утверждение только после чтения целиком (куплено не менее шести
  раз: фраза стояла в конце строки длиннее тысячи символов; «правило применил к ней, но не к себе»);
  вывод читается целиком — хвост без начала врёт как начало без хвоста; число из вывода **с итоговой
  строкой** — прогон мог оборваться. [zadanie-start 204-208; pereproverka 463-467; журнал 5174, 349,
  1113, 1224]
- ★ **Выборка, упёршаяся в лимит страницы, — обрезанный список** (число записей равно размеру
  страницы; чем шире окно, тем сильнее обрезка — наоборот ожиданию); фильтр по **сокращённому**
  идентификатору отдаёт пустой список, неотличимый от «нет». [komanda 141-150; журнал 4233-4237;
  schyot-i-perechen 153-161]
- ★ **Поиск ведётся несколькими формулировками и по смыслу**, не одной своей: шаблон не покрывает
  форму записи (вызов передан ссылкой без скобок, значение стоит списком, третье место написано
  третьими словами). README сузил это до «числа прописью». [журнал 433, 919, 1337, 1048]
- ★ **Проверка проверяется подсадкой**: негативный тест (подсаженные нарушения пойманы, чистый прогон
  — ноль), положительная канарейка, холостой проход подменой условия — «два False не отличаются от
  функции, всегда отвечающей False» (сверка ключей по длине вместо содержимого); проверка не полагается
  на текст отказа чужого инструмента — печатает свой маркер. [журнал 2050, 739, 1368, 56]
- ★ **Число пропущенных тестов сравнивается с базой и объясняется поимённо** («5 skipped» неотличимо
  от нормы — за этим скрылись молча пропущенные контрактные тесты); расхождение числа тестов
  объясняется единицей (функции против прогонов с параметризацией); плавающий тест — дефект механизма
  тестов, не работы: issue на механизм, оговорка в описании, дифф не правим. [журнал 762, 1360, 74-76]
- ★ **Ребейз**: конфликт предсказывается пробой слияния в отдельном дереве, не прогнозом по файлу;
  перед force-push проверяется, что MR ещё открыт — статус слияния отстаёт от факта (force-push стёр бы
  удалённую ветку до состояния main); после ребейза патчем — характерными строками проверить, что чужое
  не затёрто и своё не потеряно; **после ребейза перегенерируются производные** (генераты, локи), не
  только перемеряются числа — лок с `--frozen` не падает, а молча ставит старое. [журнал 274, 285,
  886, 1204, 916, 1297, 1331]
- **Замеры производительности — на свободной машине**, числа под загрузкой признаются ошибкой
  измерения; сравнение приводится по всем единицам, вывод не выбирается по удобной; два разных числа
  могут быть верны каждое на свой момент — называется момент. [журнал 136, 1323, 415]
- ★ **Проверяется не только число, но и выборка, на которой оно получено** («7 из 10 наших» — верное
  число на неверной выборке); у дроби числитель и знаменатель считают одно и то же; одно число про
  разных людей означает разное («от открытия MR до слияния» — скорость ревьюера, не наша).
  [pereproverka 330-331; журнал 6011; komanda 288-300]
- ★ **Число отставания клона — только после свежего обновления с удалённого по тому же клону**;
  локальная ссылка на удалённую ветку — «память о состоянии, а не состояние»; база сравнения диффа
  обязана быть свежей. [zadanie-start 404-424; журнал 6159]
- ★ **Версии сортируются версионной сортировкой** (лексическая ставит 0.9.7 после 0.10.0); **даты
  коммитов ненадёжны** (amend переписывает время) — начало работы берётся из трекера; **времена из
  разных источников — в одной шкале** (отметки в журнале UTC, время файла местное — три часа читаются
  как «работала ещё три часа»). [журнал 5792; komanda 302-304; otchyot-sessii 32-35]
- ★ **Служебные файлы каталога** (README, шаблон) несут те же поля и попадают в любой счёт по полям —
  исключать по имени явно; поиск по имени файла не находит варианты имени — «этого нет вовсе» только
  после второго способа; отсутствие ключевого слова ≠ отсутствие смысла (дважды «не закрыто» при
  написанном смысле); расхождение в единицу не округляется (за «38 вместо 39» — два потерянных
  предмета); три вопроса к каждому шаблону (класс символов, якорь, счёт равен перечню).
  [schyot-i-perechen 7-30, 65-84; pereproverka 133-140]
- ★ **Покрытие перегоняется после любой правки дерева**, даже «только комментариев» — README сузил
  триггер до ребейза; **причина отказа — по сравнению нескольких точек**, замер повторить через время.
  [pereproverka 150-156; журнал 4305-4307, 4462-4468]
- ★ **Проверка обязана шуметь об отказе**: dry-run глотает отказ сети и печатает «чисто»; код 0 у
  `--check` не значит «чисто»; класс «флаг вывода отнял доказательство» — печать итоговой строки
  управляется флагами, складывающимися с уже заданными в конфигурации, «падений ноль» получено из
  пустого вывода; зелёное может проходить случайно, красное может быть дефектом самой проверки —
  проверять, **почему** зелено или красно. [журнал 418-421, 180, 2894; klass-defekta 79-93]
- **Доказательство правки файла — `git diff --stat`** (строки, не зависят от локали), а не длина;
  правка из другой среды смешивает переводы строк, и удаления появляются там, где только дописывали;
  несостоявшийся замер — прочерк **с причиной**, таблица печатается и при неудавшемся замере;
  ненулевое число сверяется вторым способом так же, как пустое; вывод фоновой задачи может содержать
  нулевые байты — grep назовёт файл двоичным. [schyot-i-perechen 58-59, 107-112, 133-151;
  komanda 264-267; priznaki-zhizni 277-282]
- **Код возврата и состояние объекта, а не текст вывода** — обратная сторона правила README про
  нулевой код: кириллица в консоли нечитаема, «Затёрто исключений: 7» прочитано как «Список», отказ
  принят за успех; вывод дочернего процесса берётся с явной кодировкой. [журнал 4314-4322; CLAUDE.md;
  strazh-hook 9-15]
- **Вид на экране — не доказательство**; **инструмент разработки может ронять проверяемое** (прогон
  покрытия создал каталог под наблюдением dev-сервера — «я сломал контур»); **инструмент считает не ту
  единицу** (размер через переходник, байты вместо символов) — замеры «до» и «после» одной командой в
  одной среде. [витрина; журнал 5247]
- **«Где не проверял — сказать прямо»**: тихая догадка хуже пропуска; узкая область замера называется,
  чтобы исполнитель проверил остальное; заголовок числа не должен требовать расшифровки вопросом;
  поправки входят в вывод строкой, а не коэффициентом; одна работа не считается дважды.
  [pereproverka 124; zadanie-start 100-104; komanda 248-250, 444-467]
- **Договорный слой измерения**: собственный отчёт и план оркестратора отстают молча — положение дел
  мерится запросом в трекер, потом сверяется с отчётом (отчёт говорил 34 MR / 10 задач, запрос дал
  51 / 18); трассируемость «задача → MR» считается по **первой** ссылке в описании (в конце стоят
  попутные находки, счёт по всем вхождениям утраивается); «выкатывается» ≠ «выкачен» — развёрнутость
  доказывается статусом и датой джобы деплоя, не списком влитых MR (на стенде жила версия двухдневной
  давности); термин обязательства («MVP», «этап») проверяется грепом по канону, не подразумевается;
  готовность мерится кодом в клонах, а не документом, счёт файлов — не мера функциональности; в
  докладе нет процентов готовности и оценок чужой работы («числа по чужим модулям — факт, «отстаёт» —
  недопустимо»). [dogovor 19-28, 70-107, 111-160]

### Разд. 10–11. Артефакты вне диффа и находки

- **Подвид «артефакт вне диффа + смена базы»**: файл в диффе, а число в нём неверно после ребейза —
  автоматика не видит и часть того, что в диффе; пара «источник → производное»: производное
  генерируется и руками не правится, при правке источника сверяется автоматически.
  [klass-defekta 47-51; strazh-hook 37-43]
- ★ **Всё, что публикуется, лежит файлом в месте, переживающем перезапуск** — не в контексте сессии
  и не во временном каталоге («тексты объявлены готовыми — файлов нет нигде»); оркестратор проверяет
  файл, не отчёт; заготовки именуются с номером задачи и лежат по каталогам задач.
  [журнал 312, 346, 1035, 1090, 1502-1510]
- ★ **До вывода «это находка» — проверить, не закрыт ли дефект сценарием приёмки текущей
  постановки**: закрыт — это незакрытый сценарий, правится в той же ветке; заголовок issue сжимает и
  потому врёт — читать описание целиком. [журнал 3564-3566, 6731-6733; nahodki 40-41]
- ★★ **Аудит своих заведённых находок** как процедура: состав запросом по автору плюс заведённые
  сессиями; порядок по риску устареть (ссылающиеся на код → старше двух суток → тронутые нашей
  работой → остальные); шесть исходов (актуальна / факт устарел / закрыта нашей работой / ложная /
  класс неверен / беспредметна), каждый доказан замером — «наверное, неактуально» без замера не ответ,
  объявить находку мёртвой без замера дороже, чем оставить живой; «факт умер, вопрос остался жив» —
  два разных исхода; триггеры — много открытых наших, много чужих слияний в канон, давно не проверяли;
  строка честности в итоге — сколько проверено, сколько осталось. [nahodki 9-57, 174-204;
  komanda 704-711; журнал 250, 439]
- **Ложная атрибуция дефекта отзывается везде, где записана** — «документация, врущая о причинах,
  хуже её отсутствия»; находки одного слоя связываются перекрёстно; умолчание «попутно со следующим
  MR» исполняется следующим MR, не задним числом; дефект продукта — задача, не дефект канона (канон не
  нарушен, если молчит); метка «заблокировано» — только когда взять нельзя; в канон не вносится
  временный чужой дефект как норма. [журнал 4046-4049, 5452, 394; komanda 572; витрина]
- **Правило «у каждого факта один дом»** как норма для документов: значение живёт в одном документе,
  остальные ссылаются; норма — в общий файл, причина нормы с именами и реквизитами — в приватный;
  выжимка канона — не основание, каждый факт с файлом-источником, снимок расходится с живым
  репозиторием за дни. [витрина «Три правила»; журнал 1743-1748, 2040, 2363]

### Разд. 12–13. Классы дефектов и состояние работ

- **Классы, названные источниками и отсутствующие в таблице** (в `klass-defekta.md` десять, в README
  семь): «плюсы отвергнутого варианта решения прочитаны как решение»; «ограничение перенесено на
  объект, которого оно не касается» (причина установлена для одного, вывод применён ко всей группе);
  «флаг вывода отнял доказательство»; «выдуманный факт» (приписанное авторство решения); «ссылка по
  смыслу, а не по тексту»; «проверка существует, но молчит об отказе»; «правило машины, которого нет в
  нашей проверке»; «своё же действие как источник ошибки»; «зелёный относится к прежнему состоянию»;
  «находка устарела по нашей же вине»; «ожидание, которого процесс не требует» (сессия объявляет
  ожидание при наличии умолчаний и свободных руках, простой тихий); «вывод по сигналу вместо объекта»;
  «жду завершения вместо замера» (ход исполнителя кончается, работа стоит; отвязанный запуск защищает
  процесс, а не способность дождаться). У семи перенесённых корень и признак сокращены: у класса 2 нет
  «или числу» и «пустой вывод принят за ноль»; у класса 3 — «доставка адресату», не только
  исполнителю; у класса 4 — «версия опубликована»; у класса 9 — измеримый признак «счёт строк предмета
  равен счёту строк маркера». Веса нет: «метка вместо содержимого» — самый частый класс, **восемь из
  тринадцати**. [klass-defekta 42-43, 79-105, 120-122; schyot-i-perechen 11; журнал 409, 216,
  418-421, 5687; pereproverka 394, 504-509]
- **Починка класса «маркер без содержимого»** — считать предмет, а не маркер (число строк предмета;
  единица — только маркер); всякая фраза «ниже по тексту» проверяется тем, что ниже; **правило без
  сторожа (теста) машиной не удерживается** — оснастка стережёт себя; **правило, введённое владельцем,
  не приписывается канону** — дом правила называется явно. [klass-defekta 3-7, 120-122; журнал 5650]
- **Состояние задачи собирается одной сводной командой**, а не своими запросами; в состоянии
  различать проверенное и сообщённое, записывать проверенную причину, не гипотезу исполнителя; снятый
  вопрос помечается снятым, а не удаляется; история не переписывается; несколько сессий над одним
  файлом — дозапись безопасна, перестройка целиком нет; направление дописывания известно машине;
  «свод собран» пишется только за полный обзор; ритм сводов — не чаще 3–4 часов либо по событию.
  [zadanie-finish 63-65; журнал 4433, 1234, 1727-1731, 819, 277]
- **Передача сессии при переоткрытии** файлом: точка цикла, таблица опубликованного, порядок шагов,
  готовые тексты «не переписывать», ловушки задачи, «что уже проверено — не тратить круг», где
  физически лежит работа; длинная сессия переоткрывается через файл передачи (5 тыс. символов вместо
  4,8 МБ контекста) — работа живёт на диске и в ветках, не в контексте. [журнал 1236, 1279, 1496-1500]
- **Сводный обзор как процедура** (README называет его одной строкой в разд. 13 и 17 — недостаточно:
  это единственная процедура, обнаруживающая «возвращена с ревью», «нас догоняет чужое слияние»,
  «задачу назначили в наше отсутствие», «MR влит, а задача не сдана»): четыре части — наш срез /
  работа остальных / что догоняет / прогресс; всегда три ответа первой строкой — надо ли сейчас что-то
  делать, можно ли брать новую, по каким звать финиш; **два окна** — новостей «с прошлого свода»
  (умолчание сутки) и темпа фиксированной длины, потому что сравнение имеет смысл на одинаковой базе;
  «ничего не требуется» — законный ответ, но с «чего ждём и от кого»; когда собирается без просьбы —
  конец задачи, пауза ожидания, перед новой задачей после пары часов, возврат владельца; свод только
  читает, в трекер ничего; по человеку одна строка без оценок; переназначение задачи — изменение
  объёма, строкой с датой; чужой MR, ждущий нашего ревью, — называть даже когда пусто; что догоняет —
  пересечение репозиториев с нашей ветвью и репозиториев с чужими слияниями за окно, совпадение =
  ребейз числом коммитов, записывается в состояние. [komanda 7-53, 137-194, 540-542, 596-598;
  avtorezhim 123-143]
- **Темп и сравнение — раздела нет**: годная метрика — влитые MR по автору («закрыл» и «сделал» —
  разные люди); единица сравнения — закрытая задача, не MR (одна задача даёт 1–5 MR); три времени
  различаются; база — медиана сопоставимых по роли без руководителя и аналитика, не максимум; три
  исхода с обязательным вопросом рядом (отстаём — чем держит; впереди — не дробление ли); отставание
  из-за оснастки называется с числом времени; честность в обе стороны; ярлык только на себя, про
  других — числа без «быстрее/медленнее»; строки диффа — не труд; встроенный счётчик комментариев
  включает наши ответы. [komanda 225-475; журнал 3666-3668, 4873-4889, 5061-5076]

### Разд. 14. Оркестрация ИИ-сессий

- ★ **Таймер — первым вызовом в ответе**; одиночная синхронная проверка без таймера запрещена, пока
  работа не закончена (она даёт число, которое хочется написать, ответ ощущается готовым — таймер
  выпадает); самотест перед **любым** сообщением, включая односложные, тремя вопросами (работа
  кончена? живой таймер есть сейчас — проверено, не вспомнено? сомневаюсь — поставил новый; лишний
  таймер стоит строки, пропущенный — молчания); **отметка `[ЧЧ:ММ]` в начале каждого сообщения**,
  взятая отдельным вызовом непосредственно перед ответом, без арифметики; **строка статуса называет
  одно из трёх состояний** — работаю (над чем) / жду чужого хода (кого и чего; работы за нами нет —
  сказано прямо) / стою без работы (почему); экономия — в содержимом, не в частоте: одна строка, один
  срез, без пересказа и находок; пауза дольше интервала — сама сигнал, следующая строка называет
  причину; **механизм**: оркестратор сам не просыпается — ход возвращает завершение фоновой
  команды-таймера, которая после паузы печатает срез; ожидание держится **снаружи** среды, отказ
  которой должно обнаружить; упавший и отработавший таймер приходят одним уведомлением — читать код
  возврата; при нескольких оболочках оболочка каждой команды называется явно. Час простоя дважды.
  [priznaki-zhizni 19-70, 120-133, 158-201, 217-262, 349-407; журнал 6226, 6364]
- ★ **Живость — замером процесса исполнителя, а не оболочки-обёртки** (у неё CPU всегда ноль);
  промежуток 15–20 с; простой объявляется по двум замерам подряд, второй длиннее; поиск процесса по
  строке аргументов ловит собственную обёртку (ложная тревога о столкновении дважды) — искать по имени
  исполняемого файла и печатать перечень с pid; два процесса разных сессий — норма, столкновение —
  два с одним идентификатором; признак пропущенной проверки — в клоне правки со временем, когда
  сессия по своему отчёту там не работала. [priznaki-zhizni 79-115; avtorezhim 55-56, 191-227]
- ★ **Параллельные сессии**: самый свежий файл по времени не идентифицирует сессию — искать по
  уникальному содержимому задания и идентификатору из окружения (слово ушло в чужую сессию; два
  процесса на одной истории); пустой лог и «зависшее» сообщение — не доказательство смерти;
  исполнитель **тоже** запускает долгие прогоны отвязанно — правило одно на оба уровня.
  [журнал 6431-6433, 6461, 6504; id 8-23]
- ★ **Проверять, не встала ли сессия на ожидании, которого процесс не требует**: вопрос с умолчанием,
  MR в ожидании чужого слияния, находка — не блокируют; сессия может объявить ожидание и быть
  свободной, простой тихий; на каждой вехе перечитываются комментарии задачи — решение приёмщика
  приходит по ходу и доставляется исполнителю. [komanda 780-785; журнал 370, 427]
- ★ **Форма ответа владельцу**: порядок — проверено → найдено → блоки исполнителям → служебные
  записи → итог → блок «что от тебя требуется»; итог — последний блок ответа, ниже ничего; четыре
  строки итога (пройдена ли; что дальше — три ярлыка «идём сдавать / стоит ещё круг / нужно твоё
  решение», последний только при выборе; следующая команда именем; единственное действие владельца
  одним предложением в повелительном наклонении либо «Ничего») — три действия в блоке значит решение
  за владельца не подготовлено; ярлык определяется наличием блока с правками кода, не ощущением;
  текст для агента всегда наш — владелец копирует блоки, «скажи ей коммить» запрещено; доклад
  заканчивается пронумерованной очередью действий с именем команды и «зачем» простыми словами, шаги
  человека внутри той же очереди; в блок кода только копируемое; команда не ставится в очередь по
  формальному признаку — сначала ответить себе, что она найдёт; вопросы к владельцу отдельным блоком;
  если ответ приёмщика поправляет наши формулировки — это главное в докладе. [chto-ot-tebya-trebuetsya
  1-43; pereproverka 594-645; komanda 821-882, 897]
- ★ **Правило без пункта самопроверки живёт до первого прогона**; самопроверка — чеклист обязательных
  строк доклада в порядке доклада; пункт, прогнанный, но не выведенный в доклад, считается пропущенным
  (владелец видит доклад, а не наши запросы); обязательный блок проверяется наличием, состав сверяется
  с домом поимённо с пересчётом (таблица усохла вдвое и выглядела выполненным правилом); «нет» — текст
  дописывается, а не выдаётся. [komanda 732-740, 771-772, 818-819; журнал 4249-4256, 4692-4707]
- **Вопросы владельцу**: любой вопрос (и собственный оркестратора) сначала через канон, грепом **по
  предмету, а не по формулировке вопроса**; форма из четырёх частей (что решается; варианты по
  последствиям; рекомендация одним из них; довод фактом, добытым **до** выдачи) — отсутствие
  рекомендации признак непроверенного факта, число из отчёта исполнителя рекомендацией не
  подкрепляется до перемера; вопрос задаётся на том шаге, где нужен ответ, не раньше (признак —
  «рекомендую» и «потом» в одной фразе); снятый каноном вопрос всё равно упоминается строкой; вопрос
  закрывается **доставкой** ответа тому, кто на нём стоит, а не записью в состояние — в том же ответе
  блок исполнителю; настоящие вопросы — про выбор, не про знание; вопрос наружу сам проходит
  перепроверку («перепроверь вопрос» — снялся); при разобранных вариантах выбор владельцу не
  выносится. [vopros-vladelcu 10-72, 115-145; журнал 1370, 2874-2897; память 07.09]
- **Одна задача — одна сессия**; запуск из корня воркспейса; послойная загрузка контекста; **отдельный
  агент для тяжёлого чтения канона**, чтобы не вытеснять контекст задачи; **автономный цикл (ralph
  loop)** для однотипной мелкой работы: критерий приёмки — команда, а не пожелание, без критерия в
  цикл не берётся; не для контрактов, схем, безопасности, топологии; смотреть дифф, не отчёт цикла;
  цикл не отменяет запрет на коммит и скилл безопасности. [onboarding 08:88-123, 198-281; витрина]
- **Правило, записанное в документе, исполняется, пока о нём помнят; встроенное в команду или
  перехватчик — всегда** (принудитель); хук вместо просьбы; ограничение разрешённых инструментов как
  дисциплина («неправильная форма вызова упирается в запрос разрешения»); список запретов —
  необратимое и чтение секретов, промежуточного «спросить» нет; **тонкая команда + толстый скилл** —
  процедура в одном месте, две точки входа зовут её (лечение класса «правило жило в двух местах»);
  описание скилла как триггер; **явный вердикт по каждому пункту чеклиста** и статус «не выполнена:
  причина» — иначе модель сворачивает чеклист в одну ободряющую строку; тело скилла начинается с цены
  ошибки; **чего переносить не стоит — объёмы**: скилл на 100 КБ в небольшом проекте станет мёртвым
  текстом. [витрина «Механизмы»; karkas-upravlenie\README, разд. о переносимости]
- **Секреты в ИИ-сессии**: значения не выводятся, не печатаются даже в диагностике, не подставляются
  в примеры и не запрашиваются в переписку — остаются в истории сессии, которую читает оркестратор и
  копирует в заготовки; из файла с секретами читаются только нужные поля парсером; сессия
  запускается из каталога оснастки, иначе остаётся без команд. [журнал 1761-1765; whoami 7-22]
- **Короткое объяснение владельцу**: суть одной фразой, потом зачем; 2–5 предложений; по проекту —
  сперва источник; двусмысленность — выбрать вероятное и назвать второе строкой; не пересказывать, не
  давать план. [explain 10-17]

### Разд. 15. Машинные проверки

- **Модель вердикта**: три цвета; «не выполнилась ≠ пройдена» — обязательная проверка, не
  отработавшая, даёт красный, предупреждающая — жёлтый; три статуса «не применима / не выполнена / не
  работает»; стадии от дешёвого к дорогому, вердикт выполняется всегда, публикация и деплой в приёмку
  не входят; **подавление — пять атрибутов** (правило, место, причина, автор, срок не дольше квартала),
  всегда жёлтый; новая проверка первый месяц — предупреждающая; строки ИИ-ревью не блокируют никогда —
  блокирует детерминированная половина; самопроверка покрывает **каждое** правило машины — перечень
  правил джобы читается дословно (мерили четыре, джоба проверяет пять). [kanon-vyzhimka-priemka
  100-188; журнал 198]
- ★ **«Не выполнена» против «не применима» локально**: невыполнимая на машине проверка называется
  отдельно и цветом не красится, довод — по составу диффа из карты проверок, заменитель прогоняется,
  подавление на недоступный инструмент не оформляется (две сессии дали разный цвет на одном классе —
  значит правила не было); красное, воспроизведённое на базовой ветке и не связанное с диффом, не
  блокирует публикацию, но называется; правка без воспроизведённого красного не выдаётся за починку.
  [журнал 6291, 6303, 5584, 6435, 6457]
- **Устройство оснастки проекта**: команды старта, финиша, ADR, входа аналитика; скиллы — по одному
  на канон; **скилл безопасности — на любом диффе без исключений, включая документацию**; условия
  запуска — в одном месте, копии не делаются («разошедшаяся копия хуже отсутствующей»); локальный
  предиктор против детерминированной утилиты CI — при расхождении прав CI, чинится предиктор; хук
  секретов с тестом. [kanon-vyzhimka-zadachi 82-110; onboarding 08:9-87]
- **Локальный страж до трекера** — третий слой к хуку и CI: запускается сам после каждой правки
  текстового файла в каталоге оркестратора, проверяет то, что иначе держится на дисциплине (чужие
  следы в публикуемом по закрытому списку, значения секретов — читаются из хранилища на лету и не
  печатаются, управляющие байты, кодировка скриптов, имена и разделы постановок); **молчит, когда
  чисто** — шум приучает не читать вывод; информирует, а не блокирует правку — блокирует уже коммит;
  логика — отдельным читаемым файлом с негативным тестом, не строкой в конфигурации; гигиена смотрит
  **добавленные строки**, а не весь файл; короткий токен в списке совпал с самой частой единицей стилей
  (149 ложных) — вносить в путевой форме, шаблон сужается, обход не применяется; оснастка ставится
  идемпотентным скриптом, fail-closed, громкий отказ вместо тихой подстановки. [strazh-hook 1-53;
  settings.json; журнал 3086-3099, 3835-3863, 2649-2661, 2724-2742]
- **Среды**: четыре, с ростом цены ошибки; «работает у меня ≠ работает в контуре»; dev — автодеплой
  из main; локальный контур ведёт себя как прод (HTTPS везде, интернета нет), автономность сборки на
  своей машине не проверить; «выкатывается ≠ выкачен» (см. разд. 9). [onboarding 00:165-208;
  kanon-vyzhimka-priemka 218-233; dogovor 87-107]
- **Пайплайны создаются только на MR, не на ветку**; сканер секретов конвейера issue не проверяет.
  [журнал 5706; soobshchenie 58-60]

### Разд. 17–18. Внедрение и ограничения

- **Онбординг как норма процесса**: «один рабочий день от чистой машины до влитого MR», дольше —
  дефект документации и задача; чеклист первого дня; перечень канона, читаемого до первого коммита.
  [onboarding 09:5-7, 60-65; CLAUDE.md]
- **Канон не копируют — на него ссылаются**; выжимка не источник, при сомнении открывать оригинал;
  общие правила — отдельными файлами, которые инструкции **подключают целиком, а не пересказывают**
  («один дом у правила»). [kanon-vyzhimka-zadachi 3-7, 96-97; blokiruet-li 25]
- **Обслуживание инструкций** — раздела нет: инструкции растут по построению (каждое правило куплено
  ошибкой и приходит с разбором случая); дописанное в конец исполняется хуже стоящего в начале (две
  команды по 530–670 строк против рабочей на 17); **урок вписывается в инструкцию-точку выдачи**, а не
  в отдельный перечень; критерий сокращения — не «короче», а «не больше, чем нужно»: к каждому абзацу
  вопрос «если убрать, какая ошибка вернётся?», сжимать довод, не правило; до правок выписывается
  перечень действий, к которым инструкция обязывает, после — сверяется построчно («переехало» ≠
  «исчезло»); дубли между инструкциями ищутся замером (блок на 111 строк лежал в пяти командах); пять
  видов лишнего (дубль → общий файл; повтор внутри → строка самопроверки; разбор длиннее правила →
  «куплено <дата>: <что>»; пересказ канона → ссылка; пример без правила → убрать); не выбрасывается
  никогда — купленные правила, запреты, адресаты, **самопроверка**, числа канона; сокращение — удаление
  чужих правил, ни одна строка до согласования, отказ записывается, чтобы через неделю не предложить
  снова; не сокращать инструкцию, которую сейчас исполняешь; появились «обычно», «желательно» —
  правило испорчено. [sokratit 9-144; журнал 4935-4941, 4991-5045]
- **Новое правило формы рождается вместе с проверкой** («страж проверяет форму, а не честность»);
  черновики исполнителя — след мышления, не источник требований; производные снимки берутся из
  опубликованного состояния, не из рабочего дерева. [журнал 2980, 4776-4787, 5238-5250]
- **Минимум того, что делают команды цикла** (иначе п. 5 разд. 17 не с чего начать): старт —
  синхронизировать основную ветку, создать свою, загрузить контекст модуля, прочитать постановку;
  финиш — чеклист, артефакты, решение, проверки диффа, вердикт «выполнено / не выполнено /
  неприменимо» по каждому шагу; перечень инструкций цикла в п. 5 неполон — нет проверки исходящего,
  аудита находок, сводного обзора. [zadanie-start 108; zadanie-finish 91-93; komanda 690-692]
- **Объём урезается границами, а не молча**: предложение об урезании — в раздел «Границы» задачи
  («делаем / не делаем — почему»), письменно согласованное с приёмщиком; молчаливое сокращение и есть
  недостижение результата; чужое решение молча не откатывается; слабый вопрос заказчику снимается —
  ждать наш час ему дороже правки. Для работы по договору — центральная норма; разд. 18 отдаёт
  «объём» владельцу, не называя процедуру. [CLAUDE.md; журнал 2775-2791]
- **Приёмка по договору — отдельный слой поверх приёмки по процессу**: результат развёрнут в контуре
  заказчика плюс демонстрация; периодический отчёт как основание акта; соответствие позициям
  приложения, а не номерам задач — по каждому строка «закрыто / не закрыто / закрыто чужими руками».
  Разд. 18 законно молчит про деньги и сроки, но не про этот слой. [dogovor 61-68]

### Специфика окружения, за которой стоит переносимая норма (одной строкой)

- «Контейнеры запущены» и «дистрибутив Running» ≠ «стенд в порядке» → статус «запущен» ≠ «работает»,
  первым — дешёвый запрос по существу. [журнал 3200-3204, 1611-1620]
- Первый диагноз «нехватка памяти» неверен (гость не видит отбора CPU хостом) → диагноз проверяется
  снаружи, лечение соразмерно проверенной гипотезе. [журнал 38]
- Ошибка 403 на корень домена — не диагноз; `curl` без CRL даёт `000` при живом контуре → сначала
  проверить инструмент диагностики на заведомо живом объекте. [журнал 3196-3198, 2255-2263]
- Задание с кавычками через оболочку рвётся, лога нет → «лога нет — команда упала на разборе строки»;
  передавать файлом. [журнал 5450, 6228]
- Сообщение коммита через heredoc теряет последнюю строку → многострочное файлом, последняя строка
  проверяется после коммита. [журнал 528]
- Синтаксическая проверка скрипта пропускает незакрытый heredoc → не заменяет чтения. [журнал 5186]
- Код возврата конвейера — от последней команды, не от `grep` → код берётся у нужной команды.
  [журнал 403, 2180]
- Поиск процесса по подстроке ловит собственные оболочки ожидания → признак завершения — итоговая
  строка лога или точное имя процесса. [журнал 5390]
- `docker ps | wc -l` посчитал строки ошибки → проверять исполнением с кодом возврата, не счётом
  строк. [журнал 1674-1677]
- Права выдаются при установлении VPN-сессии → после изменения прав переустановить сессию, прежде чем
  делать вывод «не работает». [журнал 2005-2036]
- Перед переключением клона проверить незапушенное; трёхточечный дифф врёт при ушедшем main; `-d`
  отказывает после squash → сверять содержимое перед `-D`. [журнал 5723-5726, 6203]
- Хук читал весь файл, а не добавленные строки → гигиена смотрит добавленные строки, иначе блокирует
  чужое; `core.hooksPath` перекрыл бы родные хуки → конфигурация проекта не действует на чужие
  проекты. [журнал 3086-3099, 1837-1846]
- Перезапуск общего движка роняет чужие контейнеры и тестовые базы → цена действия называется вслух.
  [журнал 5766-5801]
- Обрыв VPN: пустой ответ трекера читался как «комментариев нет» — README это покрывает.
