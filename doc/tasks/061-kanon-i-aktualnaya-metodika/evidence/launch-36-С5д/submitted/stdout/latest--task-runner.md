# Раннер: автоматизация цикла сессий

Алгоритм программы, которая ведёт задачу по [task-sessions.md](../../../../publication/originals.zip) (историческая цель: `task-sessions.md`; точный оригинал — в архиве): запускает сессии агента, считает заходы, показывает прогресс по шагам, останавливается у ворот, где решает человек, и собирает запросы к модели так, чтобы кеш контекста переживал смену сессий. Правила цикла здесь не повторяются: что делает каждая сессия и когда повтор заканчивается, сказано в task-sessions.md; здесь только то, что нужно программе, чтобы это исполнить. Константы цикла — потолок заходов, число чистых заходов подряд, число проб — берутся из «Правил» task-sessions.md; в программе они названы ПОТОЛОК_ЗАХОДОВ, ЧИСТЫХ_ПОДРЯД, ПРОБ_В_ЧИСТОМ, и числа в этом файле — примеры при нынешних значениях.

## Словарь

| Термин | Что это | Пример |
|---|---|---|
| **Задача** | одно задание заказчика, одна папка задачи, одно рабочее дерево | — |
| **Фаза** | крупный отрезок цикла с одними воротами на выходе: РАЗБОР, ПЛАН, РЕАЛИЗАЦИЯ, СДАЧА, ОБРАТНАЯ_СВЯЗЬ | фаза ПЛАН заканчивается утверждением plan.md |
| **Сессия** | один промпт из task-sessions.md, выполненный агентом; виды — С1 … С9, их правки и продолжение; в логах у каждого вида код без пробелов | С6 — проверка реализации, С5п — правка реализации |
| **Диалог** | цепочка запросов к модели с общим префиксом и накопленной историей; сессия — либо новый диалог (разбор, план, реализация, проверки, сдача), либо ход живого диалога автора (правки, продолжение) | С5п — ход диалога С5 |
| **Цикл проверки** (stage) | пара «проверка ↔ правка» одного артефакта: spec, plan, review, delivery (в режиме совещания — meeting); по нему считаются заходы, потолок и чистая серия; в «Правилах» task-sessions.md это слово «цикл проверки» | review-3.md — третий заход цикла review |
| **Заход** | порядковый номер файла проверки внутри цикла проверки; при возврате в фазу не обнуляется (task-sessions.md, «N — номер захода») | review-3.md |
| **Шаг** | счётная единица работы внутри сессии; у каждого вида сессии своя единица | С5: пункт плана 7/12; С6: доказательство 2/17 |
| **Ворота** | точка, где программа останавливается и ждёт решения человека; идентификаторы В1 … В13 | В5 — утверждение spec.md |
| **Профиль запуска** | параметры одного запуска модели: класс модели, усилие, размышление, ожидаемый объём входа, срок жизни кеша | класс A, усилие 4 |
| **Класс модели** | A — самая способная, B — средняя, C — быстрая; какая модель поставщика стоит за классом, задаёт конфигурация программы | — |
| **Усилие** | ступень 1–5 от минимальной к предельной; какому уровню поставщика соответствует ступень, задаёт конфигурация программы: имена уровней у поставщиков свои и меняются | С3: усилие 5 |
| **Размышление** | вкл — модель рассуждает перед ответом и между вызовами инструментов; выкл — самый дешёвый режим рассуждений, который модель даёт отключить; если отключить нельзя, выкл значит минимальная ступень усилия. Какие сочетания усилия и размышления модель принимает, знает конфигурация программы | С7: выкл |

Ниже «цикл проверки» — пара «проверка ↔ правка»; «этап» — вид работы внутри фазы, для которого выбирается модель (раздел «Этапы и модель»); «шаг» — счётная единица внутри сессии; «пункт плана» — нумерованная строка раздела «План».

Коды сессий: С1, С1п, С2, С3, С3п, С4, С5, С5д (продолжение), С5п, С6, С7, С7п, С8, С9, КОММИТ, ПУШ; в совещании — автор А, свидетель Св, линзы Л1, Л2, … по порядку линз в задании. Автор цикла проверки: spec — С1, plan — С3, review — С5, delivery — С7; проверка: С2, С4, С6, С8; правка: С1п, С3п, С5п, С7п.

Строка прогресса для человека: `Фаза · код сессии · единица k/N · заход j/ПОТОЛОК`, где j = n − pass_origin + 1, n — номер файла проверки; у сессий без заходов часть «заход» не показывается. Пример: `РЕАЛИЗАЦИЯ · С6 · доказательство 2/17 · заход 2/4 (review-6.md)`.

## Единицы шага и откуда берётся N

| Код | Единица шага | Откуда программа берёт N до запуска |
|---|---|---|
| С1 | источник | число файлов в task/ без task/feedback-*/ плюс ссылки в task/message.md |
| С1п | существенная находка или ответ | K из первой строки файла с находками; число ответов в разделе «Ответы» spec.md |
| С2 | источник | число из строки `итого:` раздела «Опись источников» (spec.md или spec-trace.md) |
| С3 | требование | число REQ-xx в spec.md |
| С3п | существенная находка или решение | K из файла с находками; число `решено:` в plan.md |
| С4 | требование | число REQ-xx в spec.md |
| С5 | пункт плана | нумерованные строки раздела «План» plan.md |
| С5д | пункт плана | строки раздела «План» минус строки `пункт <n>: сделан` (или прежней формы `шаг <n>: сделан`) в result.md |
| С5п | существенная находка | K из review-N.md; из feedback-N.md — число замечаний с исходом «правлю» и уровнем «реализация» |
| С6 | доказательство | строки `[ ]`/`[x]` раздела «DoD» plan.md плюс строки раздела «Трассировка» result.md |
| С7 | файл | 2 или 3 по способу сдачи |
| С7п | существенная находка | K из delivery-review-N.md |
| С8 | сценарий | число AC-xx в spec.md |
| С9 | замечание | неизвестно до запуска: агент сообщает N первой строкой прогресса |
| КОММИТ, ПУШ | — | единиц нет: сессионная часть хвоста только «Сессия: <код>. Единиц нет: одна строка «<код> 0/0 старт», строку ПРОФИЛЬ не пиши» |

Если считать нечем, программа показывает `?/?` до первой строки агента. Если агент сообщил N, отличное от посчитанного, программа показывает N агента и один раз пишет расхождение в log.md: агент видит содержимое, программа только форму. k > N не ошибка: показывается как есть, шкала не выше 100 %.

## Машинные форматы

Программа читает только эти места; каждое из них требует либо промпт task-sessions.md, либо машинный хвост ниже. Всё остальное в файлах — для людей и агентов.

| Файл | Что читается | Формат |
|---|---|---|
| spec.md, plan.md | статус | первая строка начинается с `Статус: черновик` или `Статус: утверждено`; дата и кто — после запятой, программа их только показывает. Первая строка, не подходящая ни под одно, — ворота В13, а не статус «черновик»: молчаливый черновик запустит проверку заново поверх утверждённого документа |
| plan.md | базовая ревизия | вторая строка `База: ревизия <хеш>, <дата>` |
| spec.md | требования, сценарии, запреты | идентификаторы `REQ-NN`, `AC-NN`, `DNC-NN` в начале строки; каждая запись — отдельный абзац (пустая строка перед записью) |
| spec.md или spec-trace.md | опись источников | раздел «Опись источников» (в spec.md или, если он вынесен, в spec-trace.md); число из его последней строки `итого: <число>` |
| plan.md | пункты плана | нумерованные строки `1.` … `n.` раздела «План» |
| plan.md | ветка задачи | строка `Ветка: <имя>` в разделе «План» |
| plan.md | тип | необязательная строка `Тип: эпик` в разделе «План», рядом с `Ветка:`; первые две строки остаются за статусом и базой |
| task/message.md | эпик задачи | необязательная строка `Эпик: <путь папки эпика>` и REQ эпика, которые закрывает дочерняя задача |
| plan.md | DoD | строки раздела «DoD», начинающиеся с `[ ]` или `[x]` |
| plan.md | решения | строки раздела «Требует утверждения»; пометка `решено:` |
| result.md | статус | первая строка `Статус: в работе` или `Статус: готово` |
| result.md | сделанные пункты плана | строки `пункт <n>: сделан`; прежняя форма `шаг <n>: сделан` читается наравне |
| result.md | статусы критериев | слова `PASS`, `FAIL`, `NOT VERIFIED`, `N/A` в строках раздела «Трассировка» |
| result.md | решения владельца | у каждой строки FAIL, NOT VERIFIED и Known limitations пометка `решение владельца: …, <дата>` |
| spec.md, plan.md, result.md | вид остановки | первое слово последнего абзаца: `ревизия`, `план`, `требования`, `вопрос`; читается только при статусе «черновик» или «в работе» |
| *-review-N.md | итог захода | первая строка `Заход N: существенных K, поверхностных M, проб P`; у совещания (`proposal-review-N.md` и файлы линз) — строка с тремя серьёзностями, ниже |
| *-review-N.md | находки | пункт нумерованного списка `1.` … `n.`; внутри поля `критичность: существенная` / `критичность: поверхностная` и `уровень: реализация` / `план` / `требования` / `вне задачи` / `сдача`; пункт без поля критичности — существенная; у существенных находок уровня «реализация» поле `причина: модель` / `задание` / `среда` / `внешняя проверка` обязательно, если включён счёт по моделям (проверяет `verify_formats`); у совещания (`proposal-review-N.md`) — поля файлов линз, строка ниже |
| proposal-review-N-<линза>.md | находки | нумерованный список `1.` … `n.`; в каждом поля `критичность: критическая` / `значимая` / `желательная` (серьёзности `methodology.md`, раздел 18; пункт без поля или с другим значением — критическая) и `доказательство:` (пустое поле — признак несостоятельного мнения); у значимой находки, которую проверяющий находит снова после правки автора, поле `повтор: заход <M>`, M — заход, по находкам которого автор её правил (у других серьёзностей поле не читается); уровня у находок совещания нет; первой строкой итог линзы `Заход N: критических K, значимых Z, желательных D, проб P`; раздел `Ответы свидетеля:` (или строка «ответы свидетеля не использовались»); раздел `Проверено:` — прочитанные файлы и диапазоны; отсутствие любого из разделов — нарушение формы файла |
| witness-N.md | ответы свидетеля | строки, начинающиеся с `наблюдалось:`, `не наблюдалось:`, `не измерено:` или `вывод:`; строка с другим началом — нарушение формы, ответ возвращается свидетелю; у строк кроме `не измерено:` поле `источник:`, при необходимости `выдержка:`; цифры, посчитанные скриптом, идут строкой `наблюдалось:` с источником «запрос и вывод», длинный вывод — отдельным файлом, на который строка ссылается; строка без нужного начала или без `источник:` отвергается проверкой формы; последняя строка `не читал: <перечень>` |
| review-N.md | отчёт по секретам | строка, начинающаяся с `Секреты в diff:` (пункт 5 С6) |
| feedback-N.md | замечания | первая строка `Раунд N: правлю K, доводом M, отвергаю R`; пункт нумерованного списка с полями `исход: правлю` / `отвечаю доводом` / `отвергаю` и `уровень: реализация` / `план` / `требования` |
| feedback-N.md | маршрут | последняя строка `Маршрут: С1 правка` / `Маршрут: С3 правка` / `Маршрут: С5 правка` / `Маршрут: С7` |
| progress.log | прогресс | строки `<код> <k>/<N> [<время>] <подпись>`: код сессии без пробелов, первая пара чисел через `/`, необязательное поле времени в квадратных скобках (`[ЧЧ:ММ]` или `[ГГГГ-ММ-ДД ЧЧ:ММ]`, местное время), остаток — подпись; у строки `запуск` подпись — `запуск №<n>`, n — порядковый номер запуска в задаче; без поля время появления строки ставит программа при чтении. Правила строки — ниже, «Строки progress.log» |
| profile.log | подсказка профиля | строки `ПРОФИЛЬ от <код>: класс=<A|B|C> усилие=<1..5> размышление=<вкл|выкл> бюджет=<целое число токенов> причина=<текст>`; поля разбираются по отдельности, неразобранное поле — умолчание |
| state.json | состояние программы | см. ниже; агенты его не читают |

Оба лога лежат в папке задачи и только дописываются. Программа запоминает длину каждого перед запуском сессии и читает только строки, дописанные после отметки; при повторном запуске оборвавшейся сессии отметка ставится заново.

**Строки `progress.log`.** Журнал хода — сигнал для человека и программы, идёт ли работа и чем кончилась сессия, а не доказательство: завершение судится по артефакту и независимой проверке ([methodology.md](../../../../publication/originals.zip) (историческая цель: `methodology.md`; точный оригинал — в архиве), раздел 10), а агент может писать во все файлы папки задачи, поэтому нарочную подделку журнала агентом журнал не ловит и не обязан ловить; правила ниже ловят честные ошибки формы и делают журнал однозначным. Правила, без которых по журналу не отличить ход от молчания:

- время — часы 00–23, минуты 00–59, местное; берётся командой часов, а не по памяти: память ошибается, а время файла освежают слияние и переключение веток, и по нему «молчание» не отличить от хода; дата нужна, когда журнал живёт больше суток;
- одна строка на каждую завершённую единицу, дописывается сразу после неё, а не пачкой в конце: пачка в конце неотличима от молчания;
- ключевые слова — `готово`, `стоп:`, `запуск`, `старт`, `поправка:` — строчными, первым словом подписи после времени; слово читается целиком, и знак после него допустим (`старт:`, `готово —`), а у `стоп` и `поправка` двоеточие обязательно; `Готово` и `Стоп:` ключевыми не считаются: иначе слово в обычной подписи читается как конец сессии;
- первая строка самого агента в сессии — `<код> 0/<N> [время] старт` (строка оркестратора `0/0 запуск` не в счёт), N — число единиц, видимое сессии; сессия в журнале — строки с её кодом от её запуска до следующего запуска того же кода, а запуск — это то, что знает запускающий: у раннера запись в `state.launches` (номер, код, длина progress.log перед строкой `запуск`, группа процессов агента), с которой он сверяет строки `запуск`; в ручном цикле — строка `запуск` оркестратора в progress.log с полем времени, если она есть в его перечне запусков в log.md; файлы журнала и состояния от агента механизмом не защищены: агенты в state.json, log.md и строки `запуск` не пишут по правилу, запись, которую сделал агент, раннер от своей не отличит, а опора в ручном цикле — сам оркестратор; линзы совещания пишут каждая под своим кодом (Л1, Л2, …), поэтому их строки не смешиваются, даже если вторая стартует, пока первая ещё работает; каждый запуск несёт порядковый номер (`запуск №<n>`, в ручном цикле тот же номер в log.md), и одной записи запуска соответствует ровно одна строка `запуск`, вторая строка с тем же номером — существенная находка; перед повтором той же сессии прежний процесс агента останавливают и убеждаются, что его нет (раннер заводит для агента группу процессов — средство операционной системы для группы процессов, именованное, чтобы найти его после перезапуска раннера — до его старта, хранит её идентификатор и время старта в `state.running` и в записи запуска, останавливает группу целиком вместе с командами, которые агент запустил, и убеждается, что в ней не осталось процессов; идентификатор сверяется по времени старта, чтобы не остановить чужой процесс; в ручном цикле оркестратор закрывает прежнее окно агента и проверяет, что не осталось ни его процесса, ни запущенных им команд), иначе живой прежний процесс допишет строки, в том числе `готово`, в повтор; строка `старт` в сессии одна, и «N из строки `старт`» ниже — N из неё; k внутри сессии не уменьшается;
- подпись без времени — не длиннее 80 знаков, начинается с предмета (что сделано), без путей машины и секретов; номер захода — в подписи первой строки («старт заход 7»); прежние строки не переписываются: ошибка формы прежней строки исправляется не новой попыткой сессии, а строкой-поправкой той же сессии с текущим k и подписью `поправка: к строке «<начало её подписи после времени, от 10 до 30 знаков, а если подпись короче — вся подпись>» — <что не так>`; поправка не единица и не признак хода: ни показ `k/N`, ни сверка числа строк, ни «без прогресса» её не учитывают; пропуск единицы и старт не первой строкой поправкой не исправить;
- законченная сессия последней строкой пишет `<код> N/N [время] готово …`, где k сравнивается с N из строки `старт`, а не с N самой строки, и при единицах больше ожидаемых допустимо `k/N готово` с k больше N (сессия без единиц, КОММИТ и ПУШ, — только строку `0/0 старт`); последняя единица без такой строки завершением не считается (сессия может ждать человека на воротах); в строках, не последних в сессии, подпись не начинают словами «готово» и «стоп:»; после строки `готово` или `стоп:` строки той же сессии не пишутся, дальнейшее — новой сессией, которую запускает раннер или оркестратор, а не сам агент; исключений два, читается последняя строка, и исправленная строка запрет на «готово» и «стоп:» в непоследних строках не нарушает: (1) ошибку формы в самой последней строке исправляют, дописав её заново с тем же k и тем же ключевым словом в верной форме (вид остановки при этом меняется, только если прежний не из списка); строка с ошибкой в ключевом слове (`Готово`, `стоп` без двоеточия) последней строкой сессии не считается, а верная строка после неё считается её исправлением; (2) `готово` при k меньше N из строки `старт` завершением не считается и итоговой строкой не является; его исправляют по тому, что было на деле: работа идёт — поправкой и дальше единицами; сессия остановилась — строкой `стоп: <вид> — <причина>` с тем же k; работа сделана, а N в строке `старт` оказалось завышенным, — повтором `готово` с тем же k и подписью «N завышено: <причина>», что сверяется по артефакту; такая строка — итоговая и завершение, и сразу, и после прежнего `готово`;
- сессия, остановившаяся не дойдя до N или на воротах после последней единицы, последней строкой пишет `<код> <k>/<N> [время] стоп: <вид> — <причина>`, вид — одно из слов: вопрос, план, ревизия, требования, ворота; без вида причину остановки приходится угадывать;
- пока цикл ведётся вручную, перед стартом сессии оркестратор дописывает `<код> 0/0 [время] запуск №<n>`, чтобы сессия была видна, даже когда шагов ещё нет; в строках с `0/0` слово «запуск» значит «единиц пока неизвестно», слово «старт» — «единиц нет» (КОММИТ, ПУШ); строку `запуск` раннер пишет сам, до отметки, а строку `0/0 старт` у КОММИТ и ПУШ пишет агент; оркестратор каждый свой запуск, в том числе повтор оборвавшейся сессии, отмечает в log.md (`запуск №<n> <код> [время]`, тот же номер); агент строку `запуск` не пишет и в log.md не пишет;
- нарушение формы строки (ключевое слово, длина подписи, отсутствие номера захода, вид остановки, старт не первой строкой) — поверхностная находка и захода не держит; исключения — ошибка в ключевом слове последней строки, не исправленная повтором (законченная или остановленная сессия по журналу выглядит молчащей), `готово` при k меньше N из строки `старт`, не исправленное по исключению (2) (остановленная сессия выглядит законченной), строка после итоговой, кроме двух исключений (например, `готово` после `стоп: ворота`), а также `готово` в сессии без строки `старт` или со второй строкой `старт`, а также строка `запуск`, которой нет среди запусков раннера или в перечне оркестратора, строки с кодом, которого не было среди запусков, и вторая строка `запуск` с тем же номером: это существенные находки; раннер отмечает их строкой в log.md, проверяющий захода и оркестратор — находкой; пропуск единицы — поверхностная, если артефакт показывает, что единица сделана, иначе существенная.

**Записи требований, сценариев и запретов — отдельными абзацами.** В `spec.md` и `plan.md` каждая запись `REQ`, `AC`, `DNC` (и такие же списки: факты, допущения, неизвестное, вопросы, ответы, решения плана) — отдельный абзац: пустая строка перед записью, идентификатор в начале строки. Просмотрщик Markdown склеивает переносы строк внутри абзаца, поэтому подряд идущие записи без пустой строки сливаются в сплошной текст, который не прочесть глазами. Запись длиннее трёх строк делится на абзацы: суть («Когда … тогда …»), затем отдельными абзацами «Доказательство: …», «Источник: …», «Выведено: …». Таблицы — только для коротких ячеек (до 100 знаков); длинное содержимое — абзацами. Уже утверждённые документы переформатируются механической правкой (пустые строки) без изменения слов.

**Машинный хвост** — текст, который программа добавляет к промптам task-sessions.md; сами промпты не меняются, подстановки в них (`<репозиторий>`, `<источник правок>`, `<способ сдачи>`, `<ответ>`, `<ветка из plan.md>`, `<папка задачи>`) заполняет программа (см. `run`, [task-runner-pseudocode.md](../../../../publication/originals.zip) (историческая цель: `task-runner-pseudocode.md`; точный оригинал — в архиве)). Общая часть хвоста одинакова для всех сессий и живёт в системном промпте (слой 1 ниже), без подстановок. Сессионная часть подставляется в конец промпта сессии (слой 4): в ней код сессии, единица шага и требования формы, которых промпт не задаёт.


`state.json` — память программы между запусками, агенты его не видят. Пишется атомарно (временный файл, затем переименование) после каждого изменения и перед каждыми воротами.

```text

├── task_dir, repo_dir, delivery_mode        папка задачи, рабочее дерево, способ сдачи

├── step                                      ближайшее действие внутри фазы (сессия или ворота); фаза при входе продолжает с него
├── running                                   {сессия, источник, заход, время старта, группа процессов агента и время её старта} — ставится до запроса, снимается после проверки форматов
├── launches[]                                {номер, сессия, отметка длины progress.log, время, группа процессов агента и время её старта} — каждый запуск, только дописывается; граница сессии в журнале
├── next[phase]                               сессия, с которой фаза начинается при возврате, и её источник

├── lost[линза]                               подряд потерянных заходов линзы (режим совещания)

├── out_of_scope[]                            находки уровня «вне задачи» из заходов С6, ждут решения у В8
```

## Сборка запроса и кеш контекста

Кеш контекста у поставщика модели — кеш **префикса**: запрос сравнивается байт в байт от начала до точки отсечки, и любое изменение раньше точки обнуляет всё после неё. Порядок слоёв в запросе: инструменты → системный промпт → сообщения. Отсюда правило сборки: от самого стабильного к самому изменчивому, точки отсечки на границах стабильности.

```text
Слой 0  инструменты              один и тот же набор на все сессии задачи, отсортирован по имени
Слой 1  системный промпт         task-algorithm.md + «Правила» task-sessions.md + общая часть хвоста
                                 ─── отсечка 1: не меняется всю задачу
Слой 2  первое сообщение         материалы из task/ без подпапок task/feedback-*/, в порядке имён по кодам символов
                                 ─── отсечка 2: не меняется всю задачу
Слой 3  второе сообщение         spec.md, затем plan.md — после утверждения, байт в байт
                                 ─── отсечка 3 (только когда слой непуст): пишется заново при каждом утверждении
                                     и при каждом возврате в РАЗБОР или ПЛАН; слои 0–2 при этом читаются из кеша,
                                     заново пишутся только токены spec.md и plan.md — одна запись на фазу
Слой 4  дальше                   промпт сессии с сессионной частью хвоста, изменчивые файлы: result.md,
                                 review-N.md, feedback-N.md, task/feedback-N/ (только у С9), ход диалога
                                 ─── отсечка 4: автоматическая, на последнем блоке, двигается с диалогом
```

У сессий сдачи (С7, С7п, С8, КОММИТ, ПУШ) свой короткий префикс `prefix[сдача]`: слои 0–1 те же, вместо слоёв 2–3 одно сообщение с spec.md, plan.md, result.md и последним review-N.md, без материалов task/; отсечки после слоя 1 и после этого сообщения. Он пересобирается при каждом входе в фазу СДАЧА и после повтора С7. Сессии сдачи не читают кеш старших сессий и не пишут в него; поэтому у них может быть свой класс модели.

Правила, без которых раскладка не работает:

- **В слоях 0–3 нет времени, номеров заходов, кодов сессий и случайных значений.** Всё изменчивое — в слое 4. Один лишний байт в слое 1, например дата в системном промпте, обнуляет кеш всей задачи на каждом запросе.
- **Материалы в слое 2 — только форматы, которые поставщик принимает блоком документа или изображения** (текст, PDF, изображения). Остальное (видео, архивы, выгрузки, код) перечисляется в слое 2 строкой «файл <имя>, <размер> — читай инструментом», сам файл агент читает с диска. Обратная связь в префикс не входит: task/feedback-N/ приходит после сдачи и меняла бы слой 2 каждый раунд.
- **Одна модель на всю задачу.** Кеш привязан к модели: смена класса между сессиями обнуляет кеш целиком. Класс выбирается на задачу; исключение — сдача с её коротким префиксом. Если кешем управлять нельзя, правило не действует: модель выбирается по этапу (раздел «Этапы и модель»).
- **Усилие и размышление одинаковы у всех сессий фазы**: автора, проверки и правки. Их смена обнуляет кеш сообщений (слои 2–4), у части моделей и слои 0–1, поэтому проверка с другим усилием, чем у автора, слои 2–3 из кеша не читает. Если поставщик даёт задавать усилие служебным сообщением внутри диалога без сброса кеша, оно идёт в слое 4, усилие уровня запроса фиксируется на всю задачу (ступень фазы РАЗБОР), и усилие можно менять на сессию; иначе только на границе фаз.
- **Правка и продолжение — ход того же диалога.** С1п, С3п, С5п, С5д добавляют ход в диалог автора, если он жив и профиль тот же: тогда читается весь накопленный префикс. Поставщик диалог не хранит: программа сама хранит расшифровку — все ходы байт в байт, включая вызовы инструментов, их результаты и блоки рассуждений, которые поставщик требует возвращать, — в служебной подпапке папки задачи, которую промпты не называют и проверяющие не читают; «продолжить» значит отправить расшифровку целиком плюс новый ход. Если поставщик хранит диалог сам, вместо расшифровки хранится его идентификатор с теми же полями времени. Диалог жив, если с начала его последнего запроса прошло меньше срока жизни отсечки 4 (или его держало поддержание) и профиль совпадает; иначе расшифровка удаляется и сессия идёт новым диалогом. Чтение из кеша стоит доли цены входа на каждом ходе, поэтому очень длинный диалог С5 продолжать дороже, чем начать новый поверх слоёв 0–3: программа сравнивает размер расшифровки с размером слоёв 0–3 и показывает выбор у В2, когда расшифровка больше примерно вдвое.
- **Проверка — новый диалог с тем же префиксом.** С2, С4, С6 обязаны не видеть рассуждений автора, но слои 0–3 у них байт в байт те же, поэтому дорогая часть читается из кеша; свежим остаётся только слой 4.
- **Срок жизни кеша продлевается каждым чтением** и считается от **начала** запроса, который пишет или читает кеш: ход дольше короткого срока (предельное усилие, длинный выход) обнуляет свой же префикс до следующего запроса даже при нулевой паузе; для таких фаз на отсечках 1–3 выбирается длинный срок. По умолчанию срок короткий (минуты); есть длинный (час) за двойную цену записи; записи с длинным сроком должны стоять раньше записей с коротким. Выбор по паузам между запросами с общим префиксом:

| Пауза между запросами | Что делает программа |
|---|---|
| пауза плюс длительность предыдущего запроса меньше короткого срока | ничего: каждый запрос продлевает кеш |
| между коротким и длинным сроком: человек читает находки, отвечает заказчику | либо длинный срок на отсечках 1–3, либо поддержание (ниже) |
| больше часа | при длинном сроке — поддержание, пока оно дешевле перезаписи; при коротком — следующий запрос пишет кеш заново, и это нормально |

- **Поддержание** — тот же запрос с нулевым выходом: он читает кеш и продлевает его за цену чтения. Требования: без потоковой передачи, без структурированного вывода, без принудительного вызова инструментов; та же модель, усилие, размышление и те же отсечки, что у настоящего запроса, иначе поддерживается чужая запись. Период — срок жизни самой короткой живой отсечки минус минута, отсчёт от старта предыдущего запроса. Потолок — пока суммарная цена поддержания меньше цены перезаписи: при чтении в десятую долю входа это около 45 минут для короткого срока и около 19 часов для длинного; числа — пример, программа считает по формуле `keep_alive`, цена каждого вызова пишется в usage и показывается у ворот.
- **Фан-аут не раньше первого ответа.** Если программа запускает несколько сессий параллельно, первая должна начать отвечать, прежде чем стартуют остальные: иначе все пишут кеш, никто не читает.
- **Проверка после каждого запроса.** Ожидаемое чтение — токены отправленного префикса (`prefix[kind].tokens`) по счётчику поставщика. Тревога «кеш не читается», если отпечаток того же префикса не изменился (модель, усилие, размышление, байты), от начала прошлого запроса этого префикса прошло меньше срока жизни, а прочитано из кеша меньше 90 % ожидаемого. Если при этом записано в кеш больше нуля — это перезапись, и в log.md идёт её причина: истёк срок, сменилась модель или усилие, обновлён слой 3; сравнение слоёв делается только при разных отпечатках. Молчаливая потеря кеша стоит дороже всего, потому что ничего не ломается.
- **Объём.** Предел входа профиля = окно контекста модели его класса − максимум выхода − запас на ход диалога (не меньше четверти окна). Для нового диалога считаются токены префикса и промпта, для продолжения — токены расшифровки плюс ход; счётчик поставщика, моделью выбранного профиля, перед каждым запуском и после каждой пересборки префикса. Расшифровка не помещается — диалог закрывается, сессия идёт новым диалогом, строка в log.md. Новый диалог не помещается — программа не режет молча, а останавливается у В1: решает человек (разбить задачу, поднять класс, убрать лишнее из task/). Столбец «Ожидаемый вход» в таблице профилей — для оценки цены, не предел.

## Профили запуска

Класс модели — на задачу, усилие и размышление — на фазу, ожидаемый вход — на сессию. Умолчания (одно значение в клетке; подсказка агента и человек могут поднять):

| Фаза | Сессии | Класс | Усилие | Размышление | Ожидаемый вход |
|---|---|---|---|---|---|
| РАЗБОР | С1, С1п, С2 | A | 4 | вкл | материалы + spec + 60 тыс. |
| ПЛАН | С3, С3п, С4 | A | 5 | вкл | spec + код по карте + 80 тыс. |
| РЕАЛИЗАЦИЯ | С5, С5д, С5п, С6 | A | 4; 5 на всю фазу, если затронуты безопасность, деньги или данные — решает человек у В2 перед С5, подсказку даёт ПРОФИЛЬ от С3 или С4 | вкл | план + код + result + diff + 200 тыс.; при длинном прогоне — лимит на выход, если поставщик его даёт |
| СДАЧА | С7, С7п, С8 | B | 2 | выкл, если модель позволяет | spec + plan + result + review + 20 тыс. |
| СДАЧА | КОММИТ, ПУШ | B | 1 | выкл, если модель позволяет | diff + 10 тыс. |
| ОБРАТНАЯ_СВЯЗЬ | С9 | A | 3 | вкл | материалы + spec + result + feedback + 40 тыс. |

**Второе мнение** (`methodology.md`, раздел 18) идёт на классе A с включённым размышлением и усилием 3; при вопросе о безопасности, деньгах, данных или правке нормы — усилие 4; семья — другая, чем у агента, среди согласованных поставщиков, если доступно, совпадение называется (`methodology.md`, раздел 18). Модель второго мнения проект задаёт отдельно от основной модели класса.

**Подсказка агента.** После каждой сессии, кроме КОММИТ и ПУШ, агент пишет строку `ПРОФИЛЬ от <код>`. Она действует на один следующий запуск, какая бы сессия ни пошла по маршруту, и стирается после него; в log.md — «ПРОФИЛЬ от <код> применён к <код>». Порядок сравнения: класс C < B < A, усилие 1 < … < 5, размышление выкл < вкл, бюджет — по числу. Правила:

- совет выше по классу берётся только там, где умолчание допускает выбор (фаза СДАЧА); в остальных фазах класс задачи не меняется, совет пишется в log.md;
- совет выше по усилию берётся без вопроса, только если поставщик меняет его сообщением внутри диалога без сброса кеша; иначе это В2 с пометкой «смена перепишет кеш слоёв 2–4 и закроет диалог автора», а на границе фазы применяется сразу; совет включить размышление — только на границе фазы;
- для сессий «тот же диалог» (С1п, С3п, С5п, С5д) профиль диалога не меняется, совет только записывается;
- совет ниже показывается человеку всегда, даже когда В2 переведены в режим «не спрашивать при совпадении с умолчанием»;
- «выкл» при усилии, с которым модель не принимает выключение, программа понижает до допустимого и пишет это в log.md;
- совета нет или строка не разобрана — умолчание, в log.md строка «ПРОФИЛЬ не получен от <код>».

Выбранный профиль пишется в state.json и показывается у В2 вместе с ценой, которую программа оценивает по токенам слоёв.

**Этапы и модель.** Модель выбирается не только по фазе, но и по этапу: этап — вид работы внутри фазы, артефакт или его проверка. Этапов восемь; проект явно задаёт модель четырёх (plan, plan_accept, develop, develop_accept), остальные наследуют:

| Этап | Фаза | Сессии | Диалог | Модель, если не задана |
|---|---|---|---|---|
| spec | РАЗБОР | С1, С1п, С9 | С1 и С9 — новый; С1п — тот же | как plan |
| spec_accept | РАЗБОР | С2 | новый | как plan_accept |
| plan | ПЛАН | С3, С3п | С3 — новый; С3п — тот же | задаётся |
| plan_accept | ПЛАН | С4 | новый | задаётся; семья ≠ plan |
| develop | РЕАЛИЗАЦИЯ | С5, С5д, С5п | С5 — новый; С5д и С5п — тот же | задаётся |
| develop_accept | РЕАЛИЗАЦИЯ | С6 | новый | задаётся; семья ≠ develop |
| delivery | СДАЧА | С7, С7п, КОММИТ, ПУШ | С7, КОММИТ, ПУШ — новый; С7п — тот же | профиль СДАЧА |
| delivery_accept | СДАЧА | С8 | новый | профиль СДАЧА; семья ≠ delivery |

Проверка идёт на другой семье моделей, чем автор проверяемого артефакта, если доступно не меньше двух семей и выбранная модель пригодна; иначе на той же семье, и в log.md записывается «семья та же: причина»: автор и проверяющий одной семьи повторяют слепые пятна друг друга. Правка и продолжение идут в диалоге автора, пока он жив и этап тот же; сменился этап или семья — новый диалог; после правки spec.md диалоги С3 и С5 новые, после правки plan.md — диалог С5.

## Языковые границы

Необязательный режим: служебная работа ведётся на языке `ЯЗЫК_СЛУЖЕБНЫЙ`, перевод только на границах, по [methodology.md](../../../../publication/originals.zip) (историческая цель: `methodology.md`; точный оригинал — в архиве), раздел 18, «Язык служебной работы». Параметр лежит в профиле задачи (и в `state.json`), как класс модели; по умолчанию равен языку проекта, режим выключен, строка «Язык» в хвост не добавляется.

- **Вход.** До первой сессии, а затем при каждом новом входе (`task/feedback-N/`, ответы человека) программа вызывает помощника `translate_in`; копии лежат в отдельной папке рядом с `task/`, не в ней, чтобы слой 2 и счёт единиц С1 не удваивались; слой 2 берёт копию вместо оригинала, оригинал открывается только для сверки. Копия после утверждения не меняется (кеш, «Сборка запроса»).
- **Внутри.** Когда режим включён, в общую часть хвоста добавляется строка «Язык: <ЯЗЫК_СЛУЖЕБНЫЙ>» (единственное исключение из «без подстановок»: значение постоянно на задачу); роли пишут на этом языке сами, переводчика между ролями нет, строки протокола и форматы находок прежние. Тексты наружу (`customer.md`, описание изменения, коммит) пишутся на их языке.
- **Выход.** Перед показом человеку программа вызывает `translate_out` над вопросом, докладом, итогом, находками и документами для ворот (`spec.md`, `plan.md`, `result.md`); показанный перевод сохраняется рядом с оригиналом. Для ворот закрытого списка числа и отрицания сверяются по тексту роли; слово человека записывается без перевода. Отказ, ошибка или низкая уверенность помощника — человеку показывается оригинал и в журнал идёт строка «перевод не выполнен».
- **Источники.** `источник:` указывает на оригинал; секретарь отклоняет источник-копию как не найденную; в цикле без секретаря выдержки сверяет проверяющий.
- **Раздел 12.** Оригинал и всё производное от него (копия, вопрос, доклад, итог, находки), которые нельзя выкладывать на внешние сервисы, внешнему переводчику не передаются; для них работа идёт на языке проекта.

Схема опытного режима: раннером не выполняется.

## Протокол прогресса

1. До запуска программа считает N по таблице единиц и показывает `шаг 0/N`; если считать нечем — `?/?`.
2. Агент пишет строки в progress.log; программа следит за файлом от отметки, поставленной перед запуском, и обновляет `k/N` (строки `поправка:` k не меняют). N для показа — из последней строки агента, если он его назвал; завершение `готово` сравнивается с N из строки `старт`.
3. Если k не растёт дольше порога (умолчание 10 минут) и запрос ещё не завершён, программа не вмешивается, а показывает «без прогресса <минут>»: длинный ход без строк — нормально для реализации и подозрительно для проверки, решает человек.
4. По завершении запроса программа сверяет артефакт с progress.log: число строк `пункт n: сделан` (или прежней формы `шаг n: сделан`) в result.md, прибавившихся за эту сессию (раннер запоминает их число перед запуском), против строк прогресса С5 и С5д этой сессии (С5п сверяется только по находкам; считается число разных значений k больше нуля: строка `старт`, поправки и повтор итоговой строки в счёт не входят), число находок против N у правки. Расхождение — строка в log.md, не остановка.
5. Прогресс задачи — фаз завершено из пяти; прогресс фазы — заход j/ПОТОЛОК текущего повтора и шаг k/N текущей сессии.

## Что показывает интерфейс

Необязательная возможность: состав данных, а не вид экрана. Показывается только то, что раннер хранит и читает (`state.json`, `progress.log`, `log.md`, файлы проверок); чего он пока не хранит, помечено «не хранится», догадок и оценок модели на экране нет. При включённом режиме языка («Языковые границы») всё, что видит человек, проходит `translate_out`.

1. **Лента фаз.** Пять фаз маршрута (РАЗБОР, ПЛАН, РЕАЛИЗАЦИЯ, СДАЧА, ОБРАТНАЯ_СВЯЗЬ). «Готово» только при утверждённом документе фазы (`approvals[файл]` совпадает с хешем); при возврате документ снят с утверждения, и фаза снова «ожидает». «Идёт» — по `running`, «ждёт ворот» — по открытым воротам. Прогресс задачи — «Протокол прогресса».
2. **Текущая сессия.** Код сессии и шаг `k/N` (`running`, `progress.log`), «без прогресса <минут>» («Протокол прогресса», п. 3), идёт ли запрос или ждут ворота. Имя модели — из профиля и учёта, если они ведутся. Ручной признак «работаю / жду чужого хода / стою без работы» из методики здесь не показывается: раннер его не вычисляет.
3. **Цикл проверки.** Точки по заходам и номер захода из потолка. Цвет точки — по итоговой строке и решению человека у В3; зелёной она бывает только у засчитанного захода после решения В3, «не засчитан» и «ждёт В3» — отдельные цвета, по одной строке агента зелёного нет. Решение В3 по заходам не хранится. Счёт — по итоговой строке захода: «существенных, поверхностных, проб» у циклов задач, «критических, значимых, желательных, проб» у совещания («Машинные форматы»).
4. **Очередь ворот.** Код и название ворот: все ворота раздела «Ворота» (В1–В13) и ворота без номера из алгоритма. Давность, суть вопроса и рекомендация не хранятся и не показываются; рекомендация, когда появится машинная строка источника, показывается только с кодом сессии-источника (методика, раздел 18, «Кто отвечает на воротах»). Содержание находок и отчётов не показывается: человек читает файлы на воротах.

Цена и сроки («Учёт и сроки») добавляются, когда раннер их собирает; «нет данных» показывается с причиной, а не нулём.

**Легенда цветов** одна на все реализации, чтобы одну работу везде красили одинаково. Цвет видов работы не совпадает с цветами состояния «готово» и «засчитан».

| Цвет сессии | Что это |
|---|---|
| подготовка | С1 (разбор) |
| план | С3 |
| реализация | С5, С5д |
| ревью | проверка в новой сессии: С2, С4, С6, С8 |
| доработка | правка по находкам и обратной связи: С1п, С3п, С5п, С7п |

## Учёт и сроки

Необязательные возможности раннера; без них цикл исполняется, но цена процесса и его причины остаются неизвестными.

- **Запись о сессии:** время, модель, токены, стоимость, итог. Поле без данных — «нет данных: причина», а не ноль ([methodology.md](../../../../publication/originals.zip) (историческая цель: `methodology.md`; точный оригинал — в архиве), раздел 13); деньги считаются из одного источника, а не складываются из двух. Стоимость «по прайсу» оговаривается: подписка может ничего не списывать.
- **Сводка задачи:** по этапу и модели; время по часам и время сессий — разные числа (сессии идут параллельно); возвраты с причиной; число обращений к человеку и ожидание ответа. Время работы самого человека раннер не знает — так и пишется.
- **Журнал возвратов** (откуда, куда, причина, источник — файл с находками или ответом) и **журнал ворот** (когда открылись и закрылись, кто и что решил) отвечают на вопрос, почему работа повторялась и где стоял человек.
- **Таймбокс** — необязательный параметр профиля, по умолчанию выключен: достижение лимита времени останавливает сессию по идентификатору процесса, полученному при запуске; незакрытые находки и частичный результат сохраняются; решает человек на воротах В13.
- **Плато** — сигнал человеку раньше потолка: не меньше трёх заходов подряд без снижения числа существенных находок. Одного числа мало: раннер показывает, новые это находки или те же, закрытые и открытые.
- **Счёт по ролям и моделям** — необязательная возможность, параметр профиля проекта «счёт по моделям», по умолчанию выключен; рядом с журналом возвратов: нарушения формата (исправление в `run`), возвраты (круги доработки; единица работы — по методике, раздел 9), в которых хотя бы у одной существенной находки причина «модель» (причины «задание» — нарушенное требование есть в задании, «среда», «внешняя проверка» — красная проверка вне задания — отдельный класс), на единицу работы, отказы модели (причина В13 записывается отдельно: отказ модели, сбой среды, нет артефакта, форма не исправлена; в счёт модели идут первая и последняя), несостоятельные мнения совещания; один случай записывается один раз с несколькими метками признаков; находки уровней «требования» и «план» исполнителю не засчитываются; счёт виден по запросу и рядом с профилем модели не показывается, чтобы не подталкивать к замене по счёту; отметки «модель» проверяющего той же семьи, что исполнитель, подтверждает человек одним показом на воротах «принять итог» или в конце задачи; решение о замене модели принимает человек ([methodology.md](../../../../publication/originals.zip) (историческая цель: `methodology.md`; точный оригинал — в архиве), раздел 9, «Модель под наблюдением»).
- **Диспетчер нескольких задач** — слой над `run_task`: он не обходит ворота и утверждения каждой задачи; пределы и очередь держит единственный диспетчер или общее состояние слотов с атомарным занятием; потолок среды обеспечивается им или запретом на запуск сверх него ([methodology.md](../../../../publication/originals.zip) (историческая цель: `methodology.md`; точный оригинал — в архиве), раздел 18, «Параллельная работа»).
- **Вариант «разбить»** у ворот В9: требования и открытые находки переносятся в части задачи с явным покрытием; без него процесс можно формально укоротить, потеряв проблему.

## Совещание агентов

Необязательный режим программы-секретаря: ведёт согласование по [methodology.md](../../../../publication/originals.zip) (историческая цель: `methodology.md`; точный оригинал — в архиве), раздел 18, «Согласование решения несколькими агентами». Это `loop_review(meeting)` без отдельного цикла: счётчики `state.pass`, `pass_origin`, `clean_streak`, `unaccounted`, правило чистого захода без проб, потолок и ворота В3 и В9 те же, что в алгоритме (`loop_review`, [task-runner-pseudocode.md](../../../../publication/originals.zip) (историческая цель: `task-runner-pseudocode.md`; точный оригинал — в архиве)). Раздел и его псевдокод — схема реализации опытного режима, а не нормативный алгоритм; нормы — в методике. Та же схема состояниями и переходами — [task-runner-meeting-states.md](../../../../publication/originals.zip) (историческая цель: `task-runner-meeting-states.md`; точный оригинал — в архиве), её код автомата — [task-runner-meeting-automaton.md](../../../../publication/originals.zip) (историческая цель: `task-runner-meeting-automaton.md`; точный оригинал — в архиве). Различия:

- **Артефакт** — `proposal.md`; его автор (`fixer`) правит этот же файл и дописывает «Изменения захода N»; новая версия файла — вход следующего захода. Автор-человек правит сам, ворота на этом шаге его; диалог автора-сессии хранится, как у других циклов, пока жив.
- **Проверка (`checker`)** — процедура секретаря, а не одна сессия: для каждой линзы `run(проверка_линзы, source=proposal, pass=n)` (линзы запускаются последовательно, каждая в пределах сессий; вторая стартует после первого ответа первой — правило кеша «не раньше первого ответа»); `verify_formats` каждого файла `proposal-review-N-<линза>.md`; затем секретарь убирает признаки несостоятельного мнения (см. ниже) и склеивает файлы в `proposal-review-N.md` в формате обычного файла проверки, кроме поля `уровень:` (у находок совещания его нет; `parse_summary` читает только итоговую строку) («Машинные форматы»; серьёзности находок остаются): первая строка «Заход N: критических K, значимых Z, желательных D, проб P» (K, Z и D — суммы, P — наименьшее число проб среди линз, отброшенная линза даёт P=0), далее находки с меткой линзы. Серьёзности и остановка — по `methodology.md`, раздел 18: K для этого цикла — число критических, заход чистый, если их нет; Z и D для людей, `parse_summary` их не читает. После засчитанного захода с критическими правка автора получает его критические и значимые находки без поля `повтор:`; находки засчитанных заходов, не переданные в правку, секретарь копит в `state.open[meeting]` и записывает в итог как «открыто»: желательные, значимые с полем `повтор:` (значимую автор правит одной попыткой) и все находки захода, после которого правки нет (чистого или того, после которого человек у В9 выбрал «остановиться»). В `loop_review` для этого цикла вызов `run(checker(stage), pass=n)` заменён вызовом `check_meeting(n)` (ниже), а результат `halt` возвращается наружу без разбора; прочие отличия помечены там условием `stage = meeting`; в остальном склеенный файл разбирается как обычный. На время проверок линз секретарь делает `proposal.md` доступным только для чтения и возвращает запись в блоке `finally` `check_meeting`, а при старте секретаря возвращает её, если проверка не идёт; правка проверяющим затруднена (атрибут снимается командой), а изменение файла за время проверки (размер, время, хеш) делает заход недействительным: В13 с двумя файлами (копия начала захода и изменённый): человек выбирает «оставить правку», «вернуть копию» или «остановить совещание», проверки повторяются на выбранной версии, файлы недействительного захода переименовываются в `*.void-<k>.md`, лежат вне `task/` (слой 2 собирается только из `task/`), промптами не называются и в контекст не входят, прежние находки в счёт и в потолок не идут; случаев такой правки не найдено. В файле каждой линзы есть раздел `Проверено:` (прочитанные файлы и диапазоны; без него «замечаний нет» не принимается) и раздел `Ответы свидетеля:` — утверждения из `witness-N.md`, на которые опирался вывод (в том числе «находок нет»), с результатом сверки каждого, либо строка «ответы свидетеля не использовались». Раздел проверяет `verify_formats` как форму файла: нет раздела — один ход «исправь форму файла», снова нет — линза отбрасывается («Срок бездействия роли» ниже); до этого итог захода не разбирается и заход не засчитывается.
- **Файл свидетеля** `witness-N.md` необязателен: перед проверкой захода N свидетель отвечает на вопросы, оставленные автором в `proposal.md` и проверяющими в файлах захода N−1; нет вопросов — файла нет. Проверяющие читают его вместе с `proposal.md`. Строки: `наблюдалось:`, `не наблюдалось:`, `не измерено:`, `вывод:`; у каждой кроме `не измерено:` поле `источник:` с точным местом (файл со строками и версией; запись с местом и идентификатором; вывод команды или запроса со временем запуска и сохранённым файлом вывода, который сверяется как файл) и, если источник может быть недоступен проверяющему, поле `выдержка:` с дословными строками (для вычисленного числа — запрос или скрипт и вывод); секретарь проверяет только наличие: выдержка и файл сравниваются после сжатия пробельных символов и приведения кодировки, поиск идёт по названному месту и ревизии из поля `источник:`; для чисел пробелы только сжимаются, не удаляются; несовпадение текста, исчезающее при удалении всех пробелов, помечается «искажение канала» (строка подтверждена с искажением, смысл сверяется по источнику) и в счёт модели не идёт, остальное возвращается свидетелю, смысл и контекст судит проверяющий. Источник, недоступный и секретарю, делает ответ «не подтверждено»: это статус утверждения в этом цикле, измерение могло быть, но подтвердить его нечем; основанием вывода такой ответ не служит. Последняя строка файла — `не читал: <перечень>`.
- **Профили ролей** — задаёт проект; без явной настройки автор как этап plan, проверяющие и свидетель как этап plan_accept.
- **Семья моделей** — как в «Этапы и модель»: у каждой роли свой профиль, совещание — исключение из правила «одна модель на всю задачу»; независимость важнее общего кеша, при смене семьи слои 0–3 из кеша не читаются, и цена записи показывается у В2. Проверяющие по возможности разных семей между собой и от автора; совпадение пишется в log.md с причиной.
- **Несостоятельные мнения** — четыре признака (выдуманная выдержка, находка без доказательства, ответ свидетеля вне четырёх слов, ответ «согласен» без перечня прочитанного и проб, не исправленный после возврата) секретарь определяет до склейки и `parse_summary` и не включает в K, Z, D и P; опровергнутая находка остаётся в K своего захода до подтверждения опровержения следующим проверяющим или человеком, показатели не пересчитываются; все случаи идут в общий счёт по моделям («Учёт и сроки»).
- **Срок бездействия роли** — параметр секретаря: бездействие — нет байтов потока от модели (включая служебные события), вызова инструмента и новой строки `progress.log` дольше срока; один факт открытого соединения активностью не считается. Срок задаёт профиль роли не меньше самой долгой наблюдавшейся паузы модели: стартовое значение задаёт человек у В2 и оно записывается в профиль, `record_usage` пишет наибольшую паузу вызова, секретарь повышает срок по ней. Общее время ответа не ограничивается, долгая работа не нарушение, а пока роль стоит в очереди общего ресурса, срок приостановлен и потеря не возникает; очередь дольше срока затяжки проекта поднимается человеку с названием держателя места, таймер при этом остаётся приостановленным. Отбрасывание линзы идёт в счёт по моделям, только если причина «модель» (соединение оборвалось, ответ не по форме). Для линзы бездействие, отсутствие артефакта и вторая ошибка формы не доходят до В13: `run` возвращает `failed`, линза отбрасывается с записью в `log.md`, её P=0 (заход не чистый), та же линза повторяется в следующем заходе; счётчик `state.lost[линза]` растёт при каждом `failed` и сбрасывается успешным ответом линзы, при втором подряд — В13 с исходами «повторить» или «остановить совещание»; совещание продолжается остальными; нет ни одной линзы — `halt`. Для автора и свидетеля бездействие ведёт на В13 с исходами «повторить» или «остановить совещание»: «остановить» прекращает только совещание, `check_meeting` возвращает `halt`, `loop_review(meeting)` возвращает его без разбора сводки, `meeting` пишет в `log.md` остановку и незакрытые находки, программа продолжает работу, итог не принимается.
- **Пределы и очередь** — сессии совещания занимают места в тех же пределах одновременных сессий проекта и в той же машинной очереди ([methodology.md](../../../../publication/originals.zip) (историческая цель: `methodology.md`; точный оригинал — в архиве), раздел 18, «Параллельная работа»); линзы запускаются последовательно, каждая в пределах.
- **Принятие итога** — отдельные ворота после чистой серии: человек подтверждает решение и запись источника. В9 при потолке — как в `loop_review`, выбор делает человек, секретарь автоматически не выбирает, с тремя исходами для совещания: «ещё заход» (решение человека вписывается в источник правки автора: сузить или разбить предложение), «остановиться» (итог принимается с незакрытыми находками, записанными в решение) и «остановить совещание» (`halt`).

Псевдокод — [task-runner-meeting-pseudocode.md](../../../../publication/originals.zip) (историческая цель: `task-runner-meeting-pseudocode.md`; точный оригинал — в архиве).

Ворота В3 при совещании могут быть переведены в «показать и продолжить» по настройке; потолок и принятие итога — без умолчания.

| В13 | любая сессия | сессия не завершилась, артефакта нет, форма не исправлена со второй попытки, первая строка статуса не разобрана, проверка второй раз подряд без проб, роль совещания не ответила за срок: повторить или остановить программу (внутри совещания — остановить только совещание); исходы может задавать вызывающая процедура (в совещании при изменении `proposal.md`: «оставить правку», «вернуть копию», «остановить совещание») |

Отключаемы только ворота, у которых есть действие по умолчанию, не требующее записи человека: В2 (профиль равен умолчанию), В3 (засчитать заход как написано — человек вправе отказаться от этого права на задачу), В4 и В6 при пустом списке. В5, В7, В8, В10 требуют записи человека в файл или действия вне программы: статус «утверждено», ответ, пометку владельца, пуш и отправку заказчику программа без человека не ставит и не делает. В1, В9, В11, В12, В13 — решения без умолчания. Решение об отключении пишется в state.json по идентификатору ворот.

## Что проверить в программе до первой задачи

- Два запроса подряд с одинаковыми слоями 0–3 показывают чтение из кеша, близкое к размеру этих слоёв; смена промпта сессии в слое 4 этого не меняет; проверка в новом диалоге читает слои 0–3.
- Поддержание не отклоняется поставщиком и после него чтение из кеша сохраняется; период считается от старта предыдущего запроса.
- Смена усилия между сессиями одной фазы ловится как перезапись с причиной в log.md; запрос сдачи сверяется с отпечатком префикса сдачи, а не основного.
- Строка `Заход N: …` разбирается на всех четырёх видах файлов проверки; файл без строки даёт «все находки существенные», а не «чистый заход»; чистый заход без проб не засчитывается и не запускает правку; второй подряд — В13.
- Счётчик единиц даёт верное N на образце spec.md, plan.md и feedback-N.md; progress.log с другим N и строки прошлых запусков не ломают отображение.
- Ключевое слово со знаком после него (`старт:`, `готово —`) читается как ключевое, `Готово` и `стоп` без двоеточия — нет; строка `поправка:` не меняет k, не считается единицей и не снимает «без прогресса»; «без прогресса» считается по росту k; повтор последней строки в верной форме читается вместо прежней; `стоп:` после `готово` при k меньше N из строки `старт` читается как остановка; `7/7 готово` после `0/10 старт` завершением не читается, `9/8 готово` после `0/8 старт` — читается; `7/10 готово — N завышено: …` читается как завершение и сразу, и после `7/10 готово`; `готово` без строки `старт` или после второй строки `старт` завершением не читается; строка `запуск`, которой нет в state.launches, новую сессию не открывает и даёт строку в log.md; повтор сессии запускается только после того, как прежняя группа процессов агента остановлена и в ней нет процессов, включая команды, запущенные агентом; повтор номера запуска даёт строку в log.md; цитата в поправке — начало подписи прежней строки, 10–30 знаков или вся короткая подпись.
- Потолок срабатывает после ПОТОЛОК_ЗАХОДОВ заходов с существенными находками, считая от последней правки по решению владельца; «ещё заход» ведёт к правке, а не к повторной проверке того же артефакта.
- Маршрут «требования» переводит и spec.md, и plan.md в «черновик» и ставит С1п и С3п в очередь; возврат в РЕАЛИЗАЦИЯ после этого запускает С5п, а не С5; готовый result.md без очереди ведёт сразу к С6.
- Остановка С5 или С5п с каждым из четырёх слов ведёт в свой маршрут; остановка С5п видна, потому что статус result.md возвращён в «в работе»; ответ уровня «реализация» продолжает диалог С5.
- Файл со статусом «утверждено», изменённый после утверждения, переводится в «черновик» до запуска следующей сессии, и его диалоги в слое 3 закрываются.
- После обрыва процесса на любой сессии перезапуск повторяет ту же сессию тем же промптом, продолжает фазу со state.step и не перезаписывает существующие файлы заходов.
- КОММИТ не пушит; сообщение коммита сверяется с commit.txt до ворот пуша; сдача без изменений кода пропускает коммит и пуш.
- Повторная сдача не затирает customer-<round>.md прошлого раунда.
