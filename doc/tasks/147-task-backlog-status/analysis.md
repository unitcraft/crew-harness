## Отличие от `idle`

`idle` (задача 058) означает действующую задачу с сессиями методики между двумя сессиями: предыдущая сессия сдана интегратору, приёмки ещё нет; это открытый статус и допустимая точка продолжения/`deliver`. `backlog` — явное временное снятие задачи с активного списка по решению интегратора; задача не считается открытой, но сохраняет identity и ресурсы. Это разные статусы и назначения. Нельзя считать idle сессию backlog автоматически, и backlog нельзя трактовать как законченную/отменённую задачу.

## Сохранение и переход

При входе в backlog сохраняются без переписывания: JSON задачи, номер, `history` (добавляется только событие), qid/письма и архив писем, сессии и их статусы, executor/reviewer identity, модель/роль и параметры запуска, отчёты, ветка/worktree, side refs, папка, `precheck`, `checks`, `steps`, `commit`, evidence/rounds и родительские связи. Сам переход не закрывает окна, не отзывает ранее отправленные письма и не чистит ресурсы. Backlog с активным merge lock отклоняется без мутации; сначала lock явно отпускает интегратор, иначе существующий flowWatch расценил бы закрытость как брошенный замок. Resume при обнаруженном lock также отказывает без мутации до его явной проверки/отпускания. Runtime-потребители учитывают статус и перестают возобновлять/будить задачу; поздний submit/старое письмо не вызывает перехода и не ставит новую работу.

Вход в backlog сохраняет предыдущий lifecycle-статус как отдельный аудируемый факт, иначе нельзя отличить честный возврат между сессиями от активного исполнения/приёмки. Это не делает старые сведения о сессии живыми. На `resume` необходима проверка актуального статуса, сохранённой сессии/карточки и незавершённых gate/lock. `running`/`starting` без живого окна нельзя возвращать как живые без проверки, `reviewing` без живого приёмщика — нельзя представлять как активную приёмку; зелёный precheck/gate/evidence не может создаваться или обновляться автоматически.

## Принятое правило resume

Решение владельца, 2026-10-22, чат оркестратора: «проверь сессии opencode, ответь на вопросы по твоей рекомендации». Принят fail-closed вариант:

- сохранять исходный статус как аудируемый snapshot; resume не повторяет побочные эффекты старого перехода и не создаёт новый executor/reviewer;
- если сохранённый статус был `accepted`, восстановить ровно `accepted` и прежнюю очередь уборки, включая прежний `acceptedAt`; reviewer/session, check/evidence, precheck, commit и git resources сохраняются без запуска или повторной приёмки;
- не считать записанный session id доказательством живой сессии; отсутствующий live tab executor не возобновлять, его id сохраняется в `executors`, активная ссылка очищается, задача возвращается в `idle` без автозапуска;
- при исчезнувшем reviewer или неизвестном состоянии merge lock сохранить безопасное ожидание и требовать явного назначения/разблокировки интегратором, не запускать приёмку;
- не сбрасывать и не обновлять `precheck`, checks, evidence, history и relation; устарелость существующего доказательства определяется его текущими правилами;
- если состояние сессии/lock нельзя проверить достоверно — отказ без мутации, а не предположение.

Решение занесено в `log.md` с источником. Для точной реализации необходимо проверить доступные API текущего плагина: если проверки session existence/lock ownership недостаточно, resume должен отказать без изменения статуса, не имитировать подтверждённую живость.
