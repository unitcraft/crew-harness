### Разбор вопроса и классификация (REQ-04, REQ-05, REQ-07, REQ-11)

`parseTurn(text)` разбирает последний ответ хода в три слоя, и каждый слой проверяется отдельно (`crew-answer-parse`):

1. Деление на блоки по строкам `В-<число>` (отступ, маркер `-`/`*` и выделение допустимы); текст до первого идентификатора — отдельный блок без идентификатора; ответ без идентификаторов — один блок.
2. Поля по девяти именам (`Тип`, `Автоответ`, `Рекомендация`, `Варианты`, `Умолчание`, `Затрагивает`, `Адресат`, `Срок`, `Влияет`) без учёта регистра, с подписью в скобках; значение `Рекомендация` — до пустой строки, следующего поля, `В-<число>` или конца блока; повторы с разными значениями — «самая строгая запись» (владельцу); поле до первого `В-<число>` и две пары полей без идентификаторов — весь ответ владельцу.
3. Блок-вопрос: «?» в конце строки вне значений полей, допустимы после него `)`, `»`, `"`, `*`, `_`, `` ` ``, `.` и пробелы; правила места «?» — три случая REQ-04 (блок с идентификатором; блок без идентификатора, но с полями; ответ без идентификаторов и полей); блок с любой из строк `Тип:`, `Рекомендация:`, `Автоответ:` в пакете с идентификаторами — блок-вопрос и без «?».

`classify(block, ctx)` возвращает «закрыт» или «остаток» с причиной из закрытого перечня: «нет рекомендации», «нет типа/признака/неизвестный тип», «блок без полей», «ворота (тип gate)», «ворота (слова)», «сессия приёмки», «режим owner для типа», «предел автоответов», «нет «?» в конце строки». Порядок проверок — от самого строгого: тип `gate` и неизвестный тип побеждают всё; затем сессия приёмки (по карточке `review`, независимо от текста; признак липкий — допустимо, REQ-12); затем слова ворот; затем режим типа; затем рекомендация; затем предел. Условие «закрыто» — все шесть условий REQ-05 сразу. Сбой на любом шаге (исключение разбора, нечитаемый текст) — «остаток», ошибка пишется в журнал службы (REQ-11).

Словарь ворот (REQ-13) хранится в `answer-parse.ts` одним массивом `GATE_STEMS` в порядке спецификации (190 записей); `normalizeGateText` делает NFKC, снимает знаки Cf и Mn, нижний регистр, «ё»→«е», знаки кроме букв, цифр, точки и подчёркивания → пробел, подчёркивание на краю слова и серию точек в конце слова → пробел, обрамляет пробелами; сопоставление по подстроке, записи `^…` и `|…|` — с границы слова/целым словом. Какие места текста проверяются, а какие пропускаются только в узкой форме — по REQ-13 дословно (поля `Тип`, `Автоответ`, `Срок`, `Адресат`, подпись в скобках). Таблицы Т-7, Т-8, Т-9 переносятся в `answer-fixtures.mjs` дословно (исполнитель добавляет формы, не убирает); счёт строится в тесте и сверяется с цифрами спецификации (20, 30, 76 словоформ, 20 вопросов ворот, 17 жаргонных, 10 живых, 36 форм девяти глаголов).

### Журнал, идемпотентность, предел, отзыв (REQ-10, REQ-15, REQ-16, REQ-18, REQ-21)

Запись журнала — файл `answers/<вид>-<safeKey(сессия)>-<конец хода>-<номер>.json`, `вид` — `a` (ответ) или `r` (остаток; номер 0). Поля: `id`, `kind`, `session`, `project`, `task` (номер, если есть), `qn` (номер вопроса `В-NN` или 0), `type`, `mode`, `who` (`рекомендация`), `question` (до 300 знаков), `answer` (до 1000 знаков), `state` (`дан` / `владелец вмешался` / `остаток: ждёт слова владельца` / `снято: владелец написал`), `askedAt`, `answeredAt`, `remindedAt`, `letterPostedAt`.

- Создание — «если нет»: запись пишется во временный файл рядом и становится видимой через `linkSync` (при `EEXIST` второй процесс запись соседа не трогает и новое письмо не шлёт); при ошибке `EPERM`/`ENOSYS` (файловая система без жёстких ссылок) — запасной путь `writeFileSync(..., {flag: "wx"})`. Обновление состояния — временный файл и `renameSync` (как `approvals.ts`), с повтором при `EPERM`/`EBUSY`, как в `tasks.ts`.
- Порядок действий одного ответа: запись журнала → письмо → отметка `letterPostedAt` в записи → событие задачи (задача загружается непосредственно перед записью события, после чтения записи решения, чтобы не затереть чужие правки файла задачи; перед записью проверка, что в `history` нет заметки с этим id). Письмо кладётся, только если в записи нет `letterPostedAt` и общая проверка не видит письма; id письма `answer-<safeKey(сессия)>-<конец хода>-<NN>`. Две защиты письма (отметка и общая проверка) страхуют друг друга: красятся набором `GATE:once`, но каждая имеет свою ячейку (`AC-17 письмо в доставке` - с отметкой, `AC-17 без отметки` - отметка снята правкой файла записи, письмо в `delivering/`: второго нет). Общая проверка «письмо уже есть» - `letterExistsFor` из `core.ts` (экспортируется; она видит `inbox`, `read`, `delivering/<pid>-<время>/<адрес>`; списка удалённых id `.ids` она не читает - это окно закрывает отметка `letterPostedAt`), а не `letterExists` из `tasks.ts`: пока письмо лежит в `delivering/` между `claimLetters` и `confirmLetters` (до 60 с, проход службы идёт каждые 15 с), `letterExists` его не видит и достройка положила бы второе. То же для письма остатка `answer-rest-…`. Каждый шаг идемпотентен сам по себе, поэтому обрыв между шагами достраивается следующим проходом.
- Цикл защиты от гонки внутри процесса: множество «в работе» по ключу (сессия, конец хода), чтобы `nudge` и `syncStatus`, идущие вперемешку на `await`, не дублировали работу; между процессами защищает создание «если нет».
- Предел (REQ-10): счёт — число записей `дан` подряд в конце ряда записей сессии по времени ответа; ряд составляют только записи вида `a` (состояния `дан` и `владелец вмешался`), записи остатка `r-…` в ряд не входят, счёт не обрывают и не сбрасывают (REQ-10: возвраты владельцу не считаются, REQ-07: пометка остатка в счёт не идёт); обнуляет счёт только запись `владелец вмешался`, то есть слово владельца после последнего автоответа. После `answer_max` ответов следующий вопрос — остаток с причиной «предел автоответов». Правило «существующая запись решает»: если для закрываемого блока (сессия, конец хода, номер блока) запись `a-…-<номер>` уже есть, повторный проход её не пересчитывает: итог берётся из записи, решение по вопросу берётся из записи и не пересчитывается; `answerTurn` возвращает `handled` истину; из побочных действий остаются только запись состояния остатка (`remindedAt` при повторе уведомления, `снято: владелец написал`) и достройка письма и события, если их нет (обрыв между шагами), нового решения, новой записи и второго письма нет, а прежнее уведомление «ждёт вас» по этому ходу на втором проходе подавлено так же, как на первом. Порядок внутри прохода: сначала поиск записей `a-…-<номер>` по каждому блоку, затем классификация только блоков без записи. Порядок записей: сначала записи решений по закрываемым блокам (`a-…`, письмо, событие) в порядке номеров, и только потом одна запись остатка хода `r-…-0`. Запись `r-…-0` означает лишь «остаток этого хода зафиксирован»: блок без записи `a`, не имеющий причины остатка, она не закрывает и обработанным не делает; блоки остатка пересчитываются на каждом проходе (результат детерминирован, список номеров и начал нужен для повтора уведомления). При обрыве после записи остатка и до записи `a` второго блока следующий проход закрывает этот блок. Предел считает записи прежних ходов (с меньшим концом хода) и решения этого же хода с меньшим номером вопроса, но не решения, принятые в этой пачке позже, и не пересчитывается задним числом; в пачке счёт ведётся и по решениям, принятым выше в этом же проходе (записей для них ещё нет), поэтому при `answer_max: 2` и трёх закрываемых блоках итог - закрыт, закрыт, остаток, а не три закрытых; ячейка `AC-14 пачка из трёх` (красная при `GATE:limit` и на базе). Слово владельца после последнего ответа обнуляет счёт тем, что помечает записи `владелец вмешался` (REQ-18).
- Отзыв: `markInterventions(session)` вызывается в `answerTurn` и в проходе `syncStatus`, но не чаще, чем меняется `idleAt` сессии или время её последней строки `user`, и не чаще раза в минуту на сессию (ограничение «раз в минуту» не действует, когда последняя строка `user` изменилась: слово владельца обнуляет счёт на ближайшем проходе, а не через минуту; иначе задержка не больше минуты шла бы в сторону владельца - лишний вопрос ему, не автоответ); только для записей `дан` младше суток (старше - не проверяются, остаются как есть); он спрашивает новую `ownerWordAfter(session, answeredAt)` (ниже) и помечает записи `дан`, ответ которым предшествовал слову. Метки `✉ `/`⚙ ` словом владельца не считаются (`isCrewText`).
- Хранение — 30 суток; чистка — не в этой задаче (файлов мало; записи старше срока читатель пропускает, а `housekeeping.ts` не правится, DNC-09) — запись в «Допущения плана».
- Счётчики задачи не трогаются (REQ-16, AC-16): `answer.ts` вызывает только `taskEvent(t, PLUGIN_SENDER, undefined, note)` без статуса и не пишет `rework`, `syncs`, `plan.*`, `qid`; тест делает снимок `Task` до и после.

### Новая `ownerWordAfter` в `core.ts` (REQ-18)

`userAfter` (`core.ts:528`) читает не больше 20 строк `user` после момента без отбора по метке: после двадцати писем плагина слово владельца не видно. Для REQ-10 и REQ-18 это ошибка в сторону автоответа, поэтому рядом добавляется `ownerWordAfter(sessionID, at): Promise<number>` — время первого слова владельца после `at` (0 — не было), запрос по всем строкам `user` после `at` без предела, отбор по `isCrewText` в JavaScript. `userAfter` не меняется (DNC-01, DNC-04): решение РП-03.

### Места вызова (REQ-06, REQ-07, REQ-10, REQ-12)

Одна функция `answerTurn(input)` с аргументами: карточка, `end` (`TurnEnd`), настройки проекта, `now`, канал (`nudge` / `status`) и зависимость `ownerWordAfter`. Возвращает `{ handled, notice? }`. Режимы выключены (все типы `owner`) — возврат `{ handled: false }` до разбора: прежние пути работают без единой записи (DNC-01). Порядок в обоих местах вызова: сначала `loadConfig` и `answerModesOn`; если режимов нет — больше ничего (в частности `turnEnd` не вызывается: цена прохода прежняя); чтение конца хода (`TurnEnd`) — только при включённых режимах.

- `index.ts`, `nudge` (`index.ts:307`): вызов — первой строкой после загрузки настроек и проверки «режимы включены» (чтение хода — только после неё), до проверки обязательств (РП-04) и до условия `card.spawned && !turn?.owner`. `handled` — `return` (письма «Не завершено … Продолжай работу» нет, `nudges` и `empty` не растут, пересылки «спроси владельца» нет). Для вкладки владельца (не запущенной плагином) `nudge` уведомлений не шлёт — их шлёт только `syncStatus`.
- `index.ts`, `syncStatus` (`index.ts:761`): вызов — после получения `end` и до блока уведомлений; `handled` — уведомление «ждёт вас» по этому ходу подавлено целиком (`continue` до проверки `s.state !== "owner"`), а при остатке на вкладке владельца здесь же уходит одно уведомление с текстом остатка во все живые окна (заголовок «… ждёт вас» — как прежний), повтор — по `remindedAt` записи остатка и `owner_reminder_min`; `markNotified` не вызывается (файл `status/<сессия>.json` остаётся таким же). Статус `statusOf` и его сохранение выполняются как раньше.
- Остаток у сессии задачи или приёмки: письмо спросившему (те же `askers`, что в пересылке `index.ts:317–332`; id `answer-rest-<safeKey(сессия)>-<конец хода>`), текст — те же сведения, что в прежней пересылке, остаток вместо одного вопроса, способ ответить `crew_send {to: <сессия>}`. Нет спросивших — письма нет, остаток виден в `/crew`.
- Письмо закрытому вопросу идёт самой сессии, спросившей (она будится); при наличии остатка письмо называет его номера и начала (до 100 знаков) и велит по ним ждать ответа (для ворот — слов владельца).
- Сессия приёмки: любой блок-вопрос — остаток «сессия приёмки» (карточка `review`, `REQ-12`). Сессия задачи-плана: проверка по типу и по словам (`согласов`, `раунд` — в словаре), механического признака нет — принятое ограничение записано в REQ-12; контрольный случай AC-05(д).

### Граничные случаи

- Режимы включены только для части типов: «остаток» считается и для блока типа с режимом `owner` (AC-30 е); режимы включены, а в ответе нет блока-вопроса — путь прежний, с пересылкой (AC-30 д).
- Ответ состоит из одного блока без идентификатора и без полей, «?» в конце строки среди последних трёх: блок-вопрос без полей — остаток (AC-29 8, 11).
- Ход начат словом владельца и кончился блоком — автоответ дан (О-08); владелец написал после конца хода — автоответа нет, `снято: владелец написал` у записи остатка (AC-11).
- Пакет: часть закрыта, часть остаток; закрытый вопрос получает письмо с остатком, остаток — уведомление (вкладка) или письмо спросившему (сессия задачи) — по одному (AC-30).
- Предел в пакете: первые `answer_max` вопросов закрыты, остальные — остаток (AC-14).
- Повтор прохода, второй экземпляр службы, MCP-процесс: ни второй записи, ни второго письма (AC-17); оборванная между шагами работа достраивается.
- Повреждённый файл журнала (не JSON) при чтении предела или создании записи, исключение при чтении хода: вопрос владельцу, ошибка в журнале службы (AC-22).
- Сессия без карточки (`readJson` вернул `undefined`): режимы не отвечают.
- `answer_mode` в файле с ключом `gate`/`agent`/значением не той формы: запись игнорируется (тип берёт `default`, иначе `owner`), `invalid` называет ошибку, `crew_config show` и `crew_doctor` — предупреждают (AC-07, AC-09, REQ-23).
- Длинный ответ (тысячи строк): разбор идёт не чаще раза на (сессия, конец хода) — результат запоминается; режимы выключены — разбора нет.

### Допущения плана

- П-1 Письмо автоответа — на каждый закрытый вопрос (id включает номер вопроса, REQ-21); у пакета из нескольких закрытых вопросов сессия получает несколько писем в одной доставке (`formatLetters` их склеивает), остаток повторяется в каждом. Это держит id выводимым из (сессия, время, номер) и не требует «письма на ход». Цена — повтор остатка; принимается.
- П-2 Чистка журнала ответов старше 30 суток не делается в этой задаче (Д-04 говорит о хранении «не меньше 30 суток», а не об удалении): файлов — не больше числа закрытых вопросов; при росте — отдельная мелкая задача в `housekeeping.ts`.
- П-3 Текст рекомендации в письме — целиком (до 4000 знаков), в записи журнала — до 1000 (REQ-15).
- П-4 Схемный умолчательный вид `answer_mode` — `"owner"` (строка для показа), как в REQ-02; `loadConfig` читает карту типов и ключ `default` отдельно, строкового значения как карты не принимает (читается как отсутствие, замечание в `show`).
- П-5 Сессии задач без обязательств (отчёт сдан, сессия ещё открыта) получают решение через `nudge` из-за вызова до проверки обязательств (РП-04) и через `syncStatus` — оба пути идемпотентны.

## Требует утверждения

Рекомендации даны каждой записи; решает владелец. Записи читают машинные форматы (пометку «решено» с двоеточием ставит владелец после ответа; единственная пометка уже в плане - у РП-08, перенесена из слов владельца 2026-10-09 о правке spec.md).

  11. `GATE:recount` (набор из двух маркеров: `GATE:exists` - тот же ранний возврат по существующей записи, что в `GATE:once` (одно место кода - одно имя), `GATE:recount-count` - счёт предела только по прежним ходам; снимаются вместе, потому что каждое правило само делает второй проход идемпотентным): краснеют `AC-17 повтор при пределе`, `AC-14 пакет повтор` (второй проход переворачивает решение и создаёт запись остатка). `AC-02 второй проход` при этой заглушке не краснеет (при пределе по умолчанию 3 и одном вопросе перечёт ничего не меняет) - она красная только в прогоне 0.

Правило подстановки: заглушка - набор из одного или нескольких маркеров (`GATE:once` и `GATE:recount` - наборы, остальные - один маркер; маркер `GATE:exists` общий для обоих наборов), каждый маркер даёт ровно одно совпадение; маркер - только парный: `/* GATE:<имя>< */ … /* GATE:<имя>> */`, между скобками стоит заменяемое выражение или кусок (например ветка раннего возврата); одиночной формы нет, граница выражения всегда задана; скрипт хранит таблицу «маркер -> текст замены» (например `GATE:limit` -> `false`, `GATE:words` -> `undefined`, `GATE:default` -> `"recommendations"`, `GATE:exists` -> пустой кусок), одной заглушке могут соответствовать несколько замен, и заменяет в копии ровно эти места, падает, если файл после подстановки не изменился или копия не загружается (уровень A на копии), и проверяет красный по ячейкам, названным у заглушки, а не только «есть красное». Контроль скрипта: на копии, где маркер `GATE:review` удалён, скрипт падает с сообщением «маркер не найден». Скрипт тяжёлый (копия плагина, до двенадцати запусков двух-трёх тестов) — запускается один раз, при машине без нагрузки; вывод четырнадцати прогонов пишется в result.md.
