## Что сделано

- Плагин и MCP-адаптер показывают в `crew_list` отдельный блокер вопроса владельцу: текст, варианты, время,
  возраст, formID/rid; без записи формы — открытый вызов `question` по базе с пометкой «диалог без записи формы».
  Статус задачи остаётся отдельным от блокера. Диагностика не отвечает на вопрос и не будит вкладку.
- Ответ владельца идёт в штатный `POST /api/session/{sessionID}/form/{formID}/reply`, поле `answer.q0`.
  При 204 нет interrupt и обходного письма. При 409 предложенный ответ НЕ объявляется применённым;
  transport/5xx дают `unknown`, без автоматического повтора. Отсутствие регистрации службы отказывает без interrupt.
  Источник и контракт API описаны в plan.md и form-reply.ts; глобальной обёртки question нет.
- Crew сохраняет незавершённые MCP-вопросы после timeout и восстанавливает их из журнала после рестарта.
  Поздний ответ консервативно `stale`: корреляция session/question/opening/task, запись без пробуждения,
  без нового разрешения и без попытки выдать её за результат уже законченного HTTP-вызова.
- Чужая сессия не потребляет pending key. Повторный/неизвестный MCP key отказывается до native ACP fallback,
  включая холодную сессию без ACP client. Нумерация после рестарта учитывает закрытые ключи, исключая их повторное использование.
- В ACP-проекции добавлен alias `cancel_request` → `cancel`, с тестом; решение об отмене остаётся в существующей Алуле.
- Legacy-регрессии очереди/циклов используют явный сериализованный legacy fixture, а не регистрацию живой службы.
  CLI `crew-answer` различает неизвестный исход и больше не обещает interrupt+письмо после успешного reply.

## Ограничения и блокеры сдачи

1. Критерий полного зелёного набора Crew не выполнен. Следующий шаг интегратора — решить границу baseline-дефектов;
   самостоятельно расширять эту задачу на все старые сбои и публиковать красный набор нельзя.
2. Исходный HTTP/tool call после timeout/restart НЕ восстановим. Восстановление вопроса/журнала — не восстановление
   результата исходного инструмента. Поздняя запись не является свежим согласием владельца.
3. Recovery inbox Crew остаётся памятью хаба: после следующего рестарта ответ сохранён в журнале, но доставка
   recovery-письма не имеет отдельной долговечной очереди/транзакции. Полная crash-safe доставка критерия 4 не доказана.
4. Внешний reply-путь поддерживает один вопрос/поле q0; многовопросные формы направляются в окно.
   Полная поддержка multiselect и независимая аутентификация человека не добавлялись. Локальный процесс с правом
   записи в mailbox/service state остаётся в существующей границе доверия; цитата владельца не является криптографическим доказательством.
5. Новая диагностика уточняет owner-question; полного нового диагностического агрегатора инструмент/watch/очередь/PID
   не создано. Отдельная новая HOLD/STOP-проба не добавлялась; существующие регрессии входят в зелёный плагин.
6. Реальное завершение текущего question 258 не выполнялось. API reply проверен изолированным fake service;
   демонстрация на живом ожидающем вызове и интерактивный контур владельцу не выполнялись.
