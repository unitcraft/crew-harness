### Безопасный способ завершения question (критерий 3) — ПОДТВЕРЖДЁН живым API 2.0.26

Интегратор (2026-10-30): «running» инцидента получен из `GET /api/session/active`; в `/openapi.json` живого сервиса есть штатные форм-эндпоинты. Проверено по `/openapi.json` живого сервиса и исходнику v2.0.26 (9b4ec571, `packages/core/src/tool/plugin/question.ts`):

- `POST /api/session/{sessionID}/form/{formID}/reply`, тело `Form.Reply {answer: Form.Answer}`; ответ 204; повтор — **409 FormAlreadySettledError** (однократность гарантирует сервер), нет формы — 404 FormNotFoundError, плохой ответ — 400 FormInvalidAnswerError. Аутентификацию и обнаружение службы берёт на себя штатный `opencode api` CLI (та же аутентификация, что у TUI).
- `GET /api/session/{sessionID}/form` — список ожидающих форм (id `frm_…`, title, metadata, fields).
- Инструмент question 2.0.26 строит форму: `title "Questions"`, `metadata.kind "question"`, поля `key: "q0"[, "q1"…]`, `type: "string" | "multiselect"`, `options: [{value: label, label, description}]`, `custom: true`. Ответ: `answer.q0` = подпись варианта (строка) или массив (multiselect); свободный текст допустим (custom).
- Корреляция: `PendingForm.id` (frm_… из события `form.created`) = formID пути; сессия — из записи. Уже отвергаются чужие/устаревшие/повторные (`resolveAnswer`), обязательна цитата слова владельца, стоит `guardAnswer` (задача 142).
- Завершение исходного вызова: reply завершает именно ожидающий вызов question (модель получает ответ как результат инструмента, ход продолжается сам), **без прерывания хода и без письма-обхода**. После `form.replied` запись снимается штатно (form-wait.ts).
- Маршрут подтверждён интегратором: обёртку `ctx.tool.transform` над встроенным question НЕ делаем (отдельное доказательство и слово владельца); fallback, автоматически прерывающий ход, НЕ делаем — при сбое reply ответ отказывается с причиной, вопрос остаётся открытым. Многовопросные формы (nq>1) reply-маршрут отказывает (нельзя закрыть остальные вопросы «без ответа»).

Проба живого пути (read-only, 2026-10-30): `opencode api get /api/session/active` вернул `{"ses_…":{"type":"running"}}` для 4 сессий без различения блокировки — подтверждён источник ложного «running» инцидента. Вызов question инцидента в базе: created 17:26:44, completed 20:46 (статус completed — завершён, граница 258 соблюдена).

## Шаги реализации (малый маршрут, согласовано с интегратором 2026-10-30)

1. **Красная проба** (`test/crew-hidden-wait.test.mjs`): сессия с открытым вызовом question (по базе), busy, непрочитанные письма в ящике → `crew_list` показывает «занята» без блокера (ложное running инцидента 258). Падает до фикса.
2. **Диагноз в crew_list** (критерий 2): вкладка с открытым вопросом владельца показывается как «ждёт ответа владельца с ЧЧ:ММ: <вопрос> (форма frm_…)», а не «занята»; отличает owner-question (запись формы / `questionCall` open) от работы и технических ожиданий (watch, зависание, потерянное сообщение); недоступные данные — «неизвестно». Тот же признак в `tabStatus`.
3. **Доступ интегратора к незавершённому question**: текст/варианты/устойчивый id (`rid`) — в crew_list (кратко) и в существующем `scripts/crew-answer.mjs` (полностью); переживает рестарт (уже: `forms/` + `form-restore.ts`); тест восстановления без дубликатов.
4. **Завершение исходного вызова** (критерий 3): `owner-answer.ts` применяет ответ через `opencode api post /api/session/{sessionID}/form/{formID}/reply` (`{answer: {q0: "<вариант|текст>"}}`): 204 — применён (модель получает ответ как результат question, письмо и прерывание не нужны); 409 — «already answered»; 404/400 — отказ с причиной, запись остаётся; nq>1 — отказ. Прерывание и письмо убираются из штатного пути; без авто-прерывания при сбое.
5. **Дедупликация** (критерий 4): отсутствие ответа не порождает бесконечных одинаковых писем (сейчас: `FORM_MAX_REPEATS=3`, `queue-gate.ts` держит служебные письма при открытом вопросе) — закрепить тестами новых путей; после reply вкладку будит само продолжение хода, второго канала нет.
6. **HOLD/STOP** (критерий 5): новые сигналы не требуют продолжать/submit/reassign; автоотмены/переназначения/ответа за владельца нет — тест.
7. **Crew** (критерий 6): воспроизведение на машинах продукта. Модель Crew иная: ответ владельца завершает именно исходный вызов (`hub.nv:1141 @answer` → `mcp_take(key)` → канал reply → HTTP-ответ агенту). Кандидаты дефекта: (а) `mcp_pending` только в памяти хаба — рестарт теряет ожидание: HTTP-вызов оборвётся, форма в журнале останется, ответу некуда идти (`hub.nv:1164`, `ask_mcp_server.nv:208-219`); (б) таймаут ожидания ответа (`CTL_WAIT`/`timeout_ms`) возвращает агенту «таймаут ожидания ответа» и снимает форму — вопрос теряется молча для сценария; (в) `ctl_busy` (`crew_tools_hub.nv:25-28`) не различает «ждёт ответа владельца» и «работает». Доказательное воспроизведение тестом (рядом есть `chat-cancel-awaiting`, `chat-timeout-awaiting`), затем фикс подтверждённого. Решения — на Алуле, Нова — адаптеры наблюдения/доставки.
8. **Сдача**: регрессионные тесты, полный набор затронутых частей и стражи через очередь машины, отчёт SHA/команды/результаты/ограничения API/требования обновления и перезапуска.
