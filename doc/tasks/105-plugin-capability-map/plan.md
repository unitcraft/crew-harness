# План переноса плагина в продукт на машинах-данных

Задача 105. Исходные документы: [inventory.md](inventory.md) (что есть), [matrix.md](matrix.md) (как выразить), [primitives.md](primitives.md) (что писать на Нове). Цель владельца, 2026-10-19, чат оркестратора: «все возможности текущие (плагин crew-harness под opencode) + стейт-машины из методики должны быть написаны на таких стейт-машинах внутри голого продукта CrewHarness». Ограничение владельца, 2026-10-18: машины на Нове не пишутся; примитивы хозяина — на Нове один раз.

Это план исследования, а не задача переноса: он не утверждён, этапы станут задачами по слову владельца. Каждый вопрос владельцу (раздел 7) поставлен с рекомендацией и доводом; без ответа применяется рекомендация только там, где она названа «умолчанием».

## 1. Принципы

1. **Машины методики потребляются, а не переписываются.** 153 состояния и 418 строк переходов шести машин методики — данные в формате v0; переводит их методика (или переводчик по её описанию), продукт закрепляет версию по коммиту, как Канон ([ADR-0012](../../canon/decisions/ADR-0012-canon-methodology-version.md)). Своя копия с правками разойдётся с источником.
2. **Плагин рядом, пока продукт не доказал равенство.** Плагин работает как сейчас; продукт повторяет его поведение по группам; группа отключается в плагине только после сверки (раздел 4). Правила AGENTS.md пп. 11–12 (живая рабочая копия, перезапуск только владельцем) остаются.
3. **От основания к краям.** Сначала примитивы и машины, на которые опираются остальные (Шаг агента, Раннер), потом проектные машины, потом пульт и планы ([matrix.md](matrix.md), раздел 4).
4. **Равенство проверяется структурными данными**, а не текстом экрана: запись задачи, журнал движка, файлы в репозитории, состояние git. Тексты сравниваются отдельно по снимкам.
5. **Примитив пишется один раз** и сразу с вектором проверки, снятым с плагина.
6. **Нет разрывов службы.** Ни один этап не требует остановки живой системы плагина; перезапуск службы продукта — отдельное дело владельца.

## 3. Этапы

Состав этапа — строки матрицы с этим номером ([matrix.md](matrix.md), раздел 4). Критерий готовности — то, что проверяется перед сдачей этапа; проверка равенства — раздел 4. Числа этапов Э1–Э11 — те же, что в колонке «Этап» матрицы; Э0 и Э12 в матрицу не входят.

### Э0. Интерпретатор формата v0 и прогонщик сценариев (вне матрицы)

- **Что.** Читает файл машины (заголовок, типы, данные, стороны, состояния, концы, примитивы), проверяет по правилам `check-tables.py` (имена, достижимость, полнота развилок, «не убывает»), исполняет на `src/engine` с реестром примитивов; прогонщик берёт сценарий `scenario/0` и сравнивает состояние, журнал, данные и очередь. Закрывает зазоры G9–G10.
- **Критерий готовности.** «Шаг агента» из выписки пилота (14 состояний, 37 строк, 24 функции) исполняется на движке в памяти; все сценарии «Проверок 1–25» методики для этой машины зелёные; красная проба (мутация одной строки таблицы) краснит сценарий.
- **Зависит от.** Решения методики по оговоркам пилота; задача 104.
- **Оценка.** 5–7 задач.

### Э1. Основа: примитивы чтения и записи файлов, git, процессы, хранилище; оракул

- **Состав.** Строки матрицы (2): C04 Q07; примитивы, названные для Э1 в таблице «Новые примитивы по этапам» (раздел 8): `rd_clock`, `rd_new_id`, `rd_fs_*`, `rd_git_*`, `rd_proc_alive`, `rd_settings`, `rd_store_query`, `wr_fs_*`, `wr_store_cas`.
- **Что.** Каждый примитив — маленький модуль Новы с вектором проверки. **Оракул**: скрипт на Node, который грузит файлы плагина (они исполняются под Node 24 как есть) и прогоняет заданные входы через их функции, записывая пары «вход — результат» в JSON; он же вырезает из тестов плагина входные данные (реальные формы журнала 2026-10-18, 190 основ слов ворот, фикстуры планов, векторы журнала `progress-vectors.json`). - **Что.** На песочном проекте тот же сценарий идёт в плагине и в продукте; сравнение раздела 4 по уровню L4; по группам плагин отключается (флаг в настройках проекта), данные не переносятся (В-09).
- **Критерий готовности группы.** Две недели работы без расхождений уровня L4 по группе; расхождения разобраны; владелец сказал «отключай».
- **Оценка.** 3–4 задачи.

## 4. Проверка равенства с плагином

### Уровни

| Уровень | Что сравнивается | Откуда ожидаемое | Когда |
|---|---|---|---|
| L1. Примитивы | вход → результат | оракул: функция плагина на Node с теми же входами | каждый примитив, Э1 и далее |
| L2. Машина | сценарий: события → состояние, структурный журнал, данные, очередь | сценарий `scenario/0` из теста плагина или проверки методики | каждая машина, этапы Э2–Э9 |
| L3. Тексты | текст запроса агенту, письма, ответа инструмента | снимки `landing-golden.json`, `answer-golden.json`, `answer-golden-base.json` и новые снимки | этапы с текстами |
| L4. Сквозной | файлы репозитория и состояние git после одного и того же сценария в плагине и в продукте | запуск плагина против поддельного хоста и продукта против поддельного агента | Э12 и контрольные точки Э3, Э6 |

### Как берутся сценарии

1. **Из тестов плагина.** 132 файла, около 22 700 строк, по группам — в [inventory.md](inventory.md), раздел 1. Тест запускает настоящий плагин против поддельного хоста OpenCode; часть проверок — структурные (запись задачи, содержимое файла, состояние git), их переводят в ожидаемое сценария почти дословно; часть — тексты, они идут на уровень L3.
2. **Из проверок методики.** «Проверки 1–25» разделов «Маршруты» и «Проверки реализации» методики — для Раннера, Проверки цикла, Запуска сессии, Совещания, Шага агента.
3. **Из журналов.** Реальные случаи, на которых плагин менялся (задачи 036, 040, 059, 062, 063, 064, 069, 070, 076, 078, 080, 088, 096, 097), уже стали тестами; «живые случаи» этих тестов (например воспроизведение 94: пять вопросов, четыре доставленных ответа) переносятся как сценарии ВОПРОС, кроме тех, что порождены очередью OpenCode (строки «не переносить»).
4. **Красные пробы.** У плагина есть тесты с мутацией (`CREW_MODULE`, `CREW_HARNESS_*`); перенос сохраняет приём: мутация строки таблицы машины обязана краснить хотя бы один сценарий (`prove-red.sh`-подобный прогон).

### Критерий отключения группы плагина

Группа матрицы отключается в плагине, когда по всем её строкам: (а) сценарии уровня L2 зелёные; (б) уровень L4 два рабочих недели без расхождений на песочном проекте и на одной реальной задаче владельца; (в) красные пробы сохранены; (г) владелец сказал «отключай» (AGENTS.md, п. 11–12: только по его слову).

## 7. Вопросы владельцу

Каждый вопрос с рекомендацией и доводом. Вопросы пока не внесены в `doc/open-questions.md` (правка вне папки задачи 105); оркестратор переносит нужные при утверждении плана.

- **В-01. Паритет статусов плагина или Раннер методики?** Статусы задачи плагина (`starting`, `running`, `submitted`, `reviewing`, `rework`, `accepted`, `done`, `idle`, `approval`) переносим 1:1 отдельной машиной «Задача» или заменяем Раннером методики (облегчённый вариант — быстрый маршрут)? *Рекомендация: заменить Раннером; полей записи (раздел 4) достаточно для сверки.* *Довод:* плагин лишь наблюдает цикл, который ведёт человек; Раннер ведёт его сам; две машины одного цикла разойдутся, а паритет добавит 3–4 задачи и постоянную сверку. Иной ответ: машина «Задача» + 3–4 задачи.
- **В-02. Кто пишет таблицы машин методики?** Методика публикует `*.table.md` и продукт потребляет по закреплённому коммиту, или CrewHarness переводит у себя? *Рекомендация: методика публикует, продукт закрепляет версию.* *Довод:* 153 состояния и 418 строк; копия с правками дрейфует (пилот показал 49 единиц, требующих решений методики, и они принимаются там). Иной ответ: +6–8 задач и сверка с источником.
- **В-03. Где живут настройки проекта в продукте?** Файл в репозитории проекта (как сейчас, читается с целевой ветки) или таблица в базе сервера? *Рекомендация: файл в репозитории, имя ключей прежнее, база хранит снимок последнего допустимого состояния.* *Довод:* настройки правит человек и проверяют ревью и git; параллельный период требует одних и тех же ключей. Иной ответ: настройки в базе — страница правки, но теряется история и сверка с веткой (N01, N08).
- **В-04. Машина-служба или хранилище проекта?** Разрешает ли методика машину без единственного ответа (ПРОЕКТ)? *Рекомендация: спросить методику; запасной путь заложен — реестр с `wr_store_cas` и короткими вызываемыми машинами.* *Довод:* общие ресурсы проекта (номер, замок, слоты) один экземпляр машины сам не гарантирует; запасной путь не требует решения методики. Иной ответ: ПРОЕКТ как служба — на 1–2 задачи дешевле.
- **В-05. Роли сессий владельца и письма по ролям.** Оставляем `worker`, `integrator`, `acceptor`, исключительные роли, адресацию `проект.роль`, очередь по ступени? *Рекомендация: оставить только роли сторон машин (интегратор, проверяющий, исполнитель); письма между агентами — вызов машины по адресу сессии; общие роли и очередь по ступени (B10, B11) не переносить.* *Довод:* в продукте сессиями управляют машины, а не вкладки; роли нужны для прав, не для поиска получателя. Иной ответ: +2 задачи (ПРОЕКТ хранит роли и очередь).
- **В-06. Окна контекста и сводка при сжатии.** Продукт не ставит окно модели (I09, I10) и не вмешивается в сжатие (Q01) — принять? *Рекомендация: принять, вернуться при первом случае нужды.* *Довод:* и то, и другое — хуки и файлы OpenCode; ACP не даёт параметра, правило сводки остаётся в Каноне и идёт в первое сообщение сессии. Иной ответ: отдельная задача после проверки возможностей агента.
- **В-07. Автоответ: оба режима?** Переносить автоответ и на текстовые блоки «В-NN» (режим 007), и на формы (096)? *Рекомендация: оба; закрытый список — данные в Каноне проекта, а не код.* *Довод:* пакеты вопросов «В-NN» — штатный формат спецификаций методики (В4, В6 Раннера), формы — для вопросов агента по ходу; ADR-0010 и его дополнение требуют обоих. Иной ответ: режим текстов не переносить — минус 1 задача.
- **В-08. Уборка принятых задач: сама машина или агент?** Сейчас плагин проверяет, что дерево и ветка убраны, а убирает приёмщик. *Рекомендация: пока так же — убирает сессия приёмки, машина проверяет.* *Довод:* удаление ветки на сервере — действие вовне, без отката; AGENTS.md п. 6 и необратимые действия по слову владельца. Иной ответ: `ir_git_*` в ПРИЁМКЕ, +1 задача и ворота перед удалением.
- **В-09. Перенос истории плагина.** Записи задач, ответы, формы прежнего ящика переносим в продукт? *Рекомендация: нет; открытые задачи доводятся в плагине, новые заводятся в продукте.* *Довод:* разные модели данных (поля записи против данных машин), риск ошибок, малая польза. Иной ответ: разовый перенос +1–2 задачи.
- **В-10. Параллельный период и порядок отключения.** Отключаем плагин по группам матрицы после двух недель без расхождений и слова владельца? *Рекомендация: да.* *Довод:* AGENTS.md пп. 11–12 (живая система, перезапуск только владельцем); группа — наименьшая единица с замкнутым поведением. Иной ответ: отключить всё сразу после Э12 — быстрее на 2 недели, но один общий риск.
- **В-11. Заказы между проектами и планы — в конец?** *Рекомендация: да (Э8 для заказов, Э9 для планов).* *Довод:* заказы требуют вызова машины другого проекта (в 091 не вошло), планы — самая специфичная часть плагина; обе опираются на готовые Раннер, ПРИЁМКУ и ПРОЕКТ. Иной ответ: раньше — только если в ближайшие недели есть второй проект.
- **В-12. Windows-цепочка наблюдений.** Писать на Нове (`wr_proc_start`, `ir_proc_kill`) или запускать готовый скрипт-помощник репозитория (около 60 строк `sh`/PowerShell)? *Рекомендация: Нова, как велит правило «примитивы на Нове один раз»; первой задачей — проверка на машине владельца, скрипт — запасной путь.* *Довод:* скрипт-помощник проще, но это второй язык и вторая точка отказа. Иной ответ: скрипт-помощник — минус 1 задача и остаётся внешний артефакт.

## 9. Границы плана

- Сервер сессий (HTTP и WebSocket, один движок на сессию) → задача 099 / эпик 001; в оценку не входит.
- Перенос записей и журналов плагина → не нужно, потому что В-09 рекомендует не переносить.
- Совещание → задача после слова владельца, потому что норма опытная и плагин её не имел.
- Группа P (стражи и хуки git) → не нужно переносить код, потому что репозиторий хранит его независимо от плагина; продукт только вызывает стражей (Э11).
- Оценки Нова-строк и задач → уточняются после первой задачи Э1, потому что калибровка сделана по двум задачам.
