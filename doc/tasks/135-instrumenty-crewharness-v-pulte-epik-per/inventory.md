## Состояние и данные, которые нельзя свести к одной таблице

* Файловые task/mailbox metadata, визитки/идентичность вкладки и журналы `log.md`, `progress.log`, `usage.log` — отдельные продуктовые данные; PostgreSQL chat transcript и engine journal — другая история. Нельзя считать их дубликатами или переносить всё в чатовую историю.
* Сохранить номера задач и сессий, запуски и roles, owner words и источники, статусы, qid/reply/wakeup, доставленные и ожидающие письма, gate records, FAIL/stale/evidence/precheck, lock owner/lease, очереди с позициями/отменой/завершением, cleanup/keep и журналы. Нельзя автоматически мигрировать/закрывать реальные задачи чужих проектов.
* Уточнённый task lifecycle по принятому контракту задачи 136: «выполнена» — независимо принята/влита, но ждёт установки/обязательных prod-проверок; «закрыта» — отдельный финальный шаг после доставки/prod-проверок и окончательной приёмки; cleanup не закрывает задачу. Штатная корректировка выполненной задачи создаёт новый цикл под тем же номером, сохраняя identity/history/старую приёмку; для цикла — новые ресурсы/исполнитель и независимая приёмка. Закрытая задача явно переоткрывается с сохранением истории, затем новый цикл использует новые ресурсы/исполнителя и независимую приёмку; history не откатывается. Ни один путь не восстанавливает старые агрегаты и не повторяет прежние эффекты. Действующий инструмент реализует задача 136; план переноса задаёт только совместимость. Старые записи автоматически не мигрировать; реальные закрытые/отменённые задачи не менять.
* Единственный writer — постепенно переключаемый Nova API с транзакционными командами и идемпотентными ключами. При каждой фазе ровно один active writer; никакого dual-write/read, двойного wakeup, параллельного poller или дублированной истины. Backfill — только отдельная явно утверждённая операция, dry-run/сверка/backup, исходный источник сохраняется; никаких автоматических миграций при запуске.
* Безопасный cutover требует maintenance/drain для конкретного проектного scope, снимка и проверки counts/ids/relations/checksums, атомарного переключения reader/writer, rollback до первой записи в новый авторитетный источник. После новых записей rollback — только согласованный обратный экспорт/forward repair, не возврат к старому writer. Настоящая стратегия и репетиция — отдельные этапы, переключение живых данных — только по явному разрешению.

## Граница продукта и host

Пульт владеет правами, проектной и сессионной identity, задачами, почтой, журналами, очередями, gate-решениями и audit/evidence. MCP — лишь кандидат на транспорт операций пульта; ACP — способ создать/вести сессию агента; ни один протокол не подтверждает сам по себе безопасность или независимость от плагинов. Host adapter отвечает только за запуск процесса, ACP lifecycle/capabilities и явно ограниченное исполнение команд. UI/model/session-management API конкретного host не становятся продуктовой правдой.

Нужно обязательное отрицательное доказательство: инспекция эффективной конфигурации / изоляция OpenCode/Kimi должна показать, что управляющий CrewHarness plugin не загружен и не исполняет hooks/side effects, при этом только выбранный профилем список иных плагинов сохраняется. Нельзя менять глобальную конфигурацию. Если per-process/per-session безопасная изоляция не доказана на обоих host, соответствующий ACP-путь не включается, замена не объявляется готовой.

## Обязательные identity/permission отрицательные контроли

1. Проект A identity не может читать/менять task/mailbox/session проекта B, даже зная номер/qid.
2. Сессионный principal не может передать себе integrator/acceptor роль параметром или подделать `from_role`; роль берётся из серверной identity, не из запроса агента.
3. Невалидный/повторный owner word, поддельный источник/дата или истёкшее согласие не открывают fast route, plan approval либо gate.
4. Выполненная задача принимает только штатный новый correction cycle; cleanup не переводит в closed. Closed task требует явного authorized reopen; отменённая задача не переоткрывается этим путём. Оба разрешённых correction пути сохраняют исходную историю/приёмку, создают отдельный цикл и не повторяют прежние side effects.
5. Закрытая, отменённая, отозванная или переданная сессия не может отправить поздний reply, submit, permission decision либо wake; старый executor не пишет после reassign.
6. Закрытый/истёкший merge lock, чужая задача/вершина, stale precheck и невалидное evidence не дают merge/accept.
7. Невыданный capability/инструмент, секрет в args/env/логах/API, неразрешённая команда и запрос без человека в permission gate — отказ по умолчанию.

## Обязательные ACP/MCP пробы до публикации инструментов агентам и переноса ACP

Текущие `src/acp/client.nv` формирует `session/new` с `mcpServers: []`; это лишь факт исходника. `doc/research/acp-client-spec.md` прямо помечен как непроверенный черновик. Здесь не запускались бинарники, login, модельный prompt или live конфигурация. Технический spike в изолированной disposable-среде должен установить факты по версиям OpenCode и Kimi: (а) принятие MCP server в `session/new`, реальный вызов read-only probe tool, ответ/error; (б) независимость от глобальных настроек и отсутствие управляющего плагина — проверить загруженные extension/hooks и side effects на sentinel; (в) выбранный профиль иных плагинов и негативное доказательство отсутствия невыбранных; (г) shutdown/отмена/перезапуск и отсутствие двойной доставки. Выполнить для обоих ACP путей без настоящего model prompt/login. Если tool invocation потребует login/prompt или безопасный вызов пока не получается, только ACP/tool migration остаётся NO-GO/blocked и нужен отдельный вопрос владельцу о разрешении условий; это не технический NO-GO read-only task UI и не доказательство несовместимости. До разрешения факт неизвестен. Любой другой провал изоляции/transport блокирует этот ACP путь; проверить другой официальный adapter, иначе не выпускать интеграцию. E1 task metadata view не вызывает ACP и не зависит от этого spike.

## Принятые факты и неизвестное

* Подтверждено исходниками: standalone server имеет front/hub, ACP stdio client; ACP client объявляет агенту `fs`/`terminal` отсутствующими, неизвестные методы отклоняет, `session/new` отправляет пустой список MCP. Файловая и PostgreSQL конфигурации существуют; PostgreSQL journal/chat — источник transcript. Агентные настройки server-side, браузер видит только id/label.
* По текущим текстам задач: Kimi 2.1.1 подтвердил только `initialize` (см. задачу 132); это не проверка tool invocation, session prompt или MCP.
* Не подтверждено: фактические установленные версии/поведение MCP в OpenCode и Kimi, конфигурационная изоляция ACP процессов и плагинов, инструменты ACP в обеих сборках. Не проверялись live-команды, настройки, учётные записи, database или модели.
