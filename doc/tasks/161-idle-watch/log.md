## Разбор (первая часть журнала; отдельный analysis.md инструмент записи не принял)

Разбор — до кода. Источники: код плагина (`idle-tab.ts`, `index.ts`, `tasks.ts`, `queue-gate.ts`, `core.ts`, `status.ts`), запись задачи 092 проекта nova (чтение, только факты), постановка [task/message.md](task/message.md).

### 1. Что делает правило простоя сегодня

Файл `opencode-plugin/idle-tab.ts` (задачи 063, 070, 076) и проход сводок в `index.ts` (`idleStep`, `runCtx`).

- Правило смотрит на вкладку автора, а не на задачу: `idleStep` работает, только когда сводка вкладки в состоянии `tasks` («ждёт своих задач»: хода нет, вопроса владельцу нет, наблюдения нет, своего вопроса с `expect_reply` нет). Занятая вкладка (`working`) выходит первой строкой.
- Стоящая задача — одна из причин: «между сессиями» (статус `idle`), «ждёт указаний» (сессия исполнителя или приёмщика застряла перед автором или в состоянии `question`), «по статусу» (`starting/running/rework` без исполнителя, без живой сессии, с молчащим исполнителем; заказ в другой проект, который не взят), «принята, но не очищена» (все напоминания ушли, приёмщик уборку не ведёт). «Между сессиями» оправдывает любая идущая задача автора.
- Отсчёт — от `updated` задачи, конца хода вкладки или молчания сессии; порог один — `idle_tab_minutes` (20). Письмо `idle-<сессия>-<начало>` («Ты простаиваешь N мин …») уходит только самой вкладке, раз на эпизод (файл `idle-tabs/<сессия>.json`), и ответа не требует: эпизод снимает любой рабочий ход, слово владельца или смена записи задачи. После письма ни повтора, ни подъёма выше нет.
- Тип письма «idle» в `queue-gate.ts` — служебный: удерживается, пока у вкладки открыта форма вопроса владельцу.

### 2. Почему оно промолчало по 092

Запись задачи 092 проекта nova: статус `submitted` (сдан 13-й круг), у задачи есть исполнитель и приёмщик; события — сдачи кругов, «приёмка застряла», «подталкивание приёмщика» и записи плагина «ответ владельца через оркестратора на вопрос …» (последняя — 2026-10-23 18:05 UTC).

1. Правило смотрит на окно, а окно было занято: интегратор в состоянии `working` по другим задачам, и `idleStep` выходит на первой строке (`s.state === "working"`). Письма о заказах 112 и 113 шли потому, что те заказы попадали в ветку `order`, а окно освобождалось между ходами.
2. Для статусов `submitted/reviewing/accepted/approval` правило задачу «стоящей» не ставит (кроме уборки принятой): они в списке `GOING`, то есть «идут без автора, приёмщик ведёт».
3. `updated` задачи двигается от любой записи плагина (`saveTask`): заметки «приёмка застряла», «подталкивание», «ответ владельца …» сдвигают его. «Шаг не менялся» по `updated` определить нельзя — 092 выглядела свежей.
4. У правила нет срока шага: порог 20 минут считается от тишины вкладки автора, а не от записи шага у держателя.
5. Письмо без требования ответа и без подъёма: интегратору хватает хода-«понял»; новый эпизод сам не начинается, владелец ничего не видит.

### 3. Какие признаки «задача не двигается» есть в данных

| Признак | Где лежит | Годится? |
|---|---|---|
| Смена статуса | `history[].status`, время `at` | да: это смена шага |
| Запись шага или доказательства | `checking.at`, `sessions[].started/ended`, `precheck.at`, `history[]` с `by` сессии (отчёт, заметка) | да: слово держателя |
| Ответ владельца | заметка плагина «ответ владельца …» в `history` | да: владелец сдвинул шаг |
| `updated` | `saveTask` пишет при любом сохранении | нет: шум плагина |
| Заметки плагина | `history[]` с `by` = плагин | нет, кроме «ответ владельца» и смены статуса |
| Подталкивание автора | `history[]` «подталкивание …» | нет: нажим, а не движение шага |
| Ход сессии | сводка `working`, `idleAt(сессия)` | только как исключение «ход идёт» и только у исполнителя или приёмщика этой задачи |
| Ответ на письмо | `read/`, `obligations` | для «ответ на вопрос» (границы ниже) |

### 4. Решения

1. Признак «стоит»: шаг задачи не менялся дольше срока шага, независимо от занятости окна. Начало шага `stepAt` — самое позднее из: смена статуса, запись держателя (не плагина, кроме «ответ владельца …», и не «подталкивание …»), `checking.at`, начало и конец сессий задачи, `precheck.at`, создание. Поле `updated` не используется.
2. Шаги и держатели по статусу: `starting` — запуск исполнителя (исполнитель, нет его — автор); `running`, `rework` — работа исполнителя; `submitted`, `reviewing` — приёмка (приёмщик, нет его — автор); `approval` — предъявление плана (автор; при `plan_approver: owner` решает владелец через `/plans`, вопрос уже у него); `accepted` — уборка; `idle` — между сессиями (автор); заказ (`kind order`, не взят) — ответ на заказ (интегратор адресата, нет окна — автор).
3. Срок: ключ `step_term_minutes` (30; 0 — сторож выключен), значение по шагу `step_term_by_step` (`start, work, review, plan, order, cleanup, between` → минуты), продление ответом `step_extend_minutes` (30), ожидание ответа на письмо `step_answer_minutes` (15).
4. Хранение: файл `idle-watch/<проект>/<номер>.json` в ящике плагина (рядом с `idle-tabs/`, `forms/`): эпизод шага (ключ, срок, письма, ответы, вопрос владельцу) и метка HOLD/STOP. Памяти нет: после перезапуска службы срок прежний, письма не повторяются (id письма выводится из ключа шага и номера письма).
5. Лестница: письмо держателю с требованием ответа инструментом `crew_step_note` (причина и минуты, или `done`); ответ продлевает срок на 30 минут; повтор той же причины или молчание `step_answer_minutes` — вопрос владельцу; писем не больше двух; после второго ответа и нового выхода срока — сразу вопрос. Вопрос владельцу — запись с вариантами (ждать ещё, сузить задачу, сменить исполнителя, отказаться), рекомендацией и доводом из записей; видна окнам уведомлением, автору — письмом с готовым текстом для `question`, проекту — в `/crew`, панели, `/crew-progress`, `crew_doctor`; решение пишет автор после слова владельца (`crew_step_note {decide}`).
6. Исключения без тревоги: идёт ход окна по этой задаче (исполнитель или приёмщик в состоянии `working`); открыт вопрос владельцу (форма у держателя, автора, исполнителя, приёмщика); HOLD/STOP по слову владельца (метка в записи); внешний прогон — открытое наблюдение `crew_watch` держателя с потолком, потолок не вышел. Окно автора, занятое другими задачами, исключением не является: это случай 092.
7. Не меняется: правила Новы и других проектов, живая служба, настройки владельца. Прежнее правило `idle-tab.ts` остаётся (оно про вкладку автора, новое — про задачу); письма разного вида, id не пересекаются.

### 5. Границы (что не сделано и почему)

- Шаг «ответ на вопрос» (письмо с `expect_reply`) в сторожа не входит: у него нет записи задачи, его старение ведут `askedStale` и счётчики в `/crew`; ключ срока для него не заводится.
- Владелец отвечает через автора (оркестратор вызывает `crew_step_note {decide}` по слову владельца); собственного диалога окна, как у `/plans`, нет: это отдельная работа с `tui.ts`.
- Вопрос владельцу — запись плагина, а не форма встроенного вопросника OpenCode: форму создаёт только вызов `question` в ходе модели; плагин даёт уведомление и письмо автору с готовым текстом вопроса.
