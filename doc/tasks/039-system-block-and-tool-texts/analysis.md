Дата: 2026-10-14. Задание — `task/message.md`. Быстрый путь.

## 1. Где читается и пишется `cleaned` (статус и действие)

Статус задачи `cleaned` → `done`, действие `cleaned` → `cleanup` (`cleaned` остаётся синонимом действия).
Код плагина (`opencode-plugin/`):

| Файл | Что было | Что стало |
|---|---|---|
| `tasks.ts` | тип `TaskStatus` (`cleaned`, `closed`), подписи, чтение файлов | тип без `cleaned` и `closed` (есть `done`); `normTask` читает старый `cleaned` как `done` в статусе и в истории (`loadTask`, `listTasks`); подпись «готова» |
| `core.ts` | действие `cleaned` (ветка приёмщика, права acceptor, схема, тексты ответов), `finishCleaned` пишет статус, `propagateToParent`, письма о принятии, описание `crew_task`, HELP | действие `cleanup` (вход `cleaned` отображается в `cleanup` в начале `execute`), статус `done`, тексты и HELP переписаны |
| `index.ts` | подсказка приёмщику, автозакрытие сессий, напоминания о принятой и не убранной, хвосты уборки, шаги плана, пометки в заголовках сессий | то же с `done` / `cleanup` |
| `review.ts` | письма приёмщику (`reviewLetter`, `planMergeLetter`), справка о замке | `cleanup` в текстах |
| `status.ts` | подписи, отчёты приёмки, план в панели, счёт закрытых шагов | `done` |
| `precheck.ts` | список влитых (`accepted` или `cleaned`) | `accepted` или `done` |
| `tui.ts` | автозакрытие вкладок | `done` |
| `config-schema.ts` | вопрос про `accepted_slot` | слово `cleanup` |
| `README.md` плагина и корня | действие в описании приёмки | `cleanup`, абзац о статусах |

Мёртвое значение `closed` у задачи нигде не присваивалось; убрано из `TaskStatus`. Остальные `closed` в коде — карточка
порождённой сессии (`Spawned.status`), не тронуты; одна заглушка `{ status: "closed" } as Task` в `index.ts` заменена на `cancelled`.
Идентификаторы писем (`cleaned-<проект>-<n>`) оставлены: по ним плагин не шлёт письмо дважды, смена имени дала бы дубли в уже
обработанных задачах.

Тесты и golden, где встречалось `cleaned`: `crew-acceptor`, `crew-autoclose`, `crew-cross`, `crew-flow`, `crew-flowwatch`,
`crew-landing-hints`, `crew-landing-keep`, `crew-landing-letters`, `crew-landing-slot`, `crew-plan-config`, `crew-plan-task`,

(комментарий), `landing-golden.json`, `answer-golden.json`. Приведены к `done` / `cleanup`; оба golden перезаписаны (`--write`), в
дифференциале слово `cleaned` → `cleanup` в текстах. `answer-golden-base.json` (основа доказательства красного задачи 007) не тронут.

## 5. Язык HELP

HELP оставлен русским: общение с владельцем и справочник — по-русски, в историю он попадает по запросу, не в системную часть.
Внутри раздела смеси языков нет: русский текст с именами инструментов, действий и настроек латиницей (идентификаторы). Планирование,
статусы и новые имена описаны разделами «ПЛАНИРОВАНИЕ» и «СТАТУСЫ ЗАДАЧИ». Описания инструментов — по-английски, как были.

## 6. Устройство планирования (описано в HELP и описаниях)

`crew_spawn {kind: "plan"}` → задача-план; исполнитель пишет файл в `plans_dir` по шаблону (`plans.ts`), форму проверяет плагин при
сдаче → приёмка раундами (`review`, `check`, `round`; каждый раунд — новая сессия) → `plan_clean_rounds` чистых подряд либо
`plan_rounds_max` раундов → статус `approval` → согласует владелец (`/plans`) либо автор-интегратор (`plan_decide`, при
`plan_approver: integrator`) → новый приёмщик вписывает решение, вливает → `done` → при `plan_steps: auto` плагин ставит задачи по
шагам (по «после», «где», лимитам), при `manual` — письмо со списком.
